# Gustline

Gustline is a resettable, synthetic weather and air-quality App for Personal Agents' Last Exam. Every read answers from the data current at the run's virtual time and names the issuance it used. Superseded issuances, observation corrections and alert versions stay queryable. A person's own alert rules turn new data into notifications, which can be delivered to Mail.

Approved proposal: [`proposals/environment/gustline-weather-air-quality.md`](../../proposals/environment/gustline-weather-air-quality.md) (PR #126, approved at `d6509db`).

## Run it

Node.js 18 or newer; no packages to install.

```sh
# App-only business tests and the walkthrough (no runtime needed)
cd apps/gustline
npm test
npm run example

# Regenerate, or check for drift in, the generated contracts and fixtures
npm run build
npm run check

# From the repository root: real MCP verification with the public runtime
npm run app:verify -- --app apps/gustline --output .artifacts/gustline.json

# Runtime and Mail integration through real MCP processes (needs the full checkout)
cd apps/gustline && npm run integration
# The web pages, through the shared Web Host (from the repository root; see gui/README.md)
node runtime/web/server.cjs --app gustline --registry apps/gustline/registry.json --run web-demo --profile sandbox
node apps/gustline/tests/browser.test.cjs   # needs `npm ci` and `npx playwright install chromium`
```

`npm run integration` runs `tests/runtime.integration.cjs` and then `examples/mail-integration/run.cjs`. The first checks a repeated `request_id`, `stale_version` after an event, `env.advance_time` releasing a quiet-hour hold, and two byte-identical resets. The second checks Mail delivery, duplicate republishing, an ungranted recipient, and a quiet-hour release.

## Package boundary

Business tests and the example run from this folder with only the package. MCP verification needs the pinned public runtime (runtime 1.6.0, Core API 1.2.0). The package carries a byte-identical copy of Mail's wire schema (`schemas/mail-router-message.schema.json`) for its `messaging.publishes` declaration. Mail 1.3.0 and Messaging are needed only for the integration example, where Mail is a scenario recipient in the run assembly. Mail is not listed in `app.json` dependencies. No external service is used.

## Web pages

Gustline has its own web pages (`gui/index.html`, `gui/src/app.js`, declared in `contribution/gui.json`), served by the shared Web Host like the personal Apps. They cover all 25 business tools: saved places with forecasts, observations, air quality, alerts and daylight; rules; notifications; the gazetteer; and settings. See [gui/README.md](gui/README.md) for how to start them and the browser check.

## Workflows

| Workflow | Agent tools | What it covers |
| :--- | :--- | :--- |
| 1. Places and settings | `places.search`, `places.get`, `saved_places.list/add/rename/remove`, `settings.get/update` | Seeded gazetteer, saved places with the person's labels, units and the person's own time zone |
| 2. Forecasts, observations, daylight | `forecast.get`, `forecast.history`, `observations.get`, `astro.get` | Issuance current at virtual time, two providers, hourly and daily periods in the place's zone, corrections, NOAA sunrise and sunset |
| 3. Air quality | `air.current`, `air.forecast` | AQI computed from monitor concentrations with the `epa-2024` tables, averaging basis per pollutant, staleness |
| 4. Official alerts | `alerts.list`, `alerts.get` | CAP-style version chains; `upcoming`, `active`, `expired` and `cancelled` derived at read time; `area_closure` is informational |
| 5. Rules and notifications | `rules.list/get/create/update/pause/resume/delete`, `notifications.list/acknowledge` | Threshold and alert rules, trigger keys, quiet-hour holds released by the clock, Mail delivery |

All tool names carry the `gustline.` prefix. Infra-only operations (`env.load_seed`, `env.apply_event`, `env.reset`, `env.snapshot`, `env.event_status`, `env.validate_bundle`, `env.advance_time`) are not available to the Agent.

## Events

The task chooses the content and timing of every event; Gustline only defines its effect.

| Operation | Effect |
| :--- | :--- |
| `weather.forecast_issued` | New current issuance for a provider and zone; forecast rules evaluated |
| `weather.observation_recorded` | New observation, or a correction that keeps the earlier value in `revisions`; observation rules evaluated |
| `air.observation_recorded` | Hourly concentrations stored, AQI rules evaluated |
| `air.forecast_issued` | New current air-quality forecast; AQI-category rules evaluated |
| `alert.published` | `alert`, `update` or `cancel` message added to a version chain; alert rules evaluated |
| `notification.delivery_recorded` | Messaging outcome for one notification, generated by Infra |

## Time

Gustline has no timers and no clock event. Infra moves time with an event's `at` or with `env.advance_time`, which runs no App code. Time-based statuses are therefore derived from `ctx.virtual_now` wherever they are read or written. This covers alert status, air-observation staleness and the release of a notification held by quiet hours. The outbound adapter (`src/publisher.cjs`) uses the same derivation.

## Mail delivery

`src/publisher.cjs` reads notifications that are `pending_delivery` at the current virtual time from an Infra snapshot. It builds Mail's `channel.email` message (`urn:pale:email-message:2`, payload `urn:pale:email-payload:1`) with title, body and `time` frozen on the notification, so a retry sends identical bytes. It publishes with `request_id` equal to the notification ID. Infra then records the outcome with `notification.delivery_recorded`.

## Scenario packs

Each pack in `examples/packs/<name>/` has a `seed.json` and `binding.json` that a task can load with `env.load_seed`. Its `events.json` holds the seed's `virtual_now` and the events in time order. The tests load every pack and replay all its events.

| Pack | Contents |
| :--- | :--- |
| `desert-storm` | A park in `America/Denver` for a person in `America/Chicago`: two providers with three issuances each, storms arriving earlier in later issuances, a Flood Watch that is issued and then updated, an informational park closure, 48 observations, a trip-window thunder rule and an alert rule |
| `smoke-week` | Two air areas and monitors with five days of hourly PM2.5 and O3 (240 rows), ten daily air-quality forecasts, a smoke advisory that is issued, extended and cancelled, an observed-AQI trip rule and an AQI-category forecast rule |
| `commuter-week` | Home, work and school with two issuances a day for seven days, heat and wind advisories, a severe thunderstorm warning at night, four rules (commute gusts, pickup heat, heat alerts, severe alerts with the quiet-hour override) and six notifications from the previous week |

## Data

`scripts/generate-fixtures.cjs` writes every fixture and pack deterministically from a fixed seed; `npm run check` fails if a regenerated file differs.

**History from 2025-01-01.** Each account's history starts in January 2025, while each fixture's own clock (the task timeline) is in 2026 or 2027. Saved places and rules date from January 2025. Past official alerts are kept, about one per zone every other month. Past notifications come from replaying synthetic alerts, short forecasts and observations through Gustline's own event handlers in time order (`scripts/history.cjs`), so each one has exactly the trigger key, text and status rules the App itself would produce. The short forecasts and observations used for that replay are not kept, as a real service keeps its alerts and notifications but not every superseded issuance; their IDs start with `h-`, and past alerts start with `al-h-`. Every pack stays under 400 KB in total, and pack files keep one record per line. All places, stations, issuances, observations, alerts, people and rules are synthetic. The EPA AQI breakpoints and the NOAA solar equations are public-domain U.S. government works, recorded in `contribution/dataset.json`.

## Implementation notes

- **Rules:**
  - A deleted rule is kept as a tombstone (`status: deleted`) with its revision history. Its ID is never reused, and any of its notifications not yet sent are withdrawn.
  - A paused rule keeps notifications already created.
  - Forecast rules read one provider (`provider`, default `gustline`).
- **Repeat notifications:** within one window occurrence, a "met" notification is sent once. If the person already heard "met", clearing sends "cleared" (when `notify_on_clear` is set). A met notice still held by quiet hours is withdrawn without a "cleared". A condition that returns after a clear notifies again (`|met|2`). A rule without a window notifies for the first date that meets it in each evaluation.
- **Alert updates and cancels:** they must reference the latest version and keep the same `event`. Version numbers may skip but must increase.
- **Corrections:** a correction may name the observation's current or any earlier ID.
- **High and low temperature rules:** `temp_max_c` compares the warmest forecast hour of each window occurrence (or local date) within the look-ahead, and `temp_min_c` the coolest. So "high at most 15 °C" means the whole period stays at or below 15 °C, not that one cool hour exists.
- **Places:** all places are fictional. The proposal planned about six real places sourced from USGS GNIS. They were replaced so that no synthetic record implies conditions at a real location.

## Limitations

- PM2.5 and PM10 AQI use hourly concentrations, not EPA NowCast; reads label each pollutant's averaging basis.
- No live feeds, radar, maps, pollen, marine or aviation products.
- One account per App instance. The web pages run on the shared loopback Web Host; there is no production remote deployment.
- Automatic invocation of the outbound adapter after events belongs to the planned runner; the example and tests invoke it explicitly.
