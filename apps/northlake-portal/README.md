# Northlake Patient Portal App

Self-contained PALE App package, version 1.0.0, Core API 1.2.0, built for environment proposal #14 (`proposals/environment/patient-portal.md`). One synthetic patient (Rosa Delgado) reads and sends secure messages to clinic staff, reviews visit billing with insurance arithmetic, downloads itemized statements, finds in-network providers and books, cancels or reschedules appointments. Staff replies, billing postings, clinic-side changes and reminders arrive as events on the platform's virtual clock. No real patient data; everything is generated by `scripts/generate-fixture.cjs`.

## Run locally

Requires Node.js 18 or newer. No package install, account or remote service is needed (from the repository root):

```sh
node --test apps/northlake-portal/tests/business.test.cjs
node apps/northlake-portal/examples/run.cjs
npm run app:verify -- --app apps/northlake-portal --output .artifacts/northlake-portal.json
node runtime/web/server.cjs --app northlake-portal --registry apps/northlake-portal/registry.json --run web-demo --profile sandbox
```

`registry.json` inside the package registers only this App; the shared `apps.registry.json` is a platform file that maintainers extend at acceptance. With only this App folder, run `node --test tests/business.test.cjs` and `node examples/run.cjs` from inside it. `service.cjs` uses the public runtime or `PALE_RUNTIME_ROOT`; it embeds no server.

## Operations

Thirty-one agent operations in `tools.json`, fifteen reads and sixteen writes, each named `northlake-portal.<area>.<verb>` (the proposal wrote them as `portal.<area>.<verb>`; the platform requires the App ID as the first segment). Amounts are integer cents. Every write takes Core's `expected_version` and `request_id`; a repeated `request_id` returns the stored receipt and a stale version is rejected before the handler runs. Core owns the `status` of every result (`ok`, `committed`, or an error code), so an operation's own result is reported in `outcome`.

Business errors arrive as the result `status` with a plain-language `message` that carries the figures the proposal promises: `thread_closed`, `attachment_invalid`, `exceeds_balance`, `claim_not_final`, `preview_stale` (with the current figures), `slot_unavailable` (with the nearest open slots), `identity_required`, `approval_required`, `offer_expired`, `interstitial_pending`, `user_action_required`, `not_found`, `invalid_state`.

Money and identity writes are two steps. `billing.pay.preview` and `appointments.preview` store a preview with an expiry (`settings.preview_ttl_minutes`); the matching confirm checks the preview is live, that the ledger or slot has not changed since, and, for a new visit, that a `user.identity_verified` event has named the preview. With the fixture flag `settings.require_user_confirmation` on, every gated write also waits for a `user.confirmed` event: it names the preview or offer where one exists, or, for a new message, reply or billing request, the `draft-…` ID that the `approval_required` message reports (derived from the content, single use). The App keeps no clock of its own: preview and offer expiry and "completed" appointments are evaluated when an operation runs, from `ctx.virtual_now`. Where a task policy constrains a tool to certain records, Core checks the argument named `id`; every record-targeting operation therefore takes its target as `id`.

## State and time

`fixtures/minimal.json` is initial history, `fixtures/binding.json` binds the person and account, `fixtures/policies.json` grants the `scenario` profile every operation except the three money and identity confirms and the `sandbox` profile everything, and `fixtures/clock.json` sets the clock to 2026-11-18 09:00 Pacific. Seeded history runs from January 2025: routine visits, labs, statements and payments through April 2026 are synthetic filler generated by the same script, and the authored shoulder, billing and scheduling story runs from May 2026 to the clock. `validateSeed` rejects a claim whose billed amount does not equal insurance adjustment plus insurance payment plus patient responsibility, a payment above its claim's patient responsibility, a message dated before its thread opened, an appointment on a provider without a slot calendar, a booked appointment whose slot is not marked booked, and duplicate IDs across every collection. A claim with no statement is flagged `unstatemented`; a provider without reviews shows "No ratings yet"; a thread without a recipient category is listed under the clinic.

Twelve events in `schemas/events.schema.json` are applied by Infra through `env.apply_event`; the handler reads the event's `at` as now. `examples/scenario.json` is the single staff reply the public verifier applies; `examples/schedule.json` is a ten-event schedule (slot taken, waitlist offer, interstitial set and cleared by the user, adjudication, reminder, clinic-side move, thread closed, statement ready) that `examples/run.cjs` applies after it. A `reprocessed` posting records two history entries, `resubmitted` (status `reprocessing`) and then the new decision, in one event. Reminders and statements are not timers: nothing happens when `env.advance_time` moves the clock. Reset restores the seed and clears previews, approvals and offers because they live in business data.

## Documents and attachments

`billing.statement` returns a text-based PDF (Courier, PDF 1.4, hand-written by `src/documents.cjs`, no library) and `messages.export` returns UTF-8 text; both carry filename, MIME type, base64 bytes and SHA-256 in the shape `files.put` and `mail.attachment.add` accept, and both are generated from the records at read time, so the same ledger gives the same bytes. Documents attached to a message are PDF, PNG, JPEG or plain text, at most 2 per message and 512 KiB each; the handler checks format, size and hash (`attachment_invalid`) before Core stores the bytes against the message. Reading an attachment needs the platform registration `runtime/registrations/northlake-portal.json` (`message` → `northlake-portal.messages.get`). The fixture bundle holds no assets.

## Integration and review

`contribution/contribution.json` declares the operations (derived by `node runtime/build-contracts.cjs`), the twelve accepted events and the messaging directions. Notices to Mail 1.3.0 (new message, statement ready, request decided, appointment confirmation, clinic-side change, waitlist offer, reminder) are built and published by a host-run publisher after the portal's own commit; the App never observes delivery outcomes and stores no notice status. Files and Calendar are reached only by the agent's own tools. `app.json.dependencies` is empty: the package runs with the shared runtime alone.

## Package map

```text
app.json                     Package identity, entry points, twelve event types
registry.json                Package-local registry for the Web Host and examples (path ".")
tools.json                   Generated: 31 agent operations with input/output schemas
scripts/contracts.cjs        Single source for record shapes, events and tool contracts
scripts/build.cjs            Renders tools.json, seed/events/state schemas, policies (--check in tests)
scripts/generate-fixture.cjs Seeded fixture generator (authored narrative, computed arithmetic)
service.cjs                  Public MCP launcher (platform-provided entry)
plugin.cjs                   Standard hooks delegating to src/
src/common.cjs               Lookups, clock, money, ledger arithmetic, previews, gates
src/messaging.cjs            Threads, messages, attachments, export
src/billing.cjs              Ledger reads, payment preview/confirm, questions, requests, fees
src/appointments.cjs         Providers, slots, booking, cancel, reschedule, waitlist, interstitial
src/documents.cjs            Thread export text and statement PDF writer
src/events.cjs               The twelve event handlers
src/model.cjs                validateSeed and data-relationship hooks
schemas/                     Generated seed/events/state schemas and copied public media contracts
contribution/                Capabilities, GUI declaration, media catalog and dataset provenance
gui/                         Business pages (pale.web) and the compatible reviewer renderer
fixtures/                    Generated records, binding, policies and clock
examples/                    Verifier event, ten-event schedule, standalone runner, editable task data
tests/                       App-only tests, schema validator and transaction-local harness
```
