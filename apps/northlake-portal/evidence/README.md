## 2. Declared App dependency: Mail 1.3.0 (send-only notices) and the agent-side Files flow

`mail-notice-trace.json` is written by `node apps/northlake-portal/examples/mail-notice.cjs apps/northlake-portal/evidence/mail-notice-trace.json` and records 21 checks over real MCP processes (portal, Mail and Files instances in one run; the Messaging service as a separate publishing process):

- `statement_ready` applied by Infra; Mail and Files clocks advanced to the session time with `env.advance_time` before any delivery or write.
- The host-run publisher reads the committed statement through the Agent connection and publishes through Messaging; the receipt event is `router-509bc4a5dd3593003419c0990cf2ae60`, and Mail's record `router-509bc4a5dd3593003419c0990cf2ae60` holds the notice unread in the inbox with the published title. The portal's data and version are unchanged by publishing (no notice status is stored).
- The agent fetches the statement (`billing.statement`), stores it with `files.put` and attaches it to a `mail.draft.create` draft with `mail.attachment.add`; the SHA-256 `105e29fe900cfd65…` is identical in the portal response, the Files version and the Mail attachment.
- A publisher configured without a recipient grant is rejected with `recipient_not_authorized`; Mail and the portal are byte-identical before and after.
- A replay of the same `request_id` returns the first receipt with `duplicate: true`; a new request ID for the same notice deduplicates on the CloudEvents `(source, id)`; Mail's message count does not change.

The Messaging configuration is `examples/router.json` (publisher `northlake-portal`, account `acct-rosa`, one grant to Mail account `mail-rosa` on `channel.email`). The wire schema copy `schemas/router-message.schema.json` is byte-identical to Mail's; `tests/business.test.cjs` validates every notice kind against it and against `email-payload.schema.json`. Calendar is reached only by the agent's own tools (`calendar.create`); the portal sends nothing to Calendar.

## 4. GUI: implemented screenshots and ordered workflow sequences

`capture.cjs` starts the public Web Host for this App, drives a real headless Chrome over the DevTools protocol (no npm packages), performs each workflow through the actual controls, checks the persisted state over the Infra MCP connection after every write, and writes `screenshots/*.png` (1280×900) plus `gui-sequences.json`. Captured with Chrome/158.0.8127.37 on Node v24.16.0; 14 screenshots, 20 checks, all passing. Reproduce with `node apps/northlake-portal/evidence/capture.cjs` (set `CHROME_PATH` if Chrome is not found).

| Step | Workflow | State | What it shows | Checks |
| --- | --- | --- | --- | --- |
| 01-inbox | messaging | start | Inbox with the billing thread selected; unread threads marked | 1/1 |
| 02-reply-form | messaging | action | Reply form opened from the thread, body filled | 0/0 |
| 03-reply-sent | messaging | result | Reply appears in the thread; thread now awaits staff | 2/2 |
| 04-closed-thread | messaging | error | A closed thread offers no Reply control and explains that replies are not delivered | 2/2 |
| 05-billing-ledger | billing | start | Billing ledger: balance summary, charges with insurer status and flags, payments | 1/1 |
| 06-claim | billing | intermediate | Claim clm-0815: insurer arithmetic, payments applied, denial and reprocessing history, related thread | 1/1 |
| 07-pay-exceeds-balance | billing | error | Preparing $50.00 against a $40.00 charge is refused with the figures; nothing is stored | 2/2 |
| 08-pay-preview | billing | intermediate | Payment preview: allocation, balance after, expiry; nothing charged yet | 1/1 |
| 09-pay-posted | billing | result | Payment posted: the claim page shows the receipt, a $0.00 open balance and the payment in its history; the ledger balance drops to $130.00 | 4/4 |

Not yet captured: a stale preview, a user-only interstitial and the `require_user_confirmation` wait, which the business tests cover.
