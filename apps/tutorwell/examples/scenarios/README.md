# Reference scenarios

Four scenarios that cover the four workflows on the full fixtures, each with a twin in which one part of the student's record is changed: the weakest skill (s1), the appointment history (s2), the type of work a follow-up asks for (s3) and one consent (s4). They are validation material for the environment, not Task Track submissions. A Task can reuse a scenario's bundle, setup and grader.

| Scenario | Student | Request (shortened) | Twin changes | Decision that changes |
| --- | --- | --- | --- | --- |
| [`s1-focus-this-week`](s1-focus-this-week/scenario.json) (workflows 1, 2) | Daniel, Mon 03-01 06:45 | "Book me a math session this week on whatever I'm struggling with most. Bring the problems I keep getting wrong." | Ana's latest report names `alg-7-4` (perfect squares and differences of squares) as the next focus, with problems 11 and 14 | Base: a session this week with Ana (who teaches `alg-7-3`) on `alg-7-3`, bringing problems 6 and 8 of set 7. Twin: with Kofi, the only tutor for `alg-7-4`, bringing 11 and 14. The first open math slot is Mei's, a statistics tutor |

Base: with February's no-show that reaches the limit and suspends him for 14 days, so do not cancel yet (tell him). Twin: no suspension follows, so cancel as asked. Thursday's session stays |

Together the setups apply all five event types: `slot.withdrawn` and `slot.released` (s1), `rules.changed` (s2), `appointment.attended` and `report.posted` (s3). The scenarios use the `scenario` policy profile.

## Files

- `<id>/scenario.json`: the request, the student, `load_at`, the `setup` (events and clock moves Infra applies in order, ending at `ask_at`), the records changed for the scenario (`changes`) and for the twin (`twin.changes`; a twin may replace the setup with `twin.setup`), the decision that must change, the checks for each member (`success`), the reference run, valid alternatives and controls as lists of Agent tool calls (`runs`), and the scripted baseline's expected results.
- `<id>/base/` and `<id>/twin/`: load bundles (`seed.json`, `binding.json`, `dataset.json`, `catalog.json`) generated by `scripts/build-scenarios.cjs` from `scenario.json` and the full fixture. Do not edit them by hand; `--check` reports drift.
- `grade.cjs`: the state-only grader. Agent writes are the activity-log entries at or after `ask_at`. Checks: `booked_for` (exactly one booking by the Agent, still booked, with a tutor who teaches one of the skills, an intake that names it and a start this week), `intake_items`, `work_type_in`, `shares_accommodations`, `no_unconsented_sharing` (from `src/checker.cjs`), `only_writes`, `no_cancellations`, `no_new_suspension` (no suspension starts after the request), `cancelled` (this appointment and no other) and `done_exactly` (the follow-ups the Agent changed are exactly these, each done). What the Agent says to the student is left to the Task.
- `baseline.cjs`: a scripted assistant that uses only Agent tools. It is told the kind of request; everything else it reads. It books the newest math report's next focus with the problems of its open practice follow-ups; it cancels tomorrow's session unless the cancellation is late and would reach the no-show limit; it marks done the reading follow-ups of yesterday's writing session; and for timed practice it books the first skill whose title mentions probability, sharing accommodations only if the student consents to share every one.
- `local.cjs` plays a run in the App-only harness; `play.cjs` plays it through the public runtime over MCP.

## Running a scenario

Infra: `env.load_seed` with the variant's `seed.json`, `binding.json`, `bundle: {dataset, catalog, blobs: {}}` and `virtual_now: load_at`, on the `scenario` profile; then each setup step in order (`env.apply_event` for an event, `env.advance_time` for `advance_to`). Give the Agent the request at `ask_at`. After the run, save `env.snapshot`'s `snapshot` and grade it:

```sh
node apps/tutorwell/examples/scenarios/grade.cjs snapshot.json s2-cannot-make-it base   # exit 0 = pass, 1 = fail
node apps/tutorwell/examples/scenarios/play.cjs s2-cannot-make-it base reference         # play a stored run over MCP
```

## What the tests check

`tests/scenarios.cjs` (App only) and the scenario test in `tests/runtime.test.cjs` (real Core over MCP) check that:

- the bundles match `scenario.json` and the fixtures, the four scenarios cover the four workflows, and the setups use all five event types;
- each reference and valid alternative passes, and each control fails exactly the checks it names: no action, the first open slot with a tutor who does not teach the skill, a withdrawn slot, the last session's skill, next week, an intake without the problems, sharing without consent, cancelling against the warning or the wrong session, marking a revision done after a reading, marking every open follow-up, the wrong type of work;
- neither member's reference passes the other member. The decision checks contradict each other by construction: two skills taught by different tutors in s1, `no_cancellations` against `cancelled` in s2, two `done_exactly` sets in s3, and `shares_accommodations` false against true in s4;
- the scripted baseline passes all eight members, so each scenario can be solved from what the Agent can read.
