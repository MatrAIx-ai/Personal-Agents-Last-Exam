# Plateway

Plateway is a synthetic, independently branded restaurant delivery App for one account holder: browse restaurants that deliver to a saved address, build a cart with dish options and receipt labels, check out as soon as possible or for a scheduled time, follow the order through the restaurant and courier, cancel, report missing or wrong items, and rate the order. It implements the approved environment proposal [`proposals/environment/plateway-delivery.md`](../../proposals/environment/plateway-delivery.md) (PR #111) on the public runtime 1.6.0, Core API 1.2.0. Agents use the MCP tools; people and agents can also use the customer-facing business GUI on the shared Web Host ([`gui/`](gui/README.md)); Infra drives restaurant and courier events.

## Run it

Node 18 or later, no installed packages.

```sh
cd apps/plateway
npm test                    # App-only business tests (no runtime code)
npm run example             # standalone event example
node dev/check-fixture.cjs  # content checks for the representative fixture
npm run mcp                 # real MCP checks on the pinned runtime
npm run mail                # Plateway → Mail 1.3.0 through Messaging

cd ../..
npm run app:verify -- --app apps/plateway --output .artifacts/plateway.json
node runtime/web/server.cjs --app plateway --run web-demo --profile sandbox   # business GUI; open the printed link
```

The browser acceptance needs the repository's pinned Playwright: from the repository root, `npm ci`, `npx playwright install chromium`, then `node apps/plateway/tests/web.browser.cjs`. It writes `.artifacts/web/plateway/report.json` and screenshots. CI's shared browser job (`npm run test:web:browser`) is fixed to the seven personal Apps and does not run this file.

`tests/mcp.integration.cjs` and `tests/mail.integration.cjs` take `--runtime PATH` (default: `PALE_RUNTIME_ROOT`, then `../../runtime`) and `--report FILE`; the Mail script also takes `--with PATH` for the Mail package (default: `examples/apps/mail` next to the runtime). The npm scripts set only `--report`, so `PALE_RUNTIME_ROOT=… npm run mcp` and `npm run mail -- --with PATH` both work; a later flag overrides an earlier one. The Mail script copies the runtime, this package and Mail into a fresh temporary directory with its own registry, runs there and removes it.

## Workflows and tests

| Workflow | Main path | Failure paths | Tests |
| --- | --- | --- | --- |
| W1 Browse and check out | Open restaurant serving the address → dish with a required option → preview → place with the token → `submitted`, one charge, cart emptied, `notice.order_placed` with the receipt | Price change between preview and placement → `stale_preview`; declining card → `payment_failed`; expired card, outside the delivery area, closed or paused restaurant, unavailable dish or option | T01–T04 |
| W2 Lifecycle | `order.accepted` → `order.delayed` → `order.picked_up` → `order.delivered`; a scheduled order released at its release time | No acceptance within 20 minutes → `cancelled`; paused or closed at release → `cancelled`; late events commit but do not change a cancelled or delivered order (timers due by their time still apply); unknown targets → `invalid_event` | T05–T09 |
| W3 Cancel | `orders.cancel.preview` → `orders.cancel.confirm` with the token: full refund before preparation, delivery fee and tip refunded while preparing | After pickup → `invalid_state`; a token taken before a status change → `stale_preview` | T10, T11 |
| W4 After delivery | Report a line `missing` or `wrong` within 48 hours → its subtotal and tax refunded, `notice.item_refunded`; rate once within 30 days | Second report of a line → `duplicate_request`; after the window → `window_closed`; before delivery → `invalid_state` | T12, T13 |
| All | Notices written once per occurrence; repeated requests and events deduplicated; reset restores the loaded seed | `idempotency_conflict`, `stale_version`, `permission_denied` for Agent management calls; a token from another seed ID → `stale_preview` | T14–T16 |

`tests/business.test.cjs` runs the App-only tests (T01–T14, edge cases, bounds and the fixture checks); they build their per-test seeds in JavaScript (`tests/seeds.cjs`, `tests/flows.cjs`) at a fixed test clock, independent of the fixture clock. `tests/mcp.integration.cjs` covers the parts the proposal marks [MCP] and T15–T16 through real MCP clients. `tests/mail.integration.cjs` covers the Mail half of T14. `tests/web.browser.cjs` drives W1–W4 through the GUI in Chromium (see [`gui/README.md`](gui/README.md)); its generic part, `tests/web/harness.cjs`, starts the shared Host and an Infra inspector on a fresh run.

## Interface

Tools (`tools.json`), all prefixed `plateway.`:

- Reads: `account.get`, `restaurants.search`, `restaurants.get`, `menu_items.get`, `cart.get`, `checkout.preview`, `orders.list`, `orders.get`, `orders.cancel.preview`.
- Writes (each with `request_id` and `expected_version`): `cart.add_item`, `cart.update_item`, `cart.remove_item`, `orders.place`, `orders.cancel.confirm`, `orders.report_issue`, `orders.rate`.

Events (`schemas/events.schema.json`), applied by Infra through `env.apply_event`: `restaurant.status_changed`, `menu_item.availability_changed`, `menu_item.price_changed`, `order.accepted`, `order.rejected`, `order.item_unavailable`, `order.picked_up`, `order.delayed`, `order.delivered`.

## Rules in brief

- **Totals.** Line subtotal = (dish price + option deltas) × quantity; option deltas are never negative; tax 8% per line, rounded half up; service fee 12% of the subtotal; small-order fee $2.49 below a $12.00 subtotal; plus the restaurant's delivery fee and the tip (at most $1,000). The charge equals the previewed total. A cart holds at most 50 lines.
- **Previews and tokens.** `checkout.preview` and `orders.cancel.preview` store nothing and return a token: a digest of the actor, the action, its business arguments, the run, the seed ID and the business changes the confirm would make. A confirm recomputes the checks first and returns their error; otherwise a different digest is `stale_preview`. Like every write, a confirm with a fresh `request_id` and an outdated `expected_version` is refused with `stale_version` before any of this. A clock move alone does not stale an ASAP checkout token.
- **Scheduling.** A scheduled time is on a 15-minute boundary, at least 45 minutes ahead (elapsed time) and at most 7 days ahead in local wall time; its release time (delivery time minus preparation and travel) is after now and inside the restaurant's weekly hours. A pause does not block scheduling.
- **Timers.** Each order stores its due times: `release_at` for a scheduled order and `accept_by` (submission + 20 minutes) for a submitted order. Every write and event first applies the timers due by its time, in order of due time and order number, each dated at its due time; reads and previews show the same result without storing it. A timer due at the same instant as an event takes effect first. A seed may hold a timer already due at its clock. Because nothing runs between calls, a timer's refund and notice are stored, and become visible to a Mail sender, only when a later write or event commits them.
- **Cancellation and refunds.** Cancelling before preparation refunds what remains of the charge after earlier refunds; while preparing it refunds the delivery fee and tip (at most what remains); after pickup it is refused. An unavailable or reported line refunds its subtotal and tax, with `notice.item_refunded`; a $0 line (or one reached after refunds already equal the charge) gets no refund record, and its notice (titled “Item removed” or “Item reported”) says no refund was due; refunds never exceed the charge. A report or rating dated before the recorded delivery is refused (`invalid_state`).
- **IDs and time.** IDs created during a run are sequential (`o-13` follows `o-12`; lines, refunds and notices the same way) and are never reused after a removal; numeric suffixes go up to 999,999,999; once an account has used the last one, reads still show a due timer's effect, but writes and events that need a new ID are refused with `invalid_state` and change nothing, so keep seeded counters well below it. The optional seed field `issued` records the highest suffix issued per prefix (`o`, `ol`, `rf`, `n`); the App maintains it. Times the App computes (due times, estimates, release and scheduled delivery times) are written with the seed's time-zone offset; times taken from the clock or an event keep their supplied spelling.
- **Dates.** The App sets no date floor (the platform's Task template allows external-platform history from 2025-01-01); the representative fixture's history starts on 2025-01-01 and its task timeline is dated in 2026. An order cannot be changed, and an event for it is refused, at a time before that order's own recorded history: cancellation previews and confirms, reports and ratings return `invalid_state`, and the event returns `invalid_event`.

## Data

`fixtures/minimal.json` is the representative seed (94 records). Its clock is `2026-11-18T12:00:00-05:00`, the shared registry's start instant (`2026-11-18T09:00:00-08:00`), so a run started from `apps.registry.json` opens at the fixture's own present. The task timeline (2026): one account holder with two addresses in served zones and one outside them; three cards on invented networks (valid, declining, expired); six invented restaurants (one closed on Mondays, one open past midnight, one with split hours; the example scenario pauses Basil Row while it is open); 36 dishes with option groups and allergen declarations from the nine major US food allergens, including options that add an allergen and `may_contain` declarations, and a sold-out dish; ten past orders with receipts, recipient labels and four ratings, including a rejected order, a reported line, a line removed as unavailable and a small-order fee; one order being prepared and one scheduled for this evening. The order history before it (2025-01-01 to 2026-07): 40 orders with receipts, refunds, two rejections, two cancellations by the account holder, reported lines, ratings and their notices, on both valid cards, to Office on weekday lunchtimes and otherwise to Home, generated by [`dev/generate-history.cjs`](dev/generate-history.cjs), which replays the App's own tools and events with a fixed seed, so every record is one the App itself wrote; their IDs are in a separate `h` series (`o-h1` to `o-h40`, `n-h1`, …) outside the runtime counters, so the first order of a run is still `o-13`. `node dev/generate-history.cjs --check` regenerates it byte for byte. `dev/check-fixture.cjs` checks one holder, two served addresses and one outside, three cards (valid, declining, expired), six restaurants with six lead cuisines, about 36 dishes, ten past orders and four ratings in the task timeline, one scheduled and one in-progress order, at least one of each other example listed here, at least forty history orders starting in January 2025, that the history matches the generator byte for byte, its notices belong to history orders and its text names only history IDs, every task-timeline date on or after 2026-01-01, that every order was placed (or released) while its restaurant was open, the zone offset of every timestamp, that the scenario pauses a restaurant while it is open, at or after the seed clock, a brand and card-network deny-list, and recomputes every total. Provenance and reuse terms are in [`contribution/dataset.json`](contribution/dataset.json): the task timeline is synthetic, authored with AI assistance, checked by the checker and reviewed by the contributor; the history is synthetic output of the generator script.

Seed limits a Task author can hit: a restaurant rating average is between 1 and 5 even when its count is 0; preparation and travel times are 1 to 180 minutes; an option adds at most $1,000; a dish has at most 10 option groups of at most 20 options; a day has at most 4 opening spans, and a span whose end is at or before its start runs past midnight.

Task authors can replace the seed through `env.load_seed`. `schemas/seed.schema.json` and the App's `validateSeed` reject inconsistent history: fields missing or present for an order's status and mode (including the estimated delivery time), placement, release and delivery times out of order, refunds other than exactly what the App would have refunded (a cancellation refund only on a cancelled order, matching its cancellation record and the refund rule for its reason; each line refund equal to that line's subtotal and tax, capped at what remained of the charge), a reported line on an order that was not delivered, a release reason on an order that was not scheduled, a rating dated before the delivery, an account holder's cancellation whose refund does not match its stage (the cancellation's optional `stage` field, which the App records, or else the last order status recorded before it in the timeline; other timeline statuses are ignored), a `stage` its reason does not allow, a cancellation after a recorded pickup or delivery, an active order whose timeline records a later status, totals that do not recompute, options that are not on their dish (seeded cart lines are also checked against the option-group limits), unknown time zones and numeric ID suffixes above 999,999,999. Give each distinct seed its own `seed_id`: preview tokens include it.

## Delivery dataset

The evaluation dataset for the Environment window, 2025-01-01 to 2026-12-31 inclusive in `America/New_York`, is in [`dataset/`](dataset/). The smoke fixture (`fixtures/minimal.json`) and the delivery dataset share the account and the catalog (equal at the fixture clock, checked by `tests/t26-dataset.test.cjs`) but have independent order histories: the fixture serves the business tests, the examples and the proposal's example events; the dataset serves evaluation, and Tasks select their history from it with `dataset/as-of.cjs`. Their IDs overlap but name different orders: the fixture's `o-1` … `o-12` (and its `ol-`, `rf-` and `n-` IDs) are not the dataset's, and the proposal's example events name fixture IDs. Every record is synthetic, including those dated after the fixture clock. There is no real November 2026 anchor: DoorDash is only the workflow reference, the approved proposal excludes collecting its data ([`proposals/environment/plateway-delivery.md`](../../proposals/environment/plateway-delivery.md), line 96: "no crawling or copied menus") and the restaurants are invented; the coverage report states this as a gap, pending maintainer agreement, together with the absence of Mail history for the dataset's notices.

| File | Content |
| --- | --- |
| [`dataset/base.json`](dataset/base.json) | Seed at 2025-01-01T00:00:00-05:00: the fixture's account holder, addresses, cards, zones, restaurants and menu, with the menu at its earlier prices, and no orders. |
| [`dataset/replay.json`](dataset/replay.json) | Every committed step in time order: 913 tool calls by the account holder (cart edits, checkout as soon as possible or scheduled, cancel, report, rate) and 605 Infra events (accept, reject, unavailable line, delay, pick up, deliver; 18 menu price changes, 8 availability changes, 5 restaurant pauses). |
| [`dataset/full.json`](dataset/full.json) | The state after every step, at 2027-01-01T00:00:00-05:00: 198 orders with 536 lines, 34 refunds, 73 ratings, 8 reported lines and 613 notices, with the IDs the App issued (`o-1` to `o-198`, …). |
| [`dataset/COVERAGE.md`](dataset/COVERAGE.md), [`COVERAGE.json`](dataset/COVERAGE.json) | Coverage report: sources and SHA-256 hashes, record IDs and date fields, the monthly breakdown (4 to 13 orders in every month), 227 distinct dates of App records (the coverage figure; 248 when the replay log's catalog-only and cart-only days are added), real and synthetic portions, gaps, representative records and the loading demonstration. |

[`dataset/generate.cjs`](dataset/generate.cjs) replays the App's own tools as the account holder and its events as Infra through the test harness, with a fixed seed, validating every state against the seed schema and `validateSeed`. It plans one to three orders a week (two in most weeks), more in winter and December and fewer in summer, and none while the account holder is away (2025-07-12 to 2025-07-20, 2026-04-20 to 2026-04-23, 2026-08-08 to 2026-08-16) or on Thanksgiving: weekday lunches to Office (mostly on the card ending 1881 until it expires after October 2026), dinners, weekend brunches and late-night orders to Home, dinners scheduled in the afternoon and breakfasts scheduled the evening before. Restaurants are chosen among those open and delivering there; steps keep slack against the App's limits (acceptance 2 to 9 minutes into the 20, reports within 90 minutes of the 48 hours, ratings within 6 of the 30 days). A rating's text is drawn only from those its order's own record supports ([`dataset/feedback.cjs`](dataset/feedback.cjs)): a claim of being on time, quick or early needs a delivery no later than the estimate given at placement and no delay; a claim of lateness, a later delivery; a missing or wrong item, a line reported that way; a quick lunch, an Office order placed before 15:00; an evening, a delivery after 17:00; hot or warm food, a hot dish in the catalog's sense (`HOT` in that file); cold sides, a hot side dish (`HOT_SIDES`: dumplings, scallion pancake, bok choy, elote, naan, samosas) next to a main, not merely an item under $10; a usual order, earlier deliveries from that restaurant. No text is used more than four times (three for one or two stars). At the fixture clock the account and catalog equal the fixture's; the orders are the dataset's own sequence and do not include the fixture's.

Loading the whole window as one seed would present every record after a Task's first session as history, so the dataset is a base seed plus dated steps. [`dataset/as-of.cjs`](dataset/as-of.cjs) replays, through the App's handlers, only the steps dated before a first-session instant: later records do not exist in the selection, an order in progress at that instant has only the history it had then, and the counters (`issued`) and clock are the App's at that instant. A timer due before the instant with no later step yet (an acceptance limit that passed, a scheduled release) is committed in the selection at its due time, as the App's next write would commit it, so the seed, its notices and refunds, and `open_orders` agree with what Core reads at that instant; a timer due exactly at the instant is left to Core's reads, which already show it. The later steps are withheld; those that are Infra events on objects already in the selection (the pickup and delivery of an order in progress, a later price change) are returned as `events`, ready to stage through `env.apply_event`, and the account holder's later actions are left to the Task. An order still open at the instant therefore completes as in the dataset only if its next steps are Infra events: when the account holder cancelled it next (for example while preparing, as with `o-14`, or before a scheduled release), it stays open, or a timer cancels it, unless the Task takes that step. Each selection lists these in `open_orders`: the order's status as Core reads it at the instant, its outcome after the staged events, its outcome in the dataset and the withheld account-holder steps on it. `dataset/full.json` is the end state of the replay, kept so the records can be inspected and counted; it is the selection at its own clock.

```sh
cd apps/plateway
node dataset/generate.cjs --check                                 # regenerate base.json, replay.json and full.json and compare byte for byte; without --check, write them
node dataset/as-of.cjs --at 2026-11-18T12:00:00-05:00 --summary   # what a Task starting at the fixture clock would see: counts, distinct dates, counters
node dataset/as-of.cjs --at 2026-01-01 --out selection.json       # the selection: data, virtual_now, events, bundle and summary
node dataset/coverage.cjs --check --runtime ../../runtime         # recompute the report, including the MCP loading demonstration; without --check, write it
```

An instant is a date (local midnight in `America/New_York`) or a date-time with an offset, from 2025-01-01T00:00:00-05:00 to 2027-01-01T00:00:00-05:00; a record at exactly the instant is not included. Each selection has its own `seed_id`, `plateway-delivery-asof-<UTC instant to the millisecond>-<first 12 hex digits of the SHA-256 of its clock and content>`, so a preview token taken on one selection is `stale_preview` on any other. A selection's `data` and `virtual_now` go to `env.load_seed` unchanged; pass its `bundle` with a `request_id` so the run's quality report carries the dataset's provenance (record source `delivery-dataset` in [`contribution/dataset.json`](contribution/dataset.json)) instead of an unspecified import. Its `summary` (records, distinct dates, orders per month) is the starting point for a Task's own history report. `dataset/coverage.cjs` loads the selections one millisecond after the first acceptance limit that passes unanswered, at 2026-01-01, the fixture clock, 2026-12-15 and the window end through real Core over MCP, reads every order back as the Agent, checks that the monthly counts read back equal the computed ones and that `open_orders` equals the open orders Core lists, and applies the first staged event. `tests/t26-dataset.test.cjs` (part of `npm test`) checks every month of the window, the cut at nine instants (including an order in progress, a cart being built, a timer due but not yet committed and a scheduled order before its release), every replayed state, the seed IDs and a checkout token on either side of a replay step, that every rating text agrees with its order (including hot-dish and side-dish claims) and none repeats beyond its cap, that a cut just after a due timer agrees with the App's reads, that staged events (with the withheld account-holder steps where `open_orders` lists them) bring every open order to its dataset outcome, the catalog at the fixture clock, and that the committed report, hashes and counts match a fresh computation.

## Mail notifications (optional)

Plateway writes every notice to its own log (`notices` in the App state). Mail is optional: the App runs fully without it. The receiving side is Mail 1.3.0's [receive declaration](../../examples/apps/mail/contribution/contribution.json) and [wire schema](../../examples/apps/mail/schemas/router-message.schema.json).

`infra/sender.cjs` is an Infra-run sender adapter, used like Mail's own publisher: Infra supplies a Plateway Infra client, a Messaging Router client and the grants from its Router configuration, and calls `send` after commits that append notices.

```js
const sender = require('./infra/sender.cjs');
const outcome = await sender.send({ plateway: platewayInfraClient, router: routerClient, grants: routerConfig.publishers[0].allowed_recipients });
```

`send` reads the log through `env.snapshot`, treats the entries present in the loaded seed as history, and publishes each newer entry through `router.publish` as a plain-text Mail message (`channel.email`, `urn:pale:email-message:2`, payload `urn:pale:email-payload:1`, type `org.pale.mail.notification.v1`, receiver operation `mail.receive_notification`). The message `id` and the publish `request_id` are `e<epoch>-<notice id>`. Within the same Router session, while the Router is not halted and Mail's binding and epoch are unchanged, an identical retry returns the stored receipt marked `duplicate`; a notice written after a reset is a new message. It publishes only when the run binding gives the account holder a Mail account that the grants allow on `channel.email`, and the Router offers that channel; otherwise the entries stay in the log. It stops at the first receipt that is not `committed` and returns that receipt's `event_id`. A refusal before dispatch (for example `incompatible_contract` or `recipient_not_authorized`) leaves the Router running; a rejection by Mail or an unknown acknowledgement halts it for reconciliation. For that, take `receiverSetup(mailInfraClient)` when the Router starts and call `reconcile({ mail, setup, outcome })` with the `send` result after an `unknown` result: it reports `committed` when Mail's receipt and inbox record are both found, and otherwise `indeterminate` (the event ID is missing, Mail's run, account or epoch has changed, nothing is found yet, or the receipt and the inbox disagree). Infra should bring both Apps' clocks to the same time at each delivery boundary; after a Plateway reset its clock goes back, so Mail can be ahead of it. None of these outcomes changes Plateway's committed state. `infra/router.config.example.json` is an example Router configuration with the required grant; `schemas/router-message.schema.json` is the runtime's wire contract, byte for byte.

## Limitations

- Synthetic restaurants, menus, couriers and payments only. One account holder per App instance. The GUI is customer-facing only: there are no restaurant or courier screens, whose actions are Infra events. The GUI runs on the shared loopback Web Host; Refresh re-reads the App, there is no push.
- No clock event and no scheduler: due times are applied from the supplied virtual time when a write or event arrives.
- Restaurant aggregate ratings are not recomputed from new ratings. No promotions, group orders, substitutions, tips changed after delivery or real payment authorization.
- Mail failure cases in `tests/mail.integration.cjs` are induced without changing the runtime or Mail: a publisher package copy with a changed wire schema (incompatible contract), a message ID longer than Mail stores (receiver rejection), an in-process Router whose receiver reply is dropped after Mail commits (lost acknowledgement), an empty grant list and a Mail reset after Router setup.
- Not yet done: the maintainers' human review of realism and provenance, and trial runs with an Agent.
