# Plateway delivery evidence

Delivery evidence index for Plateway 1.0.0 in the format of the submission evidence contract, [`docs/submission-evidence.md` at `6933c43`](https://github.com/MatrAIx-ai/Personal-Agents-Last-Exam/blob/6933c430942c64f94874083815829e4a4b20920a/docs/submission-evidence.md). It is delivery work added to the approved scope of the environment proposal ([`proposals/environment/plateway-delivery.md`](../../../proposals/environment/plateway-delivery.md), PR #111); the scope itself is unchanged. Every screenshot, sequence and receipt below is produced by the scripts in [`tools/`](tools/) and can be regenerated with the commands at the end. Reference product: DoorDash, compared through its public help center only.

Left visible, and listed per screenshot in the manifest, are business examples (restaurant and store names, their map pins) and public map labels. The screenshots are review evidence only: the App copies no DoorDash branding, text or images. In the package, the reference product's name appears only in this folder and in the fixture checker's brand deny-list (`dev/check-fixture.cjs`).

## Workflow sequences, state and tests

[gui/README.md](gui/README.md) lists 16 sequences, 61 steps, on two runs (the second loads a policy without `plateway.orders.rate`). For every step it records the action, the expected result, the outcome on screen, the App state and version read through a separate Infra MCP client right after the step, every MCP call made in the step, the virtual time, the matching check in `tests/web.browser.cjs` and the screenshot. The script checks each expectation, scrolls the outcome into view and checks that it is fully on screen and reads as expected before taking the screenshot, and stops on the first mismatch, so the tables show observed results, not intentions. **The MCP trace.** The page's own writes and previews (`POST /api/call`) are recorded from the moment the browser sends them, with the raw request arguments and the raw reply (HTTP status and JSON body), unshortened: checkout tokens, versions, request IDs and the full fee breakdown of a preview are all there, so the token a placement sent can be matched against the preview reply the page received (the tokens are synthetic). The recorder ([tools/recorder.cjs](tools/recorder.cjs)) enforces five rules, each in one place. (1) Ownership is decided when a call is sent, for every kind of call: page reads and tool discovery, page writes and previews, forced calls, second Agent reads and writes, Infra events, clock moves, the seed load and the inspector's own snapshot reads. The owner is the step open at that moment; a step opens when the previous one is sealed or its sequence begins, so its action runs inside it. The page load before the first sequence has an owner of its own, the setup, which may make only unlisted reads and is not listed in `run.json`. The two pieces of work between sequences (switching the address back to Home after 01-browse, and the management check after 14-account) also have owners of their own; they are the two entries of `run.json` `between_sequences`. A call sent with no owner, including after the last sequence and until the browser closes, stops the script; a reply never changes ownership. (2) A step is frozen before anything is taken from it: the script reads the App's version, runs the step's check, waits until nothing the step owns is outstanding (10 seconds at most) and reads the App's state; if the version changed since before the check, the script stops. The step's observations, version and virtual time come from that frozen state, and its calls are frozen with it. The 400 ms wait and scrolling the outcome into view come after the freeze; then the step is recorded and the screenshot taken. A call sent after the freeze stops the script and cannot count toward a submitting step, which must list a write or forced call. (3) Each call has exactly one terminal outcome, the reply or a failure with its HTTP status and error; a failure or a second outcome stops the script. (4) A forced call carries a header token bound to the exact tool and arguments it was issued for, so exactly that request is recorded as the forced call and concurrent page requests are recorded as usual; a token sent with any other call stops the script. (5) Recorder errors are append-only, including a failure to close the second Agent client: a stop that a caller catches is still reported by every later check and by the teardown check after the browser closes, and the client handle is kept until its process has exited, so the close can be retried. Page reads, tool discovery and inspector reads are owned and waited for but not listed. Before capturing, `gui.cjs` runs the recorder probes in [tools/probes.cjs](tools/probes.cjs), each on a fresh page with its own recorder; every probe must make the recorder stop with its exact expected message, and the results are in `run.json` (`recorder_probes`): a page read and a second Agent call outside any step; a refusal caught by its caller after the last sequence (still reported at teardown); a forced call and a preview held at a barrier until both distinct calls, one preview and one rating, have arrived (a barrier timeout fails the probe instead of releasing one request; each recorded once, overlap asserted); two previews at that barrier (it stays closed until the rating arrives); a forced token moved to another call; a state change between a step's check and its freeze; a write during a step's preparation; a write after the screenshot (the frozen write set and version are kept); a duplicate terminal event; a failure after HTTP 200 headers (one outcome, status 200); a request during sealing (sealing waits for both replies); a call after the last sequence (the probe seeds the cart with one dish, and the recorded reply must have status ok and equal the App's answer to the same preview through the second Agent client); a second Agent close that fails once (still reported after the caller catches it, and closed on retry); a cleanup whose first step fails (every later step still runs, and every failure is reported); a late reply; a second Agent call after the screenshot (not sent); an assertion failure inside a probe, after which the HTTP server must no longer be listening, the route must no longer receive requests, the second Agent client's process must have exited and the page must be closed; and an assertion failure while closing the second Agent client fails once, or every time (the probe's error must carry the cleanup failure, and the client's process must have exited). Every cleanup step, in each probe and for the suite's browser, Host and state folder, is attempted even when an earlier one fails, and all failures are reported, appended to the probe's own error when it has one; the second Agent client is closed up to three times until its process has exited, then killed. Writes by the second Agent MCP client, Infra events, clock moves and forced calls are listed raw too, with two exceptions: in Infra event receipts the host wall-clock fields `received_at` and `processed_at` are replaced by a note, because they change on every run (the virtual times beside them are kept); and reads by the second Agent client are summarized to the fields the step checks, because the full replies (restaurants with their menus) would swamp the tables.

The cases required by the contract are covered as follows:

- **Edit and cancel:** cart quantity, edit, remove and undo; Keep order after a cancel preview; a confirmed cancellation.
- **Invalid and denied:** a required option missing, a 41-character label, a declining card, a closed restaurant, a cancel after pickup and a report after its window (both also refused through MCP), a management request from the business session (403), and a policy without `plateway.orders.rate` (Rate removed, forced call 403).
- **Stale and conflicting:** at checkout `stale_preview` after a price change and `stale_version` for a change the page has not read; outside checkout a cart edit after another client's change, a cancellation quote taken before the restaurant accepted, a cancellation confirmed after the courier's pickup, and a report of a line another client had just reported.
- **Restaurant and timer outcomes:** an unavailable item refunded, a rejection, a scheduled order released at its time, and an order not accepted within 20 minutes.
- **Reload and independent updates:** two reloads, four committed writes and one refused write through a second Agent MCP client, and Infra events and clock moves, each followed by Refresh.

The browser acceptance `tests/web.browser.cjs` remains the full GUI test (75 checks, including a cancellation confirmed after pickup, and 15 on a restricted policy, including dropped connections, retries and policy changes); App-only business tests and real MCP tests are separate. Browser automation demonstrates controls and state; it is not a model-agent evaluation.

## Regenerate

From the repository root, after `npm ci` and `npx playwright install chromium`:

```sh
node apps/plateway/evidence/tools/reference.cjs   # reference/ (needs help.doordash.com)
node apps/plateway/evidence/tools/gui.cjs         # gui/ (first runs the recorder probes in tools/probes.cjs)
node apps/plateway/evidence/tools/mail.cjs        # mail/ (also runs tests/mail.integration.cjs --evidence)
node apps/plateway/evidence/tools/digest.cjs      # App load digest and runtime tree digest
```

The capture tools launch Chromium with software rasterization on one thread (`--disable-gpu --num-raster-threads=1 --disable-partial-raster`), and the GUI capture replaces the page's random request IDs with a counter kept in the page's session storage (`web-evidence-0001`, …) without changing the GUI source. With both, two consecutive runs on the capture machine gave byte-identical files in `gui/` and `mail/`: every screenshot, `sequences.json`, `run.json`, `demo.json` and both READMEs. On another machine or Chromium build, anti-aliased edges can differ by a few pixels (up to 3/255 was seen between capture sessions before rasterization was pinned); the recorded steps, states, IDs and receipts do not. The reference screenshots depend on the live help pages.
