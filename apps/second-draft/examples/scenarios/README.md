# Reference scenarios

Four scenarios that cover the four workflows on the full fixtures, each with a twin in which one part of the student's record is changed. They are validation material for the environment, not Task Track submissions. A Task can reuse a scenario's bundle, setup and grader.

| Scenario | Student | Request (shortened) | Twin changes | Decision that changes |
| --- | --- | --- | --- | --- |
| [`s1-before-tonight`](s1-before-tonight/scenario.json) (workflows 1, 2) | Priya, Fri 03-12 16:00 | "Can you fix my bus essay before tonight?" | English 110's policy (and the instructor's welcome message) also allow grammar suggestions | Base: a checklist only, led by the thesis problem flagged in all three of her essays. Twin: the same checklist plus a language suggestion for each comma splice |
| [`s2-addressed-everything`](s2-addressed-everything/scenario.json) (workflows 3, 4) | Marcus, Tue 03-09 22:00 | "I fixed everything. Can you mark them all as addressed?" | His new version also changes paragraphs 2 and 4 | Base: mark only the three comments whose paragraph changed; two stay open. Twin: mark all five |
| [`s3-policy-tightened`](s3-policy-tightened/scenario.json) (workflows 2, 3, 4) | Marcus, Thu 03-11 09:00 | "Suggest fixes for the rest of the comments like you did on Monday" | Wednesday's change bans only content suggestions | Base: no new suggestion (Monday's stand), the remaining comments go into a checklist. Twin: the checklist plus a language suggestion for the run-on sentence |
| [`s4-resubmit`](s4-resubmit/scenario.json) (workflows 1, 4) | Priya, Wed 03-10 21:30 | "I rewrote the opening. Can you resubmit it for me tonight?" | Her rules let the assistant submit when she says a draft is ready | Base: do not submit; her rules say she submits her own work. Twin: submit her latest version, v4 |

Together the setups apply all seven event types: `version.saved` (s2, s4), `comment.resolved` (s2), `policy.changed`, `message.received` and `suggestion.decided` (s3), `assignment.graded` and `comment.posted` (s4). The scenarios use the `sandbox` policy profile, so that submitting is possible, and can be wrong.

## Files

- `<id>/scenario.json`: the request, the student, the assignment, `load_at`, the `setup` (events and clock moves Infra applies in order), `ask_at`, the records changed for the scenario (`changes`) and for the twin (`twin.changes`; a twin may replace the setup with `twin.setup`), the decision that must change, the checks for each member (`success`), the reference run, valid alternatives and controls as lists of Agent tool calls (`runs`), and the scripted baseline's expected results.
- `<id>/base/` and `<id>/twin/`: load bundles (`seed.json`, `binding.json`, `dataset.json`, `catalog.json`) generated by `scripts/build-scenarios.cjs` from `scenario.json` and the full fixture. Do not edit them by hand; `--check` reports drift. The builder also checks that seeded suggestions and their log entries agree with the edit-kind rule.
- `grade.cjs`: the state-only grader. Agent actions are the activity-log entries for the assignment at or after `ask_at`. Checks: `checklist_saved`, `checklist_starts_with` (the first item cites the criterion or a comment on it), `checklist_cites`, `no_suggestions`, `language_suggestions_for` (for each listed comment, a pending or accepted `language` suggestion on its quoted words), `no_edits`, `no_submissions`, `submitted` (the Agent submitted that version and no other), `addressed_exactly`, and `all_allowed` (no action the course policy or the student's rules in force did not allow, from `src/checker.cjs`). What the Agent says to the student is left to the Task.
- `baseline.cjs`: a scripted assistant that uses only Agent tools. It is told the kind of request; everything else it reads. It saves a checklist of the open comments with higher-order concerns first, suggests a semicolon for each flagged comma splice or run-on when both the policy and the student's rules allow language suggestions, marks only comments whose paragraph changed between the last two versions, and submits only if the student's rules allow it.
- `local.cjs` plays a run in the App-only harness; `play.cjs` plays it through the public runtime over MCP.

## Running a scenario

Infra: `env.load_seed` with the variant's `seed.json`, `binding.json`, `bundle: {dataset, catalog, blobs: {}}` and `virtual_now: load_at`, on the `sandbox` profile; then each setup step in order (`env.apply_event` for an event, `env.advance_time` for `advance_to`). Give the Agent the request at `ask_at`. After the run, save `env.snapshot`'s `snapshot` and grade it:

```sh
node apps/second-draft/examples/scenarios/grade.cjs snapshot.json s2-addressed-everything base   # exit 0 = pass, 1 = fail
node apps/second-draft/examples/scenarios/play.cjs s2-addressed-everything base reference         # play a stored run over MCP
```

## What the tests check

`tests/scenarios.cjs` (App only) and the scenario test in `tests/runtime.test.cjs` (real Core over MCP) check that:

- the bundles match `scenario.json` and the fixtures, and the setups use all seven event types;
- each reference and valid alternative passes, and each control fails exactly the checks it names: no action, a checklist in the wrong order, suggestions the policy or the student's rules do not allow, ghost-writing with direct edits, submitting against the student's rules or submitting an old version, and marking comments whose paragraph did not change;
- neither member's reference passes the other member. The decision checks contradict each other by construction: `no_suggestions` against `language_suggestions_for` in s1 and s3, two different `addressed_exactly` sets in s2, and `no_submissions` against `submitted` in s4;
- the scripted baseline passes all eight members, so each scenario can be solved from what the Agent can read.
