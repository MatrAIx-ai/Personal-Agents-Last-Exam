# CivicDesk public comments App

Self-contained PALE App package, version 1.0.0, Core API 1.2.0, built for environment proposal #16 (`proposals/environment/civic-services-portal.md`). One synthetic member (Dana Reyes) searches proposed rules (dockets) from three fictional agencies, reads a rule's summary and supporting documents, drafts a comment with validation, submits it under her name or anonymously behind a required acknowledgment, receives a receipt with a tracking number and follows the comment from received to posted. Deadlines are evaluated on the platform's virtual clock in each agency's time zone; extensions, corrections and status changes arrive as events. No real agencies, rules or data; everything is generated by `scripts/generate-fixture.cjs`, including the document files.

## Run locally

Requires Node.js 18 or newer. No package install, account or remote service is needed (from the repository root):

```sh
node --test apps/civicdesk/tests/business.test.cjs                 # 10 App-only business tests
node apps/civicdesk/examples/run.cjs                              # event example on the App-only harness
npm run app:verify -- --app apps/civicdesk --with examples/apps/mail --output .artifacts/civicdesk.json
node apps/civicdesk/examples/mail-notice.cjs evidence/mail-notice-trace.json   # real MCP: CivicDesk -> Messaging -> Mail, notice outcomes recorded, rejected delivery, replay
node apps/civicdesk/scripts/coverage-report.cjs                   # data coverage over 2025-01-01 .. 2026-12-31
node apps/civicdesk/evidence/capture.cjs                          # GUI screenshot sequences with MCP state checks (Chrome, Node 22+)
node runtime/web/server.cjs --app civicdesk --registry apps/civicdesk/registry.json --run web-demo --profile sandbox
```

`registry.json` inside the package registers only this App; the shared `apps.registry.json` is a platform file that maintainers extend at acceptance. With only this App folder, run `node --test tests/business.test.cjs` and `node examples/run.cjs` from inside it. `service.cjs` uses the public runtime or `PALE_RUNTIME_ROOT`; it embeds no server.

## Operations

Nine agent operations in `tools.json`, seven reads and two writes, each named `civicdesk.<area>.<verb>` as the platform requires: `dockets.search`, `dockets.get`, `dockets.documents`, `comments.validate`, `comments.receipt`, `comments.status`, `comments.list_mine`, `comments.draft` and `comments.submit`. The optional subscription workflow is not built. Every view object a read returns carries `id`, the value the matching operation's `id` argument expects, next to its typed key (`docket_id`, `comment_id`, ...). Every write takes Core's `expected_version` and `request_id`; a repeated `request_id` returns the stored receipt and a stale version is rejected before the handler runs. Core owns the `status` of every result, so an operation's own result is reported in `outcome`.

A comment is a draft first: `comments.draft` stores it even with problems and returns them (`too_short`, `too_long`, `name_required` for a named submission without a name, `period_closed`, `possible_duplicate`); `comments.validate` runs the same checks without storing anything. `comments.submit` is the gated write: it requires `acknowledged: true`, the member's acknowledgment that a submitted comment is public and cannot be withdrawn, and refuses with `acknowledgment_required` otherwise; a closed period is `period_closed` with the closing instant in the agency's time zone, a second non-supplemental submission on the same docket is `possible_duplicate` (mark the draft `supplemental: true` to add to the earlier comment), and any other problem is `invalid_draft`. A submitted draft is consumed, the comment carries the draft ID and a tracking number, and submitting the consumed draft again returns `not_found` while `comments.receipt` returns the receipt. Submitted comments cannot be withdrawn, as in the reference product. Whether the agent may call `comments.submit` at all is the task policy's decision; both shipped profiles offer it.

## State and time

`fixtures/minimal.json` is initial history, `fixtures/binding.json` binds the person and account, `fixtures/policies.json` declares the `scenario` and `sandbox` profiles (both allow every operation), and `fixtures/clock.json` sets the clock to 2026-11-30 18:00 Pacific. Three fictional agencies in three time zones publish 36 dockets whose comment periods are spread over January 2025 to January 2027, seven of them open at the clock, including the target docket `OCDD-2026-0031` (wearable sensor data retention, closing 2026-12-04 at 11:59 PM Eastern) and the similar `OCDD-2026-0027` that closes later; several closed dockets were extended or corrected during their period. The member holds two posted comments on closed dockets and one recent comment awaiting posting. A period's opening and closing instants are stored with the agency's IANA time zone, and a docket is open, extended or closed according to `ctx.virtual_now` at the moment of a read or write; no event closes a period, and the App keeps no clock of its own. `validateSeed` rejects a document that its docket does not list, a period that closes before it opens, an extension that does not move the closing later, a comment whose `text_sha256` does not match its text, a returned comment without a reason, two non-supplemental comments on one docket, broken history timelines and duplicate IDs across every collection.

Four events in `schemas/events.schema.json` are applied by Infra through `env.apply_event`; the handler reads the event's `at` as now. `docket.period_extended` moves the closing instant later and records the previous one, `docket.correction_published` adds a dated correction to the docket page and leaves comments unchanged, `comment.status_changed` moves a received comment to posted or to returned with the agency's reason, and `comment.notice_recorded` is the small Infra event that writes a notice's delivery outcome (delivered, rejected or unknown) into the comment's notice history after the host-run publisher reports it. `examples/scenario.json` is the single correction the public verifier applies; `examples/schedule.json` is an eight-event schedule (the target docket's extension and correction, status and notice records, extensions and corrections on other dockets) that `examples/run.cjs` applies after it. Nothing happens when `env.advance_time` moves the clock. Reset restores the seed and clears drafts because they live in business data.

## Documents and attachments

Each docket's notice of proposed rulemaking is a UTF-8 text document generated from the rule (summary, dates, addresses, supplementary information, mirroring the structure of a public-domain notice); about half the dockets add a supporting analysis, four of them as text-based PDFs written without a library. The 54 documents total about 36 KiB and are listed in `contribution/assets.catalog.json`; `civicdesk.dockets.documents` returns them with their bytes and SHA-256 by docket ID under the platform registration `runtime/registrations/civicdesk.json` (object type `docket`). Comments carry no attachments.

## Integration and review

`contribution/contribution.json` declares the operations, the four accepted events and one send-only messaging direction: `channel.email`, wire `urn:pale:email-message:2` (`schemas/router-message.schema.json`, a byte-identical copy of Mail's), payload `urn:pale:email-payload:1`, event type `org.pale.mail.notification.v1`. The two notice kinds (receipt, status change) are built in `src/notices.cjs` from the public tool views only. `src/publisher.cjs` is the host-run publisher: after CivicDesk's own commit, Infra runs it with a trusted Agent connection and a trusted publishing connection (`runtime/messaging/service.cjs --config apps/civicdesk/examples/router.json --publisher civicdesk`); it reads the committed comment, builds the CloudEvents envelope and calls `router.publish`. The receipt returns to that caller, and Infra records the outcome on the comment with `comment.notice_recorded`, which is how the proposal's notice history is kept without the App ever observing Messaging itself. `examples/mail-notice.cjs` runs the declared flow over real MCP processes: a draft and an acknowledged submission, the receipt notice committed in the real Mail 1.3.0 App with the same tracking number in the comment, the Mail record and the Messaging receipt, the delivered outcome recorded on the comment, a delivery without a recipient grant rejected as `recipient_not_authorized` with Mail unchanged and recorded as rejected, and a replay deduplicated on the receipt. Calendar and Files are reached only by the agent's own tools. `app.json.dependencies` is empty: the package runs with the shared runtime alone.

## Interactive business Web App

See [GUI startup and boundaries](gui/README.md). From the repository root run `node runtime/web/server.cjs --app civicdesk --registry apps/civicdesk/registry.json --run web-demo --profile sandbox`. The App owns its pages in `gui/src/app.js`; the shared Host exposes only the fixed Agent connection and allows no inline styles, so the App's presentation rules are a constructed stylesheet in the controller. Pages: docket search (open, closing soon, all), docket (summary, period with its time zone, extensions and corrections, documents with download, the member's comments), comment form with validation, review with the acknowledgment, receipt, and my comments with status. Deep links travel in the URL fragment next to the Host's access token: `/#docket=<id>`, `/#page=mine&comment=<id>`; the notices' `deep_link` fields use the same route IDs.
