# Mendwell Pharmacy

Mendwell is a synthetic retail pharmacy App for one household on the public PALE runtime 1.6.0, Core API 1.2.0. Prescriptions are requested, priced through the patient's drug plan, held for pharmacist review, collected in store, cancelled or returned to stock. It implements the approved environment proposal [`proposals/environment/mendwell-pharmacy.md` at `c7ddf51`](https://github.com/MatrAIx-ai/Personal-Agents-Last-Exam/blob/c7ddf519b029cebe1c93c5bed50edb889cf34deb/proposals/environment/mendwell-pharmacy.md) (PR #63). Agents use the MCP tools; people and agents can also use the member-facing business GUI on the shared Web Host ([`gui/`](gui/README.md)), added during delivery as App-owned pages over the same tools, with no business behaviour of its own; Infra drives pharmacy, prescriber, plan and counter events and applies user confirmations.

This README is completed with the first runnable version.

## Run it

Node 18 or later, no installed packages.

```sh
cd apps/mendwell-pharmacy
npm test          # App-only business tests, then the fixture checker and generator tests, then the delivery dataset tests
npm run fixture   # the fixture checker and generator tests alone
npm run dataset   # the delivery dataset tests alone
npm run example

cd ../..
npm run app:verify -- --app apps/mendwell-pharmacy --output .artifacts/mendwell.json
node runtime/web/server.cjs --app mendwell-pharmacy --run web-demo --profile sandbox
node apps/mendwell-pharmacy/dev/confirm.cjs web-demo <token>
```
The Web Host command starts the business GUI; open the link it prints. `dev/confirm.cjs` applies, as Infra, the user confirmation for a previewed grant change or prepayment, whose code the page shows. The browser acceptance needs the repository's pinned Playwright: from the repository root, `npm ci`, `npx playwright install chromium`, then `node apps/mendwell-pharmacy/tests/web.browser.cjs`. It drives the GUI through the proposal's workflows against the real App, checks each step against App state read through Infra MCP, and writes `.artifacts/web/mendwell-pharmacy/report.json` and screenshots (see [`gui/README.md`](gui/README.md)); its generic part, `tests/web/harness.cjs`, starts the shared Host and an Infra inspector on a fresh run. CI's shared browser job (`npm run test:web:browser`) is fixed to the seven personal Apps and does not run this file.

`fixtures/minimal.json` is the representative seed (217 records; 577 KB). The history runs from 2025-01-01, when Sam gives Alex the refill and pickup grants `g-h1` and `g-h2`, to the clock: 13 earlier prescriptions, 138 fills (126 collected, 8 returned to stock, 4 cancelled) with 153 claims, 5 plan requests, 119 charges, 5 collection refusals and 361 notices, and 4 grants (one expired, one revoked). Its IDs are in a separate `h` series (`rx-h1`, `f-h1`, `cl-h1`, `n-h1`, `g-h1`, …) outside the runtime counters, so a run's first new fill is still `f-21`. It is generated by [`dev/generate-history.cjs`](dev/generate-history.cjs), which replays the App's own tools and events with a fixed seed and one random stream per regimen: routine refills of eleven regimens (monthly and 90-day supplies), each requested by the household member who would make the request (Elena requests her own; Alex requests Alex's own, Sam's under Sam's refill grant and Mia's as a guardian) and collected at an open store with the collector's own card, together with every other fill of that collector that is ready there, including fills of the task timeline, whose own scheduled pickup is then skipped; prior authorizations, early requests that waited for their eligible date, cash payments, stock waits and restocks, pharmacist holds, forgotten pickups returned to stock or cancelled, and refusals at the counter (closed store, declined card); the 2025 prescriptions and grants, and two amoxicillin prescriptions, one with a fill-limited pickup grant revoked before collection. The two series share prescriptions where a household would: from `f-h86` on, the 53 routine history refills are on the current task-timeline prescriptions, and the task renewal `rn-1` renews the 2025 prescription `rx-h6`. Every request runs as the person who makes it, with that person bound as the account holder, and each state passes the App's `validateSeed` under that binding before and after the call and, for every committed state, under the fixture's own binding. Approvals used during the replay are not kept, because seeds carry none.

## Delivery dataset

The evaluation dataset for the Environment window, 2025-01-01 to 2026-12-31 inclusive in `America/New_York`, is in [`dataset/`](dataset/). The smoke fixture (`fixtures/minimal.json`) and the delivery dataset share the household and the catalog (equal at the fixture clock, store stock included, checked by `tests/t32-dataset.test.cjs`) but have independent histories: the fixture serves the business tests, the examples and the proposal's example events; the dataset serves evaluation, and Tasks select their history from it with `dataset/as-of.cjs`. The dataset's records use the App's own runtime ID series (`rx-1`, `f-1`, `cl-1`, `g-1`, `n-1`, …), so their IDs overlap the fixture's task timeline but name different records: the fixture's `f-15`, `rx-9`, `g-3` and the other IDs named by the proposal's example events are not the dataset's. [`dataset/generate.cjs`](dataset/generate.cjs) replays the App's own tools as the household member who makes each request, with that person bound as the account holder, and its events as Infra, with a fixed seed, validating every state against the seed schema and `validateSeed`. Each of the eleven regimens of the fixture's household is refilled on its own cadence from the prescriptions received in January 2025 and January 2026 (and through renewals), at the store the household uses at the time (Elena's fills at Maple Avenue while she stays with the household from 2025-06-16 to 2025-08-31, the household's at Harbor Street from 2025-10-01 to 2026-02-28), and collected at an open store by the patient, a guardian or a pickup-grant holder, who on the same visit takes every other ready, unheld fill at that store that they may collect and can pay for (so a pickup is missed, and the fill returned to stock, only when nobody who may collect it visits that store while it is ready); nobody is at the counter during the household's trips (2025-07-12 to 2025-07-20, 2026-05-23 to 2026-06-01 and 2026-12-19 to 2026-12-28; Elena's 2025-10-04 to 2025-10-12), and a maintenance refill whose supply would run out during a trip is requested before the trip if it can be collected before leaving (an early refill the plan may override), otherwise after the return. Each maintenance refill is requested when the projected supply (carried over from earlier pickups) falls to two to five days plus the time for review, any prior authorization (ten days) and pickup, and never before the plan's eligible date, so routine claims are paid when billed: across the window a request finds 0 to 39 days of supply on hand, 7 at the median, and only 9 of 175 claims are rejected as too soon (7 early requests and 2 lost supplies), from an occasional early request (about one in ten 90-day refills, when supply is ample) or a lost supply. A renewal is asked for within two days of the last refill, except when the prescriber writes a replacement at the yearly visit in the following 45 days (listed in the coverage report). A pickup is forgotten, and returned to stock or cancelled, only after such an early request. Supply is counted with one stated method: every pickup adds its days of supply to what is left (supply carries over), and a documented lost supply empties all supply on hand at the moment the household asks for the replacement. Under that method every gap is reported: the only two follow the lost supplies: Elena's warfarin for 4.0 days, from 2025-11-07 11:24 until the replacement was collected on 2025-11-11 12:14, and her atorvastatin for 3.1 days, from 2026-08-09 09:49 until 2026-08-12 11:40 (times in America/New_York), and the coverage report lists them. The generator stops on any other gap between pickups or before 2026-12-31, on a gap of more than seven days after a loss, on a maintenance regimen never collected, on a fill that becomes ready while its patient is away, or on two pickups of one regimen returned to stock in a row. Around these, the window holds every claim rejection (prior authorization, quantity limit, too soon, not covered) and its resolution, plan requests approved, denied and withdrawn, renewals approved, denied and withdrawn, holds during review and while ready, stock waits ended by a restock or a store change, prepayments captured or voided, refusals at the counter for each reason, pickups returned to stock or cancelled, Mia's inhaler fill cancelled when its prescription expired while the pharmacist waited for the prescriber to confirm the quantity, nine amoxicillin courses for Mia, and the household's grants given, extended, expired and revoked by events and by the account holder; `dataset/generate.cjs` stops if any of these is missing. A card is declined at the counter by a seeded choice for each person that depends on the visit (more often in the two weeks after a trip, when the travel card is still in the wallet); after that one decline Alex stops carrying the travel card and pays with another card a few minutes later or comes back another day. Arriving after closing is likewise drawn per person for visits planned close to closing time. The prescriber's office writes prescriptions, sends prior-authorization forms, answers renewals and confirms a dose or quantity only from Monday to Friday, 09:00 to 17:00, never on U.S. federal holidays or December 24, and plan decisions keep the same business hours. Nobody walks into the same closed store twice in one evening, and a ready fill is collected before its prescription expires. Every donepezil fill goes through its own prior authorization: in this App an approved request waives the rule for its own fill only, a simplification of real drug plans, where an approval usually covers a period of time. The generator stops on any step that would not change the state, such as a decision on a request that has already closed. A prepayment or grant change that needs the person's confirmation is replayed as preview, `user.confirmed` and confirm at one instant, and the used approval is not kept, because seeds carry none. The free texts the generator supplies are checked against the records they describe ([`dataset/notes.cjs`](dataset/notes.cjs)): a travel note on an early-refill request needs a trip of the patient starting within 14 days; a lost-supply note, a collection of that drug in the 21 days before; a prior-authorization note is the first form, chart notes after a denial or a corrected form after a withdrawal of the same fill's request; a renewal note says the prescription expired or its last refill was used exactly when that is so; and a hold note is answered by its own release note, is placed in review or while ready as it says, and a hold that ended has its release; prior-authorization notes and the prescriber's release notes fall in the office's hours.

Loading the whole window as one seed would present every record after a Task's first session as history, so the dataset is a base seed plus dated steps. [`dataset/as-of.cjs`](dataset/as-of.cjs) replays, through the App's handlers, only the steps dated before a first-session instant: later records do not exist in the selection, a fill in progress at that instant has only the history it had then, and the counters (`issued`), store stock and clock are the App's at that instant. A timer due before the instant with no later step yet (a review, a resubmission, a pickup warning or return, a prescription expiry) is committed in the selection at its due time, as the App's next write would commit it, so the seed, its notices and claim reversals, and `open_fills` agree with what Core reads at that instant; a timer due exactly at the instant is left to Core's reads, which already show it. The later steps are withheld. The Infra events among them that apply to the selection as it stands and have there the same effect as in the dataset (prescriptions and renewal replies, decisions on existing plan requests, holds, restocks, grant changes, counter collections of existing fills) are returned as `events`, in order, ready to stage through `env.apply_event`; they are what happens if nobody in the household acts. An event whose effect depends on a withheld household action, such as Sam's pickup of a fill Alex prepays or a pickup of a fill that becomes ready only after a withheld plan request, is not among them, so staging the `events` as given writes nothing the dataset lacks. `account_holder` names the bound account holder (Alex, `p-2`) and the fills, and open fills, that the account holder may see at the instant. Each selection lists the fills open at the instant in `open_fills`, each with its status as Core reads it, whether the account holder may see it, and the withheld household actions on it (on the fill itself or on plan requests made for it, including requests that withheld actions create), each labelled with the person who takes it and whether the account holder can take it. `account_holder_script` is the ordered list of exactly what reproduces the dataset as far as the account holder can: the events, the account holder's withheld actions (with arguments renamed to the IDs the App issues when they are taken without the other withheld steps), and the Infra events that only apply after those actions, which are also listed in `conditional_events` with the actions they wait for, such as a plan decision on a request the account holder makes. ## Infra

The optional Mail flow is run by Infra with `infra/sender.cjs`, never by the Agent (`npm run mail` checks it against Mail 1.3.0). It relies on these Infra assumptions:

- Build each Mail session with `openSession` from one grant: it opens the Mail instance in the account's digest namespace, checks its seed and binding, then starts the Router with that namespace and grant. The adapter refuses sessions it did not build or that were built for another run, and checks every Router and Mail endpoint against the run before aligning clocks or publishing. It handles errors on the input streams of the clients it opened this way and writes nothing to a client whose input is closing or closed, so the objects that `openMail` and `openRouter` return must expose the client's `child` process; a `stdin` property alone covers the input, but then the adapter cannot see the Router's exit.
- The Router does not report which inbox it is bound to. A Router that Infra opened for another inbox of the same owner is caught only from its receipt, after delivery; the adapter then halts every session.
- A publish whose outcome is unknown (its Router reply times out or is lost, or the reply shows neither that Mail answered nor that nothing was dispatched, such as `receiver_unconfirmed`) halts the run at once through `onHalt`, before any other call to that Router, and keeps the publish lock, so writes through `adapter.exclusive` wait, until the dispatch is settled on the Mail side. After a lost reply the same Router must first answer a later request (it handles requests in order, so the earlier one has then finished or been refused) or its process must have exited, as its client's child process reports; a client error alone, such as a write after its input was closed, does not count. Then the session's Mail instance must show the event committed, be in a new epoch, or commit a 1 ms `env.advance_time` from the adapter: a receive still queued in Mail, including one left running by a killed Router, carries an older expected version, so Mail refuses it after that write. That write leaves Mail's clock 1 ms ahead in the halted run. Only then is the halt checked and reported. A Router that never answers or exits, or a Mail instance that cannot be read or written, keeps the lock. Infra may close only a Router that does not answer; the close counts once its process has exited, and Mail must stay reachable. Closing a Router that still answers, or killing one, can end or orphan its Mail receiver in the middle of a transaction: a close ends the Router's input and, if the Router is still running 1 s later, sends it SIGTERM; the Router then closes its receivers at once, even while one of its requests is pending, and a receiver still running 1 s after that gets SIGTERM. That can leave the Mail instance unusable. The run then stays halted and the adapter keeps the publish lock, so nothing is delivered after a revocation, but whether the pending entry was delivered is unknown: Core stores the notice and its receipt before it releases the Mail lock, so an interrupted receiver may already have stored it, and an orphaned one that finishes later stores it then (the adapter then settles as `committed`, still before any revocation). Infra ends that run. While the adapter settles, `status()` reports the halt and its cause without `stop_verified`.
- Pass an `onHalt` function that halts every Router session of the run, such as writing the Router's stop file. The adapter refuses to start without it, verifies after each halt that every session refuses, and otherwise reports the halt as unverified. Adapters in one Infra process share the halt; another process must ask the Router. The function may run while the publish lock is held, so calling `send`, `align`, `reconcile` or `exclusive` of an adapter for the run from inside it is refused with an error.
- Apply grant changes, other Mendwell events and resets through `adapter.exclusive(fn)` while a pass may run: each publish is checked against a fresh snapshot under that lock. A write applied any other way, through another Core client or in the same process outside `adapter.exclusive`, can land between that final snapshot and its publish, and the adapter cannot see it.
- Wrap only Mendwell writes, events and resets in `adapter.exclusive`. Calling `send`, `align`, `reconcile` or `exclusive` of an adapter for the same run from inside it is refused with an error, because it would wait for its own lock.
- A person with several granted inboxes is served only when exactly one route is usable and every other one is ruled out for a configuration reason. While two routes are usable, or one is usable and another is merely unreachable for a pass, the entry waits as `ambiguous_route`; when no route is usable it waits with the first route's own reason, for example `router_unavailable` when every Router is down, even if the inboxes can be read. Once an entry has been sent, or its outcome is in flight or unknown, every retry goes to that inbox only, and the entry waits while that inbox is unusable (`destination_unavailable`) or while another inbox of the recipient cannot be checked for an earlier delivery (`destination_unknown`).
- The destination record lives in the adapter's process and is shared by every adapter there. An adapter in another Infra process learns of an earlier delivery only by reading the recipient's inboxes (Infra itself can also find a confirmed delivery in the Router's audit log, `messaging.receipts.jsonl`), so run one sender process per run.
- `adapter.status()` answers `unknown` until the adapter has resolved its run (`await adapter.ready`, retried by every `send` or `align`), and only then `ready` or `halted`; `send` and `align` refuse a halted run in any case.
- A configuration verdict once recorded for a session (an incompatible contract, another run's Router or Mail, no Email channel) keeps that route out even while the session is also unreachable.
- A session whose Router, Mail instance or clock fails during a pass is left out of that pass (`router_unavailable`, `receiver_unavailable`, `clock_unaligned`) and its entries stay in the log; the other sessions continue. If Mendwell's own clock cannot be aligned, nothing is published.
