For every step the table records the action, the expected result, the element the step checks (outlined in orange in the screenshot), the test's own reading of the App state together with every record that changed since the previous step, read through a separate Infra MCP client from the frozen state, the MCP calls the recorder lists for the step, the version, the virtual time and the checks passed. The recorder follows Plateway's rules: every call, in every tab of the browser context, is owned by the step open when it is sent; a step is frozen before anything is taken from it and stops the script if the version moved between its check and its freeze; each call has exactly one terminal outcome; a forced call carries a token bound to its exact tool and arguments; and recorder errors are append-only. Two additions for this App: a connection the test drops on purpose (a reply lost after Mendwell committed, a call dropped before it reached Mendwell, a failed tool discovery) is declared by the step beforehand and listed with its cause, and an induced failure that never happens is reported at teardown; and confirmations applied with `dev/confirm.cjs` (a separate process) are recorded as calls of the step that makes them, with that helper's random event ID replaced by a note. Before capturing, `gui.cjs` runs the 27 recorder probes in [tools/probes.cjs](tools/probes.cjs), each on a fresh page; each must stop the recorder with its exact expected message or show the declared outcome, and the results are in `run.json` (`recorder_probes`).

- **Edit and cancel:** discarding a grant preview, a quantity change, a store change made with Move fill (read back through MCP and after a reload), keeping a fill after its cancellation preview, a confirmed cancellation, a cancellation that withdraws a pending plan request with it, withdrawing a renewal and a plan request, clearing a collector.
- **Invalid and denied:** a fill request with no fills left, a collector without pickup access, an unknown person ID, a held fill (no store, quantity, cash or prepay change), a declined card for a prepayment, an expired, reused or wrong-person confirmation (`confirmation_invalid`), management requests from the page session (403), a policy without `plan_requests.create` (control removed, forced call 403), and a refusal and a read Mendwell refuses, each explained in plain words without internal IDs.
- **Stale and conflicting:** a preview made stale by another change (new code shown, nothing sent), writes refused as `stale_version` after a change made outside the page, reads that keep changing during a refresh, access revoked between reads or while a request is unanswered, previews and forms from before a reset or reload, a preview repeated or answered across a reset, a reset between the re-preview and the write, a reset right after a commit (its success message kept), an answer stamped for another epoch (not taken as success), and replies lost after Mendwell committed (retried, or reported as unconfirmed after a reload).
- **Approval states:** waiting for the confirmation, active, used, expired and from someone else, for grant changes and prepayments; after a reload no preview is kept in the browser, the confirmation stays listed, and the same preview gets the same code, already confirmed.
- **Reload and independent updates:** see the index row above; every Infra event, confirmation and clock move is followed by Refresh, and each step's state is read through Infra.

- **Files and content:** N/A for files: Mendwell has no attachments or media (`app.json` limitations: "No attachments or media: resources are not used."). Untrusted text is shown as text and never as HTML: [05.4 A collection while held is refused](gui/05-w4-holds/04-a-collection-while-held-is-refused.png) shows a pharmacist note containing markup and an image tag with an error handler as its literal text, with no element created, and [03.2 Ask the plan for an early refill](gui/03-w3-claims/02-ask-the-plan-for-an-early-refill.png) stores a plan-request note typed with such a tag exactly as entered.
The browser acceptance `tests/web.browser.cjs` remains the full GUI test; App-only business tests and real MCP tests are separate. Browser automation demonstrates controls and state; it is not a model-agent evaluation.

## App limits shown in the GUI

- Mendwell returns only each fill's latest plan request, without its note or the plan's reasons, so the page shows earlier requests for the same fill only as far as the fill's timeline names them.
- No Agent read returns the App's current time or a card's state, so the Account page shows each card's expiry month and does not mark an expired card; a payment with it is refused by the App (`payment_failed`) and shown.

## Not covered

- No public reference image of the signed-in CVS pages exists; every reference is an archived help page, and the comparison awaits reviewer agreement. The CVS page on caregivers picking up prescriptions has no usable snapshot, and no archived page covers a pharmacist's hold, a prepayment for pickup or a plan request.
- Pharmacist, prescriber, plan and counter screens are not part of the approved scope; their actions are Infra events.
- Business confirmation of a Mail notice is not claimed.

## Regenerate

From the repository root, after `npm ci` and `npx playwright install chromium`:

```sh
node apps/mendwell-pharmacy/evidence/tools/regenerate.cjs --date 2026-11-28   # gui/, mail/ and this index, then the App load digest
node apps/mendwell-pharmacy/evidence/tools/reference.cjs      # reference/ (needs web.archive.org; --update replaces a capture that changed)
node --test apps/mendwell-pharmacy/evidence/tools/reference.test.cjs   # the refusal and capture-date rules of reference.cjs, with stubbed captures
```

`regenerate.cjs` runs `tools/gui.cjs` (which first runs the recorder probes), `tools/mail.cjs` (which also runs `tests/mail.integration.cjs`), `tools/index.cjs` and `tools/digest.cjs` in that order and stops at the first failure. `gui.cjs` and `mail.cjs` write their captures to a temporary folder and replace the files in `gui/` and `mail/` only after the whole run has passed, so a failed run leaves the committed evidence as it was. The capture tools launch Chromium with software rasterization on one thread (`--disable-gpu --num-raster-threads=1 --disable-partial-raster`), take screenshots with animations disabled and replace the page's random request IDs with a counter kept in a cookie of the page's origin (`web-evidence-0001`, …), leaving the browser storage the test checks untouched, without changing the GUI source. With these, two consecutive runs of `regenerate.cjs` on the capture machine with the same `--date` gave byte-identical files in `gui/` and `mail/`, and the same index and App load digest. On another machine or Chromium build, anti-aliased edges can differ by a few pixels; the recorded steps, states, IDs and receipts do not.

`captured_on` (in [gui/run.json](gui/run.json) and [mail/demo.json](mail/demo.json), and shown in [gui/README.md](gui/README.md), [mail/README.md](mail/README.md) and this index) is the capture date. `gui.cjs`, `mail.cjs` and `regenerate.cjs` take it from `--date YYYY-MM-DD`, or else from the day of the run in UTC; regenerating on another day without `--date` therefore changes those five files and with them the package digest, even when every capture is unchanged. Passing the committed date (2026-11-28) keeps it.

The reference captures in `reference/` are not reproducible in the same way: they depend on the Internet Archive answering, and an archived script that fails to load can change how a page renders (a question list that does not open, for example). `reference.cjs` therefore compares every capture with the committed [references.json](reference/references.json) before writing anything, and stops, keeping the committed files, when a capture's rendering mode (the page as it renders, or content revealed by setting its opacity to 1) or its size differs from the committed entry; `--update` replaces such captures once they have been checked by eye. A capture whose bytes are unchanged keeps its committed `captured_on`; a changed one takes `--date` or the day of the run.
