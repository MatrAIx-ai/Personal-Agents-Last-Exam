# Mendwell Pharmacy Web App

`index.html` and `src/app.js` own Mendwell's member-facing business interface for the bound account holder: fills and pickup, prescriptions and renewals, plan requests, household access grants, cards and stores. The shared public `runtime/web/client.js` provides the session, tool discovery, text-only rendering and the shell; `runtime/web/server.cjs` serves this page and forwards only the Agent tools the current policy allows. `src/view.js` remains the compatible reviewer renderer.

From the repository root:

```sh
node runtime/web/server.cjs --app mendwell-pharmacy --run web-demo --profile sandbox
```

Open the access link printed by the Host. A new run starts from the fixture at the shared registry's start instant (Wednesday 18 November 2026, 12:00 in New York) as Alex Rivera; starting against existing state never resets it or changes its policy. Pharmacist, prescriber, plan and counter actions (reviews completing, holds, plan decisions, renewal replies, restocks, grant changes made by others, collections at the counter) and user confirmations are Infra events or Infra clock changes sent through a separate Infra MCP process; press Refresh to see them. The page has no route for them.

## User confirmations

Grant changes (`grants.change.confirm`) and prepayments (`fills.prepay.confirm`) need a `user.confirmed` event from the person who must approve: the patient or guardian making the grant change, or the card owner. A page cannot issue that event, so the page works like this:

- The preview shows what changes and explains in plain words that the person who must confirm (the account holder is addressed as “you”) confirms the change outside this app, as with a code sent to them; that the confirmation shows on the page after Refresh; and that it stays valid for 30 simulated minutes and works once. The confirmation code (the preview token) is shown as a secondary reference. In this local preview no code is sent to anyone, and the panel says that the confirmation is given as described in this README (with `dev/confirm.cjs`, below); the page itself shows no developer command.
- Confirm before the confirmation arrives shows a waiting state (“Waiting for your confirmation”), not an error; nothing changes.
- Infra applies the confirmation. For a local run, from the repository root and with the same run and state directory as the Host:

  ```sh
  node apps/mendwell-pharmacy/dev/confirm.cjs web-demo <token>
  ```

  `--state-dir` and `--registry` default to the Host's defaults (`.state` and `apps.registry.json` at the repository root); `--by` defaults to the bound account holder and `--at` to the App's current time. The helper refuses a run that has no state in that directory, an unknown option and an option without its value before issuing any event, so a mistyped run name or a bare `--by` confirms nothing. In a scenario the same event comes from the user simulator or the task's events.
- Refresh shows the confirmation (confirmed at, valid until, or expired or used). Confirm then commits.
- Every Confirm first previews again with the same frozen inputs. If the code or the listed effects changed (another grant change, a hold, a reset), the page shows the updated preview, sends nothing and needs a fresh click, and for a grant change or prepayment a new confirmation for the new code. Otherwise it sends the frozen arguments and code with the version read together with that preview and a new request ID. An expired, used or wrong-person confirmation is refused (`confirmation_invalid`) with no success message, and the preview stops saying it is waiting. A preview belongs to the fill or person it was made for: it is shown and confirmed only there, with that record's ID, whatever is selected later.
- The page keeps no business state in the browser (no local or session storage of previews, selections or outcomes). After a reload an open preview is gone, and the panel says so in advance: preview the same change again; Mendwell returns the same reference code for an identical preview, so a confirmation already given still applies within its 30 minutes. The account's confirmations stay listed in any case (Household for grant changes, the fill for prepayments). Only one preview is open at a time; starting another while one is open on a different record is refused with a pointer to it.

Cash and cancellation have no user confirmation; they use the same preview, re-preview and confirm steps.

## What the page does

- **Fills.** Grouped as needs attention (rejected by the plan), in progress (pharmacist review, waiting for stock, waiting for the plan), ready for pickup and past (collapsed). A fill shows the patient, drug, store, quantity, the plan's answer (paid, or the rejection reason with the eligible date and any waived reason), a cash price, the plan request, the amount due, a prepayment and its state, a counter charge, who will collect, due times (review, resubmission, pickup reminder, return to stock), a cancellation, counter refusals, the pharmacist's hold and notes, the account's confirmations for it and the timeline. Actions follow the state and the account's authority: change quantity (requested, or rejected for the quantity limit), change store with stock shown, wait for the eligible date, ask the plan for an early-refill override or prior authorization and withdraw it, pay the cash price, prepay with one of the account's cards, name or clear who will collect (any household member, or another person by ID; the App accepts the patient, a guardian of a minor or a pickup grant covering the fill and says so otherwise), and cancel. Actions the App would certainly refuse for the state on screen are not offered, and the reason is shown instead: a held fill offers no quantity, store, cash or prepayment change and says it cannot be collected until the pharmacist releases it; while a plan request is pending, the page says that the cash price needs the request withdrawn first. Withdrawing a plan request and scheduling the resubmission (“Resubmit to the plan on …”) ask for confirmation first. A ready fill says plainly whether it can be collected now and what is left to pay (for example “Nothing more: $65.00 is prepaid and charged when collected”); a cancelled, returned or collected fill shows nothing outstanding and its original price on a separate line. The timeline is numbered in order and names each step from what happened (for example “Plan request withdrawn”); Mendwell returns only the latest plan request's outcome, so the latest request's outcome (withdrawn, denied or approved, including an approval followed by a claim rejected again) labels the step it caused, and for an earlier request the page says that Mendwell does not report how it ended; the cancel preview says in plain words what stops. Pickup-only access shows the logistics view (store, status, amount due, ready and return times, the account's own prepayment, and Prepay when the fill is ready with an amount due); that view carries no pharmacist hold, so a ready fill is shown as ready “as the pharmacy reports it”, without promising that it can be handed over; the logistics read carries no patient, so the page names the patient from the account's pickup grant when that grant identifies one.
- **Prescriptions.** By person, active first: drug, form, quantity, fills left, prescriber, written and expiry dates, replacement after a renewal, renewal requests, the label facts with their cited source, and the prescription's fills. Request a fill (store with stock and opening, quantity), ask for a renewal (optional note) and withdraw a pending renewal (after a confirmation step). A prescription with no fills left offers no fill request and says to ask for a renewal; the label source is a link.
- **Plan requests.** Fills with a plan request, pending first, then decided or withdrawn; selecting one opens the fill. Until one is chosen, no fill is shown there; this page keeps its own selection, independent of the Fills page. Each row shows when the request was sent and when it was decided or withdrawn, taken from the fill's timeline; Mendwell returns only each fill's latest request, without its note or the plan's reasons, so earlier requests for the same fill, notes and denial reasons are not shown.
- **Household.** The people the account acts for and its powers for each, grants given and received with their state, a Give access form (person, view, refill or pickup, pickup optionally limited to one open fill, optional end in Eastern Time; when the chosen fill is no longer open, the form clears the limit, says so and keeps Preview disabled until a fill, or all of that person's fills, is chosen again) and Revoke on each active grant the account controls; the account's confirmations with their state. No Agent read returns the name of someone known only from a grant (not in `household.list`), so the page calls them “a family member you do not have access to” and shows their ID only as a small reference. The collector form explains that anyone else needs pickup access first; its link opens Household with the Give access form filled in for that person and fill.
- **Account.** The holder, the time zone, masked cards with their expiry month, and the three stores with their addresses, weekly hours and whether each is open now. No Agent read returns the App's current time or a card's state, so the page does not mark a card as expired; a prepayment with an expired or declined card is refused by the App (`payment_failed`) and shown.

Times are shown in Eastern Time (America/New_York), the App's zone, whatever the browser's zone. The sidebar names the signed-in account holder. Choosing a record in a list reads only that record (no page-wide refresh) when Mendwell has not changed since the last refresh, and a full refresh otherwise; a search that no longer matches the open record clears the detail. On a phone the list is not boxed into its own scroll area, and buttons are at least 44 px tall. Notices go to Mail through the Infra sender; no Agent read returns the notice log, so the page shows none.

Every value shown comes from Agent reads made at the last refresh, and the reads of one refresh must share one Core version `{epoch, revision}`; otherwise the page reads again (three times, then asks for Refresh). A detail read refused with `not_authorized` or `not_found`, or a record missing from its list, removes that record at once, together with the person's other records, drafts and previews when the account lost its access to that person, even if the next read fails. Such a refused read discards the whole refresh, which is read again; when any household list answer the page receives (a refresh's own read or the page shell's) shows that access to a person ended, that person's records, forms, prompts and messages leave the screen at once, and when the grants list shows that the pickup grant covering a pickup-only fill has ended, that fill leaves the screen at once; both happen even if a later read of the same refresh fails; a refused read for a record just chosen in a list removes that person's records at once, before any refresh. When Mendwell is reset or reloaded (a new epoch), every open form, draft, preview and confirmation dialog from before is closed and the page says so; an unanswered request from before is not sent again and is reported as one whose outcome cannot be confirmed. Nothing from before a reset is ever sent. Unsent inputs and open forms are kept only while their action is still offered for the record as it now reads: a record that is no longer listed, access reduced to the pickup view, a state that no longer allows the action or a policy that drops its tool closes them, and they do not come back if the access is given again. A form remembers the record as it was when opened: if another change reaches that record and the form was not edited, it shows the current details and says so; if it was edited, the entry is kept, the form says the record changed and its button reads “Save anyway”. If the reads for a newly chosen record fail, the page shows neither the old nor the new record and accepts no change until a Refresh succeeds. Nothing from the App is rendered as HTML. Each write carries the Core version read at the last refresh (a confirm carries the version of its re-preview) and a new request ID. If the connection drops, or the Host answers with an error that carries no App status, the page shows a "Waiting for Mendwell" banner holding that exact request: Retry sends it again unchanged, so it takes effect at most once, and the page says whether it had already gone through, was not applied, or (after a reset in between) cannot be confirmed; Dismiss drops it. If the record it concerns is no longer visible to the account, or the account can no longer change it (for example access reduced to pickup), the banner no longer names it and offers only Dismiss; an unanswered prepayment whose fill drops to the pickup view is described from the fill as it is now visible (“a pickup”) and keeps Retry, since pickup access still allows prepaying. On every refresh, names are recomputed from what is still visible (an open preview or an unanswered request about someone whose access ended no longer names them), open confirmation dialogs are closed when their action is no longer offered or the request they were opened for is no longer the pending one, and messages about a person who is no longer visible are removed. The page checks the epoch of every answer it receives (reads, previews, writes and Retry receipts). The moment any answer shows a newer epoch, every form, draft, preview and confirmation dialog from before is closed. A preview answered from another epoch than the one the click was made in is not kept, Confirm is offered only for a preview of the epoch currently shown, and a write or Retry answer stamped for another epoch is reported as one whose outcome cannot be confirmed, without a success message. Until it is settled, other changes wait. After a change the status reads “Saved. Loading the latest state…” while the page refreshes. If that refresh fails, the page says the change was saved and asks for Refresh, and further changes wait until Refresh succeeds. Only a dropped connection or a Host error that may have reached Mendwell is treated as unknown; a refusal by the Host itself (the policy no longer allows the operation, or the session is no longer valid) is shown as a plain refusal with nothing sent and no Retry. App refusals are explained in plain words without internal IDs (for example “Mia Rivera cannot collect this fill …”, or for a fill already in progress “This prescription already has a fill in progress …”; an unknown person ID typed into a form gets “No person with that ID …”, an access change Mendwell cannot make is named for what it is (“This person already has exactly this access …”, “That end time has already passed …”), and a quantity the medicine does not come in is refused with the quantities it does come in); a read Mendwell refuses is shown as “Mendwell refused to show its current state …” (or “This record is not visible to this account” when the record is not visible), never as the App's own message. The page rewrites only the message of refused reads and keeps the HTTP status, status text and headers of every answer; refused writes reach the page unchanged and are explained from their code. An operation's outcome message (success, refusal or unknown outcome) stays through refreshes and resets until the user dismisses it or acts again. While a refusal is shown the status says “Nothing was changed”; when the outcome is unknown (a dropped reply, a reset in between) or a Retry is still outstanding it says “Whether your last change took effect cannot be confirmed”; it never says “All changes saved” next to either, also after a manual Refresh. IDs appear only as small references (“Reference pr-13”). Refusals are shown where they happen: `stale_version` (Mendwell changed since the page last read it) apart from a preview that changed, and the App's own errors such as `no_fills_remaining`, `on_hold`, `payment_failed` and `confirmation_invalid`. While an operation runs, the page's controls are disabled; unsent form inputs survive a Refresh. Opening a form moves the keyboard focus to its first field, and closing it returns the focus to the button that opened it. Controls and open forms for tools the current policy does not allow are not shown (a policy change takes effect on the next Refresh), and a forced call is refused by the Host. The page needs `mendwell-pharmacy.household.list`.

## Why the page draws its own views

Mendwell's reads take `fill_id`, `rx_id` and `patient_id` rather than `id`, and its two-step previews and confirmations, the waiting state for user confirmations, card choice and store stock are not expressible as the shared generic forms. The controller therefore draws its own views through the configuration that `runtime/web/client.js` `mount` accepts and the other Apps use: the list call is `mendwell-pharmacy.household.list` with no records (so nothing is auto-selected), `load` fetches the views, `renderList` and `emptyView` draw them, and every read, preview and write goes through `ui.call`. It hides the shell's record-count badge, which would always read 0. Styling uses the shared classes plus element styles, as the Host's content security policy allows; the shared Host, client and stylesheet are unchanged.

node apps/mendwell-pharmacy/tests/web.browser.cjs

a prescription with no fills left offering no request (the App's refusal checked directly), a renewal withdrawn after a confirmation step and re-sent, a late reply ignored, `stale_version`, a fill request whose reply is dropped after the commit, another change refused while it is unanswered, and the retry returning the stored receipt;
