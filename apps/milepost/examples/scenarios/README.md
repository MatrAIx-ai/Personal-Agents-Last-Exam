# Reference scenarios

Four scenarios that cover the four workflows on the full fixtures, each with a twin. They are validation material for the environment, not Task Track submissions. A Task can reuse a scenario's bundle, setup and grader.

| Scenario | Student | Request (shortened) | Twin changes | Decision that changes |
| --- | --- | --- | --- | --- |
| [`s1-cells-exam`](s1-cells-exam/scenario.json) (workflows 1, 2) | Daniel, Mon 03-01 09:00 | Plan practice for Thursday's cells exam so every skill reaches its target, without time on what he already knows | Two platform sessions on Sun 02-28 (bio-5-1, bio-5-3) | Base: practise all five skills (reference 260 minutes). Twin: bio-5-1 and bio-5-3 are already on target, so practise only the other three (200 minutes) |
| [`s2-four-blocks`](s2-four-blocks/scenario.json) (workflows 1, 3) | Maya, Sat 03-06 13:00 | "I did all four blocks… Tuesday's late, around 9… make sure my record is right" | The platform also recorded Wednesday's and Friday's blocks, each started an hour late | Base: report Wednesday's and Friday's practice only; Tuesday's was recorded at 19:30. Twin: add nothing |
| [`s3-exam-moved`](s3-exam-moved/scenario.json) (workflows 2, 4) | Maya, Wed 03-03 08:10 | The cells exam moved to Monday and she lost Wednesday and Thursday evenings: keep only practice that gets a skill to its target, say which won't | Six more February sessions on the cells chapters | Base: only bio-4-3 can still reach its target (bio-4-4 already has); the three bio-5 skills get no practice. Twin: one block each and every target is reached |
| [`s4-checkin-result`](s4-checkin-result/scenario.json) (workflows 1, 2, 4) | Daniel, Fri 03-05 12:30 | The check-in results came in: update the plan for next Friday's quiz, drop practice he no longer needs | Three spaced February sessions on alg-7-5 | Base: alg-7-5 was measured at 0.66 but fades to 0.585 by the quiz, so keep one short review. Twin: it holds at 0.642, so drop every alg-7-5 block |

Together the setups apply all five event types: `practice.completed` (s2, s4), `assessment.added` and `assessment.result_posted` (s4), `assessment.moved` and `preferences.changed` (s3).

## Files

- `<id>/scenario.json`: the request, the student, `load_at`, the `setup` (events and clock moves Infra applies in order), `ask_at`, the records added for the scenario (`changes`) and for the twin (`twin.changes`), what the twin changes and why no run passes both (`twin.decision`, `twin.proof`), the checks for each member (`success`), and the reference run, valid alternatives and controls as lists of Agent tool calls (`runs`).
- `<id>/base/` and `<id>/twin/`: load bundles (`seed.json`, `binding.json`, `dataset.json`, `catalog.json`) generated by `scripts/build-scenarios.cjs` from `scenario.json` and the full fixture. Do not edit them by hand; `--check` reports drift.
- `grade.cjs`: the state-only grader. Checks: `all_targets_reached`, `min_targets_reached`, `no_broken_rules`, `no_unneeded_practice` (no block for a target skill that reaches its target without planned practice), `blocks_in_scope` (target skills and their prerequisites only), `only_reached_targets` (every block is for a target skill that reaches its target), `nothing_after_assessment`, `max_planned_minutes` (1.5 times the reference), `reports_exactly` (new student reports match the listed blocks: same skill and day, length within 10 minutes) and `no_plan_changes`. What the Agent says to the student, for example which skills will not make it in s3, is left to the Task.
- `baseline.cjs`: a scripted planner that uses only Agent tools: it removes blocks that break a rule or come after the assessment, removes blocks their skill does not need, fills the smallest gaps first in the earliest free slots with the longest allowed blocks, and drops the furthest skill when not everything fits. For s2 it records every missed block of the week.
- `bound.cjs`: the optimistic bound used in s3's proof (no forgetting before or between sessions, full prerequisite credit, the least possible forgetting after the last session).

## Running a scenario

Infra: `env.load_seed` with the variant's `seed.json`, `binding.json`, `bundle: {dataset, catalog, blobs: {}}` and `virtual_now: load_at`; then each `setup` step in order (`env.apply_event` for an event, `env.advance_time` for `advance_to`). Give the Agent the request at `ask_at` with the `scenario` policy profile (s2 needs `sandbox`, which adds the practice tools). After the run, save `env.snapshot`'s `snapshot` and grade it:

```sh
node apps/milepost/examples/scenarios/grade.cjs snapshot.json s3-exam-moved base   # exit 0 = pass, 1 = fail
```

## What the tests check

`tests/scenarios.cjs` (App only) and the scenario tests in `tests/runtime.test.cjs` (real Core over MCP) check that:

- the bundles match `scenario.json` and the fixtures;
- each reference and valid alternative passes, and each control fails exactly the checks it names (no action, over-planning, rule-breaking, out-of-scope, spreading time thin, double counting reported practice, editing the plan when only the record was asked for);
- a twin differs from its base only in the declared practice history, and neither reference passes the other member;
- the twin proofs hold: in s1 and s4 a skill short without practice in the base reaches its target without practice in the twin; in s2 the base needs two new reports and the twin none, and the twin's sessions start after the planned times, so reports at the planned times are not refused there; in s3 the four skills short in the base are short in the twin, and even the optimistic bound needs 50 + 74 + 66 + 49 = 239 minutes for them, more than the 180 the rules leave before the exam;
- the scripted baseline passes 7 of the 8 members: it fails the s1 base by planning 450 minutes against a limit of 390.
