# Fernshelf delivery evidence

This directory holds the delivery evidence that the repository's [submission evidence contract](https://github.com/MatrAIx-ai/Personal-Agents-Last-Exam/blob/main/docs/submission-evidence.md) (merged after this App's plan was approved) asks of an Environment: GUI workflow sequences with a reference-product comparison, real dependency demonstrations, and a dataset coverage report. It was added to the approved package as recorded delivery work for that contract. It changes nothing the App does: no file under `src/`, `gui/`, `schemas/`, `fixtures/` or `assets/`, and not `tools.json`, `plugin.cjs` or `contribution/`, differs from the submitted revision `18ab392`. Everything below is synthetic and every file here is produced by a checked-in script.

## GUI workflow sequences

`node scripts/capture-workflows.cjs` (`npm run evidence:capture`) starts the shared Web Host on a fresh run, uses the page's real controls in Chromium, and after every step reads the record through a separate Agent MCP connection to the same run. Changes from outside (a rename and a restore through MCP, a join and a removal request through Infra `env.apply_event`) are made on separate connections while the page is open. It fails, and writes no complete report, if a step does not produce the expected state, if any frame's visible text shows a record ID, `null`, `undefined` or Agent wording, or if the browser reports a JavaScript error. It writes the PNG frames (recompressed losslessly with `zlib`; 57 frames, 2,994,820 bytes in all, 15 KB to 167 KB each, the four largest being whole-viewport frames), [`gui/sequences.json`](gui/sequences.json) and [`gui/SEQUENCES.md`](gui/SEQUENCES.md). It needs the repository's Playwright and Chromium, like `tests/web-browser.cjs`, and is not part of `npm test`.

Every frame was also looked at. The frames are reproducible in content, not in bytes: a rerun produces the same sequence and the same records, while pixels, wall-clock fields and a few versions can differ with timing.

Intentional differences, for every workflow:

- **Branding and data.** Fernshelf has its own name, mark and colours, and shows a fictional account with drawn stand-in images; nothing from either product is reused.
- **Scope cuts from the plan.** No face recognition, visual search or pixel duplicate detection (search is on captions here, with the other filters on the MCP tool); no uploads, editing of pixels, partner sharing, comments, memories or locked folder; one account and its own albums only.
- **Roles.** Fernshelf's roles are viewer and contributor (Immich: viewer and editor; Google: collaborators); other people act only through Infra events, so a join or a removal request appears after Refresh.
- **Removal requests (W4)** have no counterpart in either product; the page shows where each named photo is visible before the owner answers, and what was already seen and cannot be called back afterwards.
- **Delete of a shared album** needs "Also end access" ticked, where the products end sharing without that step; and an action drawn from an older view is refused as a conflict rather than applied.
- **Storage** counts declared sizes against a 15 GB plan, and only deleting for good frees space, as in R2 and R8.

## Dependency demonstrations

`node scripts/dependency-evidence.cjs` (`npm run evidence:dependencies`) runs both against the real pinned runtime and Mail package, each in disposable copies, and writes a transcript of every request and result:

- [`dependencies/mail.json`](dependencies/mail.json): revisions and the exact contract (both wire-schema hashes equal), account binding (Fernshelf `fernshelf-maya` and Mail `mail-maya`, both owned by `person-maya`; the router grant), initial states; Dana's removal request committed in Fernshelf as a notification with its stored wire message (**local commit**); `router.publish` with its request ID, CloudEvents source and ID, and the committed receipt naming `mail-maya` and the Mail event ID (**receiver delivery and commit**); inside Mail, `mail.get` of the record whose ID is that event ID (inbox, subject and body equal to the notification, `read: false`), Mail's `env.event_status` receipt and its version, and Fernshelf's state hash and version unchanged by the dispatch. Failure paths, each with both Apps' states before and after: an identical retry and a re-run under a new request ID (same Mail event, one inbox record); a lost acknowledgement, injected by dropping the answer of the router's real call to Mail (the result is `unknown` with the event ID and no commit time, Mail's own receipt shows the commit, the run halts and refuses further publishing, Fernshelf unchanged); no Infra grant (`recipient_not_authorized`, nothing in Mail); a run without Mail (`recipient_unavailable`, Fernshelf unchanged and usable); a Mail copy whose receive schema differs (`incompatible_contract`, neither App changes); email notices off (nothing to publish). **Recipient or business confirmation** is not established: nothing reads, answers or acknowledges the Mail record, and a delivery receipt proves only that Mail stored it.
- [`dependencies/resource-access.json`](dependencies/resource-access.json): the registration file and its hash, the source file (asset ID, catalogue SHA-256, bytes on disk), `fernshelf.items.read` returning bytes whose SHA-256 equals both, version and business data unchanged, the same bytes again and through Core `resources/read`; refusals for another item's asset (`not_found`), a trashed item (`in_trash`, and `resources/read` refused), a video (`no_file`), a task policy limiting `fernshelf.items.get` to another item (`not_available`); and, on runtime copies, the registration removed or mapping another object type (`items.read` `not_available`, other reads unchanged).

The existing `scripts/mail-flow.cjs` and `scripts/real-mcp.cjs` remain the package's pass/fail checks for these paths; the demonstrations add the transcripts and the unknown-outcome, missing-Mail and incompatible-contract cases.

## Dataset coverage

`node scripts/coverage-report.cjs` writes [`coverage/report.md`](coverage/report.md) and [`coverage/report.json`](coverage/report.json) from the fixture the App loads, in `America/Los_Angeles`, with one authoritative date field per record family, per-month and per-source counts, the global distinct-date count, provenance, exclusions, the scheduled due times after the clock and the file hashes. `--check` (also run by `npm test` through `tests/coverage.test.cjs`) fails if the committed report differs from the fixture; the output is byte-identical on Node 18 and 22. `--query` loads the fixture into a fresh run of the public runtime and reads each counted family back through the App's tools ([`coverage/query.json`](coverage/query.json)); the activity log, which has no Agent read, is read through Infra `env.snapshot`.

## Not provided

- Reference screenshots are referenced by URL, not copied (licences above); no capture of either product was made.
- No reference exists for W4 in either product.
- Recipient confirmation of a Mail notice: no flow in the plan has one.
- The Mail flow cannot be started from the page, and the page has no Mail view.
- History after the fixture clock: December 2026 has scheduled due times only; this is reported as a gap, not filled.
- A per-record provenance tag: the fixture does not store one; provenance is given per record family and source.
- The capture script and the browser test are not run in CI (the repository's browser job covers other Apps); their results here are local.
