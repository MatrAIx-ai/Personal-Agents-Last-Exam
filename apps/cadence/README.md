# Cadence class booking App

Self-contained PALE App package, version 1.0.0, Core API 1.2.0, built for environment proposal #15 (`proposals/environment/class-booking.md`). One synthetic member (Amara Bello) checks her plan and trial rules, searches classes priced under her plan, books, cancels, reschedules, checks in, rates and waitlists classes without overlapping her own reservations, and reads studio pages. Studio cancellations and schedule changes, waitlist promotions, plan renewals, trial reminders and session expiry arrive as events on the platform's virtual clock. No real studios, members or payments; everything is generated by `scripts/generate-fixture.cjs`, including the studio images.

## Run locally

Requires Node.js 18 or newer. No package install, account or remote service is needed (from the repository root):

```sh
node --test apps/cadence/tests/business.test.cjs                 # 16 App-only business tests
node apps/cadence/examples/run.cjs                              # event example on the App-only harness
npm run app:verify -- --app apps/cadence --with examples/apps/mail --output .artifacts/cadence.json
node apps/cadence/examples/mail-notice.cjs evidence/mail-notice-trace.json   # real MCP: Cadence -> Messaging -> Mail, Calendar, rejected delivery, replay
node apps/cadence/scripts/coverage-report.cjs                   # data coverage over 2025-01-01 .. 2026-12-31
node apps/cadence/evidence/capture.cjs                          # GUI screenshot sequences with MCP state checks (Chrome, Node 22+)
node runtime/web/server.cjs --app cadence --registry apps/cadence/registry.json --run web-demo --profile sandbox
```

`registry.json` inside the package registers only this App; the shared `apps.registry.json` is a platform file that maintainers extend at acceptance. With only this App folder, run `node --test tests/business.test.cjs` and `node examples/run.cjs` from inside it. `service.cjs` uses the public runtime or `PALE_RUNTIME_ROOT`; it embeds no server.

## Operations

Twenty-four agent operations in `tools.json`, ten reads and fourteen writes, each named `cadence.<area>.<verb>` (the proposal wrote them as `<area>.<verb>`; the platform requires the App ID as the first segment). The twenty-three proposed operations are all present; `studios.image` is the one addition, the read tool that the platform's resource registration (`runtime/registrations/cadence.json`, object type `studio`) needs so an agent can fetch a studio's image bytes. Every view object a read returns carries `id`, the value the matching operation's `id` argument expects, next to its typed key (`class_instance_id`, `reservation_id`, ...). Every write takes Core's `expected_version` and `request_id`; a repeated `request_id` returns the stored receipt and a stale version is rejected before the handler runs. Core owns the `status` of every result, so an operation's own result is reported in `outcome`.

Business errors arrive as the result `status` with a plain-language `message` that carries the figures the proposal promises: `class_full` (points to `waitlist.join`), `overlap` (names the conflicting reservation and its times), `not_included` (with the reason: premium excluded, repeat visit, plan cancelled), `insufficient_credits`, `outside_horizon`, `preview_stale` (with the current price, spots and a waitlist hint), `late_cancellation`, `payment_declined`, `price_changed`, `checkin_window`, `not_attended`, `too_early`, `already_rated`, `not_full`, `offer_expired`, `change_pending`, `same_plan`, `unknown_plan`, `signed_out`, `approval_required`, `not_found`, `invalid_state`.

Prices under the plan are computed at read time, never stored on the class: a trial includes the first visit at each studio in the current period and excludes premium classes; a credit plan pays the class's credit cost (premium classes cost more). Booking, late cancellation and plan changes are two steps: `reservations.preview`, `reservations.cancel_preview` and `plan.preview` store a preview with an expiry (`settings.preview_ttl_minutes`) and a fingerprint of what they looked at; the matching confirm checks that the preview is live and that nothing it depends on changed, otherwise `preview_stale`. A cancellation inside the free window (`settings.late_cancel_hours` before the class) needs no preview; after it, the call must name a live cancel preview, forfeits the credits spent or charges `settings.late_cancel_fee_cents` for an included class, and records a receipt. With the fixture flag `settings.require_user_confirmation` on, every gated write (`reservations.confirm`, a late `reservations.cancel`, `waitlist.accept` when credits are charged, `plan.change`, `plan.cancel`) also waits for a `user.confirmed` event naming the preview or offer. The App keeps no clock of its own: windows, horizons, offer expiry and "attended" are evaluated when an operation runs, from `ctx.virtual_now`.

## State and time

`fixtures/minimal.json` is initial history, `fixtures/binding.json` binds the person and account, `fixtures/policies.json` grants the `scenario` profile every operation except the two plan money writes (`plan.change`, `plan.cancel`) and the `sandbox` profile everything, and `fixtures/clock.json` sets the clock to 2026-12-06 18:00 Eastern. Twenty fictional studios with two instructors each run two weeks of classes from December 7, 2026 (one class per room and start time); the member's history is an 8 Credits membership from January 2025 to July 2026 with attended classes and monthly receipts, then a win-back trial from December 6, 2026 with three included bookings (Monday at Ironworks Strength, Tuesday at Still Point Yoga, Thursday's Strength 60 at Granite Barbell) and one waitlist place on a full Saturday class. `validateSeed` rejects a class without a valid time range or in a room its studio does not have, a reservation on an unknown class, bookings above capacity, two scheduled classes overlapping in one room, a rating without reviews, mismatched trial status, broken history timelines and duplicate IDs across every collection.

Nine events in `schemas/events.schema.json` are applied by Infra through `env.apply_event`; the handler reads the event's `at` as now. `examples/scenario.json` is the single capacity change the public verifier applies; `examples/schedule.json` is the eight-event schedule from the proposal table (session expiry and restore, the Strength 60 schedule change, capacity change and studio cancellation, the waitlist promotion, the trial reminder and the renewal into 8 Credits) that `examples/run.cjs` applies after it. A promotion holds the spot that opened for the offered entry; a capacity below current bookings is rejected with `capacity_below_bookings` and changes nothing; previews on a changed class go stale through their fingerprint rather than disappearing. Nothing happens when `env.advance_time` moves the clock. Reset restores the seed and clears previews and offers because they live in business data.

## Documents and attachments

Studio images are script-drawn PNG marks (160 by 100 pixels, about 8 KiB in total for 18 studios; two studios have none and show a placeholder), listed in `contribution/assets.catalog.json` and read through `cadence.studios.image` by studio ID under the platform registration `runtime/registrations/cadence.json`. The App stores no other media; nothing is attached to reservations.

## Integration and review

`contribution/contribution.json` declares the operations, the nine accepted events and one send-only messaging direction: `channel.email`, wire `urn:pale:email-message:2` (`schemas/router-message.schema.json`, a byte-identical copy of Mail's), payload `urn:pale:email-payload:1`, event type `org.pale.mail.notification.v1`. The six notice kinds (booking confirmation, studio cancellation, schedule change, waitlist offer, trial-ending reminder, renewal receipt) are built in `src/notices.cjs` from the public tool views only. `src/publisher.cjs` is the host-run publisher: after Cadence's own commit, Infra runs it with a trusted Agent connection and a trusted publishing connection (`runtime/messaging/service.cjs --config apps/cadence/examples/router.json --publisher cadence`); it reads the committed record, builds the CloudEvents envelope and calls `router.publish`. The receipt returns to that caller; Cadence never observes delivery and stores no notice status (the proposal's `notice_status: rejected` on the reservation is therefore not recorded; the connected example shows the rejected delivery by comparing snapshots instead, as agreed in design review). `examples/mail-notice.cjs` runs the declared flow over real MCP processes: the studio cancellation, the notice committed in the real Mail 1.3.0 App, the agent cancelling the Calendar entry with `calendar.cancel`, booking a replacement with `reservations.confirm` and creating its Calendar entry with `calendar.create`, a delivery without a recipient grant rejected as `recipient_not_authorized` with Mail and Cadence unchanged, and a replay deduplicated on the receipt. Calendar is reached only by the agent's own tools; Cadence checks overlaps only among its own reservations. `app.json.dependencies` is empty: the package runs with the shared runtime alone.

## Interactive business Web App

See [GUI startup and boundaries](gui/README.md). From the repository root run `node runtime/web/server.cjs --app cadence --registry apps/cadence/registry.json --run web-demo --profile sandbox`. The App owns its pages in `gui/src/app.js`; the shared Host exposes only the fixed Agent connection and allows no inline styles, so the App's presentation rules are a constructed stylesheet in the controller. Pages in this version: class search (every class priced under the plan, with the included-only filter), class (studio, instructor, price, spots, two-step booking, waitlist), reservations (upcoming and past, cancel inside the window or late-cancel after a fee preview, check in, rate), waitlist (accept, decline, leave) and plan (rules, credits, trial end, payment method, two-step plan change or cancellation). Deep links travel in the URL fragment next to the Host's access token: `/#page=reservations&reservation=<id>`, `/#page=plan`, `/#page=waitlist`; the notices' `deep_link` fields use the same route IDs. Studio and account pages, reschedule in the pages and the rating prompt after class are remaining work for the next milestone.
