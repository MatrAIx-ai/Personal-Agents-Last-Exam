# Subscription Exit
A standalone fictional subscription environment in PALE #20. Original app code and synthetic fixtures: MIT, Xiao Cui (@2018cx). Shared PALE Runtime 1.6.0 / Core API 1.2.0; no other App, third-party package, live account, payment, or media is needed. The Spotify support workflow in the proposal is only a design reference; the synthetic behavior is not Spotify policy.

The shared Web Host connects the three browser views to the same seven Agent MCP tools. All state is persisted by PALE Core. Reads: `read_plan`, `read_status`, `read_receipt`. Writes: `prepare_cancellation`, `prepare_revocation`, `confirm`, `abandon`. Writes require the most recent Core version and a stable request ID. An identical confirmation request returns the original result and receipt without a second mutation. To retrieve a receipt in a new call, use `read_receipt`. A second new confirmation request on the same preview is rejected with its original receipt ID.

Use only Infra `env.load_seed`, `env.reset`, `env.advance_time`. No scheduled process or event is necessary: status derives the modeled billing boundaries from Core virtual time, with the transition taking precedence at exact equality. Pending cancellation becomes free at the boundary; otherwise, the plan remains paid and its period moves to the single next predeclared period, with no charge. The renewed period accepts a fresh cancellation preview and confirmation before its end; a pending renewed-period cancellation takes effect at that end. If the clock skips both dates without cancellation, only the first renewal is projected and no further entitlement write is accepted. Older previews are invalid at their own boundary; no additional renewal is inferred. Reads and rejected old previews never change business data or revision. The saved entries remain intact.

The default seed is active and writable. Infra can load the pending or free fixture (set the Free fixture clock to 2026-02-01T00:00:00Z or later), or map the read-only policy to its scenario. The same schema also accepts task-supplied dates, status and saved entries; a different account ID requires a matching trusted binding. The browser uses the session-bound account. Agent calls can omit the account ID or explicitly supply the matching ID. The default historical data begins 2025-01-01; task clock starts 2026-01-15. All dates are UTC in App records. Browser labels include the simulated UTC date. For arbitrary dates in the evaluation window, use the [clock-cutoff and matching bundle helper](evaluation/COVERAGE.md). Scope excludes resubscription, mailbox, payments, streaming and cross-App workflows.

For verification, see [VALIDATION.md](VALIDATION.md) and the [workflow/evidence index](evidence/README.md). For the separately loadable six-account evaluation history and reproducible UTC counts, see [evaluation/COVERAGE.md](evaluation/COVERAGE.md). The App uses the official PALE launcher and shared schemas; the reused notices are retained. The transport setup in the browser test is adapted from PALE Refund-only Returns (#7), under MIT.

### Timeline and confirmations
The read-only history list comes from the loaded seed. Live confirmations persist a separate receipt in Core and update entitlement, but do not append to seed history. The exact access-end boundary is computed by Core from virtual time; it does not append a second receipt or mutate the historical seed. For the outcome of a live decision, use the current entitlement and its confirmation receipt.
