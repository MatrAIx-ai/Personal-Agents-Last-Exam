# Larkfield Web App

`index.html` and `src/app.js` own Larkfield's member-facing business interface: the household and its access grants, claims with their lines, the plan's questions and every explanation of benefits (EOB) version, the two attestations, prior authorizations (PAs) with expedited review, appeals (file, add a statement, withdraw) and the plan's amounts used. The shared public `runtime/web/client.js` provides the session, tool discovery, text-only rendering and the shell; `runtime/web/server.cjs` serves this page and forwards only the Agent tools the current policy allows. `src/view.js` remains the compatible reviewer renderer.

From the repository root:

```sh
node runtime/web/server.cjs --app larkfield-health --run web-demo --profile sandbox
```

Open the access link printed by the Host. A new run starts from the fixture at the shared registry's start instant (Wednesday 18 November 2026, 12:00 in New York), with Jordan Hale (m-1) as the account holder; starting against existing state never resets it or changes its policy. Claims, PA requests and decisions, appeal decisions and grants given by others arrive as Infra events sent through a separate Infra MCP process; press Refresh to see them. The page has no route for them.

## Approvals

The five confirmed changes (giving, changing or removing access; the other-coverage answer; an accident answer; filing an appeal; withdrawing one) need the account holder's approval, which comes from Infra as a `user.confirmed` event, never from the page. A preview shows what the change will do, its approval code, who must approve it and that an approval can be used once, for 30 minutes after it is given. To approve a code in a local run, from the repository root (same run and state directory as the Host):

```sh
node apps/larkfield-health/dev/confirm.cjs web-demo <approval code>
```

(`--state-dir DIR` and `--registry FILE` select the Host's state directory and registry, `--by PERSON` names a different confirming person and `--at TIME` the event time. The helper refuses a code that Larkfield's own parser does not accept or whose action does not fit its subject, unknown options, an option without a value or given twice, and a run that has no state in that directory, so a mistyped code or run name confirms nothing and creates nothing.) A scenario event or a user simulator does the same in a Task. Then press Refresh: the preview shows the approval and until when it can be used. Confirm can be pressed at any time: without an approval Larkfield answers that it needs one, and the page keeps the change waiting instead of reporting an error; an expired or already used approval, or one given by someone other than the account holder, is refused and shown in plain words, with no success message.

Confirm first previews the same request again. If the approval code or what the change will do differs (for example a second other-coverage question opened after the approval, which the same answer would also cover), the page shows the new effects and sends nothing until Confirm is pressed again; if Larkfield was reset or loaded with new data, at any point before the send, it asks for a fresh preview and sends nothing. Otherwise it sends the previewed arguments and code with the version read in that same preview and a new request ID, so a change made by anyone else after it is refused as `stale_version`. A preview belongs to the question, appeal or grant it was made for and to the record shown when it was made: a preview whose answer arrives after its form changed, or after another record was selected, is discarded and cannot enable Confirm; selecting another record, or a member filter that hides the selected one, drops the previews made on the record left (an other-coverage preview made on a claim included); changing a form or the selection while Confirm is checking stops the send; and an accident answer is sent only if Larkfield's preview names the same question. The panel also says that in this local preview no code is sent to anyone, and that after a reload the same change previewed again gets the same code. After a reload the page lists the approvals it no longer tracks; previewing the same request with the same details reproduces the code and shows it approved, while a changed detail gets a new code that waits again.

## What the page does

- **Claims.** Waiting for answers, in review and processed, for every member the account holder may see, with a member filter and the shared search box (claim, provider, member or service). A claim shows its provider and network status, receipt and review times, its lines (service, service date, units, billed amount, emergency and accident flags, current outcome), the plan's questions with their deadlines and answers, every EOB version (the newest open) with each line's allowed amount, copay, deductible, coinsurance, member cost, plan payment, amount not allowed and PA units, and its appeal window and appeals. An open accident question is answered on its line; open other-coverage questions are answered once for the member and plan year, and the preview lists every question the answer covers and the claims it completes. A processed claim with a denied line offers an appeal unless an appeal on it is open or decided, or its window certainly ended (its end is earlier than a record Larkfield has shown); otherwise Larkfield decides at preview or at Confirm's check, and when it answers that the window has ended the page shows the window as closed. When no appeal can be filed, the claim says why. Larkfield offers no read of its clock, so the page cannot tell by itself that a window has just ended: it shows the window's end as “until …” and lets Larkfield's preview decide. Amounts not allowed are explained, and a newer explanation of benefits says which lines changed.
- **Prior authorizations.** Open and decided, with the requested and approved units and dates (an approval ends at 11:59 PM on its last day), units used, the decision due (and since when it is overdue), the plan's requests for information, the expedited review record, requests covered by an approval and appeals. Ask for expedited review takes an optional reason while the request is undecided and has no expedite record; otherwise the page says when it can be asked for. A denied PA offers an appeal, standard or expedited; an expedited appeal needs the urgency attestation, and the preview shows the decision due if filed now.
- **Appeals.** Open and closed, with the target, the lines appealed, filing time, decision due and overdue mark, the statements, the plan's requests for information, the decision and its outcome. An open appeal takes a statement (one that answers the plan's request returns it to review) and can be withdrawn; a withdrawn target can be appealed again until the original window ends.
- **Plan & costs.** Each plan year's deductibles, out-of-pocket maximums, coinsurance, copays, network rule and the services that need a PA; per member, the deductible and out-of-pocket amounts used and the other-coverage answer. Family totals appear only when the account holder may see every member enrolled that year; otherwise the page says that another enrolled member is not visible. An unanswered other-coverage question says that Larkfield asks it when a claim of that year needs it.
- **Household.** The members the account holder may see (themself, children they are a guardian of, and anyone who has given them access) with their powers; the access grants on each member's records with their state, Change (scope and end) and Remove access on active grants the account holder controls; Give access to the account holder's or a child's records, for view or act, optionally ending at a date and time entered in Eastern Time (an empty time means the end of that day, 11:59 PM; a time skipped when clocks go forward is refused in the form). The person list starts empty and leaves out the account holder for records they already control. Change starts with the grant's scope and its end date and time in Eastern Time; changing only the scope keeps the stored end exactly, and a changed date or time is stored as entered. An end that is not later than Larkfield's current time, or a change to the access and end a grant already has, is refused by Larkfield and the form says which, with nothing changed.

All times are shown in America/New_York with the zone named, whatever the browser's zone; nothing from the App is rendered as HTML. Records are named in words (provider, service, dates); their IDs appear only as small references, and a person the account holder cannot see is shown as another person with a reference. Every App error is explained in plain words. Larkfield's notices go to Mail (see the package README); no Agent tool reads the notice log, so the page shows none.

Opening a form or a preview moves keyboard focus into it, and closing or cancelling returns focus to the control that opened it; selecting a record moves focus to its heading and, on a phone, scrolls it into view. The sidebar names the signed-in account holder and stays in view on a wide screen. Filtering a list by member clears a selected record of another member. Appeal outcomes are written out (upheld: the denial stands; overturned: the plan reversed its denial). List groups are headings and answer choices are labelled groups. Below 760 px wide, every button, field and choice is at least 44 px tall and the lists are not boxed in their own scroll area.

## Refresh and writes

A refresh reads every view the policy allows (a policy without the plan read leaves only the plan section unavailable) and keeps them only if all reads saw the same Core version (epoch and revision); a refused detail read also discards the whole read, which is then repeated, up to three times. Every successful read the page receives, including the shell's own member read at the start of each refresh, is applied at once, before the rest of the refresh, unless it is older than what the page already holds (each answer carries the Core version it was answered at, and an older answer, such as one from a refresh overtaken by a newer one, changes nothing; an answer from new data loaded since the page's last full read still removes at once what that data no longer shows, but its approvals are not compared with those of the earlier data): a member missing from the member list loses all their records, a record or a member's amounts missing from a newer read are hidden, and an approval missing from a newer read, a plan year's member rows included, is removed (if that means the account holder can no longer act on that member, the forms and previews that need it close). Whenever a read shows that the account holder can no longer see a member (the member list no longer includes them, or a read is refused as `not_authorized`), the page removes at once that member's records, their open previews, approval controls, drafts and messages, and every family total that depended on them, even when the rest of the refresh then fails; they stay hidden until a refresh succeeds that shows them again. When the member list shows reduced access (act to view), the forms and previews that need the removed power close at once in the same way, and the approvals given for them are no longer shown. Notices about a member or one of their records are removed when access to that member ends. A selected record that Larkfield no longer has (`not_found`, for example after new data was loaded) is removed the same way, and a change form whose access grant was changed by someone else closes with a note. Every answer from Larkfield carries its run state (epoch); as soon as any answer shows that Larkfield was reset or loaded with new data, every form, draft and preview made before is closed and nothing from them is sent, a preview answered in the newer run is not kept, and writes wait until a refresh shows the newer run. The page keeps no business state in browser storage (the shell remembers only the open section), so after a reload everything is read again from Larkfield.

Each write carries the Core version read at the last refresh (a confirm, the version of its own preview) and a new request ID. If the connection drops, or the Host answers with an error that carries no App status and is not one of its own refusals (for example a timeout), the page shows a “Waiting for Larkfield” banner holding that exact request: Retry first checks that Larkfield is still in the same run (after a reset it says the outcome cannot be confirmed and sends nothing), then sends the request again unchanged, so it takes effect at most once, and says whether it had already gone through or was not applied; an answer that carries another run's state is reported as cannot be confirmed and never applied; Dismiss drops it. If the request concerned records the account holder can no longer see or act on, the banner stops describing it and offers no Retry, and the answer to a Retry about such records never names them: Retry reads the member list first, so a stored receipt is reported as “an earlier request … was confirmed” and a refusal without the record's name, even when the refresh after it fails. A statement whose reply was lost keeps its text: the page never decides from the appeal alone whether it was stored. When a statement with that text appeared after it was sent, the form says it was probably stored; either way it warns that sending it again may add it twice (its button reads “Send it again anyway”), and Retry's answer settles it: a stored receipt clears the form, and an answer that it was not applied keeps the text without the warning. A preview that cannot reach Larkfield is a read failure: the page says nothing was changed. A refresh that cannot reach Larkfield says so and asks for another Refresh, or, while a change's outcome is still unknown, says that its outcome cannot be confirmed. Until it is settled, other changes wait. The Host's own refusals (policy, session, origin or request checks) are plain errors: nothing was sent and nothing is pending. If the refresh after a change fails, the page says the change was saved and refuses further changes, with nothing sent, until Refresh succeeds. Refusals are shown where they happen and stay on the page through refreshes and resets until the next action or Dismiss, and the status line follows a Dismiss; while one is shown, or a Retry is outstanding, the status line says so; otherwise it says “Up to date” after a read and “Saved” only after a change was committed (never “All changes saved”). Controls for tools the current policy does not allow are not shown, views whose reads it does not allow say so, and a forced call is refused by the Host.

## Why the page draws its own views

Larkfield's reads take `claim_id`, `pa_id` and `appeal_id` rather than `id`, the plan is read per year, and its confirmed changes need a preview, an outside approval and a second request, which the shared generic forms do not express. The controller therefore draws its own views through the configuration that `runtime/web/client.js` `mount` accepts and the other Apps use: the list call is `larkfield-health.members.list` with no records (so nothing is auto-selected), `load` fetches the views, `renderList` and `emptyView` draw them, and reads, previews and writes go through `ui.call`. It reads the shared toolbar's search box as the record search and hides the shell's record-count badge, which would always read 0. Styling uses the shared classes plus element styles, as the Host's content security policy allows; the shared Host, client and stylesheet are unchanged.

```sh
node apps/larkfield-health/tests/web.browser.cjs
```
