# Larkfield Health Plan

A synthetic, resettable member portal for one employer health plan (EPO), for PALE. A household reads claims and explanations of benefits (EOBs), answers the plan's information requests, follows prior authorizations (PAs), and files, supports or withdraws appeals within their deadlines. The App records facts, statuses, amounts and consequences; it does not decide medical necessity, rank options or say what the right action is. It implements the approved environment proposal [`proposals/environment/larkfield-health.md` at `c0f566a`](https://github.com/MatrAIx-ai/Personal-Agents-Last-Exam/blob/c0f566a3c5be418cd0c971d58e4144cb8085d25a/proposals/environment/larkfield-health.md) (PR #64). Agents use the MCP tools; people and agents can also use the member-facing business GUI on the shared Web Host ([`gui/`](gui/README.md)); Infra drives the plan's and providers' events and the account holder's approvals.

This README is completed with the delivered version, 1.0.0. All 21 tools, all 11 events and all six timers (claim review, request expiry, PA validity end and decision due, appeal decision due, window closing) are built and tested; so are the real-MCP checks, the optional Mail delivery (see Infra), the representative fixture with its generated history (see Fixture) and the member-facing GUI with its browser acceptance (see [`gui/README.md`](gui/README.md)); the delivery evidence is indexed in [`evidence/README.md`](evidence/README.md), and the validation report is [`docs/validation/larkfield-health-v1.0.0.md`](../../docs/validation/larkfield-health-v1.0.0.md). Every call first applies the timers due at its time.

## Run

```sh
npm test            # tests/business.test.cjs, tests/t31-fixture-checks.test.cjs and tests/t32-dataset.test.cjs
npm run example
npm run app:verify -- --app apps/larkfield-health   # from the repository root
node runtime/web/server.cjs --app larkfield-health --run web-demo --profile sandbox   # business GUI from the repository root; open the printed link
```

The browser acceptance needs the repository's pinned Playwright: from the repository root, `npm ci`, `npx playwright install chromium`, then `node apps/larkfield-health/tests/web.browser.cjs`. It writes `report.json` and screenshots to a new folder per run under `.artifacts/web/larkfield-health/` (or to `PALE_WEB_REPORT_DIR`); its generic part, `tests/web/harness.cjs`, starts the shared Host and an Infra inspector on a fresh run. CI's shared browser job (`npm run test:web:browser`) is fixed to the seven personal Apps and does not run this file. The GUI runs on the shared loopback Web Host; Refresh re-reads the App, there is no push, and approvals come from Infra (`dev/confirm.cjs` in a local run).

## Task rules

- Clock range. New claims and PAs (`claim.received`, `pa.submitted`) are accepted until 2199-12-31; every other event and every tool works until 2200-12-31, so work accepted at the end of 2199 can still be read, answered, decided and appealed. A deadline the App would set after 2200-12-31 cannot be reached: a Task should not schedule work there.
- PA choice. A claim line uses the approved PA of its member and service whose validity contains the service date and whose remaining units cover the line, with the earliest `valid_until`, then the lower PA ID as a string (`pa-10` before `pa-9`); lines are priced in service-date order, then by position.
- Same-instant order. Due timers run before any action at the same instant, in object-ID string order (`cl-10` before `cl-9`); one confirm posts every claim it completes together, in received order.
- Shared numbering. Run-issued IDs (`ir-`, `eob-`, `ap-`, `gr-`, `cf-`, `n-`) are numbered across the whole household, so their numbers reflect activity on members the caller may not see, as `not_authorized` already does.

## Delivery dataset

The evaluation dataset for the Environment window, 2025-01-01 to 2026-12-31 inclusive in `America/New_York`, is in [`dataset/`](dataset/).

### Relation to the fixture, and what is real

- The smoke fixture (`fixtures/minimal.json`) and the delivery dataset share the household, the plan, the providers and the services (equal at the fixture clock, checked by `tests/t32-dataset.test.cjs`) but have independent histories: the fixture serves the business tests, the examples and the proposal's example events; the dataset serves evaluation, and Tasks select their history from it with `dataset/as-of.cjs`.
- The dataset's records use the App's own runtime ID series (`cl-1`, `pa-1`, `ap-1`, `gr-1`, `n-1`, …), so their IDs overlap the fixture's task timeline but name different records: the fixture's `cl-7`, `pa-4`, `gr-2` and the other IDs named by the proposal's example events are not the dataset's.
- Every record is synthetic, including those dated after the fixture clock. There is no real health-plan record to anchor November 2026 or any other month: claims, EOBs, prior authorizations and appeals are a real member's protected health information, the reference product shows them only in a signed-in member account, and the approved proposal (PR #64, at its approved revision [`c0f566a`](https://github.com/MatrAIx-ai/Personal-Agents-Last-Exam/blob/c0f566a3c5be418cd0c971d58e4144cb8085d25a/proposals/environment/larkfield-health.md), lines 6, 103 and 104) describes a synthetic plan with the reference site as a workflow reference only, excludes data collection and calls for no real member data.
- No code set is used: the services keep the fixture's plain descriptions, with no procedure, diagnosis, drug or provider codes.
- The only real public facts are the U.S. federal holidays of 2025 and 2026 as observed, with December 24, which set the business days of the providers and the plan, and the `America/New_York` daylight-saving rules; neither is stored as a record.
- The coverage report states as gaps the missing real data (pending maintainer agreement), the absence of Mail history for the dataset's notices and the semaglutide authorizations that are never used (see Care and episodes).

### How the generator works

- [`dataset/generate.cjs`](dataset/generate.cjs) replays the App's own tools as the household member who makes each request, with that person bound as the account holder, and its events as Infra, with a fixed seed, validating every state against the seed schema and `validateSeed`.
- Jordan acts for himself and for Riley as a guardian, and for Casey only while she gives him an act grant; Casey acts for herself, for Riley and, under the act grant Jordan gives her on 2025-01-01 and extends in December 2025, for Jordan; Riley, a minor, never acts.
- Every draw comes from a stream of its own, keyed by the encounter, PA or appeal it decides, so a branch in one episode does not change the draws of another; either branch of the expedited surgery appeal generates every required kind of record, which the tests check by generating both.
- The generator stops on any step that would not change the state, such as a decision on a PA that has already closed, and when any kind of record, outcome, event or write tool is missing from the window.
- A step that needs the person's confirmation is replayed as preview, `user.confirmed` and confirm at one instant, and the used approval is not kept, because seeds carry none.

### Care and episodes

- Routine care comes from seeded draws for each person and month: sick visits, more in winter and fewer for Riley in summer, nurse phone consultations, specialist visits, joint pain with an X-ray, ordered imaging, of which one in five is done at the out-of-network imaging center, and injuries whose cause is drawn per person.
- Scheduled care: a yearly physical for each adult and a checkup for Riley, Jordan's visits every 12 to 14 weeks and a yearly lab visit for Casey.
- Riley's ankle (2025) and knee (2026) physical therapy, and Jordan's work injury and his back therapy.
- Casey's scheduled ultrasound at the out-of-network imaging center, and her semaglutide prior authorization, renewed every six months.
- Casey's knee: an MRI, a surgery request the surgeon withdraws for therapy first, the knee locking, an expedited surgery request and an expedited appeal, which the plan overturns with a seeded chance and otherwise upholds until the surgeon asks again after more therapy, the surgery and therapy after it, one session of which reaches her out-of-pocket maximum, and her act grant to Jordan for the recovery.
- The emergency at the out-of-network hospital on 2025-12-31 during the winter trip, posting to both plan years.
- Riley's emergency on the 2026 summer trip, billed without the emergency flag and then corrected by a claim whose replay step names the claim it corrects (`corrects`; a claim is corrected at most once).
- Therapy runs two sessions a week from a few days after the approval; a missed session is made up later, so one session can fall after the authorization ends and be denied (the course stops there), and the household appeals it when it was a moved session; the clinic sometimes sends a request that the approval already covers.
- Casey's semaglutide authorizations (`pa-3`, `pa-7` and `pa-11`) are each approved for 6 units and end with 0 units used, and no claim line bills the medicine: it is a pharmacy item and the catalogue has no pharmacy among its providers, so the authorization is never used in this App. Each request follows a visit at the family practice, which bills the visit; the dataset invents no pharmacy claims, and the coverage report lists this as a gap.

### Calendar

- Visits fall on business days unless they are emergencies, and each member keeps one calendar across routine care and the episodes: no two visits at one provider on one day, at least four days between two office visits, at most one sick visit and two office visits in a month, apart from injuries.
- Injuries are kept apart: a routine injury never falls within two weeks of an episode's injury, two injuries of one member are more than 14 days apart, two routine injuries of one member more than 30 days apart, and a member has at most one routine injury a quarter.
- Each original claim is billed 2 to 11 business days after its last service, at the provider's office hours, and the corrected claim for Riley's summer-trip emergency arrives 8 business days after the appeal it answers.
- The plan's information requests and decisions fall in its business hours, Monday to Friday from 09:00 to 17:00, never on U.S. federal holidays or December 24, and the providers' submissions, documents and withdrawals in theirs, from 08:00.

### Labels on the replay, and the generator's check

- Each claim's replay step names its kind of visit in `visit` (such as `sick`, `strep`, `physical`, `labs`, `work-up`, `follow-up`, `injury` or `therapy`).
- An injury claim's step names its episode in `episode`: a routine injury's `injury:<member>:<date>` names its member and day, a story's is one of the five episodes above, each bound to its member and opened by one injury visit.
- A therapy claim's step and a therapy request's step name the course in `course`.
- The generator's check reads these labels from the replay and holds every claim to them, in any line order: the kind fits the services billed and the kind of its provider, and every service its provider's kind (an arthroscopy only at a hospital, an office visit only at the family practice).
- An episode's claims fall within 30 days of its first visit, and the calendar limits above hold.
- Each adult has one physical a year and Riley one checkup, Casey one lab visit a year, and Jordan's visits are 12 to 14 weeks apart from within 14 weeks of the window's start to within 14 weeks of its end.
- Each of Casey's semaglutide requests has a visit of its own 1 to 10 days before it (the work-up before the first, a follow-up before each renewal), and every work-up and follow-up has its request.
- A course has at most one session outside its own authorizations (the PAs whose request names the course), its last, after one ends, counting a corrected session once.

### Household answers, appeals and the plan's workload

- The household answers the plan's questions at its own hours (Jordan in the evening and at weekends, Casey at lunch, in the evening and at weekends) with a delay drawn per person, an occasional late answer, and a chance per question set to leave it unanswered until it expires (other-coverage questions 0.1 for Jordan and 0.06 for Casey, accident questions 0.22 and 0.13, higher on trips and during Casey's recovery).
- Riley's other coverage for 2026 is a school accident plan, answered as secondary.
- A denial is appealed with a chance that depends on its reason and a delay drawn per person; a work injury denied as another party's is not appealed, and its window sends its closing notice.
- The plan asks for documents on some appeals and PAs and decides with seeded outcomes, except that an appeal which supplies a missing answer is overturned.
- Each busy period of the plan (the plan-year surge, January 2 to March 15, the summer staffing period, June 15 to August 31, and the holiday backlog, November 20 to December 31) has a heavy or light backlog by a seeded draw per period (in this dataset all are heavy but the 2026 plan-year surge, as the coverage report lists).
- A decision planned in a busy period slips past its due date with chance 0.6 when heavy and 0.1 when light (0.03 outside those periods; half of these for PA decisions).
- A decision that waits for requested documents follows them by some business days, so a late reply can make it overdue; an expedite request is decided within a few business hours, and an approved expedite's decision follows the same way.

### Generated texts

- The free texts the generator supplies are parsed and checked against the records they name ([`dataset/notes.cjs`](dataset/notes.cjs)).
- An appeal statement names the service and date of every line it appeals and the provider, in one of the wordings its reason has, and gives the reason that matches the denial: the ordering visit for an out-of-network scan, the trip for an emergency, the question left unanswered, the moved session and the authorization that still had sessions left, the surgeon's visit in the week before an expedited surgery appeal.
- A reply gives the facts of the document the plan asked for (the order's visit and its three-week limit, the moved session and the end of the authorization, the visit whose notes record the earlier treatments), all of which the records hold, and promises no attachment, since appeals carry text only.
- An expedite reason names the orthopedic or surgical visit before it, and the plan's information requests fit the service and the visits before them.
- A member who writes about their own care writes in the first person (Casey's surgery appeal and expedite request), and a text names an authorization in words, not by its ID.

### Selecting a Task's history

- Loading the whole window as one seed would present every record after a Task's first session as history, so the dataset is a base seed plus dated steps.
- [`dataset/as-of.cjs`](dataset/as-of.cjs) replays, through the App's handlers, only the steps dated before a first-session instant: later records do not exist in the selection, a claim, PA or appeal in progress at that instant has only the history it had then, and the counters (`issued`), accumulators and clock are the App's at that instant.
- A timer due before the instant with no later step yet (a claim review, a request expiry, a PA's due date or validity end, an appeal's due date, a window's closing notice) is committed in the selection at its due time, as the App's next write would commit it, so the seed, its EOBs and notices, and `open_items` agree with what Core reads at that instant; a timer due exactly at the instant is left to Core's reads, which already show it.
- The later steps are withheld. The Infra events among them that apply to the selection as it stands and have there the same effect as in the dataset (claims, PA submissions and the providers' documents and withdrawals, the plan's decisions and requests on existing PAs and appeals, grant changes) are returned as `events`, in order, ready to stage through `env.apply_event`; they are what happens if nobody in the household acts.
- An event the dataset records in response to a withheld household action, directly or through other events (the plan's decision on an appeal after the reply it asked for, its decision on an expedite, the claims of a surgery an appeal approved), is not among them, so staging the `events` as given writes no claim, decision, request, filing or grant the dataset lacks and never runs ahead of a reply or filing it waits for; the App's timers then write what nobody's answers imply, such as denials for missing information with their notices and appeal windows, and `differences_from_dataset` lists these records.
- `conditional_events` lists each such event with the household actions it waits for (`after`), the people who take them (`needs`) and whether `account_holder_script` includes it. A conditional event carries its payload for each branch: `event` as it applies once every withheld household action is taken (with the dataset's IDs) and `account_holder_event` as it appears in the script (with the IDs the App issues when only the account holder acts), or null when the script cannot apply it.
- Every withheld Infra step is exactly one of `events`, `conditional_events` and `unstaged_events` (steps that wait for nothing withheld but would have another effect at the instant, each with its reason).
- `account_holder` names the bound account holder (Jordan, `m-1`), the members he may see at the instant and the open items among theirs.
- `open_items` lists the items open at the instant as Core reads them: claims in review or waiting for answers (with their open requests), PAs pending or waiting for documents, open appeals, denials that can still be appealed, and grants in force, each with whether the account holder may see it and the withheld household actions on it (answers, attestations, filings, statements, withdrawals and expedite requests, including actions on appeals that withheld filings create), each labelled with the person who takes it and whether the account holder can take it.
- Each open item gives its outcome after the `events` alone, after the `account_holder_script`, with every household action taken, and in the dataset (a claim's EOB lines and appeals, a PA's status, an appeal's status and whether its decision is overdue, a grant's state); actions that need Casey are not in the script and can be staged only by binding her.
- `account_holder_script` is the ordered list of what reproduces the dataset as far as the account holder can: the events, every withheld action of the account holder that commits without Casey's withheld actions, on open items or on records that arrive later (with arguments renamed to the IDs the App issues when they are taken without the other withheld steps), and the Infra events that wait only for those actions.
- `withheld_actions` lists every withheld household action with its person, its tool and arguments (`args`, with the dataset's IDs, as they apply once every withheld household action is taken, and `account_holder_args`, with the IDs renamed as in the script, or null when the script does not take the action), the open items it touches and whether the script takes it, so a selection alone can stage the household branch, including Casey's actions under her own binding; replaying every withheld step as its person reproduces `dataset/full.json` exactly, which the tests check.
- An action that touches several open items, such as one attestation that answers the other-coverage questions of two claims, is listed under each of them and taken once.
- `dataset/full.json` is the end state of the replay with the timers due before its clock committed, kept so the records can be inspected and counted; it is the selection at its own clock.

### Differences from the dataset

- `differences_from_dataset` compares, for the events alone and for the script, every record of every kind at the window end with `dataset/full.json`: claims, information requests, EOBs, other-coverage attestations, accumulators, PAs, appeals, appeal windows, grants and notices.
- Records are named by what they are about rather than by the IDs the App issues (a request by its claim, line and type, an EOB by its claim and version, an appeal by its target and filing time, a grant by its member, grantee and start, a notice by its kind, subject, recipient and time), with the App's sequence counters left out.
- Records that share a name, such as two grants of one member to one grantee from one instant or two appeals filed on one claim at one instant, are kept apart; identical ones in the two states are matched first and the others then paired, so only what differs is listed.
- An appeal window is listed as its opening, `window:…`, and its closing, `window:…~closing`.
- Each record that differs is listed once (`record`), with whether it is missing, extra or changed and in which fields, the withheld steps that explain it (`because`: the household actions the branch does not take, or the Infra steps it does not stage when no such action explains them) and the differing records it is traced through (`via`).
- The traces: a claim and its EOB to their questions, attestations, PAs and the appeals that overturned them; an EOB's amounts to the earlier EOBs of the member or the family whose postings move its deductible or out-of-pocket snapshot; a PA to the EOBs that first count its units; an appeal to its target; an appeal window's opening to the EOB that opened it and its closing to the appeals filed; accumulators to the EOBs that post a nonzero amount to them; and a notice to the fields it carries (an EOB, a window's end or closing, a request, an appeal or a PA) and to the recipient's grant to the member in force when it was issued.
- A notice, an EOB and an appeal window's opening carry their issuance (`issued_at`, in `dataset/full.json` when the record is there, else in the branch) and are traced only to steps before that instant and through records that existed then, so a denial notice or a window's opening never cites an appeal filed after it, which only the closing cites; the other records change over time, and each step they cite precedes a change of the record in the dataset or in the branch.
- Every record not listed ends equal, which the tests check by replaying both branches in the App (and the script in Core, which ends equal to the App).

### Commands

```sh

node dataset/as-of.cjs --at 2026-01-01 --out selection.json       # the selection: data, virtual_now, events, bundle and summary
node dataset/coverage.cjs --check --runtime ../../runtime         # recompute the report, including the MCP loading demonstration; without --check, write it
```

### Instants, seed IDs and loading

- An instant is a date (local midnight in `America/New_York`) or a date-time with an offset, from 2025-01-01T00:00:00-05:00 to 2027-01-01T00:00:00-05:00; a record at exactly the instant is not included.
- Each selection has its own `seed_id`, `larkfield-delivery-asof-<UTC instant to the millisecond>-<first 12 hex digits of the SHA-256 of its clock and content>`, so a preview token taken on one selection is `stale_preview` on any other.
- A selection's `data` and `virtual_now` go to `env.load_seed` unchanged; pass its `bundle` with a `request_id` so the run's quality report carries the dataset's provenance (record source `delivery-dataset` in [`contribution/dataset.json`](contribution/dataset.json)) instead of an unspecified import.
- Its `summary` (records, distinct dates, claims per month) is the starting point for a Task's own history report.
- `dataset/coverage.cjs` loads the selections one millisecond after an accident question expired with no later step, at 2026-01-01, the fixture clock, 2026-12-15 and the window end through real Core over MCP; the Agent, bound as Jordan, lists and reads every claim the grants in force let him see, his PAs, appeals and grants and the plan year, the monthly counts read back equal the computed ones, the open claims, PAs and appeals equal those Core shows, and the first staged event is applied.

## Infra

The optional Mail flow is run by Infra with `infra/sender.cjs`, never by the Agent (`npm run mail` checks it against Mail 1.3.0). It sends only entries appended after the loaded seed, one message per log entry, and rechecks at dispatch that the recipient is still the member, a guardian or a `view` or `act` holder in force, so a Mail-bound minor gets their own notices and a revoked or expired viewer gets none. An entry held as `access_changed` stays pending and is delivered on a later pass once the same person holds a grant on that member again. It relies on these Infra assumptions:

- Build each Mail session with `openSession` from one grant: it opens the Mail instance in the account's digest namespace, checks its seed and binding, then starts the Router with that namespace and grant. The adapter refuses sessions it did not build or that were built for another run, and checks every Router and Mail endpoint against the run before aligning clocks or publishing. It handles errors on the input streams of the clients it opened this way and writes nothing to a client whose input is closing or closed, so the objects that `openMail` and `openRouter` return must expose the client's `child` process; a `stdin` property alone covers the input, but then the adapter cannot see the Router's exit.
- The Router does not report which inbox it is bound to. A Router that Infra opened for another inbox of the same owner is caught only from its receipt, after delivery; the adapter then halts every session.
- A publish whose outcome is unknown (its Router reply times out or is lost, or the reply shows neither that Mail answered nor that nothing was dispatched, such as `receiver_unconfirmed`) halts the run at once through `onHalt`, before any other call to that Router, and keeps the publish lock, so writes through `adapter.exclusive` wait, until the dispatch is settled on the Mail side. After a lost reply the same Router must first answer a later request (it handles requests in order, so the earlier one has then finished or been refused) or its process must have exited, as its client's child process reports; a client error alone, such as a write after its input was closed, does not count. Then the session's Mail instance must show the event committed, be in a new epoch, or commit a 1 ms `env.advance_time` from the adapter: a receive still queued in Mail, including one left running by a killed Router, carries an older expected version, so Mail refuses it after that write. That write leaves Mail's clock 1 ms ahead in the halted run. Only then is the halt checked and reported. A Router that never answers or exits, or a Mail instance that cannot be read or written, keeps the lock. Infra may close only a Router that does not answer; the close counts once its process has exited, and Mail must stay reachable. Closing a Router that still answers, or killing one, can end or orphan its Mail receiver in the middle of a transaction: a close ends the Router's input and, if the Router is still running 1 s later, sends it SIGTERM; the Router then closes its receivers at once, even while one of its requests is pending, and a receiver still running 1 s after that gets SIGTERM. That can leave the Mail instance unusable. The run then stays halted and the adapter keeps the publish lock, so nothing is delivered after a revocation, but whether the pending entry was delivered is unknown: Core stores the notice and its receipt before it releases the Mail lock, so an interrupted receiver may already have stored it, and an orphaned one that finishes later stores it then (the adapter then settles as `committed`, still before any revocation). Infra ends that run. While the adapter settles, `status()` reports the halt and its cause without `stop_verified`.
- Pass an `onHalt` function that halts every Router session of the run, such as writing the Router's stop file. The adapter refuses to start without it, verifies after each halt that every session refuses, and otherwise reports the halt as unverified. Adapters in one Infra process share the halt; another process must ask the Router. The function may run while the publish lock is held, so calling `send`, `align`, `reconcile` or `exclusive` of an adapter for the run from inside it is refused with an error.
- Apply grant changes, other Larkfield events and resets through `adapter.exclusive(fn)` while a pass may run: each publish is checked against a fresh snapshot under that lock. A write applied any other way, through another Core client or in the same process outside `adapter.exclusive`, can land between that final snapshot and its publish, and the adapter cannot see it.
- Wrap only Larkfield writes, events and resets in `adapter.exclusive`. Calling `send`, `align`, `reconcile` or `exclusive` of an adapter for the same run from inside it is refused with an error, because it would wait for its own lock.
- A person with several granted inboxes is served only when exactly one route is usable for a configuration reason; a route that is merely unreachable for a pass keeps the entry waiting as ambiguous (`ambiguous_route`) while another of that person's routes is usable; when none is usable, the entry waits with the first route's own reason, such as `router_unavailable` when every Router is down and the inboxes are readable. Once an entry has been sent, or its outcome is in flight or unknown, every retry goes to that inbox only, and the entry waits while that inbox is unusable (`destination_unavailable`) or while another of the recipient's inboxes cannot be read to rule out an earlier delivery (`destination_unknown`).
- The destination record lives in the adapter's process and is shared by every adapter there. An adapter in another Infra process learns of an earlier delivery only by reading the recipient's inboxes (Infra itself can also find a committed delivery and its destination account in the Router's receipt audit log, `messaging.receipts.jsonl`), so run one sender process per run.
- `adapter.status()` answers `unknown` until the adapter has resolved its run (`await adapter.ready`, retried by every `send` or `align`), and only then `ready` or `halted`; `send` and `align` refuse a halted run in any case.
- A configuration verdict once recorded for a session (an incompatible contract, another run's Router or Mail, no Email channel) keeps that route out even while the session is also unreachable.
- A session whose Router, Mail instance or clock fails during a pass is left out of that pass (`router_unavailable`, `receiver_unavailable`, `clock_unaligned`) and its entries stay in the log; the other sessions continue. If Larkfield's own clock cannot be aligned, nothing is published.

All data is synthetic: no real people, brands, billing codes or member data.
