# Platewright

Platewright is a resettable recipe box and household meal planner, seen from one household member's account. It knows what each recipe contains, who in the household cannot or will not eat what and from which date to which date, what is planned for which meal and for whom, and what is already in the kitchen. It answers one question the same way everywhere (is this dish, as it would be cooked, right for each person who will eat it on that day?) and turns the week's plan into the quantities that still have to be bought. It sells nothing and places no order.

- App ID `platewright`, version 1.0.0, Core API 1.2.0, public runtime 1.6.0. Node.js 18+ built-ins only; nothing to install.
- Approved scope: [`proposals/environment/platewright.md`](../../proposals/environment/platewright.md). Validation, the workflow-to-test mapping and the acceptance self-review: [VALIDATION.md](VALIDATION.md).
- MCP tools for the Agent, and an App-owned web interface served by the repository's shared Web Host ([Web interface](#web-interface)). The other household members act only through events.
- Everything is fictional: the Arden-Okafor household (Nora, Evan, Eli and Ada), their guests, the 60 recipes, the substitution rules and the ingredient table were written for this package. Workflow shapes were informed by public help pages of Paprika, Plan to Eat and Mealime; the nine allergen names follow the FDA's list of major food allergens. No data, recipe text, photos, branding or icons were taken from them.
- **Not advice.** The nutrition values are rounded, illustrative figures and the suitability check is simplified. Nothing here is medical, allergy or dietary advice.

## Workflows

| Workflow | Agent operations | Events that change it |
| --- | --- | --- |
| W1 Recipe box | `recipes.search`, `recipes.get`, `ingredients.search`, `recipes.create`, `recipes.update` (also archives and restores) | `recipe.added` |
| W2 Profiles and the check | `household.get`, `recipes.check`, `members.constraint.set`, `members.constraint.remove` | `member.updated` |
| W3 Substitutions | `substitutions.list`, `recipes.variant.preview`, `recipes.variant.create` | — |
| W4 Weekly meal plan | `plan.get`, `plan.slot.set` (also clears), `plan.slot.mark` | `plan.changed`, `guest.changed` |
| W5 Pantry and shopping list | `pantry.list`, `pantry.set`, `shopping.generate`, `shopping.get`, `shopping.item.set`, `shopping.item.remove` | `pantry.changed`, `shopping.changed` |
| Notifications | `notifications.list` | all six |

All 22 tools are `platewright.<name>` (11 reads, 11 writes). Every write takes Core's `request_id` and `expected_version` (`{epoch, revision}`) and returns the object's `id` with the committed version; the object's own state is reported as `state` because Core sets `status` to `committed`. The target object is always the argument `id`: a recipe, a member (`person_id`, for constraint writes), a slot (`2026-11-14:dinner`), an ingredient (for `pantry.set`) or a shopping line. A window is always `start` / `end` as `YYYY-MM-DD` dates. The Agent always acts as the account holder bound by Infra.

App errors: `not_found`, `unknown_ingredient`, `unknown_member`, `unknown_rule`, `invalid_quantity`, `invalid_servings`, `invalid_constraint`, `invalid_window`, `invalid_state`, `no_conversion`, `not_in_recipe`, `rule_not_applicable`, `conflict`, `past_slot`, `not_yet`, `leftover_unavailable`, `derived_line`, `no_list`, and `invalid_arguments` for malformed dates and empty patches. Core adds `permission_denied`, `stale_version` and `idempotency_conflict`. A refused event is `invalid_event` with data and clock unchanged.

### Rules worth knowing

- **Time is the environment's.** There are no timers and no clock event. A constraint's `state` (`scheduled`, `active`, `expired`, `ended`), a slot's `phase` (`upcoming`, `past`) and a pantry item's `freshness` (`fresh`, `use_soon`, `expired`, `no_date`) are derived from stored dates and `ctx.virtual_now` in the household's time zone when they are read. A read writes nothing; no notification is written by a read or by the passing of time.
- **One check, on the date of the meal.** `recipes.check`, `recipes.variant.preview` and every slot's flags use the same function. A member's constraints apply as they stand on the meal's date; a constraint ended today stops applying from today's date. Verdicts in order of seriousness: `unsafe` (allergen contained, or a medical ingredient or flag; may-contain under a `strict` allergy), `may_contain`, `unsuitable` (a diet's flag), `over_limit` (nutrition per serving times the person's portion factor; a guest counts 1), `disliked` (an ingredient or an ingredient tag), else `ok`. Every finding names its lines. The verdict is the most serious finding; only when every finding is caused by optional lines alone is it `ok_if_omitted`. The lines of findings caused only by optional lines are always listed in `omit_lines` (so optional walnuts under a strict tree-nut allergy give `unsafe` with the walnuts named, even next to a firm dislike). A limit that cannot be checked because nutrition is unknown is listed in `unchecked`, never counted as zero, and shows on the slot as a `limit_unchecked` flag. `lactose` is a flag and `milk` an allergen, so lactose-free yogurt suits a lactose-free diet and is still unsafe for a milk allergy.
- **Guests exist only on their slot.** A guest's constraints are checked for that meal alone and never reach another slot or a member's profile.
- **A plan can be wrong and says so.** `plan.slot.set` never refuses a dish for whom it is wrong. Slots read with `flags`: one `person` flag per attendee or guest whose verdict is not `ok` (planned and cooked slots), plus `limit_unchecked` (a person's limit on a dish whose nutrition is unknown, with the lines that cannot be weighed), and `archived_recipe`, `stale_base`, `leftover_short` and `leftover_expired` (planned slots).
- **Servings and leftovers.** A dish's default servings are the attendees' portion factors plus one per guest, rounded up to a half. A planned source slot leaves its servings minus its default portions; a cooked one leaves `made - eaten`; a skipped or cleared one leaves nothing. Takes are counted in meal order (breakfast, lunch, snack, dinner). Leftovers older than `leftover_max_days` on the day they are planned for read `leftover_expired`.
- **Units.** Fixed kitchen values (1 tsp = 5 ml, 1 tbsp = 15 ml, 1 cup = 240 ml, 1 fl oz = 30 ml, 1 oz = 28.35 g, 1 lb = 453.6 g). Mass and volume convert only through the ingredient's density, pieces and mass only through its weight per piece; otherwise `no_conversion`. `unit_system` is `recipe` (as written), `metric` or `us`; `units` asks for one ingredient in a given unit. Shown quantities are rounded (g and ml to 1, or 0.5 below 10; spoons and cups to a quarter, an eighth below 1 tsp; whole-piece ingredients counted in `each` round up) and carry `exact`. As written, an amount below one tablespoon (or a quarter cup) is shown in a smaller spoon, so 0.1 tbsp shows as 0.25 tsp.
- **Nutrition** per serving sums grams times the per-100 g values over non-optional lines; a line that cannot be converted to grams makes it `null` with the line in `missing_for`.
- **Variants** record the base recipe, its revision and the swaps (`rule_id`, or `custom` and then the variant is `unverified`). They do not follow later edits of the base and read `stale_base` once the base moves on. A variant is not edited (save another one); a variant of a variant is refused.
- **Shopping list.** `shopping.generate` adds up the exact quantities of every planned recipe dish in the window per ingredient in the unit it is bought in (lines that cannot be converted to it are merged in the base unit of their own dimension), leaves out leftovers and optional lines (listed in `optional_lines`), takes pantry stock use by use in meal order, each lot only for meals on or before its use-by date and never once the clock has passed that date (what is left of a lot when it would expire first is listed in `expiring_before_use`; stock in a unit that cannot be converted in `stock_not_counted`), and rounds up once. 500 g of yogurt with a Thursday use-by covers Tuesday's 300 g; the other 200 g are not counted for Saturday. Each derived line lists its slots. Regenerating keeps manual lines, ticks and exclusions on lines still needed, drops unticked and excluded lines no longer needed and keeps ticked ones as `surplus`. A current list reads `stale` after any committed change to the plan slots in its window, the recipes they use, the pantry or the members' portion factors and constraints.
- **Pantry.** One item per ingredient. `pantry.set` with quantity 0 marks it `out`. Marking a slot cooked with `deduct_pantry: true` takes the exact non-optional quantities from the pantry, never below zero and never from stock past its use-by date on the slot's date, and returns what was short (`not_in_pantry`, `not_enough`, `expired`, `no_conversion`). Marking cooked with the default portions records the dish's servings as made and the attendees' portions as eaten, at most what was made.
- **Notifications and activity.** Each applied event writes one notification and one activity row. Each committed Agent write writes one activity row with its `request_id`. A replay, a refusal or a clock move writes none. Notification titles and bodies are written for people as well as for the Agent: they name ingredients, people and meals ("Maya is coming to dinner on Sat 14 Nov 2026.") and carry no record IDs; the record is in `object_id`. Pantry amounts read "12 eggs, 800 ml coconut milk (canned)". Refusal messages a person can meet in the web interface name meals, dates, recipes, ingredients, people, constraints and shopping lines the same way ("Lime is already ticked."); a refusal about an ID that matches no record repeats the ID that was sent, since there is no name to give.

## Data

`fixtures/reference.json` is the package seed (1,018,433 bytes on disk, written one record per line; 1,010,944 bytes as the compact JSON Infra sends; no media): 213 ingredients with allergens, may-contain, eight content flags, tags, units, density or weight per piece and nutrition; 48 substitution rules; 60 recipes (two of them added by members during the history) and 6 variants, one with a stale base and one unverified; four members with 23 constraints covering every kind and every state at the loaded time; 880 plan slots from 2025-01-01 (cooked, skipped, cleared and planned, with guests and leftovers); 40 pantry items with 256 history rows; a stale shopping list of 36 lines with ticks, an exclusion and manual lines; and 74 notifications with their activity rows. The loaded time is Sunday 2026-11-08, 08:00 in America/New_York.

The environment timeline has two dates: the household's history starts on 2025-01-01, and the task window starts on 2026-01-01. The five weeks from 12 October 2026 (71 slots, 14 events, the variants and the shopping list) are hand-written. The 22 months before them are generated by `scripts/history.cjs` with a fixed seed (20250101; no clock, no `Math.random`), so `scripts/build-fixtures.cjs` rebuilds byte-identical files (`node scripts/build-fixtures.cjs --check`, also run by `npm test`): 809 slots of weekly menus planned on the Saturday before each week, cooked, skipped (15) or cleared (19), packed lunches from the previous dinner's leftovers, weekend breakfasts and baking, guests, 26 plan changes and 7 guest changes by other members, five earlier constraints (Evan's dry January and an autumn calorie cap, Nora's meat-free February, Ada's and Eli's dislikes that later ended), a first stocking and a shop every twelve to sixteen days (by the account or, as `pantry.changed` events, by Evan or Eli), and occasional cooking that takes from the pantry. Every generated dish passes the App's own check for everyone at the table on its date with the household's final constraints (so no generated slot carries a flag) and contains no allergen any diner is ever allergic to; recipes join the box from 1 January 2025 (24 on the first day, then one every ten days) and are planned only once created and before archived; soups and stews come round in winter, salads and grills in summer, and favourites more often. Both parts are replayed through the App's own hooks; rows the account wrote then are marked `seed`. To keep the seed small, the 768 generated meals that were cooked or skipped exactly as planned do not keep the account's planning row: the row that records how the meal ended carries the same dishes, people and guests, so only the time of planning (the Saturday before the week) is not kept. The 41 generated meals that were cleared, changed by another member or joined by a guest keep their planning row, so their history shows what was planned before; meals in the hand-written weeks keep every row. Generated notifications have the ID series `ntf-h0001` onward, so the hand-written ones keep `ntf-0001` to `ntf-0014`. The App keeps only the current shopping list, so earlier weekly shops appear as pantry rows and `pantry.changed` events, not as old lists. `fixtures/minimal.json` is the smaller household the business tests start from and has no generated history.

`scripts/check-fixtures.cjs` checks both fixtures beyond `validateSeed`: every recipe line converts to grams or belongs to an ingredient that is not convertible on purpose, diet tags on recipes follow from their lines, titles and ingredient lists are distinct, constraint and slot states agree with the loaded time, every date is on or after 2025-01-01, the only flags present are the intended ones, and the counts match `contribution/dataset.json`. The App's record rules apply to every record of both fixtures, hand-written and generated alike: recipes planned only between their creation and archiving, each cooked dish's recipe revision as of the day it was cooked, each slot's history replayed under the App's own transitions (a meal is set when it is not planned and replaced when it is; only a planned meal is cleared, cooked, skipped or given guests; cooking keeps the planned dishes and people; nothing is planned or changed after the meal's date and nothing cooked before it; the slot is its last row; the one shortening allowed is the dropped planning row of a generated meal cooked or skipped as planned), rows written by events belonging to notified events, leftovers eaten within `leftover_max_days` and never more than were left, pantry rows in time order and never negative with cooking only ever taking stock, one notification and one activity row per event, and notification text without record IDs, slot IDs, ISO dates or vocabulary keys. For the reference household it also checks that the two years read as lived in (at least 25 slots in every month since January 2025, soups and stews at least twice as frequent in winter as in summer), the size of the default reads (`plan.get` is the current week, `recipes.search` a page of 20) and a size budget (all fixture files together at most 1,075,000 bytes on disk, a seed at most 1,015,000 bytes compact). `tests/fixtures.test.cjs` feeds the history check deliberately broken copies of both fixtures (a cleared, changed or guest meal without its plan, a meal cooked with other dishes than planned, cleared after cooking, cooked before its date, and more) and expects each to be refused.

`tools.json` (247 KB on disk, about 92 KB as compact JSON; every nested result shape is typed with `additionalProperties: false`), `schemas/seed.schema.json` and `schemas/events.schema.json` are generated by `scripts/build-contracts.cjs` (`npm run contracts:check` detects drift). All three are self-contained, with no `$ref`; see [Speed](#speed) for why the seed schema is. `schemas/state.schema.json` is the provided Core envelope; the other schema files are copies of the public shared contracts kept in sync by the repository's `npm run contracts:check`.

### For evaluators and tasks

- Evaluator records: the snapshot's activity rows, recipe revisions, constraint and slot histories and the shopping list (each derived line names its slots); Core's audit rows (with the projected `id`, `start` and `end`); and the Agent trace for verdicts and flags shown, which are never stored. `plugin.cjs` exports the pure `check` and `flagsFromSnapshot(data)` so flags at the end of a run can be recomputed from a snapshot.
- A task can fence off other members' constraints with `policies.json`, because both constraint writes target the member as `id`; list both tools, as in `fixtures/policies-fence.json` (exercised by `scripts/real-mcp.cjs`). The write result's `id` and the activity row's `object_id` are the constraint; Core's audit row records the member as its `id`.
- Seeds are validated by `validateSeed` (duplicate IDs, dangling references, a variant whose base is missing, a unit an ingredient cannot be measured in, a cooked slot dated after the loaded time, malformed dates, timestamps without a UTC offset, an account the binding does not declare, revisions out of step).

## Commands

From this folder (the package alone, no runtime needed):

```sh
npm test                 # 36 business tests: T01–T16, T17 (App side), contracts, seed validation, fixtures, diagnostics, every tool on schema-valid input, refusal wording
npm run example          # walkthrough: Evan's cilantro dislike from tomorrow flags tomorrow's tacos, not tonight's
npm run contracts:check  # generated tools/schemas match their source
npm run fixtures:check   # consistency of both fixtures
```

With the pinned public runtime (found automatically in a full checkout, or `--runtime DIR` / `PALE_RUNTIME_ROOT`):

```sh
node scripts/real-mcp.cjs [--runtime DIR] [--output FILE]                                       # 63 real MCP checks (Core side of T17)
node scripts/notes-calendar-walkthrough.cjs [--runtime DIR] [--notes DIR] [--calendar DIR]      # Notes 1.0.0 -> Platewright -> Calendar 1.3.0
npm run test:web          # tests/web-smoke.cjs: the shared Web Host serving this App (no npm dependency)
npm run test:web:browser  # tests/web-browser.cjs: Chromium click-through (needs the repository's Playwright)
```

From the repository root:

```sh
npm run app:verify -- --app apps/platewright --output .artifacts/platewright.json
npm run contracts:check
npm test
```

Run an MCP server pair by hand: `node apps/platewright/service.cjs --role infra --run demo --state-dir .state` and, in another process, the same with `--role agent`. The default `scenario` profile allows only reads; Infra selects `sandbox` with `env.reset` to allow writes.

## Web interface

The App owns its pages (`gui/index.html`, `gui/src/app.js`) and declares them in `contribution/gui.json` (the reviewer-renderer profile with `gui/src/view.js`, plus the `pale.web` extension, `status: implemented`). The repository's shared Web Host serves them; from the repository root:

```sh
node runtime/web/server.cjs --app platewright --registry apps/platewright/web.registry.json --run web-demo --profile sandbox
```

`web.registry.json` is a one-App registry for this package, so the Host needs no change to `apps.registry.json` or `runtime/`. Views: Meal plan (week by week, with the check's findings per meal), Recipes and Archived recipes (scaling, units, nutrition, check for the table, edit, archive, swap ingredients into a variant), Shopping list, Pantry, Household (members' dated needs) and Activity. Every Agent write of the five workflows has a control; see [gui/README.md](gui/README.md) for the views, the behaviour (versioned writes, retries, refusals with the App's message, restricted profiles, text-only rendering) and what is left to MCP. The interface was added after the plan was approved, at the maintainers' request; the approved plan described an MCP-only first version.

## Speed

Core reads the whole state file, validates it against the seed and state schemas (the current data and the loaded seed, so the household's history about three times over) and runs `validateSeed` on every call, reads included; an App cannot change that. The cost of a call therefore grows with the household's history. Two choices keep it small on the reference household:

- `schemas/seed.schema.json` is generated with its definitions inlined. Core's schema validator resolves a `$ref` that names a file on the file system each time it meets one, which on 880 slots made validation about four times slower than the inlined schema (about 125 ms against 30 ms per pass).
- The reference seed is 1,010,944 bytes of compact JSON (see [Data](#data)).

Measured on a 20-thread desktop under light load with the runtime's MCP client (median of 25 calls): `household.get`, `recipes.search`, `plan.get` and `pantry.list` take 0.24 s per call on Node 22 and 0.28 to 0.29 s on Node 18 (Notes' `notes.list` on the same runtime 0.013 s). The web interface sends two Core requests per read (the shared Host lists the tools before each call). With Chromium against a Host on Node 22: Pantry, Household and Activity open in 0.55 to 0.6 s, Meal plan and Shopping list in 0.9 to 1.0 s, Recipes and Archived recipes in 1.3 s, a pantry write is back to an idle page in 1.0 s, a reload takes 1.3 s and the first load 2.4 s; a form opens in 0.05 s without a call (the ingredient table is read once per page load). A Host on Node 18 is 5 to 30% slower (first load 2.9 s). The runtime's MCP client gives up after 6 s per request.

## Limitations

Out of scope in this version, as approved: prices, budgets, stores, products, carts and orders; recipe import from a web page or a photo; photos and other media; ratings and comments; automatic menu or recipe suggestion; daily or weekly nutrition totals (a `limit` is per meal); micronutrients beyond sodium; cooking timers; locking a day of the plan; several households or accounts per instance; email, push and chat notices. The web interface is a local, loopback-only business page through the shared Host; there is no reviewer console. There is no messaging in either direction. Nutrition values, substitution rules and recipes are illustrative and await human review.
