The approved plan ([`proposals/environment/platewright.md`](../../../proposals/environment/platewright.md)) is unchanged. Review evidence is separate from runtime assets: nothing in `evidence/` is loaded by the App, and it is not part of the App's media bundle (the App has no media).

## GUI workflow sequences

[gui/sequences.md](gui/sequences.md) lists every frame in order with the action taken, the expected and the observed result, the MCP read that confirms the persisted record and the App version after each write, and the reload checks; [gui/sequences.json](gui/sequences.json) holds the same data. The frames are produced by a checked-in script that drives the real Host and the real controls (it is not part of `npm test`):

```sh
# repository root, once: npm ci && npx playwright install chromium
node apps/platewright/scripts/capture-gui-evidence.cjs --zopfli
```

It starts the Host on a fresh run, clicks and types through the page in Chromium, confirms each write with an independent Agent MCP connection to the same run, reloads, applies one Infra event, checks every frame's visible text for record IDs, ISO dates, vocabulary keys and missing values before taking it, and fails on any JavaScript error. `--zopfli` recompresses the PNGs losslessly when `zopflipng` is installed. Each step also exists as an assertion in `tests/web-browser.cjs` (54 checks). Reproducible: the actions, records, versions and observed texts; `sequences.json` and `sequences.md` came out byte-identical on Node 22 and Node 18. Not reproducible byte for byte: the PNGs (42 of 47 were identical between those two runs on one machine; font rendering and anti-aliasing differ between machines and Chromium builds).

Only public help pages and public marketing pages were used; nothing was logged in to, signed up for or scraped. **No third-party image is redistributed in this repository**: the reference screenshots are referenced by URL with a description of what they show; their sites state no licence that allows redistribution (Paprika's help site gives none; the Plan to Eat help centre is "©2025 Plan to Eat, LLC."; mealime.com is "© 2026"). Every URL below returned HTTP 200 on 2026-11-25, the retrieval date. Paprika's help pages carry no publication date; the dates given for its images are the image files' `Last-Modified` headers. Platewright is independently branded, uses synthetic data and has no photos, ratings, import, prices or stores (plan, "Simplifications"); a reference is a workflow comparison, not a layout to copy.

## Dependency demonstration: Notes → Platewright → Calendar

Platewright declares no required App and no messaging (`dependencies.required_apps: []`, `messaging.publishes/receives: []`). The plan's "App integrations" row promises one walkthrough of separate Agent calls; that is the integration delivered, and it is demonstrated against the real pinned Notes and Calendar packages of this checkout through their public tools. Run from the repository root:

```sh
node apps/platewright/scripts/notes-calendar-walkthrough.cjs --output apps/platewright/evidence/notes-calendar-walkthrough.json
```

The transcript [notes-calendar-walkthrough.json](notes-calendar-walkthrough.json) (byte-identical on Node 18 and 22) records:

1. **Revisions and contracts.** Runtime 1.6.0; Platewright 1.0.0 with the SHA-256 of its `tools.json`; Notes 1.0.0 and Calendar 1.3.0 with the SHA-256 of each package and of the exact `notes.get`, `calendar.create` and `calendar.get` schemas, pinned in the script. Caller and direction: the Agent connection, as account holder `person-nora`, calls each App in turn; no App calls another. Binding: `platewright-nora`, `notes-nora`, `calendar-nora`, all owned by `person-nora`. Initial states: each App's version and data hash.
2. **Requests and results.** Every request with its `request_id` (`carry-note-1` … `carry-note-3`), every result, and each App's version and data hash after every step; Core's audit rows; the stored receipts keyed by request ID.
3. **Result in each App.** The note `note-lentil-soup` was read (body hash recorded) and its quantities are the saved recipe's lines; Platewright committed `rec-lemony-lentil-and-spinach-soup` (revision 1) and planned `2026-11-11:dinner` (local commit); Calendar holds exactly one event, `evt-local-1`, in `calendar-nora` at 18:30–19:30 on 11 November (receiver commit, confirmed by `calendar.get` and the Infra snapshot). Recipient or business confirmation does not apply and is not claimed: the event is in the account holder's own calendar, with no attendee.
4. **Failure paths**, each checked for unintended changes in every App: an argument outside Calendar's contract (`invalid_arguments`, nothing written); a stale Calendar version (`stale_version`); a write whose response the caller did not receive, resolved by resending the same request ID (stored receipt, `duplicate: true`, same event ID, one event); the same request ID with changed input (`idempotency_conflict`); the repeated Platewright write (stored receipt, no second recipe); a policy without `calendar.create` (`permission_denied`, neither App changes); Platewright alone, where `notes.get` and `calendar.create` are refused and Platewright's own write still commits; and a Calendar package of another version and contract (a temporary copy, labelled as a test double) refused by the pin check before any call.

## Dataset coverage

[dataset-coverage.md](dataset-coverage.md) and [dataset-coverage.json](dataset-coverage.json) are written by `node scripts/dataset-coverage.cjs` from the seed exactly as the App loads it (time zone America/New_York; authoritative date field per record family; per-month and per-family counts; provenance; file hashes). `npm test` fails if they no longer match the fixture. In short: 1,361 records (Core's count); 2,414 dated history rows on **631 distinct dates** from 2025-01-01 to 2026-11-07, every month from January 2025 to November 2026 with history; everything is synthetic (2,014 rows from the seeded generator `scripts/history.cjs`, seed 20250101; 342 hand-written; 58 recipe-creation rows of hand-written recipes dated by the generator), nothing is real. The loading and retrieval demonstration [dataset-query.json](dataset-query.json) (`node scripts/dataset-query.cjs`) starts the App on the public runtime in the read-only `scenario` profile and reads every counted family back through the Agent's tools: 880 slots with 1,004 history rows through `plan.get` (18 windows), 66 recipes with 73 history rows through `recipes.search` and `recipes.get`, 23 constraints with 28 rows through `household.get`, 40 pantry items with 256 rows through `pantry.list`, 36 shopping lines through `shopping.get`, 74 notifications through `notifications.list`; activity rows are an evaluator record read through Infra's `env.snapshot`. All counts match the report.

## What is not provided, and gaps

- **Dataset after the loaded time.** The reference household is loaded at 2026-11-08 08:00. History ends on 7 November 2026; 14 meals from 8 to 15 November are scheduled (planned, not history); nothing is dated from 16 November to 31 December 2026. December 2026 has no record. Post-clock activity is not invented; a Task that needs it adds records through its own seed or events.
- **Real data.** None: the plan's data are synthetic by design (no website to collect from), so there is no real November 2026 anchor.
- **Reference images** are referenced by URL, not redistributed (no licence allows it). No public screenshot was found for substitutions, per-person checks or a household change log.
- **Not run:** a model-agent or user-simulator session against the page; the verifier against a newer `main` than `a4bce02`.
