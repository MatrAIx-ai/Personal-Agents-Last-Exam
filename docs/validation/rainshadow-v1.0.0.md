```sh
cd apps/rainshadow && npm test && npm run example && npm run check:fixture && npm run check:contracts && cd ../..
npm run app:verify -- --app apps/rainshadow --output .artifacts/rainshadow.json
```

## Plan and implementation

Everything in the plan's first version is implemented: 21 operations (13 read, 8 write), five events, the state table and rules of §2, the notice log with release times, the activity log, the optional send-only Mail notices with an Infra-run outbound adapter (`infra/sender.cjs`), tests T01–T18, the fixture with its generator and consistency check, and the two real-MCP scripts. The README has the operation list, the rules and a workflow-to-test mapping. Web pages were added after the plan, at the reviewer's request (see "Changes since the first submission").

Where the implementation differs from the plan's wording, or adds to it:

- The plan lists "one small fixture per test". The tests build their small variations in code from the package fixture, so there are no separate fixture files.
- Six tests beyond T01–T18: T13b (alert messages and results that stand after the last window hour has started), T15b (the Mail flow), T16b (a seed notice still held when the seed is loaded), a check that contracts, fixture and declarations are in step, a static check that no import or file path leaves the package, and a check that the web pages are declared, name every tool and show App text as text only.
- `watches.create` and `watches.update` answer `invalid_arguments` for `aq_source_id` on a watch without an `aqi` condition, and `not_found` when an `aqi` condition has no air-quality source to use (none named and no account default). Both follow from the plan's rule that a watch stores an air-quality source exactly when it has an `aqi` condition.
- Notices that came with a seed are history for the sender, except those still held when the seed was loaded; these are published once their release time has passed.

Notes from the plan approval, and how they were followed:

- "Pull main and re-run the verifier before you submit": `main` at `a4bce023953061483c41de5a287ba5e43f4a5648` is merged into the branch below the package commit, and every result in this report was produced on that merge. `main` has since moved to `ae889d2cbbfc72242fc5e70b877f3f2a2f029618`, with changes to documentation and proposal automation only (nothing under `runtime/`, `apps/` or `examples/`); the independent base validator ran from an unmodified checkout of that commit. The runtime and Mail versions are the ones the plan names (1.6.0 and 1.3.0).
- The dates of the seeded history: the note that came with the approval asked for 2026-01-01 onward, and the first submission (commit `2019809`) kept every record in November 2026. On 2026-11-24 the reviewer corrected the note: history starts on 2025-01-01, and tasks run from 2026-01-01. The fixture now carries the account's history from 1 January 2025 to its clock (see "Changes since the first submission").
- Shared field names with #126 (Gustline): nothing changed in Rainshadow. The revised #126 proposal states that Gustline will adopt the same field names where the meaning is the same.

## Changes since the first submission

The first submission is commit `2019809892e39a3e9c3e6f86c593ed304f6c13ed`. Five changes followed it: four asked for in review on 2026-11-24, and one for the delivery evidence contract of 2026-11-26.

**Web pages.** Environments now need a GUI, so the App owns its pages under `gui/`, declared in `contribution/gui.json` through the `pale.web` extension as in `apps/notes`, and served by the public Web Host, which forwards only the Agent's tools. There are five sections: places (the forecast from one source and one issuance, the next 24 hours, the daily forecast, air quality, the latest observation, the alerts in effect and the open watches), alerts, watches, notices and settings. Every Agent tool is reachable from the pages. A write carries the version its form was opened on, an unchanged resubmission reuses its `request_id`, and an edit sends only the fields that changed, so a policy that allows one field is respected. `examples/web.cjs` starts the Host on a fresh copy of the fixture, and `tests/web.browser.cjs` is the browser check above. `app.json` names the pages in `capabilities.ui`, and `contribution/contribution.json` gains `gui_ref`.

**Late arrivals.** A forecast issuance that arrives with an older issue time than one already stored for its source and place no longer re-evaluates watches. The result was already right, but the evaluation's cause and time pointed at the late arrival; now the evaluation keeps naming the arrival that produced it. This is the only change to business code (`src/events.cjs`); T04 and T13 check it for weather and air quality.

**A new county name.** The invented county Tallowmere, which is also the title of a published game, is now Quillmere (place `pl-quillmere`, zones `z-quill-valley` and `z-quill-high`, and the IDs of its issuances and observations). The proposal never named it. Apart from these names the fixture is byte-identical to the one before the rename.

**History from 1 January 2025.**

- `dev/history.cjs` holds the timeline up to mid-November 2026: places saved and removed with the seasons, an alert rule paused each April and resumed each November, four preference changes, 27 watches with the issuances and observations they were evaluated against, and 46 alert threads, 22 of whose messages the account acknowledged. It is replayed through the App's own functions like the rest, so every notice, evaluation and activity row follows the App rules, and each scripted outcome is checked during the replay.
- The last three days are unchanged apart from the county's name. Their 54 issuances, 12 observations and 6 alert threads are otherwise identical to the first submission; their 3 watches and 8 notices are identical apart from the generated numbers, which now follow the history (`w-0028` to `w-0030`, `ntc-0059` to `ntc-0066`). The three saved places keep their labels and rules and are listed in the order they were first saved.
- Tests name the records of the last three days through helpers instead of literal IDs and check the archive where a list reaches into it (issuances back to the first hike of 2025, closed watches, notices by kind, issuance counts per source). `dev/check-fixture.cjs` checks the span (nothing before 2025-01-01, activity in every month), the archive's shorter issuances and that a notice carries a wire message exactly when email copies were on.
- The test harness no longer validates the state again after a read that left it byte-identical, and the fixture replay checks the state schema once at its end; the seed rules still run after every step. The App-only tests take about 7 s on Node 22 and 10 s on Node 18 with the larger fixture.

**Review evidence and the evaluation dataset.** On 2026-11-26 the delivery evidence contract (`docs/submission-evidence.md`, PR #260) asked every Environment for an index pairing reference-product captures with ordered browser sequences and persisted state, and for an evaluation dataset covering 2025 and 2026 separate from smoke-test fixtures. `apps/rainshadow/evidence/` is that index: 6 captures of the National Weather Service and AirNow pages named in the plan next to 36 ordered steps that `tests/web.browser.cjs --evidence` writes with the action, the expected and the observed result and the state read back through MCP. Among them an alert updated while its page is open (acknowledging is refused until the update is read), then acknowledged and cancelled, and a late forecast arrival that does not replace the latest. The browser test gains these steps and a third run on the dataset. `datasets/full-window/` is the evaluation dataset from 1 January 2025 to 31 December 2026: this fixture's history continued to the end of 2026, with its generator (`dev/dataset.cjs`), its counting script (`dev/coverage.cjs`), its card and coverage report, and `tests/dataset.integration.cjs`, which loads it through the public runtime; forecast hours, alert periods and watch windows are reported apart and never counted. The business tests gain one dataset test. `dev/history.cjs` and `dev/build-fixture.cjs` export their builders for the generator; the fixture they build is unchanged. `examples/web.cjs` takes `--dataset full-window`.

**What did not change.** Nothing under `infra/` or `schemas/`, and not `plugin.cjs` or `tools.json`: the operations, events, state and rules are those of the first submission, apart from the late-arrival rule above.

## Package boundary

The package imports only Node built-ins and its own files; a test scans every script for this. `service.cjs` is the provided launcher. `tests/schema-validator.cjs` is a copy of the public validator, and the real-MCP script checks that it is identical to the one of the runtime in use. The two real-MCP scripts are given the runtime directory (`--runtime` or `PALE_RUNTIME_ROOT`), and so are the web starter and the browser checks (`--runtime`); the browser checks also use the Playwright the repository pins. The Mail flow also needs the package inside a public checkout with the pinned Mail package, because the public Messaging router resolves a publisher package and its receiver registry relative to its own checkout. A copy that holds only `apps/rainshadow/` and `runtime/` starts the App through its launcher and passes the 90 real-MCP checks.

## Data and licence

`fixtures/minimal.json` (837 KB, 315 records, dated from 1 January 2025 to the fixture clock of 20 November 2026) is a snapshot of a scripted synthetic history: 2 invented regions in 2 time zones, 6 places, 8 zones, 3 sources, 111 issuances (81 weather, 30 air quality; 54 of them are the full issuances of the last three days), 39 observations, 52 alert threads with 66 messages, and one account with 3 saved places, 30 watches, 66 notices, 23 acknowledgements and 368 activity rows. `dev/build-fixture.cjs` rebuilds it by replaying that history through the App's own functions (the long-range part of the timeline is `dev/history.cjs`) and `dev/check-fixture.cjs` checks it independently. Nothing was crawled or copied; provenance is in `contribution/dataset.json`. There are no media assets. Code and fixtures are under the repository's MIT License. The code, fixtures and this report were prepared with AI assistance (Claude); the author reviews them and is accountable for them.

`datasets/full-window/` (1.3 MB) is the evaluation dataset: this fixture's history continued from the fixture clock to the dataset clock of 31 December 2026, 20:00 in Denver, with the steady records a weather app keeps (weekly and fortnightly air-quality outlooks, a fortnightly Quillmere issuance, routine advisories), 346 issuances, 140 alert threads, 35 watches, 104 notices and 771 activity rows. Every record is synthetic, generated by replaying a seeded script through the App's own functions; nothing is real, crawled or copied, so there is no real anchor or collection date to report. Its card gives the contents, provenance, loading and limits, and `dataset.json` declares it (`pale.dataset.v1`). The captures in `apps/rainshadow/evidence/reference/` are third-party pages kept only as review evidence, with their source, capture time and licence in the evidence index; they are not App assets and the App never reads them.

## Not claimed, and what remains

- No agent trials or model runs. The first design review left it to a maintainer whether Environment acceptance needs them.
- The web pages run on the public Web Host on loopback. No production deployment (remote authentication, HTTPS) and no user-simulator or computer-use agent runs are claimed; the browser checks are scripted.
- Mail is the only connected App, and the delivery check uses the public Messaging router with a local Infra config. Production Messaging credentials are a platform matter.
- The evaluation dataset is synthetic. Counting shows its spread over the two years; it does not show realism.
- No public product found lets a person define a watch of forecast conditions, so the watch sequences have no reference capture.
- Remaining: independent maintainer reproduction and acceptance, official PR CI on the implementation commit (`public-runtime (18)`, `public-runtime (22)`, `base-runtime-compatibility`), and human review of realism (the account's history and the evaluation dataset), of the invented names and of the web pages.
