npm run app:verify -- --app apps/belltower --output .artifacts/belltower.json

## Plan and implementation

Everything in the plan's first version is implemented: 17 operations (9 read, 8 write), four events, the state table and rules of §2, rule matching over the area tree, word search across revisions, the notification log with quiet hours, the digest, superseding and release times, the activity log, the optional send-only Mail notifications with an Infra-run outbound adapter (`infra/sender.cjs`), tests T01–T18, the fixture at the planned scale with its builder and consistency check, and the two real-MCP scripts. The README has the operation list, the rules and a workflow-to-test mapping.

The plan's three open questions were settled in review: fixtures under the repository's MIT terms; items keep body text and the `copy` and `report` links, with no further field until a consumer Task names one; a watched clipping follows the revisions of the clipped item only (T13 checks that a new item naming it as its basis brings no notification).

Where the implementation differs from the plan's wording, or adds to it:

- The fixture is a snapshot written by an authoring-time script (`dev/build-fixture.cjs`) that holds the authored content and replays it through the App's own functions. No generator runs at run time, and the tests build their small variations from the fixture in code.
- Five tests beyond T01–T18: T16b (the Mail flow), a test of the plan's four example events and its wire message, a seeded random walk with its own oracle, a check that contracts, fixture and declarations are in step, and a static check that no import or file path leaves the package.
- The plan says that search names the revisions that matched. `items.list` does the same for the window, the area, the topic and the priority: these filters are checked against every revision, and `matched_revisions` names those that pass. It also filters by item `status` and by `changed_since_read`. The priority filter is a minimum (`min_priority`), as in a follow rule.
- A retraction arrives with its number, its publication time and the publisher's note. Read as a revision, it shows the headline, topics, areas and priority of the revision before it, `body: null` and no effective period.
- `already_following` means the same sources, areas, topics and minimum priority, whatever the delivery: two such rules would match exactly the same revisions.
- The plan lists a timestamp without a UTC offset among the seeds `validateSeed` rejects. The App's rule does reject it (`invalid_seed`); on the host, Core checks `env.load_seed` against the seed schema first and answers `invalid_arguments`. Either way nothing is loaded.
- Seed rules beyond the plan's list keep a loaded history consistent with the App's own behaviour: areas form a three-level tree; a read mark and a clipping cannot be earlier than the revision they name; and the notification log must follow the notification rules (created when its revision was received, no gap once an item has a notification, superseded exactly when still held as the next was written). No seed rule reads the clock.
- `notifications.list` takes a `start` / `end` window over the creation time, so every time window in the interface has the same two names.
- A notification's `email_prepared` says that a wire message was stored with it. Whether a copy went out is read from Mail's records and the sender's report, as the plan states.
- The sender's report has `dispatched`, `skipped` (with the reason `held`, `superseded` or `replaced`) and `left_out` (counts of seed history, notifications without a wire message, and those already sent). Notifications that came with a seed are history for the sender, except those still held when the seed was loaded.
- A wire message's `subscription_ref` names the first matching rule; with no matching rule, the watched clipping; otherwise `earlier-notification`.
- The digest time is refused inside the quiet hours only while quiet hours are on. A patch that changes nothing is committed and adds no history row. IDs of removed rules and clippings are not used again, because the logs still name them.
- In the Mail flow, Infra first loads the account holder's empty mailbox into the run's Mail instance with the run's shared binding. The pinned Mail package ships only its own example account, and the plan's delivery is to "an account that has a Mail account bound in the run".

## Package boundary

The package imports only Node built-ins and its own files; a test scans every script for this. `service.cjs` is the provided launcher. `tests/schema-validator.cjs` is a copy of the public validator, and the real-MCP script checks that it is identical to the one of the runtime in use. The two real-MCP scripts are given the runtime directory (`--runtime` or `PALE_RUNTIME_ROOT`). The Mail flow also needs the package inside a public checkout with the pinned Mail package, because the public Messaging router resolves a publisher package and its receiver registry relative to its own checkout. Only `apps/belltower/` and this report are added; no registry or runtime file is changed.

## Not claimed, and what remains

- No agent trials or model runs.
- No GUI, no reviewer console and no Web/CUA adapter: the first version is MCP only, as planned.
- Mail is the only connected App, and the delivery check uses the public Messaging router with a local Infra config. Production Messaging credentials are a platform matter.
- Remaining: independent maintainer reproduction and acceptance, official PR CI on the implementation commit (`public-runtime (18)`, `public-runtime (22)`, `base-runtime-compatibility`), and human review of realism and of the invented sources, places and names.
