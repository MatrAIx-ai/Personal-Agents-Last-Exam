# Pegboard 1.0.0: implementation and verification

Owner: Ming Yin (@mingyin1). App `pegboard` 1.0.0 under `apps/pegboard/`; public runtime 1.6.0, Core API 1.2.0; Mail 1.3.0 for the optional notification flow. It implements the plan in [PR #173](https://github.com/MatrAIx-ai/Personal-Agents-Last-Exam/pull/173), `proposals/environment/pegboard.md` at `aa98311bef207f31440e1d67082580b519d5f752`, which was approved for implementation on 2026-11-22 (`/approve-plan`, recorded 01:52:53 UTC). The proposal file is unchanged since that commit. This document records implementation evidence; it claims no acceptance.

Checked on 2026-11-24 (UTC) on Linux x86_64 with Node v22.23.4 and v18.20.8; the browser checks used Chrome 153.0.8010.12 through Playwright 1.56.1, the version the repository pins. All data is synthetic. The runs used temporary directories, local stdio MCP and the public Web Host on loopback, with no network, credentials or model API. Versions, the package hash and every count below are in [pegboard/index.json](pegboard/index.json), next to the raw reports.

## Reproduce

From the candidate checkout, with Node 18 or 22 and nothing to install:

```sh
cd apps/pegboard && npm test && npm run example && npm run check:fixture && npm run check:contracts && npm run check:walk && cd ../..
npm run app:verify -- --app apps/pegboard --output .artifacts/pegboard.json
node apps/pegboard/tests/mcp.integration.cjs --runtime runtime --report .artifacts/pegboard-mcp.json
node apps/pegboard/tests/mail.integration.cjs --runtime runtime --report .artifacts/pegboard-mail.json
npm test
```

The web pages use the Playwright the repository pins:

```sh
npm ci && npx playwright install chromium
node apps/pegboard/tests/web.browser.cjs --runtime runtime --report .artifacts/pegboard-web.json   # --chrome PATH uses an installed Chrome
node apps/pegboard/examples/web.cjs --runtime runtime                                            # to look at the pages: open the printed link
```

The package alone: copy `apps/pegboard/` to an empty directory and run `npm test` and `npm run example` there. The independent check, from a separate checkout of the base revision:

```sh
node runtime/ci/verify-submissions.cjs /path/to/candidate /path/to/reports ae889d2cbbfc72242fc5e70b877f3f2a2f029618
```

The base checkout was not modified and nothing in it came from the candidate.

## Plan and implementation

Everything in the plan's first version is implemented: 22 operations (12 read, 10 write), eight events, the state table and rules of §2, the one eligibility check and the five flags, weekly hours and estimated pay, the notification log with release times, the activity log, the optional send-only Mail notifications with an Infra-run outbound adapter (`infra/sender.cjs`), tests T01–T19, the fixture at the planned scale with its builder and consistency check, and the two real-MCP scripts. The README has the operation list, the rules and a workflow-to-test mapping. Web pages were added after the first submission (see "Changes since the first submission").

The plan's four open questions were approved with its defaults: fixtures under the repository's MIT terms, a manager's decision applied as given with flags, a cover request to one named coworker, and one workplace per account.

Where the implementation differs from the plan's wording, or adds to it:

- The fixture is a snapshot written by an authoring-time script (`dev/build-fixture.cjs`) that replays a scripted history through the App's own functions. No generator runs at run time, and the tests build their small variations from the fixture in code.
- Six tests beyond T01–T19: T16b (the Mail flow), T17b (a seed notification still held when the seed is loaded), a seeded random walk, a check that contracts, fixture and declarations are in step, a static check that no import or file path leaves the package, and a check that the web pages are declared, name every tool and show App text as text only.
- The plan lists a timestamp without a UTC offset among the seeds `validateSeed` rejects. The App's rule does reject it (`invalid_seed`); on the host, Core checks `env.load_seed` against the seed schema first and answers `invalid_arguments`, as it does for a stored time-based state. Either way nothing is loaded.
- Two seed rules make "a handoff whose state does not fit the shifts it names" checkable: a shift's history must lead to the shift as it is, and an approved handoff must have a history row on each shift it moved.
- `short_rest` is flagged on both shifts either side of the short rest. A release always goes to the manager, also where `manager_approval` is off, as in the plan's state table. Notification text names people by the first word of their name.
- Notifications that came with a seed are history for the sender, except those still held when the seed was loaded; these are published once their release time has passed.
- In the Mail flow, Infra first loads the account holder's empty mailbox into the run's Mail instance with the run's shared binding. The pinned Mail package ships only its own example account, and the plan's delivery is to "an account that has a Mail account bound in the run".

## Changes since the first submission

The first submission is commit `914efbca6d4728826fa18b799293a858a59b6034`. One change followed it.

**Web pages.** On 2026-11-24 the maintainers noted that Environments now need a GUI, so the App owns its pages under `gui/`, declared in `contribution/gui.json` through the `pale.web` extension as in `apps/notes`, and served by the public Web Host, which forwards only the Agent's tools. There are seven sections: the schedule (a week of the team's shifts with my hours, and a shift with its flags, cut-off, history and whether I could take it), handoffs, time off, availability, hours, notifications and settings. Every Agent tool is reachable from the pages, and nothing changes hands in the browser: a shift stays mine until a handoff is approved. A write carries the version its form was opened on, an unchanged resubmission reuses its `request_id`, and an edit sends only the fields that changed, so a policy that allows one field is respected. `examples/web.cjs` starts the Host on a fresh copy of the fixture, and `tests/web.browser.cjs` is the browser check above. `app.json` names the pages in `capabilities.ui` and its limitations, and `contribution/contribution.json` gains `gui_ref`.

Nothing else changed: no business code, contract, fixture or event, and every test of the first submission is unchanged; the business tests gain one static check of the pages.

## Package boundary

The package imports only Node built-ins and its own files; a test scans every script for this. `service.cjs` is the provided launcher. `tests/schema-validator.cjs` is a copy of the public validator, and the real-MCP script checks that it is identical to the one of the runtime in use. The two real-MCP scripts are given the runtime directory (`--runtime` or `PALE_RUNTIME_ROOT`), and so are the web starter and the browser checks (`--runtime`); the browser checks also use the Playwright the repository pins. The Mail flow also needs the package inside a public checkout with the pinned Mail package, because the public Messaging router resolves a publisher package and its receiver registry relative to its own checkout. Only `apps/pegboard/` and this report are added; no registry or runtime file is changed.
