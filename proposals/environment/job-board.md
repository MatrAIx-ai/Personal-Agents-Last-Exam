Proposed PR title: `[Environment Proposal] [Work & business] Beacon job board (LinkedIn-inspired)`

## 1. App and domains

- **Authors / GitHub handles (required):** Sunny Yuan ([@ZichenYuan](https://github.com/ZichenYuan)).
- **Reference app or website / URL (required):** Beacon, an independently branded synthetic job board; interaction patterns reference LinkedIn Jobs (https://www.linkedin.com/jobs/) and public help pages only. No LinkedIn code, assets or data are used.
- **Primary domain (required):** Work & business
- **Secondary domains (optional):** None

## 2. What you plan to build

**✍️ Your answer (required):** A resettable job board where a user searches postings that carry level, workplace type, salary, sponsorship language, source and status; saves searches that produce thin daily alert digests inside the app; applies with a chosen resume and tracks application status in the app; and maintains a profile, resumes and open-to-work settings including who may see them. Company pages show parent and subsidiary relationships. Postings open, repost and close, digests fall due and application statuses change as events on the platform's virtual clock, so a job search can run for weeks.

Initial workflows, each complete end to end including modification, cancellation, confirmation and realistic errors:

1. **Job search and postings.** Search by keywords, location, workplace type (on-site, hybrid, remote), experience level, date posted, company and salary range. A posting page shows title, company, location, workplace type, stated level, salary range (`null` when the employer states none, shown as "Not stated"), description, requirements, posted and reposted dates, applicant count, status (`open`, `paused`, `closed`), source (company career site or aggregated repost), and whether it accepts an in-app application or hands off to an external site. A salary filter excludes postings with no stated salary unless the search sets `include_unstated`. Each posting links to a company page with industry, size, ratings and review count ("no ratings yet" when none), parent and subsidiary relationships and open roles. The catalog contains realistic noise: the same role reposted with a new date, the same role on an aggregated copy with a stale status, titles whose stated level disagrees with the requirements, and sponsorship or clearance conditions buried in the description. Errors: an unknown posting or company returns `not_found`; a search with no match returns an empty list with the filters echoed.
2. **Saved searches and alert digests.** Create a saved search from any filter set with a cadence (daily or weekly); when the task applies the digest-due event, the app produces a thin digest on the alerts page listing only title, company, location and a link, as real alert digests do. A digest covers postings posted or reposted since the search's last digest and never repeats a posting, or another member of its duplicate group, already listed in an earlier digest of that search. Pause, edit, resume and delete: a paused search produces no digests and a digest-due event for it is rejected; resuming starts the next window at the resume time with no catch-up; editing the filters keeps the dedup history; deleting removes the search and its digests. Errors: a cadence outside daily or weekly (`invalid_cadence`), an edit that changes nothing (`no_change`, no write).
3. **Applications.** In-app application as a draft: start it on an open posting, answer screening questions, select a resume version, then submit; each answer or resume change raises the draft's `content_version`, and submit must name the draft and the `content_version` the user approved, so an edit after approval returns `draft_changed`. A draft is `draft`, then `submitted`, or `discarded` by the user, or `expired` 72 virtual hours after it was started, evaluated when an operation runs. A submitted application moves through `submitted`, `viewed`, `in_review`, and ends `rejected` or `offer`, or `withdrawn` by the user. External applications hand off and are recorded as `applied_externally` with a user-entered date; the record is self-reported, implies nothing about the employer, and can be corrected or withdrawn locally. Errors: a closed or paused posting (`posting_closed`), a second application on the same posting or its duplicate group (`duplicate_application`), a missing required answer (`answer_required`), a resume over the limit (`resume_too_large`), an expired draft (`draft_expired`).
4. **Profile, resumes and open-to-work.** Profile with headline, experience, skills, location and languages; several resumes, each an immutable version with filename, MIME type, bytes and SHA-256, with one default; open-to-work preferences (titles, locations, workplace types, start date) with a visibility setting (`off`, `recruiters_only`, `recruiters_except_current_employer`, `public`) that can hide the signal from the current employer's recruiters; profile-view counts. Errors: deleting the default resume or one referenced by an open draft or a submitted application (`resume_in_use`), an upload outside PDF or plain text (`unsupported_type`), a profile update that changes nothing (`no_change`, no write).

Value for personal-agent tasks: a career move is one of the most personal decisions an agent can help with. The right posting depends on goals, true level versus title, location and sponsorship constraints, a salary floor, a current employer that must never see the search, and companies the user has already applied to or sworn off. The author's reviewed PersonalAgentEval cases supply the downstream task submitted alongside this proposal as a linked Task PR: a daily job scan tuned to the user's goals and level.

## 3. Potential app connections

- **Internal personal apps (required):** Files 1.0.0, optional, used by workflows 3 and 4 on the agent's side only: Files has no messaging receiver and Beacon has no client for other Apps, so the agent reads a resume's metadata with `files.get` and its original bytes, MIME type and SHA-256 for one immutable version with `files.read(id, number)`, then calls `resumes.upload` with those bytes and a `source` reference (`{"app_id":"files","file_id":"...","version_number":n}`); Beacon stores the bytes and SHA-256 as its own immutable resume version and records which version each application used. Career notes are read by the agent with `files.read` as separate calls; Beacon has no notes concept and no Notes integration is implied. A denied or missing file is Files' own error to the agent, and Beacon sees nothing. Mail: None. Calendar: None. Contacts: None.
- **Other apps and websites (required):** Company career sites are represented inside the environment as external-application handoffs that produce a self-reported local record; a standalone career-site environment is deferred.

### Integration details

- **Operations and access (required):** Agent-facing MCP operations, each declared read or write in `tools.json`. Reads: `jobs.search`, `jobs.get`, `jobs.similar`, `companies.get`, `companies.subsidiaries`, `saved_searches.list`, `alerts.list`, `applications.list`, `applications.get`, `resumes.list`, `resumes.get` (one version's filename, MIME type, base64 bytes and SHA-256), `profile.get`, `open_to_work.get`. Writes: `saved_searches.create`, `saved_searches.update`, `saved_searches.pause`, `saved_searches.resume`, `saved_searches.delete`, `applications.start` (stores a draft), `applications.answer`, `applications.select_resume`, `applications.submit`, `applications.discard`, `applications.withdraw`, `applications.record_external`, `applications.update_external`, `resumes.upload`, `resumes.set_default`, `resumes.delete`, `profile.update`, `open_to_work.set`. That is 31 operations. Gated writes: `applications.submit` requires the draft ID and the approved `content_version`; `profile.update` and `open_to_work.set` carry the exact patch. Whether the agent may call each is decided by the task policy's allow-list and per-tool `ids` and `fields` constraints, which Core enforces. A fixture flag `require_user_confirmation` (default off) adds a user decision to the three gated writes. With the flag off they commit at once. With the flag on, the same call is a *preparation*: a successful write that stores a pending change and returns a result with `outcome: "approval_required"`, a `change_id`, what was prepared (for `applications.submit` the draft ID, its `content_version`, the selected resume version and its SHA-256; for `profile.update` and `open_to_work.set` the exact patch and the target's current version) and an `expires_at` (the draft's own expiry, or 72 virtual hours after preparation for a patch). The application, profile and settings themselves do not change. Core treats the preparation like any successful write: the version advances and a repeated `request_id` returns the same receipt. A new preparation on the same draft or target replaces its earlier pending change, so at most one exists per target. The decision is the `user.confirmed` event, applied by Infra through `env.apply_event` with the current version read from `env.snapshot`; its handler commits the prepared write only if the App's own guards still hold (see the confirmation sequence below), because the Core version has always advanced by then and cannot serve as the guard. The package therefore runs with no user harness; the flag stays off for `app:verify` and for tasks that script no decision. Agent-facing pages (job search, posting, company, saved searches, alerts, applications, application form, profile, resumes) are App-owned `gui/index.html` and `gui/src/app.js`, declared through the optional `pale.web` extension in `contribution/gui.json` and served by the public business Web Host over the Agent MCP connection; GUI actions call the same business tools under the same policy and approval checks, and the model-side computer-use adapter is a platform component. Platform-facing operations, never listed on Agent connections: `env.load_seed`, `env.apply_event`, `env.reset`, `env.snapshot`, and the host-provided `env.advance_time`.
- **State and lifecycle (required):** App state (companies with relationships, the postings catalog with duplicate groups) is separated from account state (profile, resume versions with their default, saved searches with their digest history, applications with status timelines and the resume version used, open-to-work settings, profile-view counts) and run state (application drafts, pending changes with their `change_id`, target, recorded content and expiry, receipts, event log). All account state is seedable through the seed schema, so a task can load prior applications with statuses and timelines, earlier digests, a default resume and a visibility setting as history. The clock is Core's `ctx.virtual_now`; draft expiry and digest windows are evaluated when an operation or event runs, and the App keeps no clock or scheduler of its own. `validateSeed` rejects a posting closed before it was posted, a posting or application that names an unknown company, posting or resume, a duplicate group whose members differ in company, a digest that lists a posting outside the catalog, and duplicate IDs; a seeded resume without bytes is `invalid_seed`. Every write carries Core's `request_id` and the caller's `expected_version`: a repeated `request_id` returns the stored receipt with no second effect, and a stale `expected_version` is rejected before the handler runs, so the agent re-reads and retries. In addition, `applications.submit` on a draft whose `content_version` moved returns `draft_changed`, and on a posting that closed since the draft returns `posting_closed`. Reads cannot change business state, and a refused write has no business effect: a refused submit leaves the draft as it was. Reset restores this App instance's loaded baseline, including seeded history, and clears drafts, pending changes, receipts and the event log; business-state equality for the reset check is the canonical JSON of App and account state, excluding Core's epoch, audit and receipts, which Core resets on its own; Files is untouched, and any evaluation snapshot is taken with `env.snapshot` before reset.
- **Events and notifications (required):** Accepted events, applied by Infra with `env.apply_event`, with the handler reading the event's `at` as the current time; effects and one example each are in the table below. Published notifications: None; digests and status changes are shown inside the app on the alerts and applications pages, and both `messaging.publishes` and `messaging.receives` are empty. Nothing fires when the clock advances: a digest is produced only when the task applies `alerts.digest_due`, and a draft is found expired only when an operation runs after its deadline. Task scenarios decide when events occur.
- **Shared data and dependencies (required):** Stable IDs for the person (the run binding's `person_id`), account, company, posting, duplicate group, saved search, digest, application, draft, resume version and change. The postings catalog (1,500–3,000 postings per fixture) is JSON business state, not media: fixtures total under 10 MB of JSON. Media are separate: each fixture's asset bundle holds 3 seeded resumes (PDF or UTF-8 text, under 150 KB each) and at most 10 script-drawn PNG icons, under 1 MiB decoded in total; company logos are not stored assets, the pages render an initial-letter tile. A resume uploaded at run time is PDF or plain text, at most 1 MiB (the maximum `files.read` returns), at most 10 resumes per account, held in account state; `resumes.upload` rejects a mismatched SHA-256 with `checksum_mismatch`. The package runs on its own with only the shared runtime (Core and Messaging) and its own fixtures: `app.json.dependencies` is empty, and Files 1.0.0 is an optional run-assembly connection, not a package dependency. The linked Task #23 reads the user's career note from Files, so its run assembly enables Files for the agent. No external service at run time.

#### Accepted events

| Event | Effect on business state | Example (`{event_id, at, operation, payload}`) |
| :--- | :--- | :--- |
| `jobs.posted` | Adds an `open` posting to the catalog with the payload's fields; joins the named duplicate group or starts one; the posting becomes eligible for the next digest of any matching saved search. | `{"event_id":"evt-3001","at":"2026-12-06T09:15:00-08:00","operation":"jobs.posted","payload":{"posting_id":"job-4471","company_id":"co-helix","title":"Senior Inference Engineer","level":"senior","workplace":"on_site","location":"Seattle, WA","salary_range":null,"source":"career_site","accepts_in_app":true,"duplicate_group_id":"dg-helix-infer-2"}}` |
| `jobs.reposted` | Sets the posting's reposted date to `at` and resets its applicant count; status stays `open`; the posting is not listed again in a digest of a search that already listed it or a member of its duplicate group. | `{"event_id":"evt-3002","at":"2026-12-05T08:00:00-08:00","operation":"jobs.reposted","payload":{"posting_id":"job-4102"}}` |
| `jobs.closed` | The posting becomes `closed`; open drafts on it return `posting_closed` at submit; existing applications keep their status. | `{"event_id":"evt-3003","at":"2026-12-09T18:00:00-08:00","operation":"jobs.closed","payload":{"posting_id":"job-4102","reason":"filled"}}` |
| `jobs.paused` | The posting becomes `paused` (or `open` again when `paused: false`); submit returns `posting_closed` while paused; digests omit paused postings. | `{"event_id":"evt-3004","at":"2026-12-07T12:00:00-08:00","operation":"jobs.paused","payload":{"posting_id":"job-4388","paused":true}}` |
| `jobs.salary_updated` | Replaces the posting's salary range (or sets it to `null`); a saved search with a salary filter re-evaluates the posting at its next digest; no digest entry is repeated. | `{"event_id":"evt-3005","at":"2026-12-08T10:00:00-08:00","operation":"jobs.salary_updated","payload":{"posting_id":"job-4471","salary_range":{"min":185000,"max":225000,"currency":"USD","period":"year"}}}` |
| `alerts.digest_due` | For the named saved search, builds one digest of postings posted or reposted after the search's last digest and up to `at` that match its filters, excluding any posting or duplicate-group member listed in an earlier digest of that search; sets the search's last digest time to `at`; an empty window produces an empty digest; a paused or unknown search is rejected with `search_paused` or `not_found` and nothing changes. | `{"event_id":"evt-3006","at":"2026-12-02T07:00:00-08:00","operation":"alerts.digest_due","payload":{"saved_search_id":"ss-infer-senior"}}` |
| `applications.status_changed` | Moves a submitted application forward along `submitted`, `viewed`, `in_review`, `rejected` or `offer` and appends a timeline entry at `at`; a step backwards or a change on a withdrawn or self-reported application is rejected with `invalid_transition`. | `{"event_id":"evt-3007","at":"2026-12-06T16:40:00-08:00","operation":"applications.status_changed","payload":{"application_id":"app-2091","status":"rejected","note":"Position filled internally."}}` |
| `profile.viewed` | Increments the profile-view count and records the viewer's company and role category; with visibility `recruiters_except_current_employer`, a view by the current employer's recruiter is rejected with `not_visible` and not counted. | `{"event_id":"evt-3008","at":"2026-12-10T11:20:00-08:00","operation":"profile.viewed","payload":{"viewer_company_id":"co-northwind","viewer_role":"recruiter"}}` |
| `companies.updated` | Replaces the named company fields (for example adds a subsidiary or changes the rating); postings keep their company reference, and a subsidiary added under the current employer extends the visibility rule to its recruiters. | `{"event_id":"evt-3009","at":"2026-12-11T09:00:00-08:00","operation":"companies.updated","payload":{"company_id":"co-northwind","add_subsidiaries":["co-northwind-labs"],"rating":4.1,"review_count":312}}` |
| `user.confirmed` | Commits the pending change named by `change_id` if its guards hold (confirmation sequence below): `applications.submit` creates the application with the recorded resume version; `profile.update` and `open_to_work.set` apply the recorded patch. The pending change is removed on commit, so a second event naming it is rejected with `unknown_target`, as is any unknown ID. A failed guard rejects the event with `draft_changed`, `posting_closed`, `draft_expired`, `duplicate_application` or `settings_changed`, and Core leaves business state unchanged, the pending change included. | `{"event_id":"evt-3010","at":"2026-12-12T19:05:00-08:00","operation":"user.confirmed","payload":{"change_id":"chg-submit-app-2117"}}` |

#### Confirmation sequence (`require_user_confirmation` on)

`v` is the Core version the agent read before the first call. The guards are the App's own checks on the pending change, never the Core version: every successful write, including the preparation itself, advances the version, so the version the agent passed at preparation is stale by the time the decision arrives. A rejected decision is a failed call, and Core discards everything it attempted, so the application list, drafts, profile, settings and the pending change are exactly as before.

| Step | Call or event (version passed) | Result | Business state afterwards |
| :--- | :--- | :--- | :--- |
| Preparation | `applications.submit` on draft `d-1` at `content_version` 3 (`expected_version` `v`) | Success: `outcome: "approval_required"`, `change_id: "chg-1"`, the recorded draft, content version, resume version and SHA-256, `expires_at` | Pending change `chg-1` stored; no application; draft unchanged; Core version `v+1` |
| Replay | The same call with the same `request_id` | The stored receipt | Unchanged |
| Second preparation | `applications.submit` on `d-1` with a new `request_id` (`v+1`) | Success: `outcome: "approval_required"`, new `change_id: "chg-2"`; `chg-1` removed | One pending change for `d-1`; Core version `v+2` |
| Edit after preparation | `applications.answer` on `d-1` (`v+1`) | Success; `content_version` becomes 4 | `chg-1` still stored, now stale; Core version `v+2` |
| Decision, clean | `user.confirmed {change_id: "chg-1"}` through `env.apply_event` (current version from `env.snapshot`) | `committed`, `outcome: "submitted"`, the application ID | Application `submitted` with the recorded resume version and SHA-256; timeline entry at the event's `at`; `chg-1` removed; Core version advances |
| Decision after the edit | `user.confirmed {change_id: "chg-1"}` (current version) | Rejected: `draft_changed` | Unchanged: no application, draft `d-1` intact at content version 4, `chg-1` still stored and still stale; the next preparation replaces it |
| Decision on a closed or paused posting | `user.confirmed {change_id: "chg-1"}` | Rejected: `posting_closed` | Unchanged |
| Decision after expiry | `user.confirmed {change_id: "chg-1"}` after `expires_at` | Rejected: `draft_expired` | Unchanged |
| Decision with a twin | `user.confirmed {change_id: "chg-1"}` when an application already exists in the posting's duplicate group | Rejected: `duplicate_application` | Unchanged |
| Decision on a moved target | `user.confirmed {change_id: "chg-3"}` for a `profile.update` or `open_to_work.set` prepared at profile version 7 while the profile is now at 8 | Rejected: `settings_changed` | Unchanged |
| Second decision | `user.confirmed {change_id: "chg-1"}` after `chg-1` committed, or any unknown ID | Rejected: `unknown_target` | Unchanged |
| Cancel | `applications.discard` on `d-1` | Success | Draft `d-1` and its pending change removed |
