## 2. What you plan to build

**✍️ Your answer (required):** A complete customer-side repair workflow for clothing and household textiles, where “the same item” is not interchangeable with “a replacement that looks the same.” The environment tracks physical item/part identity, successive estimates and work tickets, material disposition, custody and actual return. It supplies facts and executable choices; task authors, not the service, decide which choices fit a particular person's history.

Six core workflows:

1. **Intake and identity:** register an existing garment/textile, attach original synthetic damage views, identify parts and treatment goals, choose assessment-only or a scoped request. A matching fabric/color does not imply shared provenance.
2. **Assessment and offers:** retrieve versioned quotes with method, target parts, price components, completion window and disposition options. Revise a brief, request alternatives, decline or hold. A newly issued quote supersedes its predecessor without silently inheriting acceptance.
3. **Production authorization:** accept a quote and inspect a separately versioned work ticket. Amend wrong parts/methods or approve the current scope. Production start is an explicit scenario event conditioned on a valid approval; a payment hold or draft ticket is not consent. An approved work order may still be held/cancelled before production.
4. **Changes during repair:** inspect a revised assessment, accept a revised scoped ticket or decline and request return unrepaired. Track work already performed and disclosed nonrefundable charges. No automatic enlargement of treatment, spend or disposal rights.
5. **Custody and delivery:** distinguish label creation, carrier collection, workshop receipt, work complete, dispatch and actual household receipt. Return removed originals as separately inventoried objects when instructed; amend a return address/window while permitted.
6. **Closeout and correction:** inspect invoices, settled refund versus promise, missing-part reports and resolution receipts. Close a job or reopen a missing-material case. An invoice alone proves neither correct treatment nor delivery.

### Integration details

- **Operations and access (required):** Both an original GUI and MCP business tools use one domain service. Six GUI areas: item/part inventory; intake; quote comparison; ticket approval/change; custody/return; invoice/case history. Target 22 business operations: item list/get, intake create/update, attachment describe, quotes list/get, quote request/accept/decline, ticket get/amend/approve/hold/cancel, return book/update, status get, invoice get, case open/get/close. Access-controlled Infra operations seed/reset/snapshot, advance virtual time and inject assessment/production/custody/payment events; none are advertised to the agent. The 22 names are planned contracts, not existing tools. Material disposition is an explicit acceptance field; the service permits property-owner disposal if selected, allowing a task's stricter “never discard” rule to be meaningfully tested.
- **State and lifecycle (required):** Separate run/account/item/part/job IDs; immutable occurrence-timestamped history and current-version pointers. Quotes bind item, part IDs, method, cost components and expiry; approvals bind exact quote/ticket versions. Mutations require expected version and idempotency key; same key/payload returns the original result, changed payload conflicts, stale writes disclose the current version without mutation. No automatic inference that approving one item approves another. Before-start cancellation differs from after-start hold/return; fees and completed work remain visible. Snapshot includes event cursor, account bindings, receipts, pending deliveries and original-material inventory. Reset scope is app_instance: restore this Mendline instance to its loaded baseline and invalidate its old handles/pending notifications; never clear Mail, Notes or Calendar. A task reset separately coordinates every participating App. Restoring must not repeat charges, disposal or production. Already delivered Mail is not undone by Mendline reset; task restoration must align snapshots and delivery cursor. Retain pre-reset audit evidence, correlate App receipts with Core read/denial records and agent call IDs, and count a retried committed effect once.
- **Events and notifications (required):** Scenario-owned ordered events include assessment-revised, production-started/completed, carrier-collected/received/delivered, charge-settled/refund-settled and case-resolution. Each uses the event_id/at/operation/payload envelope with an offset-aware at, a job reference, expected version and documented preconditions; the App retains the represented occurrence time. Production requires an approved matching ticket; duplicate/out-of-order events cannot manufacture a finished job. Example: assessment-revised(J12,v2) emits a notice carrying job/quote/version identifiers to the bound Mail account. Local outbox commit, Mail delivery and customer acceptance are three distinct states. Notification failure leaves the business record discoverable; it never implies rollback. No status read advances time or performs production. Expiry is evaluated against Core virtual_now at a business call or explicit Infra time advancement; no wall-clock timers. Example event: {"event_id":"assessment-12-v2","at":"2026-12-03T09:00:00-05:00","operation":"assessment.revise","payload":{"job_id":"J12","expected_version":1,"quote_version":2}} invalidates the earlier offer and creates a new unaccepted quote; only Infra can invoke it.
- **Shared data and dependencies (required):** Package runs independently with the shared runtime and pinned declared Mail/Notes/Calendar dependencies for integration demonstrations; App-only mode runs its domain service with a labeled disabled notification adapter. Original SVG/PNG item diagrams, UTF-8 descriptions and small JSON inventories are packaged locally with hashes; under 20 MB initial runtime media. No real faces, copyrighted garment photographs, accounts or private forum posts. No Files, Contacts, payment, shipping or sibling-environment dependency is claimed. Notes/Calendar links are record IDs used by the agent, not undeclared server-side reads.
