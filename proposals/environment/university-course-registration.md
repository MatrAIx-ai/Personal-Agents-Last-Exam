## 2. What you plan to build

**✍️ Your answer (required):** A resettable university enrollment portal supporting course and eligibility inspection, enrollment and withdrawal, waitlists with expiring seat offers, and immediate or waitlisted course swaps that preserve the original enrollment until the replacement succeeds. Personal-agent decisions depend on the student's academic record, current timetable, credit allowance and changing preferences, while the environment records the actual academic consequences of each action.

Initial scope is one fictional university and one term, with four end-to-end workflows:

1. **Inspect courses and eligibility.** Search the catalog; inspect section times, capacity, credits, completed-course prerequisites, registration windows and linked lecture/lab requirements. Read the authenticated student's academic record, enrollments and waitlists. Eligibility results identify visible rule failures; the agent cannot edit academic records or grant itself an exception.
2. **Enroll or withdraw.** Preview the proposed schedule and credit changes, then explicitly confirm or discard them. A preview is a read: it stores nothing and returns the state version it was computed from. Confirmation rechecks current eligibility, availability, permissions and deadlines. Withdrawal identifies the exact enrollment and any pending swap it would invalidate. Errors such as a full section, missing prerequisite, credit overflow, conflicting time or stale preview leave enrollment unchanged.
3. **Join and manage a waitlist.** Join or leave a queue for a specific target lecture/lab bundle; inspect the student's own rank and notices. When capacity becomes available, eligible entries receive a time-limited offer in FIFO order. The student can accept or decline; expiration releases the hold. A waitlist position or offer is not enrollment, and a notice alone does not accept an offer.
4. **Swap without losing the existing place.** Preview and confirm a replacement that is immediately available, or attach a waitlist entry to an existing enrollment. Acceptance checks the resulting timetable and credits after replacing the old bundle. The replacement and withdrawal commit together; any failure preserves the original place. A pending swap can be cancelled without dropping the original course.

The planned UI has six views: catalog, course detail, academic record and rules, current schedule, waitlists and offers, and change review/activity receipts. All material policy facts and the effects of a proposed write are available through the UI and the corresponding agent-facing interface.

### Enrollment semantics to validate

- A lecture and any required lab form one enrollment bundle. Every required section must have capacity; course credits count once and duplicate enrollment in the same course is disallowed. A swap reuses the student's occupied seat in any section shared by the old and new bundles, reserving only net-new sections. Commit transfers the bundle atomically without double-counting the shared lecture seat. For each section, enrolled occupants plus active additional holds cannot exceed capacity. The initial prerequisite model uses completed courses, not cross-course co-requisite chains or a full degree-audit engine.
- Eligibility for an ordinary enrollment uses the resulting schedule; swap eligibility uses the schedule with the named original bundle replaced. Waitlist entries count toward neither enrolled credits nor the timetable. An offer reserves capacity but is not an academic enrollment.
- Queue eligibility is rechecked when an offer is issued and accepted, and after relevant occupancy, enrollment, eligibility or offer-state changes. Entries competing for a shared section use a common join order with a stable tie-breaker. An ineligible entry remains queued with its own visible blocking reason, without holding capacity; later eligible entries may receive an offer. Rejoining the same target queue returns the existing entry without changing its rank. Changing sections of an already enrolled course requires a swap. A cancelled, declined or expired entry leaves the queue. One pending swap per original enrollment is allowed. Withdrawing the original explicitly cancels its linked pending swap and releases any target hold; it never converts that request into an unconditional enrollment.
- Every write carries `request_id` and `expected_version` from its read or reviewed preview. An intervening state commit or strictly later clock advance causes `stale_version`; confirmation then requires a fresh read and, where applicable, a new preview before reconfirmation. Within an epoch, identical retries (including the original version) return the original result with `duplicate: true`; reusing the ID with changed arguments causes `idempotency_conflict`. Writes/events commit atomically, preventing overbooking and partial swaps. A committed write returns `status: committed`, the new `version` and an App receipt ID visible in activity. Failed acceptance preserves the original enrollment; an otherwise live offer remains held until accepted, declined, cancelled or expired.
- Platform events can change a section's meeting time and create a conflict in an existing schedule. Such conflicts are visible and attributed to the event; the environment does not silently drop a course. Agent changes must not introduce new conflicts and may repair existing ones; unrelated existing conflicts do not block an action that reduces conflicts. Enrollment restrictions, personal preferences and task success criteria remain separate: a legally enrollable course may still be wrong for a particular student.

- **State and lifecycle (required):** One App instance binds one student account/run; synthetic competitors occupy the same ledger through Infra events. App data separates catalog/policies, academic records and run records: section versions, enrollments, queue order, offers/holds, notices and activity receipts. Core owns the clock, epoch/revision, request/event receipts and audit; the App adds no clock or deduplication store. `env.load_seed` loads account/history; `env.reset` restores that baseline without touching other Apps. Students see their own record/rank, not competitors' records. Writes recheck authority/versions and atomically protect capacity, credits and swaps. Fixtures define timezone/order; offers expire before confirmation at the exact deadline.
  - **Live continuation (bounded checkpoint):** The author supplies a package-local continuation integration-test script under `tests/`, using existing Agent and Infra connections for this App/account on compatible pinned versions. It is delivered in M4 within the existing Validation and reset budget of 3–4 person-days, separate from the App-only `tests/harness.cjs` context. Pause calls/events and resolve every in-flight or unacknowledged write before capturing `env.snapshot` and the script's event cursor together. Load snapshot `data`, `binding`, `policies` and `virtual_now` into the same or a fresh instance with the same active profile (`load_seed` does not select it), using the target version and a new load request ID; retries retain identical arguments. The seed schema/validator must support live offers/holds, pending swaps, queue order, notices/activity, business IDs and collision-free ID allocation; continuation tests verify this. Core clears receipts/audit and starts a new epoch. The script closes and reinitializes its controlled test clients, discards their cached versions and pending inputs, and resumes only its unprocessed input sequence; new actions read target versions and use fresh IDs, with retries within that epoch. It records the checkpoint clock/cursor and submits only unapplied events, including expiry deadlines, against Core's clock. This guarantee covers the script's own test sessions and replay sequence; it does not intercept arbitrary requests at platform or browser entry points. Reset then returns to the checkpoint; initial reset reloads the original seed and resets the script's cursor. This bounded business continuation excludes unresolved requests, historical request-result restoration and crash recovery; no platform restore operation is needed.

- **Events and notifications (required):** Three Infra operations use the App prefix. `occupancy.change` models synthetic enrollment/withdrawal, queue join/leave or offer resolution in the shared ledger, then rechecks affected queues; withdrawal atomically releases the complete bundle, without changing capacity limits. `section.reschedule` changes meetings, rechecks queues and records notices linking old/new section versions; conflicts remain visible without dropping enrollments. `offers.expire` expires due offers, releases holds and rechecks queues. Handlers use `ctx.virtual_now` (`event.at` during application). Read/write guards reject offers at/after expiry and enforce registration windows; reads never mutate state. `env.advance_time` invokes no handler: before advancing to T, Infra processes due events chronologically, including every offer deadline up to T, with expiry before same-time confirmations. Task scenarios set external events and policy fixtures; expiry follows issue time plus the policy window. Infra reads deadlines from `env.snapshot` and assigns stable event IDs; the App has no scheduler. Identical event retries within an epoch return Core's original receipt, without duplicate notices; continuation uses the cursor rule above. No cross-App messages. Example envelopes with a 24-hour offer window:

```jsonl
{"event_id":"evt-0007","at":"2027-01-11T09:30:00-05:00","operation":"university-course-registration.occupancy.change","payload":{"enrollment_id":"enr-synthetic-017-cs240","occupant_ref":"synthetic-017","change":"withdraw"}}
{"event_id":"evt-0012","at":"2027-01-12T08:00:00-05:00","operation":"university-course-registration.section.reschedule","payload":{"section_id":"sec-math221-lec1","meetings":[{"days":["TUE","THU"],"start":"14:30","end":"15:50"}]}}
{"event_id":"evt-0015","at":"2027-01-12T09:30:00-05:00","operation":"university-course-registration.offers.expire","payload":{}}
```

In this fixture, `evt-0007` withdraws the synthetic student's complete CS240 bundle, freeing the last needed lab seat for the first eligible entry; its offer expires at `2027-01-12T09:30:00-05:00`. `evt-0012` moves an enrolled MATH221 section into another enrolled course's time, producing a visible conflict and notice. With no intervening acceptance, `evt-0015` expires the CS240 offer, releases its hold and offers the bundle to the next eligible entry.
