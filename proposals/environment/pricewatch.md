## 2. What you plan to build

**✍️ Your answer (required):** Build a small MCP App in which a personal agent reads exact product identities and account-eligible checkout quotes, registers a constrained price watch, inspects matching offer candidates, and pauses or revises that watch when the user's intentions change. Incoming scripted quote changes evaluate the rules the agent actually saved. The App preserves why a candidate became available, was withdrawn or expired; it never decides which product the person should want.

This supports #207's formula-specific repurchase watch and later withdrawal after a new personal diary entry. The same operations can support a household's approved food variant or a specific replacement consumable. Tasks supply histories, preferences and events; those personal decisions, story dates and gold answers are not App business logic. #207 is a downstream task, not a dependency required to launch this App.

### First-version workflows and boundaries

| Workflow | Success and observable result | Error or incomplete case |
| :--- | :--- | :--- |
| Inspect products and quotes | Read released current quotes with canonical product/variant, pack, quantity, seller, currency, item/shipping/tax/eligible-discount lines, validity and provenance. | Missing tax, unresolved variant, unknown eligibility, wrong size/currency or expired quote is reported explicitly and cannot produce a qualifying candidate. | Create or modify a watch | Persist one account-local logical watch with exact identity/pack, one specified quantity, allowed sellers and inclusive-price ceiling. An existing logical target is updated, not silently duplicated. |
| Observe a qualifying price event | A trusted quote episode under a saved active rule creates a candidate linked to the watch revision, quote and event. Replaying that episode creates no duplicate. | Paused watch, ineligible terms or incomplete payable quote creates no candidate. Reusing an event ID with conflicting content rejects the event without changing business records. |
| Pause, resume or change criteria | Pause atomically withdraws currently available candidates. Resume opens a new activation; a material criteria change increments the rule revision and, if active, also opens a new activation. Both re-evaluate current quotes, without rewriting earlier candidate history. | An unchanged-rule retry is a no-op for business transitions; a denied write leaves the previous rule and candidates intact. Resume is an explicit agent action, not an automatic response to another price drop. |
| Inspect current validity and history | Read current watches and candidate/transition history with the simulated as-of time. ### Integration details

- **Operations and access (required):** Proposed single App ID `pricewatch`, installed at `apps/pricewatch/`, subject to maintainer naming/scope review. Agent access is stdio MCP through the shared runtime, with four business operations: `pricewatch.offers.list` reads released current identities/quotes; `pricewatch.watch.upsert` creates or revises a logical rule and its `active`/`paused` state; `pricewatch.watch.list` lists the account's watches and summaries; `pricewatch.watch.get` reads one rule, candidates and retained transitions. Lists are bounded/paginated and get provides inspectable history. All writes require the public Core `expected_version` and `request_id`. At the reviewed runtime 1.6.0 / Core API 1.2.0, `expected_version` is `{epoch, revision}` for the App state. An exact same-ID/same-arguments retry returns its original receipt; changing any argument, including the version, requires a new request ID. After a stale-version rejection, re-read and submit the revised action under a new request ID. Business no-op means no rule/candidate transition, not a promise that Core revision/audit is unchanged. Payload schemas will be checked against that pinned contract before implementation. The agent cannot set account identity, the clock, quote sources, eligibility facts or management events. Infra alone uses existing `env.load_seed`, `env.apply_event`, `env.advance_time`, snapshot and reset operations. First-version Agent GUI/CUA and a separate HTTP service are out of scope; any review rendering reads the same state and is not advertised as a new Agent interface.

- **State and lifecycle (required):** Core owns run/account binding, authorization, its version envelope, commits, write conflicts and transport retry behavior. A Core `expected_version` is the current App-state version, not a per-watch counter. App-owned `watch_revision` and `activation_id` separately identify rule/state history. Watch keys are unique within the authenticated account; candidate identity is server-derived from the logical watch, rule revision/activation and offer episode. No business record crosses run/account boundaries. Initial seeds can contain neutral catalog, account terms, quotes and coherent watch/candidate history; validation rejects dangling references, inconsistent totals, conflicting duplicate IDs and impossible transitions. Reset restores the loaded data/time baseline and clears post-seed effects according to Core's contract; a snapshot is inspection evidence, not a promise of arbitrary checkpoint restore.

  Rules use exact opaque product-family and variant-revision IDs, pack amount/unit, requested quantity, allowed seller IDs, currency and a ceiling in integer minor currency units. Price arithmetic is item total + quoted shipping + quoted tax − eligible discount, with each discount applied once. There is no currency conversion or tax inference. Eligibility comes from trusted released account/quote facts, never a client-supplied assertion of membership. Missing facts remain unknown, not zero or eligible. Mutable rule records contain no arbitrary health notes, personalization explanation or medical fields.

  A material criteria change increments `watch_revision`, withdraws old available candidates with a reason and, when the watch is active, opens a new activation and re-evaluates current quotes. A paused watch may save revised criteria but stays paused with no candidate creation until explicit resume. Pausing withdraws available candidates atomically but retains their earlier availability and source. A paused price event may update market quotes but cannot create a candidate or reactivate the watch. Explicit resume creates a new activation and may create a new candidate for a currently valid quote; the old withdrawn/expired candidate is not rewritten as if it had always remained active. A same-rule write/retry produces no duplicate transition or candidate. An offer episode is an immutable complete quote, including its price/terms/validity: the same episode ID with different content is rejected even under a new transport/event ID. A price or term change uses a new episode ID, with explicit `supersedes` references when it replaces an earlier quote. Supersession/revocation withdraws earlier available candidates, retains the immutable old quote and never reactivates it on replay. Candidate uniqueness includes this immutable episode ID, watch revision and activation. Distinct concurrent offers may coexist; an unchanged episode produces no extra candidate for the same logical watch, rule revision and activation; it may produce a new candidate after a genuine rule revision/new activation, with the old record still retained.

  Candidate stored states are `available_in_app`, `withdrawn` and `expired`. Each read also reports effective status at `ctx.virtual_now`: `now >= valid_until` is expired regardless of whether a later maintenance event has persisted that transition. Read-only handlers never mutate business history. Tasks/Infra can inject an App-owned `offer.expire_due` event through `env.apply_event` to record due expiry transitions; they schedule it using the existing runner, not an App timer. Documentation/tests distinguish computed expiry from a committed transition. Watch/candidate views expose App source/transition IDs, Core state version and quote validity so traces and administrative snapshots can be joined without inventing a read receipt.

- **Events and notifications (required):** Accept App-owned quote upsert/revocation and due-expiry operations via Infra's existing `env.apply_event`; exact event schema/operation spelling is finalized with the Core contract. Quote events carry stable event/offer-episode IDs, account scope, exact product/pack/seller/quantity/currency, checkout lines, eligibility evidence, validity interval and source provenance. Trusted simulated event/application time controls release; no agent call can see a future quote or advance time. V1 exposes quotes only when their validity has begun: seeds/events reject a quote whose `valid_from` is later than the trusted current/event time. A future sale is kept in the runner's unreleased event data and injected when it starts, rather than preloaded and silently expected to match after clock advancement. Future-start/pre-announced quote publication is outside v1. Due expiry events are separately supported as described above. Repeated identical events are business-idempotent independently of transport request IDs; conflicting reuse rejects. New offer episodes can produce distinct candidates, while a superseded/revoked/expired quote cannot remain an effective match. The task owns chronological event ordering and session timing; this App supplies business effects only. No Messaging `publishes` or `receives` capability is declared in v1. A stored `available_in_app` candidate proves only that App state exists; an actual assistant notice is established by a separate task transcript. There is no phone push, read receipt, purchase, reservation or external subscription.

### Proposed event examples

These are proposed App payloads inside the existing `{event_id, at, operation, payload}` event envelope, not executed traces or a claim that the App schemas already exist. Cases are independent: the expiry example starts from an unrevoked matching candidate. Account scope must match the trusted run binding.

```json
{"event_id":"quote-event-1","at":"2026-12-02T09:00:00-08:00","operation":"offer.quote_upsert","payload":{"account_id":"account-a","offer_episode_id":"filter-quote-1","product_family_id":"filter-family","variant_revision":"R1","pack_amount":1,"pack_unit":"filter","quantity":1,"seller_id":"seller-a","currency":"USD","item_total_minor":2500,"shipping_minor":0,"tax_minor":200,"eligible_discount_minor":0,"eligibility":"eligible","eligibility_source_id":"terms-a-1","valid_from":"2026-12-02T09:00:00-08:00","valid_until":"2026-12-02T10:00:00-08:00","source_id":"synthetic-quote-1","supersedes":[]}}
{"event_id":"revoke-event-1","at":"2026-12-02T09:10:00-08:00","operation":"offer.revoke","payload":{"account_id":"account-a","offer_episode_id":"filter-quote-1","reason":"seller_revoked"}}
{"event_id":"expiry-event-1","at":"2026-12-02T10:00:00-08:00","operation":"offer.expire_due","payload":{"account_id":"account-a"}}
```

Under an active matching filter watch with a USD 30 ceiling, the first event makes one USD 27 candidate available; exact replay makes none extra, while changed content under the same episode ID rejects. The second event withdraws an available candidate with `seller_revoked` and retains its source/history; an unknown episode reference rejects. In the independent expiry case, the third event records the due `expired` transition and leaves no effective available candidate for that quote; an event before expiry does not expire it, and an exact replay creates no duplicate transition. With clock advancement alone to 10:00, the read projection is already non-actionable/expired before this explicit expiry commit. A paused-watch counterpart to the first event produces no candidate. No example carries a personal diary or a desired-product label.
