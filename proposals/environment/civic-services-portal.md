## 2. What you plan to build

**✍️ Your answer (required):** A resettable public-comment portal where a user searches proposed rules (dockets) with open, extended or closed comment periods, reads a rule's summary and supporting documents, drafts and submits a comment under their name or anonymously behind a required acknowledgment, receives a receipt with a tracking number, and follows the comment's status from received to posted. Deadlines, extensions, corrections and status changes run on the simulated clock. An optional workflow adds docket subscriptions that deliver notices to Mail.

Workflows 1 and 2 form the initial scope. Workflow 3 is optional: it is not part of the acceptance baseline and will be built only if design review asks for it. Each delivered workflow is complete end to end, including modification, cancellation, confirmation and realistic errors:

1. **Dockets and documents.** Search dockets by keyword, agency, status and closing date. A docket page shows the agency, the rule summary, supporting documents, the comment period with its opening and closing time in a stated time zone, and a status of open, extended or closed. Extensions and corrections to a rule arrive as events and are shown on the docket page with their dates. Errors: a docket that does not exist, a document that is not yet published.
2. **Public comments.** Draft a comment with validation (length, required fields); choose named or anonymous; review the final text; a required acknowledgment checkbox; submit to receive a receipt with a tracking number. Status moves from received to posted on a schedule, or the comment is returned with a reason. A second distinct submission on the same docket triggers a duplicate warning; a supplemental comment is a separate, labeled flow. Submitted comments cannot be withdrawn, as in the reference. Errors: a closed period, a missing acknowledgment, a submission that repeats an existing draft ID (returns the existing receipt).
3. **Docket subscriptions (optional).** Subscribe to a docket; extension and correction notices are delivered to Mail; list and cancel subscriptions. A closing sends no notice, because nothing fires when the clock advances; the closed status is visible on the docket page.

Value for personal-agent tasks: a public comment is deadline-bound, irreversible once submitted, must carry the user's own reasons rather than generic talking points, and involves identity choices (named or anonymous) and a legal acknowledgment that only the user should approve. The rule can change under the user's feet through extensions and corrections, and the right response to an extension is usually to do nothing. The author's reviewed PersonalAgentEval cases supply the downstream task submitted alongside this proposal as a linked Task PR: submitting a comment from the user's own reasons and closing it out correctly.

## 3. Potential app connections

- **Internal personal apps (required):** Mail 1.3.0, optional, used by workflow 2 and by the optional workflow 3: CivicDesk publishes text notices (receipt, status change and, if workflow 3 is built, extension and correction notices) on `channel.email`, wire `urn:pale:email-message:2`, payload `urn:pale:email-payload:1`, event type `org.pale.mail.notification.v1`, received by Mail's `mail.receive_notification`; the notices carry no files, so the attachments channel is not used. Calendar 1.3.0, optional, reached only by the agent's own tools: Calendar has no messaging receiver, so a deadline reaches the calendar when the agent calls `calendar.create` or `calendar.update`, and CivicDesk sends nothing to Calendar. Files 1.0.0, optional, agent-side only: the agent reads the user's notes with `files.list`, `files.get` and `files.read` when the task policy allows, and CivicDesk has no client for Files. Contacts: None. Newsletters that link to dockets are plain Mail seed data.
- **Other apps and websites (required):** None in the initial scope.

### Integration details

- **Operations and access (required):** App ID `civicdesk`; every tool name carries that prefix, as the runtime registry requires. Agent-facing MCP operations, each declared read or write in `tools.json`. Reads: `civicdesk.dockets.search`, `civicdesk.dockets.get`, `civicdesk.dockets.documents`, `civicdesk.comments.validate` (checks a draft and returns its problems without changing it), `civicdesk.comments.receipt`, `civicdesk.comments.status`, `civicdesk.comments.list_mine`. Writes: `civicdesk.comments.draft`, `civicdesk.comments.submit`; for the optional workflow, `civicdesk.subscriptions.create` and `civicdesk.subscriptions.delete` (writes) and `civicdesk.subscriptions.list` (read). Every write takes Core's `request_id` and `expected_version`: a repeated `request_id` returns the stored receipt, and a stale version is rejected. `civicdesk.comments.submit` is an approval-gated write: it requires `acknowledged: true` in the call, an App-level check, and rejects otherwise; the task policy decides whether the tool is offered at all. Agent-facing pages for the public business Web Host (`gui/index.html` and `gui/src/app.js`, declared through the optional `pale.web` extension): docket search, docket, documents, comment form, review, receipt and my-comments, plus a subscriptions page if the optional workflow is built. The pages expose only agent-authorized tools and carry no reset, history or event controls; there is no separate reviewer console. Infra-only operations, unavailable to the agent: `env.load_seed`, `env.reset`, `env.snapshot`, `env.apply_event`, `env.advance_time`.
- **State and lifecycle (required):** App state (agencies, dockets, documents, comment periods) is separated from account state (drafts, comments, receipts and, optionally, subscriptions) and run state (receipts by `request_id`, event log). The clock is Core's `ctx.virtual_now`; the App keeps no clock of its own. A comment period's opening and closing instants are stored with the docket's IANA time zone, and the period is open, extended or closed according to `ctx.virtual_now` at the moment of a read or write; no event is needed to close a period, and `docket.period_extended` changes the stored closing instant. Comment status moves only through `comment.status_changed` events. Reset reloads the seed and clears drafts; submissions return receipts with tracking numbers; repeating a submit with the same `request_id` or draft ID returns the existing receipt. Duplicate rule, an App business rule: a second submission by the same account on the same docket that is not marked `supplemental: true` returns `possible_duplicate` and submits nothing; marked supplemental, it is accepted and labeled.
- **Events and notifications (required):** Accepted events, applied by Infra with `env.apply_event`, with the handler reading the event's `at` as the current time: `docket.period_extended` (new closing instant), `docket.correction_published` (a correction with its date, shown on the docket page; comments are unchanged), `comment.status_changed` (received to posted, or returned with a reason). Published notifications: send-only on `channel.email` to Mail 1.3.0 as in the example below; `messaging.receives` is empty. CivicDesk commits its own record first and then constructs the notice; the publisher's receipt is recorded in the comment's notice history. A rejected or unknown receipt leaves the comment submitted and is visible in that history; a replay with the same `request_id` returns the stored receipt and publishes nothing. Task scenarios decide when events occur.
- **Shared data and dependencies (required):** Stable IDs for the person (the run binding's `person_id`; one account per instance), account, agency, docket, document, draft, comment, receipt and subscription. Supporting documents are mostly UTF-8 text (`text/plain`) with a few text-based PDFs (`application/pdf`), addressed by asset ID and within the reference profile's limit of 64 assets and 1 MiB of decoded bytes per fixture bundle; docket text is JSON business state, not media. Required package dependency: none; the package runs on its own with runtime 1.6.0 and Core API 1.2.0. Optional connections: Mail 1.3.0 (send-only notices, contract above), Calendar 1.3.0 and Files 1.0.0 (reached by the agent's own tools). No external service at run time.

#### Example notice (comment receipt)

A full CloudEvents 1.0 envelope as Messaging routes it to Mail's `mail.receive_notification`; the `recipient` is a logical person reference that Infra binds to the user's Mail account.

```json
{
  "specversion": "1.0",
  "id": "civicdesk-notice-cmt-0031-1",
  "source": "urn:pale:app:civicdesk:account:acct-dana",
  "type": "org.pale.mail.notification.v1",
  "datacontenttype": "application/json",
  "dataschema": "urn:pale:email-payload:1",
  "time": "2026-12-02T21:14:00-05:00",
  "subject": "cmt-0031-1",
  "data": {
    "channel": "channel.email",
    "recipient": { "kind": "person_ref", "id": "person-dana" },
    "source_object": { "app_id": "civicdesk", "account_id": "acct-dana", "object_type": "comment", "object_id": "cmt-0031-1" },
    "content": {
      "title": "Your comment on docket OCDD-2026-0031 was received",
      "body": { "format": "text/plain", "text": "CivicDesk received your anonymous comment on docket OCDD-2026-0031 on December 2, 2026 at 9:14 PM ET. Tracking number: CDK-2026-0031-00417. Comments are usually posted within three business days; follow the status under My comments." },
      "asset_ids": [],
      "deep_link": { "app_id": "civicdesk", "route_id": "my_comments", "object_id": "cmt-0031-1" }
    },
    "extensions": []
  }
}
```
