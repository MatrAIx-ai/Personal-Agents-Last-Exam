## 2. What you plan to build

**✍️ Your answer (required):** A resettable public-comment portal where a user searches proposed rules (dockets) with open, extended or closed comment periods, reads a rule's summary and supporting documents, drafts and submits a comment under their name or anonymously behind a required acknowledgment, receives a receipt with a tracking number, and follows the comment's status from received to posted. Deadlines, extensions, corrections and status changes run on the simulated clock. An optional workflow adds docket subscriptions that deliver notices to Mail.

Workflows 1 and 2 form the initial scope. Workflow 3 is optional: it is not part of the acceptance baseline and will be built only if design review asks for it. Each delivered workflow is complete end to end, including modification, cancellation, confirmation and realistic errors:

1. **Dockets and documents.** Search dockets by keyword, agency, status and closing date. A docket page shows the agency, the rule summary, supporting documents, the comment period with its opening and closing time in a stated time zone, and a status of open, extended or closed. Extensions and corrections to a rule arrive as events and are shown on the docket page with their dates. Errors: a docket that does not exist, a document that is not yet published.
2. **Public comments.** Draft a comment with validation (length, required fields); choose named or anonymous; review the final text; a required acknowledgment checkbox; submit to receive a receipt with a tracking number. Status moves from received to posted on a schedule, or the comment is returned with a reason. A second distinct submission on the same docket triggers a duplicate warning; a supplemental comment is a separate, labeled flow. Submitted comments cannot be withdrawn, as in the reference. Errors: a closed period, a missing acknowledgment, a submission that repeats an existing draft ID (returns the existing receipt).
3. **Docket subscriptions (optional).** Subscribe to a docket; extension, correction and closing notices are delivered to Mail; list and cancel subscriptions.

Value for personal-agent tasks: a public comment is deadline-bound, irreversible once submitted, must carry the user's own reasons rather than generic talking points, and involves identity choices (named or anonymous) and a legal acknowledgment that only the user should approve. The rule can change under the user's feet through extensions and corrections, and the right response to an extension is usually to do nothing. The author's reviewed PersonalAgentEval cases supply the downstream task submitted alongside this proposal as a linked Task PR: submitting a comment from the user's own reasons and closing it out correctly.

## 3. Potential app connections

- **Internal personal apps (required):** Mail: receipts and status notices arrive here, newsletters in Mail link to dockets, and the optional subscription workflow delivers extension and correction notices. Calendar: comment deadlines. Files: the user's notes that hold their reasons for commenting. Contacts: None.
- **Other apps and websites (required):** None in the initial scope.

### Integration details

- **Operations and access (required):** Agent-facing MCP operations: `dockets.search|get|documents`, `comments.draft|validate|submit|receipt|status|list_mine`, and, for the optional workflow, `subscriptions.create|list|delete`. `comments.submit` is an approval-gated write that requires `acknowledged: true` and rejects otherwise. A GUI renderer presents docket search, docket, documents, comment form, review, receipt and my-comments pages for computer-use agents, plus a subscriptions page if the optional workflow is built. Platform-facing operations: `env.reset`, `env.load_seed`, `env.snapshot`, `env.inject_event`.
- **State and lifecycle (required):** App state (agencies, dockets, documents, comment periods) is separated from account state (drafts, comments, receipts and, optionally, subscriptions) and run state (clock, event log). Reset reloads the seed and clears drafts; submissions return receipts with tracking numbers; repeating a submit with the same draft ID returns the existing receipt (idempotent), while a second distinct submission on the same docket is flagged as a possible duplicate; period closings are computed from the clock in the docket's stated time zone.
- **Events and notifications (required):** Accepted events: `docket.period_extended`, `docket.correction_published`, `docket.closed`, `comment.status_changed`. Published notifications: text emails to Mail for receipts and status changes, and, for the optional workflow, extension and correction notices; calendar updates for deadlines, following the shared Mail and Calendar apps' formats. Task scenarios decide when events occur.
- **Shared data and dependencies (required):** Stable IDs for the person, account, agency, docket, document, draft and comment; supporting documents as short text PDFs addressed by asset ID. Depends on the shared Mail, Calendar and Files apps and the platform clock; no external service at run time.
