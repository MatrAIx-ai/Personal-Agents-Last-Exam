## 2. What you plan to build

**✍️ Your answer (required):** Build a resettable browser App and MCP business interface for one fictional student-loan servicer and borrower dashboard. The initial version will support four complete workflows:

1. **View a loan portfolio:** list loans, servicers, balances, interest rates, disbursement dates, current repayment plan, next payment, delinquency/forbearance status, and qualifying-program counters. A detail view shows the fields needed to understand eligibility and separates principal, accrued interest, scheduled payment, and account status. Sensitive identifiers are masked.
2. **Compare and choose a repayment plan:** calculate deterministic estimates for eligible fixed and income-driven plans using the seeded loan type, disbursement date, income, family size, and tax-filing profile. Compare monthly payment, total projected payment, term/end date, interest, forgiveness estimate, and important tradeoffs. Ineligible plans explain the reason. The Agent must explicitly confirm a selected plan before submitting a request; viewing an estimate never changes the account.
3. **Submit and track an application:** create a repayment-plan or annual income-recertification application with a selected plan, borrower attestations, and either synthetic IRS-consent status or synthetic income-document metadata. Validate required fields, preserve a submission receipt and submitted snapshot, and expose `submitted`, `processing`, `approved`, `denied`, `needs_information`, and `withdrawn` outcomes. Duplicate submissions and stale edits are idempotent or rejected without creating a second application.
4. **Handle repayment status changes:** task-scheduled servicer events can change an application decision, monthly payment, due date, delinquency, deferment/forbearance, servicer assignment, or loan transfer. The Agent can inspect the change, acknowledge a notice, provide requested information, or compare and submit a new eligible plan. A failed payment or missing document remains visible and actionable; an event never silently changes the borrower's selected plan or invents a completed payment.

The environment is useful for personal-agent evaluation because safe loan management requires joining multiple loans, dates, eligibility rules, income facts, application status, deadlines, servicer transitions, and explicit authority for a consequential financial submission. It supports tasks such as finding a lower-payment eligible plan, correcting a missing income document, understanding why an application is delayed, or responding to a servicer transfer without losing history.

The GUI will expose the same business state and actions as MCP through dashboard, loan-detail, plan-comparison, application, and status-notice views. It will not be a generic state inspector.

### Integration details

- **Operations and access (required):** Agent-facing MCP and GUI operations will cover portfolio/list and loan detail, plan eligibility/estimates, application draft/read/update/submit/withdraw, document metadata submission, notice list/read/acknowledge, and status/history reads. Representative names are `loan.portfolio.list`, `loan.get`, `repayment.plan.compare`, `repayment.application.create`, `repayment.application.update`, `repayment.application.submit`, `repayment.application.get`, `repayment.application.withdraw`, `repayment.document.add`, `loan.notices.list`, `loan.notice.acknowledge`, and `loan.history.list`; exact schemas will be declared in `tools.json`. Infra-only `env.load_seed`, `env.apply_event`, `env.advance_time`, `env.snapshot`, and `env.reset` load histories, inject servicer outcomes, advance deadlines, inspect results, and restore a clean run. Setup, reset, time control, and event injection are not Agent operations.
- **State and lifecycle (required):** Each App instance represents one borrower account and is isolated by Core's `run_id` and `app_id`. Synthetic seed data includes loans, servicer assignments, plan rules, borrower income/family facts, saved consent state, masked contact/payment metadata, applications, notices, and status history. Estimates are immutable calculation records tied to an input snapshot; an application preserves its submitted snapshot and transitions through explicit statuses; a loan transfer preserves history while changing the current servicer. Writes use idempotency keys and expected state versions. Duplicate successful retries return the prior result, stale concurrent edits fail without partial changes, and commits return object status plus Core epoch/revision. Reset replaces business state, audit/receipts, and task-loaded events with the fixture baseline; snapshots are review evidence, not an Agent restore capability.
- **Events and notifications (required):** The App accepts task/Infra events for `loan.application_status_changed`, `loan.payment_status_changed`, `loan.repayment_status_changed`, and `loan.servicer_transfer_completed`. Events include stable loan/application/servicer IDs, effective virtual time, status, and a bounded reason or requested action; they are idempotent and reject invalid transitions. An event can create an in-App notice but cannot submit a plan, mark a payment complete, or alter borrower facts without an explicit operation. Brightpath optionally publishes compatible `channel.email` CloudEvents for the Mail messages above. A notice identifies the Brightpath loan/application as `source_object`, includes the status and next safe action, and excludes sensitive data. Sender commit, receiver commit, and delivery acknowledgement remain separate outcomes.
- **Shared data and dependencies (required):** Shared references include `person_id`, `borrower_account_id`, `loan_id`, `servicer_id`, `plan_id`, `estimate_id`, `application_id`, `document_id`, `notice_id`, and `event_id`. Borrower identity, income, tax, and payment fixtures are synthetic; responses expose masked account/loan references and document metadata rather than SSNs, bank details, or document contents. The initial App requires no media attachments, though document metadata includes filename, type, period, and checksum. The package runs independently with the repository's pinned public Core/runtime and Node.js 18+ using only built-ins. Mail 1.3.0 is optional in run assembly for notification evidence and is not required for core loan workflows.
