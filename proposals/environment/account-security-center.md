## 2. What you plan to build

**✍️ Your answer (required):** Build Gatehouse, a standalone synthetic business-account security center with an Agent-facing MCP interface and a Web interface over the same state. Reusable workflows include reviewing sign-in activity, inspecting and selectively revoking sessions, finding and removing suspicious mail-forwarding rules, and reviewing or revoking connected-app grants. Tasks can provide changing histories and explicit target-level action permissions, so an agent must distinguish evidence from assumptions, act only within scope, and avoid disrupting trusted access. This is an auditable account-management environment, not a threat detector or a real identity provider.

### Integration details

- **Operations and access (required):** Package `apps/gatehouse/` will expose `gatehouse.overview`, `gatehouse.activity.list`, `gatehouse.sessions.list`, `gatehouse.sessions.revoke`, `gatehouse.forwarding.list`, `gatehouse.forwarding.create`, `gatehouse.forwarding.update`, `gatehouse.forwarding.remove`, `gatehouse.app_grants.list`, `gatehouse.app_grants.revoke` and `gatehouse.recovery.list`. Write operations affect one selected record; the account's seeded action policy authorizes specific actions and target IDs, and the App rejects out-of-scope targets. No bulk lockout, password changes or recovery-method changes are in scope. Writes require the public Core's `expected_version` and `request_id`. The Web interface will provide the same reads and writes, including confirmation for destructive actions, and will use the shared public Web Host. Only the Agent business connection receives these operations. Trusted Infra uses the public runtime's seed, event, reset and snapshot operations; the Agent and browser do not receive those management operations.
- **State and lifecycle (required):** A run contains one synthetic account and its own activity and settings; Core persists each App/run independently. The seed includes a stable account ID, synthetic account policy, allowed action/target pairs, activity history, sessions, forwarding rules, connected-app grants and recovery-option summaries. Tasks may replace the seed with a complete scenario history. Reset restores that seed and its baseline clock; snapshots are evidence for trusted Infra, not an Agent restore feature. Repeating an accepted write with the same request ID returns its prior result without repeating the effect; reusing the ID for a different request or writing against a stale version fails explicitly. Each successful Agent mutation appends a Gatehouse activity entry with its operation, target, virtual time and actor class (`Agent action`); injected provider observations are marked separately. The entry does not assert a real person's identity. Cross-App transactions and direct access to other App state are not used.
- **Events and notifications (required):** Infra applies `security.sign_in.observed` with `{event_id, at, operation, payload}` where the payload contains `account_id`, `outcome` (`success` or `blocked`), optional `session_id`, `device_label`, `coarse_location`, `source` and `verification_status`. `security.forwarding_rule.observed` and `security.app_grant.observed` carry the same envelope and a `record_id` plus an `action` (`added`, `updated` or `removed`); added or updated records include their destination or app label. Replaying an identical event ID is idempotent; conflicting reuse and invalid events fail without changing business data. The activity feed preserves source and verification metadata and does not treat location or device labels as proof of identity. Gatehouse sends no messages and schedules no Agent sessions. Notification delivery, session wakeups and multi-App scheduling remain runner/Infra responsibilities, outside this App and distinct from the scope of approved/in-progress Environment proposal [#191](https://github.com/MatrAIx-ai/Personal-Agents-Last-Exam/pull/191).
- **Shared data and dependencies (required):** Target runtime is public runtime 1.6.0 / Core API 1.2.0, Node.js 18+, and the repository's standard App package contract. Gatehouse owns all record schemas and IDs; it has no required sibling-App dependency, shared media, external service, or private repository path. Seed and event schemas define timestamps, account relationships, observed changes, and synthetic-only destinations. Input and output validation, explicit write effects, and account/run binding are checked through the public host.
