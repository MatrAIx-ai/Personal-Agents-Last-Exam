## 2. What you plan to build

**✍️ Your answer (required):** A resettable travel workspace in which a plan can be correct on a desktop but unusable on the traveler's phone. Six views connect an itinerary, regional transport information, on-site observations, venue learning content, a downloadable guide library, and device delivery/playback. The initial scope supports two complete workflows: revise a day trip when published service differs from observable conditions, and prepare, deliver, revise and use a route-ordered audio guide through an offline interval.

The environment does not prescribe an agent strategy. It supplies observable evidence, editable artifacts and auditable device behavior. It must distinguish planned/scheduled information, confirmed arrangements, observed progress, and unknown operational status.

### Initial workflows

1. Import fictional reservations and prior plans, attach provenance, revise stop order and mark visits complete; retain version history and allow undo.
2. Query a synthetic regional timetable and journey planner, inspect publication/observation timestamps, and view separately delivered roadwork notices or stop-sign photos. Timetable data may be internally correct but operationally stale. Requesting a new on-site observation costs simulated time and does not expose hidden simulator state.
3. Build a guide from a bounded venue catalog: select points of interest, author/edit Mandarin narration, order it along a walk, generate or attach audio, and publish a versioned package.
4. Transfer the package to the traveler's distinct phone profile; verify a completed download, cold-open it without network access, navigate sections, play/pause/resume local audio, and use text if audio is unavailable.
5. Revise a guide when a room is closed or already visited, resume interrupted transfers, replace a package atomically, and remove a package without deleting the source. A failed update must leave the last complete version available.

The phone holds the artifact, not a guaranteed offline language model. During a phone outage, the scripted traveler can use downloaded material; remote generation, retrieval and messages to the agent are unavailable on that channel. The agent can still work on its networked workstation, but cannot silently deliver changes to an offline phone.

## 3. Potential app connections

- **Internal personal apps (required):** Initial scope uses local message, reservation and calendar fixtures within TrailPocket. Messages carry observations and delivery acknowledgments; reservations anchor deadlines; visit history records actual progress. Future adapters may connect platform Mail/Calendar/Messages, but no external app is a runtime dependency of v1.
- **Other apps and websites (required):** Synthetic regional transport pages, an inspectable transport-quotation fixture, a venue catalog, and a free-tier text-to-speech service fixture. These are replayable provider surfaces, not live scraping or real purchases. No commercial map SDK or real traveler account is required.

### Integration details

- **Operations and access (required):** Browser UI for all workflows; equivalent documented API/MCP actions for itinerary CRUD, evidence retrieval, content authoring, speech generation, package export, delivery status and playback inspection. Setup/reset, clock advancement, event injection and authoritative state assertions are evaluator-only. Agents see only authorized user surfaces, including a phone preview that represents the actual destination profile. Test actions consume simulated time; schemas will follow the released PALE infrastructure.
- **State and lifecycle (required):** Separate run-scoped provider state, itinerary versions, workstation files, device profiles, package manifests and playback progress. Asset checksums and byte counts distinguish queued, partially transferred and installed packages. Revision IDs prevent stale writes; idempotency keys prevent duplicate generation and transfers. A package is installed only after all required assets verify; concurrent room-order edits return a version conflict rather than overwrite silently. Reset restores clocks, caches, permissions, provider responses and both device stores. Snapshots include event seeds and version hashes.
- **Events and notifications (required):** Accept service delay, relocated stop, roadwork notice, venue room closure, connectivity transition, TTS quota/error, interrupted download and user visit-completion events. Example agent-visible event: `{type: 'stop_photo', observed_at: '16:05', attachment_id: 'scene-07'}`; provider pages need not mirror that observation. Delivery notifications report package/version/device/status, not just a URL. Offline notifications queue and carry their original timestamps after reconnection. Scenario authors decide timing and notification policy.
- **Shared data and dependencies (required):** Fictional traveler/group IDs, stop aliases, route edges with walking durations, reservations with time zones, POI IDs, visit order, content/source records and artifact versions. Formats: JSON, HTML, UTF-8 text, PNG/SVG signs and floorplans, and local WAV/MP3 audio. A manifest declares every required offline asset. Network enforcement must block external requests from the phone and log attempted fetches, including remote audio, fonts, scripts and streamed TTS. Private grading state is stored outside agent-visible accounts and file paths.

- **Scope boundary and open questions (required):** No full map engine, live GPS tracking, complete ticket marketplace, emergency dispatch, or general offline conversational model. The first phone/browser target and the platform's offline test contract will be fixed with maintainers before implementation. Separate workstation/phone origins, queued delivery and cold-start enforcement are required; a decorative offline toggle is insufficient. Reference task adapters may choose packaged HTML or the library UI; functional equivalence is assessed by device probes. Both supporting task proposals remain independently reviewable and do not establish multiple accepted contributions automatically.
- **License and external dependencies (required):** New code, original synthetic records and authored assets will be MIT-compatible with explicit per-asset metadata. No private chats, passenger names, hotel bookings, payment data, location traces or third-party personal information are included. The source is an author's Italy/Spain travel retrospective: local transcripts support the transport/planning friction; indoor signal loss and a custom route-aligned synthesized-audio guide are author recollections, not independently recovered execution evidence. All benchmark dates, people, routes, orders and failure schedules will be invented. Any externally sourced art facts or voice models require documented reuse terms before inclusion; otherwise use original synthetic content. All runtime providers are controlled fixtures, not live services.
