## 2. What you plan to build

**✍️ Your answer (required):** RecallWatch is a resettable, independently branded product-safety, recall-advisory and remedy-claim simulator where an action can succeed cleanly on the portal and still be wrong for a specific person or household. Real consumer recalls carry lot/batch codes, manufacture-date windows, UPCs, severity tiers (`class_i` / `class_ii` / `class_iii`), allergen or hazard tags, and time-limited remedy windows (`refund`, `replacement`, `repair_kit`), and notices are frequently expanded or amended after initial publication. A personal agent must match household purchases, gifts and pantry/nursery inventory against exact lot ranges rather than headline brand names, reconcile conflicting household preferences or prior returns, and act before remedy deadlines expire.

Core reusable workflows (entities, state transitions, reads/writes, and failure/control paths):

1. **Search and inspect recall advisories (`recall_notice`: `active -> expanded -> amended -> closed`):**
   - *Reads:* search/filter recalls by UPC, brand, category, hazard/allergen tag, severity class, lot code or publication window; inspect full advisory details including affected lot ranges, excluded lots, remedy options and remedy claim deadline.
   - *Failure/control:* querying a non-existent recall ID returns `NOT_FOUND`; querying a lot outside the affected range returns `exposure_status: unaffected` without creating a claim.
2. **Manage household product inventory and exposure matching (`registered_item`: `registered -> matched_recall | unaffected -> resolved`):**
   - *Reads/writes:* register, update or archive owned household products (UPC, brand, lot/batch code, purchase date, holder `person_ref`, location note such as `home_pantry` or `daycare_bag`, disposal/return status) and run deterministic exposure evaluation against current recalls (`unaffected`, `matched_active`, `matched_remedy_expired`).
   - *Confirm/modify/cancel & error paths:* updating a lot code recomputes exposure deterministically; archiving a returned/discarded item removes it from active exposure alerts; registering a duplicate serial/item with a stale `expected_version` fails with `VERSION_CONFLICT`.
3. **Manage recall alert watchlists (`watchlist_rule`: `active -> muted | paused -> deleted`):**
   - *Reads/writes:* create, update, pause, mute or delete alert subscriptions scoped by brand, UPC, category or allergen tag, with minimum severity threshold (`class_i`, `class_ii`, `class_iii`) and quiet/digest preferences.
   - *Failure/control:* invalid severity enum or unknown category returns `VALIDATION_ERROR`; deleting an already-deleted rule with a new `request_id` returns `NOT_FOUND`.
4. **Submit, modify and withdraw recall remedy claims (`remedy_claim`: `draft -> submitted -> under_review -> approved_refund | approved_replacement | approved_repair_kit | rejected | withdrawn`):**
   - *Reads/writes:* preview remedy eligibility (checking lot match, proof-of-purchase asset reference and virtual-time claim deadline), create a draft, submit a claim, amend shipping/payout details while `draft` or `submitted`, or withdraw a claim before fulfillment.
   - *Failure/control:* submitting after the recall's virtual-time `remedy_deadline_at` fails with `REMEDY_WINDOW_EXPIRED`; submitting for an unaffected lot fails with `LOT_NOT_AFFECTED`; modifying a `withdrawn` or `approved_*` claim fails with `INVALID_STATE_TRANSITION`; duplicate submission with the same `request_id` replays the original committed receipt without creating a duplicate claim.

Reuse across distinct task situations: (a) a parent reordering children's snacks must check whether a newly expanded Class I allergen recall covers the exact lot in a daycare bag while a newer lot at home is unaffected; (b) a household caregiver managing an OTC medication recall must decide whether to file a replacement claim before the virtual-time cutoff or withdraw a draft claim after noticing a receipt in Mail/Files shows the item was already returned; (c) a homeowner must update a watchlist after an appliance recall expands to a second model batch and coordinate disposal with a housemate. Every task seeds its own catalog, lot ranges, household items and recall timeline cleanly.

### Integration details

- **Operations and access (required):**
  - **Agent-facing business operations** (exposed via both `agent-mcp` stdio tools and the App-owned Web GUI reading/writing the same authoritative state):
    - `recall.search` (`MCP` + `GUI`, `read`): search/filter recalls by UPC, brand, category, lot code, allergen/hazard, status or date range.
    - `recall.get` (`MCP` + `GUI`, `read`): fetch full advisory details, lot ranges, remedy rules and deadline.
    - `inventory.list` / `inventory.get` (`MCP` + `GUI`, `read`): list or inspect household registered items and computed exposure status.
    - `inventory.register` / `inventory.update` / `inventory.archive` (`MCP` + `GUI`, `write`): register a household item, update lot/location/holder, or archive returned/discarded items.
    - `inventory.check_exposure` (`MCP` + `GUI`, `read`): deterministically evaluate one item or the whole household inventory against active/expanded recalls without mutating business state.
    - `watchlist.list` (`MCP` + `GUI`, `read`) and `watchlist.create` / `watchlist.update` / `watchlist.delete` (`MCP` + `GUI`, `write`): manage household safety alert subscriptions.
    - `claim.list` / `claim.get` / `claim.preview` (`MCP` + `GUI`, `read`): list claims, inspect status/receipts, or check eligibility and remedy deadline without mutating state.
    - `claim.create_draft` / `claim.update_draft` / `claim.submit` / `claim.withdraw` (`MCP` + `GUI`, `write`): full remedy-claim lifecycle.
  - **Infra-only privileged operations** (strictly on `infra-mcp`, unavailable to the Agent and absent from the Agent Web GUI): `env.load_seed`, `env.apply_event`, `env.reset`, `env.snapshot`, `env.event_status`, `env.validate_bundle`, `env.advance_time`.
  - **Reviewer console:** None inside the Agent GUI; any inspection uses Core's administrative snapshot/audit interface.
- **State and lifecycle (required):**
  - **State separation:** App-level catalog state (`recalls[]`, reference categories/severity rules), account-level state (`account_id`, household `inventory[]`, `watchlists[]`, `claims[]`, `notifications_sent[]`), and run-level Core isolation (`run_id`, `app_id`, virtual clock, receipts and audit log). Each task loads its own initial catalog, accounts and historical claims/items via `env.load_seed` against `schemas/seed.schema.json`.
  - **Commit evidence, retries and concurrency:** Every write accepts `request_id` and `expected_version`, returns `{committed: true, receipt_id, entity_id, version, state_epoch}` on commit, replays the identical receipt when the same `request_id` is retried (preventing duplicate claims or duplicate items), and rejects stale `expected_version` with `VERSION_CONFLICT` without mutating state. Reads never mutate business state; rejected writes preserve business state and record a denial row in Core `state.audit`. Evaluator correlation joins App retained claim/watchlist/inventory revision history with Core `state.audit` and supplied Agent execution records; snapshots are retained prior to reset.
  - **Reset and restore:** `env.reset` enforces `reset_scope: app_instance`, returning only this RecallWatch instance to its loaded baseline seed without touching Mail or any other App. Snapshots are inspection evidence, not a cross-App rollback mechanism; notifications already committed in Mail are not automatically undone on local reset.
- **Events and notifications (required):**
  - **Accepted Infra events** (task scenarios choose timing and payload; RecallWatch defines deterministic business effects):
    - `recall.publish`: adds a new active recall notice and recomputes matching exposure flags. Example: `{"event_id": "evt-rw-001", "at": "2026-11-18T14:00:00+00:00", "operation": "recall.publish", "payload": {"recall_id": "RW-2026-014", "brand": "SunMeadow", "upc": "012345678905", "severity": "class_i", "hazard": "undeclared_peanut", "affected_lots": ["LOT-26A", "LOT-26B"], "remedy_types": ["refund", "replacement"], "remedy_deadline_at": "2026-12-02T23:59:59+00:00"}}`.
    - `recall.expand_lots`: transitions `active -> expanded`, appends newly affected lot ranges and optionally extends `remedy_deadline_at`. Example: `{"event_id": "evt-rw-002", "at": "2026-11-19T09:30:00+00:00", "operation": "recall.expand_lots", "payload": {"recall_id": "RW-2026-014", "added_lots": ["LOT-26C"], "reason": "Secondary packaging line cross-contact"}}`.
    - `recall.amend_or_close`: transitions `active|expanded -> amended|closed`, updating excluded lots or closing the advisory. Example: `{"event_id": "evt-rw-003", "at": "2026-11-25T16:00:00+00:00", "operation": "recall.amend_or_close", "payload": {"recall_id": "RW-2026-014", "status": "amended", "excluded_lots": ["LOT-26A-REV2"]}}`.
    - `claim.decision`: transitions a `submitted` or `under_review` claim to `approved_refund`, `approved_replacement`, `approved_repair_kit`, or `rejected` with an explanation code. Example: `{"event_id": "evt-rw-004", "at": "2026-11-20T18:00:00+00:00", "operation": "claim.decision", "payload": {"claim_id": "clm-101", "decision": "approved_refund", "amount_cents": 1899, "note": "Verified lot LOT-26B"}}`.
  - **Virtual-time business rules:** All remedy claim deadlines (`remedy_deadline_at`), watchlist pause expirations (`pause_until`), and recall publication timestamps are evaluated strictly against Core's supplied virtual time (`env.advance_time` / event `at`), never host wall-clock time.
  - **Messaging directions:** `publishes`: `channel.email` (send-only, CloudEvents 1.0 wire envelope matching `urn:pale:email-message:2` / `urn:pale:email-payload:1` / `org.pale.mail.notification.v1` -> Mail `mail.receive_notification`). `receives`: `None` (RecallWatch receives updates only via Infra `env.apply_event`). Wire-message payload example (matches `examples/apps/mail/schemas/email-payload.schema.json`, `asset_ids: []`):
    `{"channel": "channel.email", "recipient": {"kind": "person_ref", "id": "person-priya"}, "source_object": {"app_id": "recallwatch", "account_id": "acct-priya", "object_type": "remedy_claim", "object_id": "clm-101"}, "content": {"title": "RecallWatch Claim Submitted: RW-2026-014", "body": {"format": "text/plain", "text": "Your refund claim clm-101 for lot LOT-26B has been submitted."}, "asset_ids": []}, "extensions": []}`.
    Sender commit and Mail receiver commit are separate; delivery rejection leaves Mail state unchanged and records the failed delivery receipt in RecallWatch without rolling back the local claim.
- **Shared data and dependencies (required):**
  - People and accounts are referenced by shared IDs (`person_ref`, `account_id`) via `fixtures/binding.json`; RecallWatch never duplicates Contacts or Mail account stores.
  - Assets and media fit PALE's reference profile: synthetic PNG/JPEG label/lot-code sample images and UTF-8 JSON/text advisories, at most 12 bundled assets and <= 250 KiB total decoded bytes (strictly within the 64-asset / 1 MiB reference-profile ceiling). Missing optional asset IDs return a structured `ASSET_MISSING` warning on read rather than crashing.
  - Standalone package boundary: `apps/recallwatch/` runs independently using only Node 18+, pinned Core API `1.2.0` / public runtime `1.6.0`, and its own package files (no private imports, no repository-relative hacks). `examples/apps/mail` (`v1.3.0`) is declared as an optional integration target supplied via `app:verify --with examples/apps/mail` during integration checks.
