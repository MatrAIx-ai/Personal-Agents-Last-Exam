# Environment Track proposal

**Proposed PR title:** `[Environment Proposal] [Work & business] Meeting Poll`

Meeting Poll is an independently branded, Doodle-inspired meeting coordination App. It targets public runtime 1.6.0 / Core API 1.2.0, with a business GUI and MCP interface. A preparatory implementation exists locally and is not included in this proposal-only PR; it does not imply plan approval or implementation acceptance. Implementation and evidence remain in the same PR after approval.

## 2. What you plan to build

**✍️ Your answer (required):** A resettable workplace meeting poll that supports draft creation, invitations, availability responses and changes, manual confirmation, reopening and cancellation. An agent must reconcile the latest responses with the user's meeting requirements rather than automatically choosing the highest vote count. Stable slot IDs, response history, superseded meetings and app-local notices expose observable outcomes for multiple independent tasks.

The first version supports 2–12 participants and 2–10 active candidate slots per poll, with durations of 15–120 minutes. Five business views cover the poll list, creation/editing, participant responses, organizer availability overview, and meeting/activity details. Notifications have a separate inbox view.

| Workflow | Preconditions and action | Observable result and error/control |
| :--- | :--- | :--- |
| Draft and invite | Organizer creates/edits a draft, then explicitly publishes | Draft is private and sends no notices; publication records invitations for its fixed participant list. Invalid dates and unknown people fail atomically. |
| Respond and revise | Invited account submits yes / if-needed / no for every active slot before the deadline; may change or withdraw | Append-only response history; missing and withdrawn responses are not no/yes votes. A participant cannot answer for another person. |
| Confirm | Organizer reviews current replies and selects an active future slot | Exactly one active meeting and app-local confirmation notices. Core rejects a stale version if a response changed after the read. |
| Change or reopen | Edit open poll metadata/slots; reopen a closed/finalized poll with a future deadline and reason | Reopening supersedes the old meeting; removed slots retain history and replacement slots receive new IDs without inherited votes. |
| Cancel and inspect | Organizer cancels any non-cancelled state and reads activity | Active meeting becomes cancelled; already-cancelled calls produce no new notice. Cancelled polls cannot accept votes or confirmation. |

Deadline equality closes voting immediately. Closed polls may still be finalized, cancelled or reopened. A new deadline must precede every active slot; when old candidates have already elapsed, cancel and create a new poll. Published participant lists are fixed; changing that list requires a new poll. Recurrence and automatic optimization are outside scope.

**Main Web/MCP acceptance scenario:** Publish a poll and collect replies, then remove one candidate slot and add a replacement through the actual Web controls. Keep the identities and votes of unchanged slots; retain the removed slot only in history and start the replacement with no responses. After the organizer reads the current version, apply an independent participant update through the public interface and attempt finalize using the older version: it must fail without creating a meeting or confirmation notice. Refresh, inspect the latest replies and finalize a valid slot. Reload the page and independently query through MCP to verify precisely one current active meeting, matching selected slot and persisted version. Link the ordered browser actions, intermediate states, tool results and receipts; test failures separately from successful retries. Reopen/reconfirm checks must distinguish superseded meetings from the single current meeting.

Potential tasks include preserving a necessary participant despite majority preference, revising a decision after a reply changes, and respecting time-zone constraints. The App does not encode the correct scheduling answer or introduce hidden preference gates.

[Pegboard #173](https://github.com/MatrAIx-ai/Personal-Agents-Last-Exam/pull/173) concerns employee shifts, coworker acceptance and manager approval. Neither is a required dependency; maintainers may refine the scope division during review.

### Integration details

- **Operations and access (required):** `apps/meeting-poll/` exposes 13 declared business tools through the public MCP host: list/get/context/notifications, create/edit/publish/respond/withdraw/finalize/reopen/cancel/notification.read. The App's five GUI views use the public `pale.web` v1 Agent bridge and the same tools. Core supplies separate Infra seed, reset, snapshot, event status, event application and clock operations; the App does not implement authentication, persistence or a parallel REST backend. Management tools are unavailable to the Agent even by guessed name.
- **State and lifecycle (required):** Core isolates by run/App, binds one trusted account owner per run, and persists seeds, business records, notifications, versions and receipts. The owner can organize one poll and participate in another; other people's actions enter through Infra, never an Agent-provided actor override. Organizers see all replies on their own polls; participants see only their own replies/history and notices. Drafts and uninvited polls are hidden. State transitions are draft → open → closed → finalized, open → finalized, closed/finalized → open, and any non-cancelled state → cancelled. Reads derive effective closure without mutation. Every write uses an observed epoch/revision and retry-stable request ID; Core provides locking, atomic commit and duplicate receipts. Snapshot exports current state; reset restores the loaded baseline and advances the epoch. Snapshot export does not claim an unsupported `env.restore` operation.
- **Events and notifications (required):** `meeting-poll.action` applies a bound actor's declared domain action using the same business rules; `meeting-poll.close_due` persists closure for due polls. The planned `apps/meeting-poll/examples/scenario.json` event changes Alex's availability at a supplied time. Core supplies `ctx.virtual_now`; tasks/Infra own scheduling. Clock advancement alone does not emit events. Notifications are delivered synchronously as app-local records in the business transaction, with type, poll, recipient, time and read status. A delivered record is not an email or cross-App receipt. Failed writes leave no notice; deduplicated calls/events add no duplicate effects. No external outbox worker, subscription or messaging channel is declared.
- **Shared data and dependencies (required):** Polls reference bound person IDs and stable slot IDs; responses, meeting revisions and activity remain in the poll; notifications reference the poll and recipient. Directory output contains only the owner and people present in visible polls. A task needing additional people supplies visible poll history through its seed. All data is JSON/text, with no attachments or collected media. Required dependency: the public PALE runtime 1.6.0 (Core API 1.2.0, contribution contract 0.4.0, public Web Host). Node 18+ suffices; Node 22.16.0 is the reproduction version. App business checks run from the App directory alone. Real MCP/GUI checks use only the pinned shared runtime, and Playwright 1.56.1 for browser validation. No other App or private source is imported. A package-local registry runs Meeting Poll without changing the seven-App reference assembly.

### Environment evaluation-data plan

- **Scope and distribution:** Deliver realistic meeting-coordination records spanning 2025-01-01 through 2026-12-31 inclusive, covering all 24 months rather than only endpoints. Start with eight distinct polls per month (192 total), varying team membership, meeting purpose, candidate times, response changes and finalized/cancelled/reopened outcomes. This is a planning scale, not a date-count qualification threshold. Preserve coherent chronology, stable identities and permissions across linked records; avoid duplicated filler. Include month/year boundaries and daylight-saving transitions in the three display zones. The eight smoke fixtures remain separate from this dataset. Report actual distribution and gaps; activity on every day and a 300-date minimum are not required.
- **Sources, synthesis and access gaps:** Meeting coordination contains private account data; no authorized real Doodle poll dataset is currently available. Propose fully synthetic business records generated with a fixed seed and versioned configuration, informed by the linked public workflow documentation. Record reference URLs, access dates and source revisions/hashes where available; documentation is a workflow reference, not observed poll data. Ask the reviewer to confirm this explicit real-data access gap and synthetic-only approach. If an authorized real source around November 2026 becomes available, record it as a separate provenance-labelled anchor and synthesize unavailable periods; do not imply that such an anchor already exists. Label all generated records, including future-dated records, synthetic. Keep provenance in a sidecar manifest with stable record IDs and dataset/generator hashes, without introducing a new Core schema.
- **Date fields and counting:** Use the IANA zone `Etc/UTC` for coverage calculations, normalizing timestamp offsets before deriving calendar dates; display-zone variation does not change that counting rule. Map polls to `created_at`, candidate slots to `start`, response/history/meeting-revision records to `at`, and notifications to `at`. Treat `deadline`, slot `end` and `updated_at` as consistency fields, not extra records or additional coverage dates; meeting-revision `at` describes the decision, while the referenced slot describes the scheduled occurrence. Identify nested records by parent ID plus stable child ID or documented sequence index. Report counts by record type and globally deduplicate dates across sources. Exclude out-of-window records and disclose their counts, reasons and missing/invalid timestamps. Count represented business dates, never generation/export/file-modification dates; date-only values, if introduced, are interpreted in the declared zone.
- **Reproduction and delivery checks:** Supply the generator/configuration, exact commands, dataset revision and hashes, field mapping and exclusions. Compute reports from the actual delivered records: totals, per-source distinct dates, globally deduplicated dates, earliest/latest dates, all 24 monthly counts, real/synthetic proportions and explicit gaps. Load each monthly partition through the pinned public seed/import interface with a declared virtual clock and account binding; retrieve representative polls, replies, meetings and notices through public tools, reconcile IDs and counts to the coverage input, and check unauthorized visibility and reset reproducibility. Preserve raw load/query results and representative content for human realism review. Historical partitions must not contain actions after their snapshot clock; future records selected for a Task must be staged through authorized events rather than exposed as prior history. No completed dataset or coverage report is claimed at proposal review.
