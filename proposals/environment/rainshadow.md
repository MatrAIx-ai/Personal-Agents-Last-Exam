## 2. What you plan to build

**✍️ Your answer (required):** Rainshadow is a resettable weather app in which every forecast has a source and an issue time, and every alert is a message that can be updated or cancelled, so the right answer depends on which place and which hours matter to this person. One account keeps saved places with alert rules and weather watches (a place, a time window and personal thresholds); the task supplies hourly and daily forecasts from several sources, observations and alerts on its own clock. Four workflows are complete in the first version.

**Entities.** Place (name, time zone, alert zones), source (weather or air quality), issuance (one source's forecast for one place at one issue time: hourly rows and daily rows), observation, alert thread (messages `alert`, `update`, `cancel`), saved place with its alert rule, acknowledgement, watch with its latest evaluation, notice, account preferences.

**Simplifications.** Forecasts are whatever the task supplies; Rainshadow has no weather model and does not score accuracy. One App instance holds one account. Hourly rows are whole hours in the place's own time zone. Alerts have four severity levels (`minor`, `moderate`, `severe`, `extreme`) and eight categories (`flood`, `storm`, `winter`, `wind`, `temperature`, `fire`, `air_quality`, `other`). Air quality is the US 0–500 index with its six public category names.

- **W1 Places and preferences.** Search the seeded gazetteer, save a place under the user's own label ("Mom's house") with an alert rule (categories, minimum severity, paused or not), change or remove it; set units, default source, quiet hours and email notices. Paths: modify = `places.update` / `preferences.update`; cancel = `places.remove`; errors = unknown place (`not_found`), saving twice (`already_saved`), removing a place an open watch still uses (`place_in_use`), unknown time zone (`invalid_timezone`). Confirm: not applicable, because nothing here spends money or commits the user to anything and every write can be undone by another write.
- **W2 Forecast evidence (read-only).** List sources and issuances, read hourly and daily forecasts for a place and window, read current conditions. A read returns the latest issuance of the chosen source for that place and always names it (`issuance.id`, `issued_at`, `is_latest`); an explicit `issuance_id` returns an earlier one. Hourly rows and the daily headline of one issuance are returned exactly as issued, even when the headline describes the whole day and the hours the person cares about look different. `coverage` lists requested hours the issuance does not contain; Rainshadow never interpolates and never falls back to another source. Rows carry the place's own UTC offset. Paths: modify, cancel and confirm are not applicable to reads; errors = `not_found`, `invalid_window`; no issuance yet returns an empty result with `coverage.reason: no_issuance`, not an error.
- **W3 Alerts.** Alerts arrive as events. The Agent lists the alerts that affect a place in a window, reads the full message history and acknowledges the latest message. Paths: an `update` replaces timing, severity and text and clears the acknowledgement; a `cancel` closes the thread; errors = acknowledging a superseded message (`stale_message`), acknowledging twice (`already_acknowledged`), acknowledging a closed thread (`invalid_state`).
- **W4 Watches and notices.** Create a watch: a place, a window, a source and one to six alternative conditions, such as `pop ≥ 40`, `thunder_prob ≥ 20`, `wind_gust ≥ 35 mph`, `aqi ≥ 101`, or "any `air_quality` alert of at least `moderate` severity". Rainshadow evaluates it at once and again whenever new information arrives, and writes a notice when the result changes. Paths: modify = `watches.update` (re-evaluated, no notice, because the user caused the change); cancel = `watches.cancel`; errors = window already over or longer than 10 days (`invalid_window`), changing a closed watch (`invalid_state`), more than 20 open watches (`limit_exceeded`). Notices respect quiet hours; `extreme` alerts bypass them.

| Object | From | Trigger | To |
| :--- | :--- | :--- | :--- |
| Alert thread | — | `alert.issued` | `upcoming` (before onset) or `active` |
| Alert thread | `upcoming` | clock reaches onset | `active` |
| Alert thread | `upcoming` or `active` | `alert.updated` | same thread with a new latest message; status recomputed; acknowledgement cleared |
| Alert thread | `upcoming` or `active` | `alert.cancelled` | `cancelled` |
| Alert thread | `upcoming` or `active` | clock reaches `ends` | `expired` |
| Watch | — | `watches.create` | `no_data`, `clear` or `triggered` |

| Watch | `triggered` | a new issuance or alert message leaves no condition met | `clear`, notice `watch.cleared` |
| Watch | `no_data`, `clear` or `triggered` | `watches.update` | re-evaluated, no notice |
| Watch | `no_data`, `clear` or `triggered` | `watches.cancel` | `cancelled` |
| Watch | `no_data`, `clear` or `triggered` | clock reaches the window end | `ended` |

| Notice | — | created inside quiet hours | `held` |
| Notice | `held` | clock reaches the end of the quiet period | `released` |

Rules:

- A thread's status is derived from its latest message and the current time: `cancelled` if that message is a `cancel`; otherwise `upcoming` before `onset`, `active` from `onset` until `ends`, and `expired` from `ends` on. An alert affects a place when they share a zone.
- A watch is evaluated against the latest issuance of its source for its place, over the hours of its window that the issuance covers and that have not started; `aqi` conditions use the latest daily air-quality forecast for the dates the window touches; alert conditions use `upcoming` or `active` threads that affect the place and overlap the window. Conditions are alternatives: one met condition in one hour is enough. A watch whose forecast conditions cannot be evaluated, and whose alert conditions are not met, is `no_data`.
- A watch is re-evaluated only when new information arrives (an issuance from its source for its place, or an alert message for its zones) or the Agent edits it. Time alone only ends it. Each status change caused by new information writes exactly one notice; the evaluation record always names the issuance used and the hours that met a condition.
- An alert message writes one notice per account when a saved place shares a zone with it, the place's rule includes the category, the severity is at least the rule's minimum and the rule is not paused.
- Stored values are metric; results are converted to the account's units and name them. Thresholds are compared on unrounded converted values.

**Value for personal-agent tasks.** The same forecast calls for different actions for different people. A 60% daily headline does not matter to someone who leaves by 13:00; an air-quality index of 110 matters only if someone in the group has asthma; the place that matters may be a parent's town; and an agent that advised yesterday must notice that a newer issuance changed the afternoon. Rainshadow makes these checkable: which issuance the agent read and when, which places, rules and thresholds it left in the account, and what the user was told. Distinct task situations (separate Task proposals): (1) brief a once-only park visit from hourly rows when the daily headline turns alarming, then catch a real change the next morning (Task #95 plans this with an in-task fixture); (2) act on a smoke advisory before a refund deadline because of one companion's private health note (Task #113); (3) set a heat watch for an elderly parent's town with thresholds from the family's own history; (4) keep a child's outdoor party or a cyclist's commute under a watch whose thresholds differ per person; (5) decide whether an update at night is worth waking the user. Fixtures are plain seed data, so each task loads its own places, sources, forecasts, alerts and account history.

**Boundaries and overlap.** Proposal list checked on 2026-11-19: no other general weather environment. #25 (Switchback, same domain) is a campground reservation site; it carries facility-scoped alerts that affect reservations (fire restriction, road, outage, smoke advisory) and a scripted five-day forecast panel per facility. Rainshadow is the general weather source: any place, several sources, hourly rows, the message history of area alerts, and a personal layer of saved places, rules and watches. The two share no state; a task that uses both seeds consistent data in each, and facility, road and venue status stays with Switchback or the task. Tasks #95 and #113 currently plan narrow in-task forecast and air-quality fixtures; Rainshadow could serve both, and I will ask their authors in this PR which fields they need.

## 3. Potential app connections

- **Internal personal apps (required):** Mail only, optional and send-only, used by W3 and W4 notices: when `email_notices` is on, each released notice is also built as a plain-text message for the existing receive declaration of Mail 1.3.0 in `examples/apps/mail` (channel `channel.email`, wire `urn:pale:email-message:2`, payload `urn:pale:email-payload:1`, type `org.pale.mail.notification.v1`, receiver operation `mail.receive_notification`), reviewed at `main` commit `534bed4` ([wire schema](https://github.com/MatrAIx-ai/Personal-Agents-Last-Exam/blob/534bed4/examples/apps/mail/schemas/router-message.schema.json)). Rainshadow declares the matching `messaging.publishes` entry and builds no inbox. Calendar: none; it has no messaging receiver and Rainshadow never reads or writes it (a watch may store an optional `linked_object` reference that the Agent supplies, for example a Calendar event ID). Contacts and Messages: none. No workflow needs the Agent to call another App's tools, and all four workflows complete with Rainshadow alone.
- **Other apps and websites (required):** None required. Optional pairing with #25 and with Tasks #95 and #113 happens through task-supplied seeds and events, not through an App-to-App channel. No external website or live weather service is called at run time.

### Integration details

- **Operations and access (required):** 21 Agent-facing MCP operations over stdio (`service.cjs --role agent`), registered in `tools.json` as `rainshadow.<name>`. Read (13): `places.search`, `places.list`, `sources.list`, `forecast.issuances`, `forecast.hourly`, `forecast.daily`, `conditions.get`, `alerts.list`, `alerts.get`, `watches.list`, `watches.get`, `notices.list`, `preferences.get`. Write (8): `places.save`, `places.update`, `places.remove`, `preferences.update`, `alerts.acknowledge`, `watches.create`, `watches.update`, `watches.cancel`. Every write takes Core's `request_id` and `expected_version` and returns the object's `id` with the committed version. The target object is always the argument `id` and a time window is always `start` / `end`; the reference host's audit projection at `534bed4` keeps `id`, `start` and `end` among the few inputs it records, so its audit rows show the place or object and the window of every call, reads included. The Agent acts as the bound account holder set by Infra, never through an argument; a task can narrow tools, objects and fields with `policies.json`. App errors: `not_found`, `already_saved`, `place_in_use`, `invalid_window`, `invalid_timezone`, `stale_message`, `already_acknowledged`, `invalid_state`, `limit_exceeded`. Core adds `invalid_arguments`, `permission_denied`, `stale_version` and `idempotency_conflict`. Infra-only operations: `env.load_seed`, `env.apply_event`, `env.reset`, `env.snapshot`, `env.event_status`, `env.validate_bundle`; they are not listed on the Agent connection and Core returns `permission_denied` if the Agent calls them. The first version has no GUI and no reviewer console.
- **State and lifecycle (required):** State is separate per run and App instance, and one instance holds one account (`isolation_keys: run_id, app_id`). The seed schema carries world records (places, sources, issuances, observations, alert threads) and account records (preferences, saved places and rules, acknowledgements, watches, notices, activity rows), so a task can load any history, including earlier issuances and an account that already has watches. `validateSeed` rejects duplicate IDs, dangling references, timestamps without a UTC offset, out-of-range values and an account that the binding does not declare (`invalid_seed`). The seed is history: every record in it counts as already issued, and new information arrives only through events. Writes follow Core: an exact repeat of a committed `request_id` or `event_id` returns the stored receipt marked `duplicate`; the same ID with different input returns `idempotency_conflict`; a stale `expected_version` returns `stale_version`; a failed call leaves data, version and notices unchanged and Core appends a denial audit row. Reads never change business data: statuses are computed from stored records and `virtual_now`. Reset is Core's: it restores the loaded seed and the time loaded with it (`reset_scope: app_instance`) and touches no other App; messages already delivered to Mail stay there. Evaluator records come from three places: (a) App state in the snapshot (activity rows with sequence, virtual time, actor `agent`, `event` or `timer`, action and object ID for every committed write, event and timer effect; each watch's evaluation record; notices with creation time and disposition); (b) Core audit rows for every allowed or denied call with virtual time and the projected `id`, `start` and `end`; (c) full arguments and results in the supplied Agent execution trace. They join on `request_id`, `event_id` and version. Take the snapshot before a reset, because reset clears the audit.
- **Events and notifications (required):** Six events through `env.apply_event`, in Core's envelope. The clock moves only through events. For an event at time T, Rainshadow first runs timers due at or before T in due-time then ID order (release held notices, end watches), then applies the event, then re-evaluates the watches it affects and writes notices. Core rejects an event dated before the App's current time (`invalid_event`); Rainshadow also rejects a payload timestamp later than the event's `at`, an update or cancel for an unknown or cancelled thread, and a duplicate message or issuance ID (`invalid_event`, state unchanged).
