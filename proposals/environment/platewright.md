- **Authors / GitHub handles (required):** Junnan Li (@lijrjyan)

- **Secondary domains (optional):** Shopping & groceries

## 2. What you plan to build

**✍️ Your answer (required):** Platewright is a resettable recipe box and meal planner for one household, seen from the account of one of its members. It knows what each recipe contains, who in the household cannot or will not eat what, from which date and until which date, what is planned for which meal and for whom, and what is already in the kitchen. It answers one question everywhere in the same way: is this dish, as it would be cooked, right for each person who will eat it on that day? It then turns the week's plan into the quantities that still have to be bought. It sells nothing and places no order. Other household members act through task-supplied events, and every time-based state follows the environment clock. Five workflows are complete in the first version.

**Entities.** Household (time zone, week start, unit system, `leftover_max_days`, `use_soon_days`), member (the account holder and the others; a portion factor; a list of constraints), constraint (one of five kinds: `allergy`, `medical`, `diet`, `limit`, `dislike`; what it names; `strict` for allergies; `effective_from`, `expires_on`; a note on where it came from; its history), ingredient (name and aliases, the allergens it contains and may contain, eight content flags, the units it can be measured in with a density or a weight per piece where known, nutrition per 100 g, whether it is sold in whole pieces), recipe (title, base servings, ingredient lines with quantity, unit and `optional`, method tags, steps, tags, active and total minutes, revisions, and for a variant the base recipe, its revision and the swaps applied), substitution rule (from, to, ratio, the method tags it is valid for, a note), plan slot (date and meal, dishes, attendees, guests with their own constraints, its history), pantry item (ingredient, quantity, unit, use-by date), shopping list (its window, derived lines, manual lines, ticks), notification.

**Simplifications.** One App instance holds one household and one account. The other members are not accounts: what they do arrives as events. There are no prices, stores, orders or budgets: money belongs to the store App. There are no photos, no recipe import from a web page, no ratings and no automatic menu suggestion. The allergen list is the FDA's nine (`milk`, `egg`, `fish`, `crustacean_shellfish`, `tree_nut`, `peanut`, `wheat`, `soy`, `sesame`). The content flags are `meat`, `poultry`, `fish_or_seafood`, `animal_product`, `gluten`, `lactose`, `pork`, `alcohol`, and a diet is a fixed set of flags a person avoids (`vegetarian`, `vegan`, `pescatarian`, `gluten_free`, `lactose_free`, `no_pork`, `no_alcohol`). `lactose` is a flag and `milk` is an allergen, so lactose-free yogurt suits a lactose-free diet and is still unsafe for a milk allergy. Nutrition is five values (kcal, protein, carbohydrate, fat in g, sodium in mg). A `limit` constraint is a per-meal bound on one of the five. The values in the ingredient table are illustrative and the checks are not medical or dietary advice.

- **W1 Recipe box.** Search recipes by text, ingredient, tag, time, allergen-free and diet; read one at any number of servings and in either unit system, with its per-serving nutrition and its revisions; search the ingredient table; save a new recipe; edit one, which adds a revision; archive and restore. Paths: modify = `recipes.update`; cancel = `recipes.update` with `archived: true`, undone with `false` (an archived recipe stays readable and stays in past plans; a call that changes only `archived` adds no revision); confirm = not applicable, the save is the commitment; errors = unknown recipe or ingredient (`not_found`, `unknown_ingredient`), a quantity that is not positive or a unit the ingredient cannot be measured in (`invalid_quantity`), a requested conversion between mass and volume for an ingredient with no density (`no_conversion`), changing anything but `archived` on an archived recipe (`invalid_state`), servings outside 1 to 200 (`invalid_servings`).
- **W2 Household profiles and the suitability check.** Read the household with each member's constraints and their state on a given date (`household.get`, for all members or one); add, change or end a constraint with its dates and a note; check a recipe for a set of members and guests on a date (`recipes.check`), which returns one verdict per person and the ingredient lines behind it. Paths: modify = `members.constraint.set` with the constraint's `id` (it replaces the constraint and adds a history row); cancel = `members.constraint.remove` (it ends the constraint from now and keeps its history); confirm = not applicable; errors = unknown member (`unknown_member`), an allergen, diet, ingredient or nutrient that is not in the tables (`invalid_constraint`), `expires_on` before `effective_from` (`invalid_window`), removing a constraint that has already ended (`invalid_state`).
- **W3 Substitutions.** List the rules that apply to an ingredient or to each line of a recipe, with the reason any rule does not apply; preview a recipe with a set of swaps, which writes nothing and returns the new lines, nutrition and check; save it as a variant. Paths: modify = not offered, because a variant records what was swapped: save another variant; cancel = archive the variant (W1); confirm = `recipes.variant.preview` shows exactly what `recipes.variant.create` would save; errors = the ingredient is not in the recipe (`not_in_recipe`), no such rule (`unknown_rule`), the rule is not valid for this recipe's method tags (`rule_not_applicable`), the same line swapped twice (`conflict`), a variant of a variant (`invalid_state`: start from the base).
- **W4 Weekly meal plan.** Read the plan for a window with each slot's flags; set a slot (its dishes, each a recipe at a number of servings or a number of portions of leftovers from an earlier slot, its attendees and its guests with their constraints); clear it; mark it cooked or skipped. Paths: modify = `plan.slot.set` replaces the slot; cancel = `plan.slot.set` with no dishes clears it, or `plan.slot.mark` with `skipped` keeps the record; confirm = not applicable; errors = setting or clearing a slot whose date has passed (`past_slot`), marking a future slot cooked (`not_yet`), unknown member or recipe (`unknown_member`, `not_found`), leftovers from a slot that is later, is itself only leftovers or does not exist (`leftover_unavailable`), changing a cooked slot (`invalid_state`). A dish that is wrong for an attendee is planned and flagged, never refused.
- **W5 Pantry and shopping list.** Read the pantry with what is past or near its use-by date; set an item's quantity and date; generate the shopping list for a window from the plan and the pantry; add, change and remove manual lines; tick and untick lines; exclude a derived line with a reason. Paths: modify = `pantry.set`, `shopping.item.set` with the line's `id`, and `shopping.generate` again after the plan changes; cancel = `pantry.set` with quantity 0, `shopping.item.remove` for a manual line, `shopping.item.set` with `excluded: true` for a derived one; confirm = not applicable; errors = unknown ingredient (`unknown_ingredient`), a unit the ingredient cannot be measured in (`invalid_quantity`), a window that ends before it starts or is longer than 28 days (`invalid_window`), removing a derived line (`derived_line`: exclude it), an unknown line (`not_found`), any line write before a list exists (`no_list`).

Rules:

- Time is the environment's. Platewright has no timers, no scheduler and no clock event: Infra moves `virtual_now` with an event or with Core's `env.advance_time`, which runs no App code. Every time-based state is therefore stored as a date and derived from `ctx.virtual_now` where it is read or checked: a constraint's `state`, a slot's `phase`, a pantry item's `freshness`. "Today" is `virtual_now` in the household's time zone.
- A read writes nothing. Flags, verdicts, `stale`, `freshness` and scaled quantities are computed when read and are never stored, and no notification is written by a read or by the passing of time. Notifications are written only inside an event handler.
- One check is used everywhere: by `recipes.check`, by `recipes.variant.preview`, and for the flags of every plan slot. For each person and each ingredient line it applies that person's constraints **as they stand on the date of the meal**, not as they stand today: a constraint that starts tomorrow does not flag tonight's dinner and does flag tomorrow's, and one that expired yesterday flags nothing. The verdict per person is the most serious finding, in this order: `unsafe` (a line contains an allergen the person has an `allergy` to, or an ingredient or flag named by a `medical` constraint); `may_contain` (a line may contain the allergen; reported as `unsafe` when the allergy is `strict`); `unsuitable` (a line carries a flag the person's `diet` avoids); `over_limit` (the dish's nutrition per serving times the person's portion factor breaks a `limit`); `disliked` (a line is an ingredient or tag named by a `dislike`); otherwise `ok`. Every finding lists the lines that cause it. If all the causing lines are `optional`, the verdict is `ok_if_omitted` and names them.
- Guests exist only on the slot that names them. A guest carries a name and constraints of the same five kinds, and is checked like a member for that meal alone; nothing a guest needs is carried to another meal or to a member's profile.
- A plan can be wrong, and says so. `plan.slot.set` never refuses a dish for whom it is wrong; each slot reads with `flags`: one per attendee or guest whose verdict is not `ok`, plus `archived_recipe`, `stale_base` (a variant whose base recipe has a later revision), `leftover_short` (more portions of leftovers are planned than the source slot leaves) and `leftover_expired` (the leftovers are older than `leftover_max_days` on the day they are planned for).
- Servings. A dish's servings default to the sum of the portion factors of its attendees and guests (a guest counts 1), rounded up to a half; an explicit number replaces it. A cooked slot records `portions_made` and `portions_eaten` (default: the same sum); what is left is available as leftovers to later slots until `leftover_max_days` have passed.
- Scaling and units. A quantity scales by target servings over base servings. Conversions use fixed kitchen values (1 tsp = 5 ml, 1 tbsp = 15 ml, 1 cup = 240 ml, 1 fl oz = 30 ml, 1 oz = 28.35 g, 1 lb = 453.6 g). Mass and volume convert into each other only through the ingredient's density, and pieces into mass only through its weight per piece; where that is missing the answer is `no_conversion`, never a guess. Shown quantities are rounded (g and ml to the nearest 1, or 0.5 below 10; spoons and cups to the nearest quarter, or an eighth below 1 tsp; an ingredient sold in whole pieces rounds up to a whole piece) and each carries its exact value as `exact`. Sums always use the exact values.
- Nutrition per serving is the sum over lines of grams times the table's values, divided by servings. Optional lines are left out and listed. A line that cannot be converted to grams makes `nutrition` `null` with the line named in `missing_for`; nothing is counted as zero.
- A substitution rule replaces one ingredient with another at a ratio and is valid only for the method tags it lists (`bake`, `simmer`, `raw`, `fry`, `sauce`). A swap with no rule can be previewed and saved as `custom`, and the variant is then marked `unverified`. A variant is a recipe of its own: it records the base recipe, the base revision and the swaps, does not follow later edits of the base, and is checked like any recipe, so a swap that removes one allergen and brings another is reported.
- The shopping list is derived, and what a person did to it survives. `shopping.generate` takes every `planned` slot in the window, adds up the exact quantities per ingredient in the unit the ingredient is bought in, leaves out leftovers and optional lines (optional lines are listed separately), subtracts pantry stock whose use-by date is not before the day of the first meal that needs it, and rounds up once at the end. Stock that would expire before it is used is not counted and is listed under `expiring_before_use`. Regenerating keeps manual lines, keeps a tick or an exclusion on a derived line that is still needed, drops unticked and excluded derived lines that are no longer needed, and keeps ticked ones that are no longer needed as `surplus`. Each derived line lists the slots it is for.
- Marking a slot cooked with `deduct_pantry: true` takes the dish's exact quantities from the pantry, never below zero, and returns what was short. Without it the pantry is unchanged.

**Value for personal-agent tasks.** The same recipe is right for one table and wrong for another, and the difference is who sits at it and what has changed since they last ate it. A curry that the family has cooked for a year becomes unsafe on the night a guest with a strict tree-nut allergy comes, and only on that night. The swap that fixes it for the guest can break it for the child who cannot have soy. A member who wants no cilantro "just today" and one who wants none "from tomorrow" look the same in an order history and differ only in the dates of a constraint. A dietitian's cap of 700 kcal per sitting makes a doubled portion wrong for one person and fine for the other. A dozen eggs bought this morning should come off the list, and the yogurt that expires on Thursday should not be counted for Saturday. The reference products the App is modelled on store recipes and lists but do not check a dish against a person; Platewright does, and so makes the outcome checkable: which recipes and profiles the agent read, what it planned for whom, which flags it left standing, which variant it cooked from, what it put on the list and why each line is there.

Distinct task situations (separate Task proposals): (1) dinner for six with one strictly nut-allergic and one vegetarian guest, scaled from a recipe for two, with two cans already in the pantry; (2) a shared account in which one person's one-day exception must not become a standing preference and another's standing change must start on its date; (3) a week of eating occasions under a per-meal energy cap for a lactose-intolerant student, with food that expires mid-week; (4) a grandparent visits for four days on a sodium limit set by a doctor, and the plan for those days, and only those, has to change; (5) a member changes Friday's dinner while the account holder is shopping from a list that is now stale. Three open Task proposals already stand on this ground without an App for it: #38 keeps the recipe, the guests' allergies and the pantry in Notes and Messages and leaves the scaling to the agent; #79 keeps two people's tastes and their scoped changes in chat history; #52 keeps recipes in Files and needs per-occasion energy, lactose and use-by dates. The README's own example of a routine purchase made unsafe by a child's allergy is the same situation. None of these proposals has adopted Platewright, and the rationale does not depend on any one of them. Fixtures are plain seed data, so each task loads its own household, constraints, recipes, plan and pantry.

**Boundaries and overlap.** Proposal list checked on 2026-11-22, up to #193: no Environment proposal covers recipes, household dietary profiles, meal planning or a derived shopping list. In Food & dining, #111 is restaurant delivery and #40 and #41 are reservations. The nearest proposal is #37 (FreshCart, grocery delivery): it sells products from store catalogs, takes orders, handles substitutions by the shopper and issues receipts. Platewright is the other half of the same evening: it owns what the household cooks, for whom and from what, and ends at a list of ingredients and quantities. It has no products, prices, stock, carts or orders, and its ingredient table is not a catalog. An agent carries the list to a store App with that App's own tools; there is no channel between the two. Notes 1.0.0 can hold a recipe as free text, as #38 does; it cannot scale it, check it against a person or add it to a plan. Calendar 1.3.0 can hold "dinner at 18:30"; it does not know what is for dinner or who can eat it.

## 3. Potential app connections

- **Internal personal apps (required):** None required, and no messaging in either direction. Reviewed at `main` commit `a4bce02`. Mail 1.3.0 (`examples/apps/mail`) has an implemented receiver for `channel.email` (`mail.receive_notification`), which Platewright does not use: a household's own planner sends its members no email, and its notifications stay in its own log, read with `platewright.notifications.list`. - **Other apps and websites (required):** None required. A grocery App such as FreshCart (#37, not merged) is used by the agent with its own tools; the shopping list is a record here and is not sent anywhere. A task that uses both seeds each App separately. No external website, recipe site, nutrition service or store is called at run time.

### Integration details

- **Operations and access (required):** 22 Agent-facing MCP operations over stdio (`service.cjs --role agent`), registered in `tools.json` with the app ID as prefix, `platewright.<name>`. Read (11): `household.get`, `ingredients.search`, `recipes.search`, `recipes.get`, `recipes.check`, `substitutions.list`, `recipes.variant.preview`, `plan.get`, `pantry.list`, `shopping.get`, `notifications.list`. Write (11): `recipes.create`, `recipes.update`, `recipes.variant.create`, `members.constraint.set`, `members.constraint.remove`, `plan.slot.set`, `plan.slot.mark`, `pantry.set`, `shopping.generate`, `shopping.item.set`, `shopping.item.remove`. Every write takes Core's `request_id` and `expected_version`, where the version is Core's object `{epoch, revision}`, and returns the object's `id` with the committed version. The target object is always the argument `id` (a slot's `id` is its date and meal, such as `2026-11-14:dinner`) and a window is always `start` / `end`; the reference host's audit projection at `a4bce02` (`runtime/core/mcp.cjs`) keeps `id`, `start` and `end` among the inputs it records, so its audit rows show the recipe, slot or line and the window of every call, reads included. The Agent acts as the bound account holder set by Infra, never through an argument; a task can narrow tools, objects and fields with `policies.json` (for example, forbid `members.constraint.set` for other members). App errors: `not_found`, `unknown_ingredient`, `unknown_member`, `unknown_rule`, `invalid_quantity`, `invalid_servings`, `invalid_constraint`, `invalid_window`, `invalid_state`, `no_conversion`, `not_in_recipe`, `rule_not_applicable`, `conflict`, `past_slot`, `not_yet`, `leftover_unavailable`, `derived_line`, `no_list`. Core adds `invalid_arguments`, `permission_denied`, `stale_version` and `idempotency_conflict`. Infra-only operations: `env.load_seed`, `env.apply_event`, `env.reset`, `env.snapshot`, `env.event_status`, `env.validate_bundle`, and the clock operation `env.advance_time` of runtime 1.6.0; they are not listed on the Agent connection and Core returns `permission_denied` if the Agent calls them. The first version has no GUI and no reviewer console.
- **State and lifecycle (required):** State is separate per run and App instance, and one instance holds one household and one account (`isolation_keys: run_id, app_id`). The seed schema carries reference records (the ingredient table and the substitution rules, which a task may extend or replace) and household records (settings, members and their constraints with history, recipes with revisions, plan slots in every state with history, the pantry, the shopping list, notifications, activity rows), so a task can load any history: last month's plan, a constraint that ended, a pantry bought yesterday. `validateSeed` rejects duplicate IDs, dangling references (a recipe line with an unknown ingredient, a slot with an unknown recipe or member), a variant whose base is missing, a quantity in a unit its ingredient cannot be measured in, a cooked slot dated after the loaded time, malformed dates, timestamps without a UTC offset, and an account that the binding does not declare (`invalid_seed`). Writes follow Core: an exact repeat of a committed `request_id` or `event_id` returns the stored receipt marked `duplicate`, so a repeated request creates no second recipe or line; the same ID with different input returns `idempotency_conflict`; a stale `expected_version` returns `stale_version`; a failed call leaves data and version unchanged and Core appends a denial audit row. Reads never change business data. Reset is Core's: it restores the loaded seed and the time loaded with it (`reset_scope: app_instance`) and touches no other App. Core owns storage, seed loading, reset, snapshot and event application; Platewright supplies only the plugin hooks (`validateSeed`, `handleTool`, `applyEvent`, `records`, `objects`, `references`). Evaluator records come from three places: (a) App state in the snapshot: activity rows with sequence, virtual time, actor `agent` or `event`, action, object ID and the `request_id` or `event_id` behind them, one for every committed Agent write and one for every applied event; recipe revisions; each constraint's and slot's history; the shopping list with, for each derived line, the slots it is for; (b) Core audit rows, one for every allowed call that is not a replay and one for every denied call, with the projected `id`, `start` and `end`; (c) full arguments and results in the supplied Agent execution trace, which is where the verdicts and flags the agent was shown are found, since they are never stored. They join on `request_id`, `event_id` and version. Counting rules: committed writes and events from the activity rows, one row each; a replay appears only in the trace with `duplicate: true` and counts as a retry; rejected attempts from the denial audit rows, one per attempt; reads from the allowed audit rows and the trace. Flags at the end of a run are recomputed by the evaluator from the snapshot with the same check, which the package exports as a pure function. Take the snapshot before a reset, because reset clears the audit.
- **Events and notifications (required):** Six events through `env.apply_event`, in Core's envelope, each handled at its own time. Platewright has no clock event. Core rejects an event dated before the App's current time (`invalid_event`); Platewright also rejects an unknown member, recipe, ingredient, slot or line, a constraint that fails the checks of `members.constraint.set`, a change to a cooked slot, and a duplicate recipe ID (`invalid_event`, state unchanged). Each applied event writes one notification and one activity row.

  Notifications, each written once per event at the event's time: `member.updated`, `recipe.added`, `plan.changed`, `guest.changed`, `pantry.changed`, `shopping.changed`. None is written for the account's own writes, for a read or for the passing of time. Messaging directions: publishes none, receives none.
- **Shared data and dependencies (required):** Stable IDs for members, constraints, ingredients, recipes, substitution rules, slots (date and meal), pantry items, shopping lines and notifications. The account's `account_id` and `owner_person_id` are the shared values of the run's `binding.json`, and members are named by `person_id`, so a task that has the same people in Contacts, Messages or Calendar gives them the same IDs in its seeds. Platewright stores only what a kitchen knows about a person (a display name, a portion factor and constraints), not a copy of a contact. It is the source of truth for its recipes, constraints, plan, pantry and list and keeps no copy of another App's records. Missing data is explicit: an unknown ID returns `not_found`; an ingredient without a density returns `no_conversion` where one is needed; nutrition that cannot be computed is `null` with the lines named; a pantry item without a use-by date never expires and says so; a member with no constraints is `ok` for everything. All records are JSON; there are no images, audio, video or attachments (`capabilities.resources: false`, 0 of the profile's 64 assets). Runtime needs: the public Core/Messaging runtime 1.6.0 (Core API 1.2.0) at `main` commit `a4bce02`; `dependencies.required_apps` is empty; no external service. The package runs on its own: a copy that holds only `apps/platewright/` and the pinned runtime starts the App, and its business tests and example run from the package alone. It imports and reads nothing outside its own folder. Dates use IANA time zones through Node's built-in `Intl`, so no package is installed.
