# Environment Track proposal

Proposed PR title: `[Environment Proposal] [Media & entertainment + Social & communities] Fernshelf photo library: albums, sharing, removal requests, storage and trash`

## 1. App and domains

- **Authors / GitHub handles (required):** Junnan Li (@lijrjyan)
- **Reference app or website / URL (required):** Fernshelf, an independently branded synthetic personal photo library seen from one person's account (library, albums, shared albums, share links, removal requests, storage and trash); workflow references: Google Photos Help (https://support.google.com/photos/) for shared albums, link sharing, storage and trash, and the Immich documentation (https://docs.immich.app/) for albums, stacks, shared links and trash. No data, text, photos, branding or icons are reused.
- **Primary domain (required):** Media & entertainment
- **Secondary domains (optional):** Social & communities

## 2. What you plan to build

**✍️ Your answer (required):** Fernshelf is a resettable personal photo library, seen from one person's account, in which a photo can be visible in several places at once (shared albums and the links to them) and a copy that someone has saved cannot be called back, so an action the app accepts can still be wrong for this person, for the people in the picture or for the family that values one version over another. The account holds the person's photos and videos with their time, place, people labels and captions, the albums they are in, who each album and link has reached, and the storage they use; other people (album members, link viewers, someone who appears in a photo) act through task-supplied events, and every time-based state follows the environment clock. Five workflows are complete in the first version.

**Entities.** Account (owner, storage quota, trash retention, time zone, `email_notices`), item (a photo or a video: `taken_at`, `added_at`, place label with optional coordinates, people labels, caption, `source` of `camera`, `screenshot`, `download` or `saved_from_share`, `favorite`, `archived`, `declared_bytes`, `content_hash`, pixel size, an optional image file and a history of changes), stack (several items that are versions of one shot, of kind `edit`, `burst` or `duplicate`, with one cover), person label (a name the account uses for someone who appears in items, with an optional shared `person_id`), album (title, ordered items, and when shared: members with a role and a status, and the items each member contributed), share link (the album it shows, an expiry, and a record of every view and every save), removal request (a person asks that items showing them be taken down from where they are shared), notification, activity row.

**Simplifications.** One App instance holds one account, and every album in it is the account holder's own. Other people are not accounts: what they do arrives as events. There is no face recognition, no visual search and no duplicate detection by looking at pixels: people labels, places, captions and stacks are records that the task seeds or the Agent edits, exact duplicates are items with the same `content_hash`, and near-duplicates exist only as seeded `duplicate` stacks. People labels themselves are seed data: the Agent puts them on items and takes them off, and does not rename or create them. There is no upload from the Agent and no editing of pixels: new items arrive through events (a phone backs up, a member contributes) and an edited version is a seeded item in an `edit` stack. A link always shows one album; loose items are shared by putting them in an album. Storage is counted from each item's `declared_bytes`, the size the original is said to have, and not from the small image file the package carries, so a library can be 14 GB on a 15 GB plan while the bundle stays under 1 MiB; videos are metadata only. There are no payments: the plan, its quota and the account's preferences are seed data and cannot be changed by the Agent.

- **W1 Library, search and storage (read-only).** Read the account with its people labels and how many items carry each (`account.get`); search items by time window, place, person label, album, kind, source, favourite, archived, minimum size and caption text (`items.search`, stacks collapsed to their cover by default); read one item with its metadata, history, albums, removal history and, when it is in a stack, every version of that stack (`items.get`); read its image bytes when it has a file (`items.read`); list albums, and read one with its items, members, contributions and links (`albums.list`, `albums.get`); read the storage summary (`storage.summary`: quota, bytes used, bytes in trash, bytes by kind and by source, bytes held by non-cover items of `duplicate` stacks, and the largest items); read where one item is visible (`exposure.get`: each shared album with its joined members, each active link, every recorded view and every save, and every removal request about it); read notifications (`notifications.list`). Paths: modify, cancel and confirm are not applicable to reads; errors = unknown ID (`not_found`), a window that ends before it starts (`invalid_window`), bytes of an item that has no file (`no_file`) or that has been purged (`gone`).
- **W2 Organising.** Edit an item's caption, favourite, archived flag, people labels and corrected time, or make it the cover of its stack (`items.update`); create an album (`albums.create`); rename it and add, remove and reorder its items (`albums.update`); delete it (`albums.delete`). Paths: modify = `items.update` and `albums.update`; cancel = `albums.update` with `remove_ids`, and `albums.delete` (the items stay in the library); errors = an item that is not mine, such as a member's contribution (`not_yours`), an item in the trash (`in_trash`) or purged (`gone`), an item already in the album (`already_in_album`) or not in it (`not_in_album`), making a cover of an item that is in no stack (`not_stacked`), a people label the account does not have (`not_found`), more than 50 items in one call (`limit_exceeded`), deleting an album that still has joined members or an active link without `confirm: true` (`confirm_required`). Confirm: the write is the commitment; only deleting an album that is still shared asks for `confirm`. One `albums.update` is all or nothing.
- **W3 Sharing: shared albums and links.** Invite people to an album with a role of `viewer` or `contributor` (`albums.members.invite`); change a role or remove a member (`albums.members.update`); save a member's contribution into my library (`albums.save_item`); create a link to an album with an optional expiry, and revoke it (`links.create`, `links.revoke`). Paths: modify = `albums.members.update`, and `albums.update` for what an album and its links show (a link itself is not edited: revoke it and create another); cancel = removing a member, and `links.revoke`; errors = inviting someone who is already invited or joined (`already_invited`), changing a person who is not a member of the album (`not_member`), an expiry that is not in the future (`invalid_window`), a link that is not active or a member who has already declined, left or been removed (`invalid_state`), saving an item that is not a member's contribution (`not_shared`), a save that would pass the quota (`over_quota`). Confirm: the write is the commitment, and every write that would show items to someone (`albums.members.invite`, `links.create`, and `albums.update` adding items to an album that has members or an active link) returns `warnings` that name each person who has an honoured removal request on an item the write would show.
- **W4 Removal requests and what stays visible.** A person asks that items showing them be taken down, for a named album or for every place the items are shared; the request arrives as an event and can be withdrawn the same way. The Agent reads the requests in full (`removals.list`, filtered by status), reads where each item is visible (`exposure.get`) and answers (`removals.respond`): `honor` removes the named items from the named albums, and so from every link that shows those albums, in one step and records what was cleared; `decline` records a note and changes nothing. Paths: modify = a declined request can be honoured later; an honoured one is not reopened, because the items can be shared again only by a new, separate write that returns the warning; cancel = `removal.withdrawn` (the requester's), which closes a pending request and changes no album; errors = answering a request that is not pending or declined (`invalid_state`), unknown request (`not_found`). Confirm: `exposure.get` previews exactly what `honor` will clear; the answer is the commitment. What honouring cannot do is stated in its result: the views and saves already recorded for each item, by whom and when.
- **W5 Storage, versions and trash.** Move up to 50 items to the trash (`items.trash`), restore them (`items.restore`) and delete them for good before the retention ends (`items.purge`). A trashed item leaves every album view and link at once and still counts against the quota; it is purged when the clock reaches its `purge_at`, and only then are its bytes freed. Which version of a stack to keep is read with `items.get` and `storage.summary`, and the kept version is made the cover with `items.update`. Paths: modify = not applicable; cancel = `items.restore` while the item is in the trash, which puts it back in the albums it was in; `items.purge` cannot be undone and needs `confirm: true`; errors = an item that is not mine (`not_yours`), trashing an item already in the trash or restoring or purging one that is not (`invalid_state`), an item already purged (`gone`), a missing `confirm` (`confirm_required`), more than 50 items (`limit_exceeded`). Each call is all or nothing: one refusal leaves every named item unchanged.

Rules:

- Time is the environment's. Fernshelf has no timers, no scheduler and no clock event: Infra moves `virtual_now` with an event or with Core's `env.advance_time`, which runs no App code. Every time-based state is stored as a due time and derived from `ctx.virtual_now` wherever it is read or checked: an item reads `purged` from its `purge_at`, a link reads `expired` from its `expires_at`, and the bytes used leave out purged items. Writes and events use the same derivation: a purged item cannot be restored, and a view of an expired link is rejected as an event.
- Visibility has one definition, used by `exposure.get`, by the warnings and by `removals.respond`. An item is visible to a person when it is `active` and (a) it is in an album where that person is `joined`, or (b) it is in an album that an `active` link shows, to anyone who holds the link. Trashing an item ends both at once without changing album membership records, so restoring it brings them back.
- What has left the account stays out of reach. A view or a save recorded on a link or a shared album is a fact about the past: revoking the link, removing the member, honouring a request or trashing the item changes what is visible from then on and never removes a recorded view or save. `exposure.get` and the result of `removals.respond` list them, so a task can check whether the Agent told the user and the requester what could not be undone.
- Fernshelf does not judge consent; it records it. An honoured request leaves a `removal_history` row on each item (the person, the surfaces cleared and the time). A later write that would make such an item visible again through a shared album or a link is accepted and returns one `removal_honored` warning per person and item; the row and the warning are in the activity log. A pending or declined request produces no warning.
- A removal request names items and a scope (`album` with an album ID, or `everywhere`). `honor` with scope `album` removes the items from that album only; with `everywhere` it removes them from every album that has an invited or joined member or an active link. A link follows its album, so nothing else has to be cleared. Items the requester named that are not mine (another member's contributions) are listed in the result as `not_removable` and are left alone; albums that are shared with no one and the library itself are never touched.
- Storage. `used_bytes` is the sum of `declared_bytes` over my items that are `active` or `trashed`; a member's contribution counts only once saved. Events are facts: an `item.added` that takes the account past its quota is still recorded, with `backed_up: false`, and it is the Agent's own `albums.save_item` that is refused with `over_quota`. Only a purge frees bytes.
- Stacks. A search returns one row per stack, its cover, with `stack_size`, unless `collapse_stacks` is false. Trashing a cover promotes the most recently taken active item; trashing the last active item leaves the stack empty until one is restored. `items.get` on any item of a stack returns every version with its size, kind and whether it is the cover. `storage.summary` counts as `duplicate_bytes` the non-cover items of `duplicate` stacks and the later-added items among those that share a `content_hash`; it recommends nothing.
- Contributions. A joined contributor's items sit in the album without being mine: they use no storage, cannot be edited, trashed or removed by the Agent, and leave the album when that member leaves or is removed. `albums.save_item` copies one into the library as an item of mine with source `saved_from_share`, which then follows every rule above.
- Notifications are written for what other people and the device do, never for my own writes and never for a change that time alone causes: `album.activity` (a member joined, declined, left or contributed), `removal.requested`, `removal.withdrawn`, and `storage.threshold`, written once each time an event takes `used_bytes` from below to at or above 80% or 100% of the quota.
- Every committed Agent write and every applied event adds activity rows (see §3).

**Value for personal-agent tasks.** The same request, "clean up my photos", "share the reunion pictures" or "make a roundup for the family", calls for different actions for different people, and the app knows only part of each person. Which of two near-identical shots the family treasures is in a message thread or a note, not in the stack; whether a friend has withdrawn consent, and whether that was for one album or for good, is in the request history and in what she said elsewhere; whose pictures stay out of the family album this year is a boundary the user stated once, in another session. Because a photo can be visible in several places, because a trashed photo is recoverable only for a while, and because a saved copy cannot be recalled, the order and completeness of what the agent does are part of the answer. Fernshelf makes these checkable: which items, stacks and exposure the agent read, what it trashed, purged, shared or removed and with which warnings, what was still visible to whom afterwards, and what had already been viewed or saved. Three open Task proposals work with personal photos, and no Environment proposal provides a photo library (checked on 2026-11-22 up to #193). Messages 1.0.0 has a `channel.chat` receiver, which Fernshelf does not use: it sends no chat messages. Files, Notes, Tasks and Contacts 1.0.0 (the shared packages at `a4bce02`): none. Separate Agent tool use, not an App connection and not needed by any workflow: an Agent that holds those tools may pass the file object returned by `items.read` (`filename`, `mime_type`, `base64`, `sha256`, `media`) to `files.put`, `mail.attachment.add` or `messages.attachment.add`, whose inputs take that shape at `a4bce02`; Fernshelf learns nothing of such a copy and does not record it as exposure. All five workflows complete with Fernshelf alone.
- **Other apps and websites (required):** None required. A task that also uses Messages, Notes or Contacts seeds consistent people in each; there is no App-to-App channel. No external website, photo service, map service or model is called at run time.

### Integration details

- **Operations and access (required):** 23 Agent-facing MCP operations over stdio (`service.cjs --role agent`), registered in `tools.json` as `fernshelf.<name>`. Read (10): `account.get`, `storage.summary`, `items.search`, `items.get`, `items.read`, `albums.list`, `albums.get`, `exposure.get`, `removals.list`, `notifications.list`. Write (13): `items.update`, `items.trash`, `items.restore`, `items.purge`, `albums.create`, `albums.update`, `albums.delete`, `albums.members.invite`, `albums.members.update`, `albums.save_item`, `links.create`, `links.revoke`, `removals.respond`. The App ID is `fernshelf`, with no underscore, and every tool name starts with it. Every write takes Core's `request_id` and `expected_version`, the version being Core's object `{epoch, revision}` and not a number, and returns the object's `id`, the committed version and, for writes that show items to someone, `warnings`. A single target is always the argument `id`; calls on several items take `ids` (1 to 50) and are all or nothing, and `albums.update` takes `add_ids` and `remove_ids` under the same limit; a time window is always `start` / `end`. The reference host's audit projection keeps `id`, `start` and `end` among the few inputs it records, so for calls with several items the items come from the App's activity rows and the supplied execution trace, not from Core audit. The Agent acts as the bound account holder set by Infra, never through an argument; a task can narrow tools, objects and fields with `policies.json` (for example, deny `items.purge`). App errors: `not_found`, `not_yours`, `in_trash`, `gone`, `no_file`, `already_in_album`, `not_in_album`, `not_stacked`, `already_invited`, `not_member`, `not_shared`, `over_quota`, `confirm_required`, `limit_exceeded`, `invalid_window`, `invalid_state`. Core adds `invalid_arguments`, `permission_denied`, `stale_version` and `idempotency_conflict`; Fernshelf also answers `invalid_arguments` for what an input schema cannot express (an empty `patch`, inviting myself, the same item in `add_ids` and `remove_ids`). Image bytes are read with `items.read`, which uses Core's `ctx.assets.read` under the parent item; this needs the registration `runtime/registrations/fernshelf.json` with `{"app_id":"fernshelf","resource_access":{"item":"fernshelf.items.get"}}`, a read-tool mapping of the same form as Files' and Mail's, submitted in this PR for Infra review (fallback in §4). Infra-only operations: `env.load_seed`, `env.apply_event`, `env.reset`, `env.snapshot`, `env.event_status`, `env.validate_bundle`, and the host's clock operation `env.advance_time` of runtime 1.6.0; they are not listed on the Agent connection and Core returns `permission_denied` if the Agent calls them. The first version has no GUI, no reviewer console and no view for other people: members, viewers and requesters act only through events.
- **State and lifecycle (required):** State is separate per run and App instance, and one instance holds one account (`isolation_keys: run_id, app_id`). The seed schema carries the account (quota, retention, time zone, `email_notices`), items with their history, stacks, people labels, albums with members and contributions, links with their views and saves, removal requests in any state, notifications and activity rows, so a task can load any history, including items already in the trash or purged, links already viewed and requests already honoured. `validateSeed` rejects duplicate IDs, dangling references (an album item, a stack member, a label, a view of an unknown link), a stack whose cover is not one of its items, an honoured request without its cleared surfaces, a trashed item without `purge_at`, a file reference that the bundle does not contain, timestamps without a UTC offset and an account that the binding does not declare (`invalid_seed`). The seed is history: everything in it has already happened, and new facts arrive only through events. Writes follow Core: an exact repeat of a committed `request_id` or `event_id` returns the stored receipt marked `duplicate`, so a repeated request trashes, invites or answers nothing twice; the same ID with different input returns `idempotency_conflict`; a stale `expected_version` returns `stale_version`; a failed call leaves data, version and notifications unchanged and Core appends a denial audit row. Reads never change business data and write no notification, flag or activity row: purge, expiry, bytes used and exposure are derived at read time from stored records and `virtual_now`, and notifications are written only inside the event that causes them. The file of an item that has become `purged` by the clock is refused by `items.read` from that moment (`gone`); its stored reference is dropped by the next write or event the App commits, which changes nothing that a read returns. Reset is Core's: it restores the loaded seed, its files and the time loaded with it (`reset_scope: app_instance`) and touches no other App; messages already delivered to Mail stay there. Evaluator records come from three places: (a) App state in the snapshot: activity rows with sequence, virtual time, actor `agent` or `event`, action, object IDs (every item a call named), warnings returned and the `request_id` or `event_id` behind them, one for every committed Agent write, one for every applied event and one for each effect of that event; each item's history and `removal_history`; each link's views and saves; each removal request with its answer and cleared surfaces; notifications; (b) Core audit rows with virtual time and the projected `id`, `start` and `end`: one for every allowed call that is not a replay, one for every denied call, and one for every `env.advance_time`; (c) full arguments and results in the supplied Agent execution trace, which is where search filters and the items a read returned are found. They join on `request_id`, `event_id` and version. Counting rules: count committed activity rows, not calls; a replay adds no row; a refused call appears only in Core audit and the trace; what was visible to whom at a given moment is recomputed from the snapshot with the visibility rule of §2, which the package exposes as a pure function for graders. A snapshot must be taken before reset, which clears audit and receipts.
- **Events and notifications (required):** Six events through `env.apply_event`, in Core's envelope. Fernshelf has no clock event. An event is handled at its own time T, which is `ctx.virtual_now` inside the handler in runtime 1.6.0. Core rejects an event dated before the App's current time (`invalid_event`); Fernshelf also rejects a duplicate item, view or request ID, an unknown album, member, link, label or item, a contribution from someone who is not a joined contributor, a view or save on a link that is revoked or expired at T or of an item it does not show, a removal request that names no item of the account or a scope album that does not exist, a member change for someone who was not invited, and a withdrawal of a request that is not pending (`invalid_event`, state unchanged). Tasks decide which events happen and when; Fernshelf only defines their effects.

- **Shared data and dependencies (required):** Stable IDs for items, stacks, people labels, albums, links, views, removal requests and notifications. The account's `account_id` and `owner_person_id` are the shared values of the run's `binding.json`, so the person has one ID in Fernshelf and Mail, and notifications address the recipient by `person_ref`. Members, viewers and requesters are named by `person_id`; a people label may carry the same `person_id` or none (a label for someone the task's other Apps do not know). A task that has the same people in Contacts or Messages gives them the same IDs in its seeds; Fernshelf stores only a display name per person and keeps no copy of a contact. Fernshelf is the source of truth for its items, albums, shares and requests and keeps no copy of another App's records. Missing data is explicit: an unknown ID returns `not_found`; an item without a place, people or a caption has `null` or an empty list; an item without a file has `file: null` and `items.read` returns `no_file`. Media: PNG and JPEG image files only, referenced by asset ID and described in `contribution/assets.catalog.json` with MIME type, SHA-256, pixel size and provenance; videos are metadata only in the first version. The reference fixture carries 48 PNG files of at most 16 KB each, about 0.6 MiB in total, inside the reference profile's 64 assets and 1 MiB per bundle. A task supplies its own library through the same seed schema and its own image files in its bundle under the same limits; a task that needs more or larger images than the profile allows depends on the planned dataset and asset-reader adapter described in `docs/environment-architecture.md`, a platform dependency that this proposal does not provide and does not need. Runtime needs: the public Core/Messaging runtime 1.6.0 (Core API 1.2.0) at `main` commit `a4bce02`; Mail is optional; `dependencies.required_apps` is empty; no external service. The package runs on its own: a copy that holds only `apps/fernshelf/` and the pinned runtime starts the App, and its business tests and example run from the package alone. It imports and reads nothing outside its own folder and uses no other App's files or state; the real-MCP scripts are given the location of the pinned runtime, and the Mail flow also needs the pinned Mail package. Search windows by local day use IANA time zones through Node's built-in `Intl`, so no package is installed.
