## 2. What you plan to build

**✍️ Your answer (required):** Build a resettable browser App and MCP business interface for one fictional parking-reservation marketplace. The initial version will support four complete workflows:

1. **Search and compare parking:** search by destination and arrival/departure time, then compare available facilities by total price, walking distance, access type, hours, vehicle-size limit, height clearance, covered parking, accessibility, EV charging, and in-and-out privileges. Results and facility details will clearly expose taxes/fees, cancellation terms, entry instructions, and material restrictions. Expected failures include invalid time ranges, closed facilities, unsupported vehicles, and no matching inventory.
2. **Quote and reserve:** obtain a time-limited itemized quote, select a saved synthetic vehicle, and create a reservation with entry instructions and a synthetic entry pass code. The accepted quote, price, policy, facility, vehicle, and time window are preserved with the reservation. Expired quotes, sold-out inventory, stale state, and duplicate submissions fail without a partial booking or double charge.
3. **Modify or cancel:** retrieve an upcoming reservation, request new arrival/departure times, review any availability and price difference, and explicitly accept a replacement quote before the reservation changes. Cancellation computes the disclosed synthetic refund or fee from the accepted policy and records a confirmation. Completed, cancelled, or already-started reservations cannot be edited through the upcoming-reservation flow.
4. **Handle an unavailable facility:** a task-scheduled facility-closure event marks affected upcoming reservations as `action_required` and protects their original paid value. The Agent can inspect the disruption, search eligible nearby alternatives for the same time window, and either accept a replacement reservation with an itemized price difference or cancel for a full synthetic refund. If no replacement exists, the refund path remains available. Replayed closure or resolution requests are idempotent, and a closure never silently moves a customer to another facility.

The environment is useful for personal-agent evaluation because a correct action depends on time-sensitive inventory, walking distance, vehicle and access constraints, price/refund policy, changing plans, and explicit authority before a repriced or relocated booking is committed. It supports realistic tasks such as finding parking near an appointment, extending a stay without losing a valid reservation, or recovering from a last-minute garage closure.

The GUI will expose the same business state and actions as MCP through product-oriented search/results, facility/quote, checkout, reservation-management, and disruption-resolution views. It will not be a generic state inspector.

### Integration details

- **Operations and access (required):** Agent-facing MCP and GUI operations will cover parking search, facility details, quote creation/read, reservation list/read/create/requote/modify/cancel, disruption alternatives, and disruption resolution. Exact names and schemas will be declared in `tools.json`; representative names are `parking.search`, `parking.facility.get`, `parking.quote.create`, `parking.reservation.create`, `parking.reservation.list`, `parking.reservation.get`, `parking.reservation.requote`, `parking.reservation.modify`, `parking.reservation.cancel`, `parking.disruption.alternatives`, and `parking.disruption.resolve`. Infra-only `env.load_seed`, `env.apply_event`, `env.advance_time`, `env.snapshot`, and `env.reset` will load histories, inject world changes, advance deadlines, inspect outcomes, and restore a clean run. Setup, reset, time control, and event injection will not be exposed to the Agent.
- **State and lifecycle (required):** Each App instance represents one customer's account and is isolated by Core's `run_id` and `app_id`. Synthetic seed data will contain facilities, operating hours, amenities/restrictions, time-bounded inventory and rates, cancellation policies, a customer profile, saved vehicles, redacted payment-method metadata, and optional reservation history. A quote is immutable and expires at a declared virtual time; a reservation preserves the accepted quote/policy and revision history; cancellation or disruption resolution creates immutable adjustment records. Writes use idempotency keys and expected state versions. Duplicate successful retries return the prior result, stale concurrent changes fail without partial state changes, and each commit returns the resulting object status plus Core epoch/revision. Reset replaces business state, audit/receipts, and task-loaded history with the fixture baseline; snapshots provide deterministic review evidence but are not an Agent restore feature.
- **Events and notifications (required):** The App will accept task/Infra events for `parking.facility_availability_changed` and `parking.inventory_adjusted`. A facility-unavailable event includes stable event/facility IDs, affected time bounds, reason category, and effective virtual time; it marks overlapping active quotes invalid and upcoming reservations `action_required` without selecting an alternative. Inventory events change future availability and prices but never rewrite an accepted reservation. Events are idempotent, and quote expiry/cancellation deadlines are evaluated against Core virtual time. Parkstead will optionally publish compatible `channel.email` CloudEvents for the Mail messages listed above. A disruption message identifies the Parkstead reservation as `source_object`, summarizes the affected booking and available next actions, and excludes raw payment credentials or full App state. Sender commit, receiver commit, and delivery acknowledgement remain separate outcomes. Task scenarios, not the App, decide when external events occur.
- **Shared data and dependencies (required):** Shared references include `person_id`, `parking_account_id`, `facility_id`, `rate_id`, `vehicle_id`, `quote_id`, `reservation_id`, `adjustment_id`, and `event_id`. Vehicles use synthetic make/class/color/plate-region metadata; payment methods are redacted synthetic records containing only brand, last four digits, expiry month/year, and eligibility flags. The initial App requires no attachments. Facility imagery will be original simple SVG/PNG illustrations or neutral generated placeholders with catalog provenance and graceful missing-image behavior. The package will run independently with the repository's pinned public Core/runtime and Node.js 18+ using only built-ins. Mail 1.3.0 is optional in run assembly for notification evidence and is not required for core parking workflows.
