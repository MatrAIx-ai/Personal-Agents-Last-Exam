## 2. What you plan to build

**✍️ Your answer (required):** Lintel is a resettable rental app covering both ends of renting: finding a place (search, saved searches, tours with exclusive slots, applications with a fee charged once) and keeping one (lease terms, renewal offers with several term options, landlord offers, notice to vacate). The writes that matter are final or cost money, and the right one depends on dates and plans that are not in the request.

Eight workflows, each end to end including change and cancellation:

1. **Search.** Filter listings by rent, bedrooms, pets, move-in date, lease length and neighborhood. Listing detail shows fees, deposit, required documents and the lease terms on offer.
2. **Saved searches.** Save a search, read its new and changed matches at any time, and get one dated digest a day when there are any. Delete it to stop.
3. **Tours.** See open slots, get a quote for one, confirm, reschedule or cancel, and export the tour as an iCalendar file. Slots are exclusive, and one can be taken by another renter between quote and confirm. The landlord can cancel a tour.
4. **Applications.** Start an application, attach the required documents, get a quote for the fee, submit once, or withdraw. The fee, once paid, covers further applications for 30 days, so what a submit costs depends on what the user already paid. Status moves by event (received, more information needed, approved, rejected). If the listing is withdrawn, its undecided applications close and its booked tours are cancelled.
5. **Lease.** Read the current lease: term, rent, deposit, break clause, notice period, early-termination charge, renewal window and the lease text.
6. **Renewal.** Read the landlord's offer and its deadline, ask for terms that are not offered by default (a shorter term, a break clause) and read the landlord's answer when it arrives, get a quote for what an option costs and what leaving would cost, then accept or decline. If the deadline passes unanswered, the default stated in the lease applies.
7. **Landlord offers.** Accept or decline a mid-term offer before its deadline, for example a cash incentive to convert to a longer term.
8. **Notice to vacate.** Get a quote for the earliest penalty-free end date and any charge, confirm, or withdraw while the lease allows it.

Housing requests are underdetermined on their own. "Renew like always" or "book the Saturday tour" is right or wrong depending on a possible job change, a lease that ends six weeks before the new one starts, or a neighborhood the user ruled out after an earlier visit, and those facts sit in history and in other apps. The costs are concrete: a slot someone else took, a fee that is charged once, a 24-month term with a penalty for leaving. Every outcome a task is likely to grade is a stored field with a receipt (which slot, which term, what it cost, when it was confirmed), so a grader can read state instead of judging a transcript.

One success and one refusal per workflow, with the state a grader would read. A refusal returns the named status with `applied: false` and changes nothing.

### Integration details

- **Operations and access (required):** MCP only in the baseline: 34 tools on the Agent connection (19 reads, 15 writes), and Core's Infra operations on a separate connection.
  - Search: reads `lintel.listings.search`, `lintel.listings.get`, `lintel.policies.get`. No writes.
  - Saved searches: reads `lintel.saved_searches.list`, `lintel.alerts.list`. Writes `lintel.saved_searches.create`, `lintel.saved_searches.delete`.
  - Tours: reads `lintel.tours.slots`, `lintel.tours.list`, `lintel.tours.book.preview`, `lintel.tours.export_ics`. Writes `lintel.tours.book.confirm`, `lintel.tours.reschedule`, `lintel.tours.cancel`.
  - Applications: reads `lintel.applications.list`, `lintel.applications.get`, `lintel.applications.submit.preview`, `lintel.payments.schedule`. Writes `lintel.applications.start`, `lintel.applications.update`, `lintel.applications.submit.confirm`, `lintel.applications.withdraw`.
  - Lease: read `lintel.lease.get`. No writes.
  - Renewal: reads `lintel.renewal.get`, `lintel.renewal.accept.preview`. Writes `lintel.renewal.request_terms`, `lintel.renewal.accept.confirm`, `lintel.renewal.decline`.
  - Landlord offers: read `lintel.offers.list`. Write `lintel.offers.respond`.
  - Notice: read `lintel.notice.preview`. Writes `lintel.notice.confirm`, `lintel.notice.withdraw`.
  - Notifications: read `lintel.notifications.list`. No writes.
  - Reads return `status: ok` and never change data. Writes take `request_id` and `expected_version` and return `committed` with the new version. Tools name their target as `id` and field changes as `patch`, so Core policy constraints on IDs and fields apply.
  - Quotes: the four `*.preview` tools are reads. Each returns a quote (the terms, the cost and `quoted_at`, the value of `ctx.virtual_now` when it was computed) and stores nothing. The matching `*.confirm` is a write that carries the quote back unchanged. Lintel recomputes the terms and cost at the confirm's own time and commits only if they match; otherwise it returns `quote_changed` with the current quote and applies nothing. A quote has no expiry of its own, so nothing depends on a preview being kept. `lintel.payments.schedule` is a read: ledger entries so far and upcoming rent dates from the lease.
  - Consequential writes: `lintel.tours.book.confirm`, `lintel.applications.submit.confirm` (charges the fee), `lintel.renewal.accept.confirm`, `lintel.offers.respond` and `lintel.notice.confirm`. Lintel has no approval prompt of its own; a Task policy allows, denies or constrains them per profile.
  - Infra only, provided by Core and neither listed nor callable on the Agent connection: `env.load_seed`, `env.apply_event`, `env.reset`, `env.snapshot`, `env.event_status`, `env.validate_bundle` and `env.advance_time`. Lintel implements the plugin hooks `validateSeed`, `handleTool`, `applyEvent`, `records`, `objects` and `references`.
  - No GUI and no reviewer console in the baseline. Web pages are optional module D in section 4.
- **State and lifecycle (required):** One Lintel instance is one renter account. Core owns versions, receipts, the clock and reset; Lintel owns its records.
  - Ownership: Lintel's data, all of it loadable through `schemas/seed.schema.json`, is the catalog (listings, landlords and agents, tour slots, lease templates, policies), the account's records (saved searches, tours, applications and their documents, lease, renewal offers, terms requests, landlord offers, notice, payment ledger) and its notification records. Core's state is `virtual_now`, epoch and revision, request and event receipts, audit, the binding and the policy profile. A second renter is a second App instance with its own state, as in the Mail-to-Mail example.
  - Records and states: listing `listed` → `withdrawn`. Tour slot `open` → `booked` (this account), `taken` (another renter) or `closed` (the landlord). Tour `confirmed` → `cancelled`, and it reads as `completed` once its start has passed. A reschedule keeps the tour ID and moves it to another open slot, and a renter's cancel or reschedule reopens the old slot. Application `draft` → `received` → `approved` or `rejected`, with `more_info_needed` in between (an update that adds the missing documents returns it to `received`), `withdrawn` by the renter and `closed` when its listing is withdrawn. Renewal offer `open` → `accepted`, `declined` or `lapsed`. Terms request `open` → `granted` or `declined`. Landlord offer `open` → `accepted`, `declined` or `expired`. Notice `given` → `withdrawn`. Lease `active` → `notice_given`, and back to `active` if the notice is withdrawn. Saved search `active` → `deleted`. Records are closed, never removed.
  - History: a Task loads its own account and history with `env.load_seed`. Past tours, applications and ledger entries and a lease at any stage use the same seed schema. `validateSeed` rejects unknown references (a lease naming a missing template, a tour on a missing slot), impossible dates and a renewal option whose cost cannot be recomputed from its stored terms.
  - Writes: Core's rules apply unchanged. A repeated `request_id` with the same arguments returns the stored result with `duplicate: true`, a different payload returns `idempotency_conflict`, and a stale `expected_version` returns `stale_version`; nothing is applied in the last two cases. Lintel's own refusals are `not_found`, `invalid_state`, `slot_unavailable`, `quote_changed`, `listing_withdrawn`, `missing_documents`, `already_submitted`, `deadline_passed`, `already_responded`, `notice_too_short` and `no_lease`. New record IDs are the next number after the highest of that type in Lintel's data, and times come from `ctx.virtual_now`, so the same seed and the same calls give the same data.
  - Time: Lintel has no scheduler and accepts no clock event. Every time-dependent value is derived from `ctx.virtual_now` when a tool or event runs. A tour whose start has passed reads as `completed`. A renewal offer past `respond_by` reads as `lapsed` and the lease shows its stated default (month to month at the stated rent, or ending at term end). A landlord offer past `respond_by` reads as `expired`. The 30-day fee window, the renewal window and the earliest penalty-free end date are computed from the clock. A read computes these without storing them. The next write or event stores what has fallen due, in the same commit, before doing its own work. Advancing the clock with `env.advance_time` therefore changes what reads return without Lintel being called.
  - Reset and snapshot: Lintel declares `reset_scope: app_instance`. `env.reset` returns this instance to its loaded seed and clock, starts a new epoch and clears receipts and audit. It touches no other App: mail already delivered stays in Mail, and calendar entries the agent made stay in Calendar, until Infra resets those Apps too. `env.snapshot` is inspection evidence and no restore operation is promised. To return to an earlier point, Infra reloads that snapshot's `data` with `env.load_seed`, which also starts a new epoch and clears receipts and audit, so the snapshot is exported first. Where tests compare or hash states they cover `snapshot.data` and `snapshot.virtual_now` only, never epoch, revision, receipts or audit.
  - Grading evidence: each record written by a tool stores the `request_id` of the write that created or last changed it, so a grader can join Lintel's records in `env.snapshot` to the agent's own execution records and to Core's receipts. A repeated request adds no record and no ledger entry.
  - Missing data: an unknown ID returns `not_found`. A listing with no open slots returns an empty list. An account with no tenancy returns `no_lease` from the lease, renewal, offer and notice tools. An application missing a required document cannot be submitted.
- **Events and notifications (required):** Eight task-scripted events in the runtime envelope, one send-only Mail channel, no clock event, and nothing received from other Apps.
  - Events are applied by Infra with `env.apply_event`, and the handler sees the event's `at` as `ctx.virtual_now`. The Task decides content and timing; Lintel defines the effect. An event that does not fit the current state is rejected as `invalid_event` and changes nothing.
    - `lintel.listing.upsert`: creates a listing or replaces its listed fields. From that time, saved searches it matches show it as new or changed in `lintel.alerts.list`. Example: `{"event_id": "evt-lst-0142-post", "at": "2027-06-09T09:30:00-04:00", "operation": "lintel.listing.upsert", "payload": {"listing": {"id": "lst-0142", "landlord_id": "ll-07", "address": "41 Alder St, Unit 3B", "neighborhood": "Eastbank", "rent": 1840, "bedrooms": 2, "pets": "cats", "available_from": "2027-08-01", "lease_months": [12, 24], "application_fee": 35, "deposit": 1840, "required_documents": ["photo_id", "pay_stub"], "status": "listed"}}}`.
    - `lintel.listing.withdraw`: the listing becomes `withdrawn` and leaves search. Its confirmed tours become `cancelled` with `cancelled_by: landlord`. Its applications in `draft`, `received` or `more_info_needed` become `closed` with reason `listing_withdrawn`; decided applications are unchanged. A fee already charged stays in the ledger and still covers other applications for its 30 days. One `tour.cancelled` or `application.status_changed` notification per affected record. Example: `{"event_id": "evt-lst-0142-gone", "at": "2027-06-15T16:30:00-04:00", "operation": "lintel.listing.withdraw", "payload": {"listing_id": "lst-0142", "reason": "leased"}}`.
    - `lintel.tour.slot_take`: another renter takes an open slot and it becomes `taken`. A later confirm or reschedule naming it returns `slot_unavailable`. Example: `{"event_id": "evt-slot-1400", "at": "2027-06-10T09:55:00-04:00", "operation": "lintel.tour.slot_take", "payload": {"slot_id": "slot-0142-0612-1400"}}`.
    - `lintel.tour.cancel_by_landlord`: the tour becomes `cancelled` with `cancelled_by: landlord`, its iCalendar sequence increases so the export is now a cancellation, and the slot becomes `closed` unless `slot_reopens` is true. One `tour.cancelled` notification. Lintel does not touch Calendar. Example: `{"event_id": "evt-tour-7-cancel", "at": "2027-06-11T18:00:00-04:00", "operation": "lintel.tour.cancel_by_landlord", "payload": {"tour_id": "tour-000007", "reason": "agent unavailable", "slot_reopens": false}}`.
    - `lintel.application.set_status`: sets an application in `received` or `more_info_needed` to `more_info_needed`, `approved` or `rejected`, with a note. One `application.status_changed` notification. Example: `{"event_id": "evt-app-3-info", "at": "2027-06-14T10:00:00-04:00", "operation": "lintel.application.set_status", "payload": {"application_id": "app-000003", "status": "more_info_needed", "note": "Upload a recent pay stub."}}`.
    - `lintel.renewal.issue_offer`: creates an `open` renewal offer with its term options and deadline. One `renewal.offer_issued` notification. Example: `{"event_id": "evt-rnw-1", "at": "2027-05-03T09:00:00-04:00", "operation": "lintel.renewal.issue_offer", "payload": {"renewal_id": "rnw-0001", "lease_id": "lease-0001", "respond_by": "2027-05-31T23:59:59-04:00", "options": [{"option_id": "opt-24", "term_months": 24, "rent": 1060, "early_termination_fee": 4240}, {"option_id": "opt-12", "term_months": 12, "rent": 1150, "early_termination_fee": 2300}]}}`.
    - `lintel.renewal.answer_terms`: the landlord's answer to one open request written by `lintel.renewal.request_terms`. `granted` adds the option to the offer; `declined` closes the request and changes nothing else. One `renewal.terms_answered` notification. Example: `{"event_id": "evt-rnw-1-answer", "at": "2027-05-06T14:00:00-04:00", "operation": "lintel.renewal.answer_terms", "payload": {"renewal_id": "rnw-0001", "terms_request_id": "trq-000001", "decision": "granted", "option": {"option_id": "opt-12b", "term_months": 12, "rent": 1190, "break_clause_after_months": 6}}}`.
    - `lintel.offer.issue`: creates an `open` mid-term landlord offer. If the renter accepts before `respond_by`, the lease converts to the offered term and the incentive is credited in the ledger. One `offer.issued` notification. Example: `{"event_id": "evt-ofr-1", "at": "2027-06-10T09:00:00-04:00", "operation": "lintel.offer.issue", "payload": {"offer_id": "ofr-0001", "lease_id": "lease-0001", "kind": "convert_term", "term_months": 24, "incentive": 500, "respond_by": "2027-06-24T17:00:00-04:00"}}`.
  - Notifications: nine kinds, each a Lintel record created in the commit that causes it: `tour.confirmed`, `tour.rescheduled`, `tour.cancelled`, `application.received`, `application.status_changed`, `renewal.offer_issued`, `renewal.terms_answered`, `offer.issued` and `saved_search.digest`. The digest is the only one driven by time: at most one per saved search per day, due at 08:00 in the account's time zone when there are new or changed matches since the last one. It is created by the first write or event at or after its due time. If nothing is written none is created. `lintel.alerts.list` returns the digests so far and the matches not yet in one, so the matches are readable either way.
  - Mail contract: Lintel is send-only. It will declare one `messaging.publishes` entry, `{"channel": "channel.email", "event_type": "org.pale.mail.notification.v1", "schema_id": "urn:pale:email-message:2", "schema_ref": "schemas/router-message.schema.json", "payload_schema_id": "urn:pale:email-payload:1", "status": "implemented"}`, with a pinned copy of Mail's wire schema, and an empty `receives` list. This matches the `channel.email` receive declaration of Mail 1.3.0. Each message has one recipient (the account owner as a `person_ref`), one `source_object` (the tour, application, renewal offer, landlord offer or saved search it is about) and a plain-text body with empty `asset_ids`. The message `id` is `lintel-` plus the notification's record ID, and `subject` is the ID of the record it is about. Full wire message for a tour confirmation:

    ```json
    {
      "specversion": "1.0",
      "id": "lintel-ntf-000012",
      "source": "urn:pale:app:lintel:account:lintel-maya",
      "type": "org.pale.mail.notification.v1",
      "time": "2027-06-10T10:05:00-04:00",
      "subject": "tour-000007",
      "datacontenttype": "application/json",
      "dataschema": "urn:pale:email-payload:1",
      "data": {
        "channel": "channel.email",
        "recipient": {"kind": "person_ref", "id": "person-maya"},
        "source_object": {"app_id": "lintel", "account_id": "lintel-maya", "object_type": "tour", "object_id": "tour-000007"},
        "content": {
          "title": "Tour confirmed: 41 Alder St, Unit 3B on Sat 12 Jun at 11:00",
          "body": {"format": "text/plain", "text": "Your tour of 41 Alder St, Unit 3B (Eastbank) is confirmed for Saturday 12 June 2027, 11:00 to 11:30 (UTC-04:00), with Dana Whitlock of Alder Property Group. Tour ID: tour-000007. You can reschedule or cancel in Lintel until the tour starts."},
          "asset_ids": []
        },
        "extensions": []
      }
    }
    ```

  - Delivery: the Lintel write and the Mail delivery are separate commits, with no outbox. Lintel ships an App-owned outbound adapter (`src/publisher.cjs`, the same arrangement as Mail's) that turns a notification record into the wire message above. A trusted runner reads the record and passes the message to `router.publish`. Lintel never calls Mail, stores no delivery status and never rolls a write back, so its own records are the same in every case below: the write is committed and the notification is listed by `lintel.notifications.list`. A committed receipt means Mail stored the message; whether the tour is confirmed is decided by Lintel's record alone. Outcomes, read from the receipt and from Mail:
    - `committed`: Mail holds one message whose ID is the receipt's `event_id`.
    - Retry of the same message: the same receipt with `duplicate: true`, and still one message in Mail.
    - `rejected` (for example `recipient_not_authorized` when the run grants Lintel no Mail route, `recipient_unavailable` or `incompatible_contract`): no message in Mail.
    - `unknown` (`receiver_unconfirmed`): the acknowledgement was lost. The run stops with the attempted `event_id`, and the runner inspects Mail before retrying the same message.
  - Calendar: Lintel sends Calendar nothing. `lintel.tours.export_ics` returns the tour as one UTC `VEVENT` in the subset that `calendar.import_ics` accepts, with a stable `UID` and a `SEQUENCE` that increases on reschedule and cancellation, so the agent's import creates, moves or cancels one calendar event. Export for the tour above:

    ```text
    BEGIN:VCALENDAR
    VERSION:2.0
    PRODID:-//PALE//Lintel//EN
    BEGIN:VEVENT
    UID:tour-000007@lintel.pale.example
    DTSTAMP:20270610T140500Z
    DTSTART:20270612T150000Z
    DTEND:20270612T153000Z
    SUMMARY:Tour: 41 Alder St\, Unit 3B
    LOCATION:41 Alder St\, Unit 3B\, Eastbank
    SEQUENCE:0
    STATUS:CONFIRMED
    END:VEVENT
    END:VCALENDAR
    ```

  - Checks run on these examples at `61b6371` (public runtime 1.6.0): every event example validates against the reference event envelope with `runtime/contracts/schema-validator.cjs`, and the wire message validates against Mail's `router-message.schema.json`. Through real MCP processes, `router.publish` delivered the message to Mail 1.3.0 once from a throwaway send-only fixture carrying the declaration above, returned `duplicate: true` on retry, and returned `recipient_not_authorized` without a grant, leaving Mail unchanged. `calendar.import_ics` in Calendar 1.3.0 accepted the export, moved the same event on a higher `SEQUENCE` and cancelled it on `STATUS:CANCELLED`. These check the examples against the receiving contracts, not a Lintel implementation, which does not exist yet.
