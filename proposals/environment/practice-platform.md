## 2. What you plan to build

**✍️ Your answer (required):** Milepost is a resettable practice platform that tracks one student's mastery skill by skill, so tasks can test whether an agent plans practice that fits this student and replans when results or dates change.

Study help differs from an errand: the same plan can be right for one student and useless for another, depending on what this student knows, what they have forgotten and when they can study. Milepost makes that checkable. For any plan it reports the level each covered skill is projected to reach by the date and, to the grader, every study rule the plan breaks. Tasks define success, including trade-offs and how much practice is too much. The projection uses a synthetic learner rule (v1, below) and assumes planned practice is completed; it is not evidence of real learning gains.

Each instance holds one student account. The four workflows below are the acceptance baseline.

1. **Where the student stands.** Courses, units and skills with their prerequisites; the student's mastery of each skill and when it was last practised; assessments with their date, skills and a target level per skill; past results. Mastery fades with the time since practice, more slowly after spaced practice (learner rule v1 below). An unknown ID returns `not_found`.
2. **Plan practice.** A study block has a date, a start, a length and one skill, and can be added, changed and removed. `plan.project` returns, for the stored plan and one assessment, the level each covered skill would reach by that date if every planned block is completed. Broken study rules are not in its result; the plan checker reports them to the grader. Errors cover overlapping blocks, a block in the past and an unknown skill.
3. **Record practice.** A completed session arrives as an event with its skill and minutes and raises mastery, less so when the skill's prerequisites are weak. The student can also report practice done elsewhere; the agent records it with its source and time and can remove it but not edit it (a correction is remove, then record); removal recomputes the skill from its history without that entry, so later assessment results stay. Sessions that arrived as events cannot be removed. A report in the future or over a recorded session is refused. A planned block that passes without practice is marked missed.
4. **Replan after a change.** A posted result sets the mastery of the skills it measured. An added or moved assessment, or a change to the student's study rules, changes what can be reached. The plan is edited to fit, and `plan.project` shows what it still reaches. Events follow the ID rules in section 3; a refused event changes neither data nor the clock.

The student's study rules (hours available, daily cap, rest days, block length) are readable. Milepost enforces only its own limits, such as no overlapping blocks. It does not stop a plan that breaks the student's rules or a record of practice that did not happen: every committed write goes to an evaluator-only activity log, and the task's grader decides.

Illustrative uses, not Task Track submissions:

- "Get me ready for Friday's quiz": plan only what this student needs. In the twin, the projection shows every covered skill above its target on Friday without practice, and the right answer is to say so and plan nothing.
- The exam moves three days earlier and two evenings are lost: plan what fits and say which skills will not be reached.
- "I did all four blocks": `practice.list` shows two. Check the times the student reports against the recorded sessions before adding any student-reported practice.

Each reference scenario has a twin: a copy of its seed in which one part of the student's record is changed, either mastery with the practice history that explains it, or a study rule. Each pair states which decision must change and why.

The scenario design and the learner rule below come from my own pre-release [LearnerAgentBench](https://github.com/LixinTu/LearnerAgentBench/blob/ff3807ae6bd531f41a34528443658987dca13b55/src/learneragentbench/learner/model.py) (its transparent learner model at commit `ff3807a`). The App is new code in the public App package format.

### Learner rule v1 and expected states

`milepost-learner/1` is App business logic: tasks read its results and define their own success. Each skill record holds a level *m*, a stability *S* in days and the time *t₀* that *m* refers to; a skill never practised or assessed has no *t₀* and does not fade. Each student has learning parameters, kept in evaluator-only data. The defaults are learning rate λ = 0.5 per hour, prerequisite floor φ = 0.3, retention base ρ = 0.9, stability growth γ = 0.6 and spacing bonus β = 0.5; *S* stays within 1–60 days.

```text
level at time t:            L(t) = m · ρ^((t − t₀) / S)            t − t₀ in days
practice, d min ending t:   R = ρ^((t − t₀) / S);  a = m · R
                            P = lowest prerequisite level at the session's start (1 if none)
                            m ← min(1, a + λ · (d / 60) · (1 − a) · (φ + (1 − φ) · P))
                            S ← S · (1 + γ + β · (1 − R));  t₀ ← t
result ℓ posted at t:       m ← ℓ;  t₀ ← t           S and the last-practised time unchanged
```

Weak prerequisites lower the gain, and practice after more forgetting (lower *R*) raises *S* more, so spaced practice fades more slowly. A skill's state is recomputed from its seeded record by applying its sessions (at their end) and results (at their posting) in time order, a result after a session at the same instant. Removing reported practice deletes that entry and recomputes: a later result still sets the level at its own time, and only *S*, and with it the fading afterwards, changes. `plan.project` applies each planned block that ends after now and by the assessment's time as a completed session, in time order, and returns *L* at that time for each target skill with its target; missed blocks change nothing. Results show levels to three decimals and name the rule version; the rule itself is not rounded. Changes from the source model: one skill per session (the source split a block across skills); posted results, removal and the replay order are new.

### Integration details

- **Operations and access (required):** 13 agent-facing MCP tools, prefixed `milepost.`: `courses.list`, `skills.list`, `mastery.get`, `assessments.list`, `practice.list|record|remove`, `plan.list|project|add_block|update_block|remove_block`, `preferences.get`. The `list`, `get` and `project` tools only read; the other five write. One reviewer renderer in `gui/` has four views (overview, skills and mastery, plan, practice log); reviewers are the only GUI audience the reference profile accepts. Infra operations are the runtime's six lifecycle operations (`env.load_seed`, `env.reset`, `env.apply_event`, `env.snapshot`, `env.event_status`, `env.validate_bundle`) and the host's clock operation `env.advance_time`, all kept off the agent connection by Core. Task graders call the App's plan checker, a pure function that is not an agent tool: its input is a snapshot and an assessment ID, and its output, for graders only, is the projected level of each target skill and the study rules the plan breaks.
- **State and lifecycle (required):** As in the public runtime, state is kept per run and App instance, and only Core commits, resets or snapshots it. Milepost's data has three parts: course data (the shared catalog), the student's record (the account's mastery, practice, plan and study rules), and evaluator-only records (the activity log and the student's learning parameters), which only `env.snapshot` returns, never a tool result, error or page. A task loads its own seed, including practice history and past results, and its starting time (`virtual_now`) with `env.load_seed`; `env.reset` restores that seed and time for this App instance only, and `env.snapshot` returns the whole state. Each write takes a `request_id` and an `expected_version` and returns the committed result with the new version; a repeated `request_id` with the same request returns the first result, a reused one with a different request fails with `idempotency_conflict`, and a stale `expected_version` fails with `stale_version`. A grader joins the activity log with Core's audit and the supplied agent execution trace by `request_id` and version; a repeated `request_id` adds no entry, and graders read `env.snapshot` before any reset, which discards the run's log and audit. Mastery and missed blocks are one deterministic function of state and virtual time, computed when read; reads change nothing. Core moves the clock with `env.apply_event`, whose handler sees the event's time as `ctx.virtual_now`, or with `env.advance_time`, which runs no handler; tool results do not carry the clock, so every Milepost read returns the current virtual time. Times use the student's time zone.
- **Events and notifications (required):** Scenario events use the reference format and are applied with `env.apply_event`: `milepost.practice.completed` (a session is recorded), `milepost.assessment.result_posted` (sets the mastery of the measured skills), `milepost.assessment.added` (a new assessment), `milepost.assessment.moved` (an existing assessment gets a new date) and `milepost.preferences.changed` (the student edits a study rule). Task scenarios decide when they occur; between sessions Infra moves the clock with `env.advance_time`. Milepost neither publishes nor receives messages. Example input: `{"event_id": "ev-7", "at": "2027-03-02T19:40:00-05:00", "operation": "milepost.practice.completed", "payload": {"block_id": "blk-1", "skill_id": "alg-factoring", "minutes": 40}}`, with the effect in E3. All five share this envelope. ID rules: `practice.completed` may name a planned block of the same skill; `result_posted` `{assessment_id, results: [{skill_id, level}]}` needs an existing assessment, at or after its date, only its target skills and levels from 0 to 1, once per assessment; `added` `{assessment_id, date, targets: [{skill_id, level}]}` needs a new ID (an existing one is `duplicate_id`), a date after the event and at least one target on a known skill; `moved` `{assessment_id, date}` needs an existing assessment without a result and a date after the event; `preferences.changed` `{rule, value}` takes `available_hours`, `daily_cap_minutes`, `rest_days` or `block_minutes`, for example `{"rule": "rest_days", "value": ["Sat"]}`. A missing assessment, skill or block is `unknown_reference` and a bad value `invalid_value`; a refused event changes neither data nor the clock (E5).
- **Shared data and dependencies (required):** Stable IDs for the student and every object. `binding.json` maps the student to a person ID. Text only, with an empty asset catalog. The package runs on its own with only its files and the pinned shared runtime (release 1.6.0, including Core's virtual time): no other App, no other App's state and no external service. Calendar is a separate App the agent may call, not a package dependency.
