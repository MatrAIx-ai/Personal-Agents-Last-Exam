## 2. What you plan to build

**✍️ Your answer (required):** Payleaf is a resettable employee self-service portal, seen from one salaried employee's account, in which every change waits for a deadline that the person did not choose: a new bank account applies only from the first pay run whose cut-off has not passed, leave needs notice and hours, and benefits can be chosen only while a window is open. So a change the portal accepts can still arrive too late for this person's rent, trip or surgery. The account holds the person's pay settings, questions to payroll, leave requests and benefit choices; payroll, the manager and the benefits team act through task-supplied events, and every time-based state follows the environment clock. Four workflows are complete in the first version.

**Entities.** Employer (time zone and five rules), employment record (job, department, manager, hire date), pay calendar entry (pay period, pay date, cut-off time; `planned` or `paid`), pay statement (pay date; lines for earnings, taxes and deductions; net pay; one deposit for each account that receives money), deposit setup (up to three accounts, each with a label and a share of net pay), withholding form (filing status, an amount for dependents, an extra amount for each pay), retirement contribution (a percentage of salary), setting change (which setting, the new value, when it was made, state), pay inquiry (the statement or one of its lines, the question, an amount, a note; state and answer), leave type (hours earned for each pay period, a carryover cap and a carryover date), leave entry (earned, corrected or forfeited hours), leave request (type, first and last day, hours for each day, state), company holiday, benefit plan (its options with a cost for each pay, a yearly maximum where it has one, and whether it rolls over), enrollment window (plan year, opening and closing time), election set (one choice for each plan, for one plan year), notification, account preferences.

**Simplifications.** One App instance holds one salaried employee's account at one fictional employer. Payroll staff, the manager and the benefits team are not accounts: what they do arrives as events. Payleaf computes no tax: the earnings and the taxes of each pay run are task data. It does compute what follows from the person's own choices: deductions from the benefit elections and the retirement percentage, net pay, and the split of net pay across the deposit accounts. There are no hours, shifts or overtime, no expense reports, no health claims, no dependents, beneficiaries or life events, and no document files. Money does not move: a deposit is a record, and a bank account is a label. A day is a calendar day in the employer's time zone, and a working day is Monday to Friday that is not a company holiday. The employer's rules are five values: how many days ahead vacation and personal leave must be asked for (`leave_notice_days`), how many days back sick leave may start (`sick_backdate_days`), how many days after its pay date a statement can be questioned (`inquiry_window_days`), the largest retirement percentage (`max_retirement_percent`) and the number of pay periods in a year (`pay_periods_per_year`).

- **W1 Pay, the calendar and records (read-only).** Read the employment record (`employment.get`); list the pay calendar in a window of pay dates, with each entry's cut-off (`calendar.list`); list pay statements in a window of pay dates and read one with its lines, its deposits and the settings it used (`pay_statements.list`, `pay_statements.get`; the lists filter and sort by pay date only); read the pay settings: the deposit setup, the withholding form and the retirement percentage, each with the value the last run used and any change that is waiting or locked, with the pay date it will first apply to (`settings.get`); list setting changes (`changes.list`); list pay inquiries (`inquiries.list`); read leave balances with what is available and what will expire (`leave.balances`); list leave requests (`leave.list`); check in advance what a leave request would cost (`leave.preview`: the working days and hours it would take, the hours available, and every rule it would break); list enrollment windows (`benefits.windows`); read the plans, the elections in force, the saved choices and the submitted set of a window (`benefits.get`); list notifications (`notifications.list`); read the account's preferences (`preferences.get`). What payroll and the manager do is taken as given, and flags say where it leaves a problem. Paths: modify, cancel and confirm are not applicable to reads; errors = unknown object (`not_found`), `invalid_window`.
- **W2 Pay settings, questions to payroll, and preferences.** Replace the deposit setup (`deposit.update`); replace the withholding form (`withholding.update`); set the retirement percentage (`retirement.set`); cancel a change that is still waiting (`changes.cancel`); ask payroll about a statement or one of its lines, with an amount and a note (`inquiries.open`), or withdraw the question (`inquiries.withdraw`); set the account's preferences (`preferences.update`: the time zone used in notification text, and `email_notices`). Each setting change waits for the first pay run whose cut-off has not passed. Paths: modify = make the change again: a newer change replaces one of the same setting that is still waiting; an inquiry records what was asked: withdraw it and ask again; cancel = `changes.cancel` before the cut-off, which brings back an earlier change for the same run if there is one, so each unwanted change is cancelled on its own; and `inquiries.withdraw` while the inquiry is open; errors = an unknown time zone (`invalid_timezone`), a deposit setup with more than three accounts, without exactly one account that takes the remainder, or with percentages above 100 in total (`invalid_split`), a retirement percentage above the largest allowed (`over_limit`), a cancellation after the cut-off (`too_late`), an inquiry later than `inquiry_window_days` after the pay date (`too_late`), a second open inquiry on the same statement line (`already_open`), a change that is not waiting or an inquiry that is not open (`invalid_state`). Confirm: `settings.get` shows the pay date a change would first apply to; the change is the commitment.
- **W3 Leave.** Ask for leave of one type from a first day to a last day, with the hours for each working day (`leave.request`); cancel it (`leave.cancel`). The manager's decision arrives as an event. Paths: modify = not offered, because a request records what was asked: cancel it and ask again; cancel = `leave.cancel` while the request is pending, or approved and before its first day; errors = vacation or personal leave that starts sooner than `leave_notice_days` from today, or a cancellation of approved leave on or after its first day (`too_late`), more hours than are available (`insufficient_balance`), days that overlap another pending or approved request (`conflict`), a last day before the first day, a range longer than 30 days, a range with no working day, or sick leave that starts more than `sick_backdate_days` ago (`invalid_window`), a request that is not pending or approved (`invalid_state`). Confirm: `leave.preview` runs the same checks without writing; the request is the commitment.
- **W4 Benefits enrollment.** While an enrollment window is open, save a choice for a plan: one of its options, a yearly amount for a plan that takes one, or no coverage (`benefits.elect`); submit the saved set (`benefits.submit`). A submitted set can be changed and submitted again until the window closes. Paths: modify = `benefits.elect` and `benefits.submit` again while the window is open; cancel = not offered: after a submission, the way back is to submit another set before the window closes; errors = a choice or a submission outside the window's opening and closing times (`window_closed`), an unknown plan or option (`not_found`), a yearly amount above the plan's maximum (`over_limit`), a submission in which a plan has no saved choice (`incomplete`). Confirm: `benefits.get` shows the saved choices beside the elections in force and what would happen if nothing is submitted; the submission is the commitment.

Rules:

- Time is the environment's. Payleaf has no timers, no scheduler and no clock event: Infra moves `virtual_now` with an event or with Core's `env.advance_time`, which runs no App code. Every time-based state is therefore stored as a due time and derived from `ctx.virtual_now` wherever it is read or checked: a change's `locked` from the cut-off, a leave request's `taken` or `lapsed` from its days, a window's `open` and `closed` and an election set's `final` or `defaulted` from the window's times, and the end of the inquiry window. Writes and events use the same derivation: a locked change cannot be cancelled, and a choice after the closing time is refused. Nothing is rewritten when a due time passes.
- A limit of N days after a moment ends at the end of the calendar day that is N days after the day of that moment, in the employer's time zone: this holds for `inquiry_window_days`. Leave that needs notice must start on or after the day that is `leave_notice_days` after today; sick leave may start on or after the day that is `sick_backdate_days` before today.
- A setting change applies to one pay run: of the planned runs whose cut-off is later than the moment the change was made, the one with the earliest cut-off, as the calendar stands. A cut-off that has passed cannot be changed and no cut-off can be put before the present, so once a change is `locked` its run is fixed. Until its run posts, a change's state is computed when read, and only `cancelled` is stored: of the changes of one setting that apply to one run and are not cancelled, the latest one made counts and reads `waiting` or `locked`, and the earlier ones read `replaced`. Cancelling the latest change therefore brings back the one before it, if that one is not cancelled. When a pay run posts, the handler uses the latest change for each setting and stores `applied` on it and `replaced` on the earlier ones of that run; a stored state does not change again. A change made after a cut-off does not replace the `locked` change of that run: it applies to the run after it. A change made while the calendar has no planned run reads `waiting` with no pay date until `calendar.changed` adds one.
- Net pay is computed by the handler when a run posts: the earnings in the event, minus the taxes in the event, minus the deductions. The deductions are taken in this order: the cost for each pay of every option in the election set in force for the pay date, in the order of the plans; for a plan that takes a yearly amount, that amount divided by `pay_periods_per_year` and rounded up to the cent, and never more than what is left of the yearly amount in that plan year; then the retirement percentage in force times the salary lines, rounded half up to the cent. If the pay left after the taxes does not cover a deduction, that deduction is taken in part, the later ones are not taken, and the statement carries a flag.
- Net pay is split across the deposit accounts in the order of the setup: first the accounts with a fixed amount; then each account with a percentage, which takes that percentage of what is left after the fixed amounts, rounded down to the cent; then the one account that takes the remainder. If net pay does not cover the fixed amounts, they are filled in order until nothing is left, and the statement carries a flag. Each deposit is a record with its own reference, and no record is written for an amount of zero.
- Payroll, the manager and the benefits team are not checked. A posted run, a changed calendar, an updated deposit, an answer, a decision, a leave correction and an opened window are applied as given; only the structure of the data is validated (§3).
- An inquiry can be opened on a statement, or on one of its lines, for `inquiry_window_days` from its pay date. A statement line has at most one open inquiry, and a question on the whole statement counts as its own line. An answer with the outcome `corrected` may name a correction; the money itself arrives on a later pay statement, as a line that names the inquiry.
- Leave hours are computed when read. A request costs its hours for each working day in its range, and nothing for a weekend day or a company holiday. `balance` is the hours earned and corrected, minus the hours of requests that are `taken`. `available` is `balance` minus the hours of requests that are `pending` or `approved`. A request needs `available` to cover its cost. `leave.request` and `leave.preview` check in this order: the type exists; the range is valid; the notice or the back-dating limit is kept; no day overlaps another pending or approved request; the hours are available. A write returns the first refusal, while `leave.preview` lists every rule that fails. Each posted pay run adds one leave entry for each leave type with the hours earned for a pay period. A request of a type that needs notice and is still `pending` on its first day is `lapsed` and frees its hours; sick leave needs no notice and stays `pending` until the manager decides.
- A leave type can have a carryover cap and a carryover date. `expiring` is what would be above the cap on that date: `balance`, minus the hours of pending and approved requests for days on or before the carryover date, minus the cap, never below zero. It is shown until the carryover date. The forfeit itself is the employer's act and arrives as a leave correction.
- A plan year is a calendar year and has one election set in force and at most one enrollment window, which closes before the plan year starts. When a window opens, the saved choices start as the choice in force for each plan that rolls over, and empty for each plan that does not roll over or is new. `benefits.elect` saves one choice and changes nothing else; `benefits.submit` takes the saved choices as a whole and needs one for every plan in the window. The set in force for the plan year is the `final` set, or, if nothing was submitted, the `defaulted` set: the choice of the year before for each plan that rolls over, and no coverage for each plan that does not roll over or is new. A plan that is not in the window keeps the choice of the year before. A plan year with no window takes the same default as a window with no submission. Deductions follow the set in force from the first pay date in the plan year.
- Flags are computed when read and never stored. On the account: `change_waiting` (a setting change is `waiting` or `locked`), `deposit_returned` (a deposit is `returned` and not yet `reissued`), `leave_expiring` (`expiring` is above zero), `enrollment_open` (a window is open and no set is submitted) and `will_default` (the same, with a plan that does not roll over and has a choice this year). On a pay statement: `short_deposit` (net pay did not cover the fixed amounts) and `deductions_cut` (the pay did not cover every deduction). On a leave request: `lapsing` (it needs notice, is `pending` and starts within `leave_notice_days`).
- Notifications are written for what payroll, the manager and the benefits team do, never for my own writes and never for a change that time alone causes (a cut-off that passes, a window that closes and a request that lapses write none). One is written for each event: `payroll.run_posted`, `calendar.changed`, `deposit.updated`, `inquiry.answered`, `leave.decided`, `leave.adjusted` and `enrollment.opened`. A notification is listed from the moment it is written.

**Value for personal-agent tasks.** "Move my pay to the new account" is a different job on Monday and on Wednesday, and the portal says yes both times. After the cut-off, Friday's pay still goes to the old account, so the person must not close it yet. A pay date that the employer moves by three days can break a rent payment planned around the usual date. A reimbursement that was promised through payroll and is missing from the statement can be questioned only for a limited time, and asking twice makes two cases. Benefits that are not chosen while the window is open fall back to last year's, except the plan that does not roll over, which the person may need most next year. Leave above the cap disappears at the carryover date, and a week off needs notice. Because every change has a cut-off, every window an end and every request a balance, the order and the timing of what the agent does are part of the answer. Payleaf makes these checkable: which statements, calendar entries, settings and balances the agent read, which changes it made and when against each cut-off, which inquiries it opened, which leave it asked for and cancelled, which choices it saved and submitted and how long before the window closed, and what the account was told. Distinct task situations (separate Task proposals): (1) the person is closing a bank account and asks to move the pay, the cut-off for this week's run has passed, and the agent must say which pay date is the first to change; (2) the employer moves a pay date, and a plan the agent made around the usual date must be redone (Task #100 meets this problem with a pay date that is known only from emails); (3) a travel reimbursement paid through payroll is missing from a statement, and the agent must ask payroll once, inside the window, with the right amount (Task #129 meets this problem and plans a task-owned payroll inbox); (4) the enrollment window closes on Friday, the person has said nothing, and one plan will not roll over; (5) thirty hours of leave will be lost at the end of the year, and the days the person wants need notice and a manager's approval; (6) the person is ill today: sick leave can start today and vacation cannot. No Task proposal depends on Payleaf, and both tasks can keep their own fixtures; the rationale is independent of any one task. Fixtures are plain seed data, so each task loads its own employer rules, calendar, statements, settings, leave history, holidays, plans and windows.

A message to payroll or to a manager outside these workflows goes through the person's own Apps.

### Integration details

- **Operations and access (required):** 25 Agent-facing MCP operations over stdio on the Agent connection of the public host (`node runtime/cli.cjs serve --app apps/payleaf --role agent`), registered in `tools.json` as `payleaf.<name>`. Read (14): `employment.get`, `calendar.list`, `pay_statements.list`, `pay_statements.get`, `settings.get`, `changes.list`, `inquiries.list`, `leave.balances`, `leave.list`, `leave.preview`, `benefits.windows`, `benefits.get`, `notifications.list`, `preferences.get`. Write (11): `deposit.update`, `withholding.update`, `retirement.set`, `changes.cancel`, `inquiries.open`, `inquiries.withdraw`, `leave.request`, `leave.cancel`, `benefits.elect`, `benefits.submit`, `preferences.update`. Every write takes Core's `request_id` and `expected_version` and returns the object's `id` with the committed version. The target object is always the argument `id` and a time window is always `start` / `end`. For an operation that creates an object or acts on the account, `id` is the object it is about: the account for `deposit.update`, `withholding.update` and `retirement.set`; the pay statement for `inquiries.open`; the leave type for `leave.request` and `leave.preview`; the enrollment window for `benefits.elect`, `benefits.submit` and `benefits.get`. The reference host's audit projection at `61b6371` keeps `id`, `start` and `end` among the few inputs it records, so its audit rows show the object and the window of every call that has them, reads included; the first and last day of a leave request are passed as `start` and `end`. The Agent acts as the bound account holder set by Infra, never through an argument; a task can restrict the allowed tools with `policies.json`. App errors: `not_found`, `invalid_window`, `invalid_state`, `invalid_timezone`, `too_late`, `invalid_split`, `over_limit`, `already_open`, `insufficient_balance`, `conflict`, `window_closed`, `incomplete`. Core adds `invalid_arguments`, `permission_denied`, `stale_version` and `idempotency_conflict`; Payleaf also answers `invalid_arguments` for what an input schema cannot express (an amount or a number of hours of zero or less, more than eight hours for a day, a choice that names both an option and no coverage). Infra-only operations: `env.load_seed`, `env.apply_event`, `env.reset`, `env.snapshot`, `env.event_status`, `env.validate_bundle`, and the host's clock operation `env.advance_time` of runtime 1.6.0; they are not listed on the Agent connection and Core returns `permission_denied` if the Agent calls them. The first version has no GUI, no reviewer console and no console for payroll, a manager or the benefits team: other people act only through events.
- **State and lifecycle (required):** State is separate per run and App instance, and one instance holds one account (`isolation_keys: run_id, app_id`). The seed schema carries employer records (time zone, rules, company holidays, the pay calendar, leave types, benefit plans and enrollment windows) and account records (the employment record; pay statements with their lines and deposits; the deposit setup, the withholding form and the retirement percentage with their changes; pay inquiries; leave entries and leave requests; election sets and saved choices; preferences, notifications, activity rows), so a task can load any history, including many past pay statements, a change that is locked for the next run, a returned deposit, an open inquiry, leave above the cap and a window that is about to close. `validateSeed` rejects duplicate IDs, dangling references, a calendar entry whose cut-off is after its pay date, a paid entry with no statement, a statement whose net pay and deposits do not match its lines and the setup it names, a deposit setup that breaks the split rules, two open inquiries on one statement line, leave requests that overlap while pending or approved, a leave request with no working day, a window that closes before it opens or after its plan year starts, two windows or two election sets in force for one plan year, timestamps without a UTC offset and an account that the binding does not declare (`invalid_seed`). The seed is history: everything in it has already happened, and new facts arrive only through events; calendar entries that are still `planned`, and windows that have not closed, are the employer's published plan. Writes follow Core: an exact repeat of a committed `request_id` or `event_id` returns the stored receipt marked `duplicate`, so a repeated request makes no second change and asks for no second leave; the same ID with different input returns `idempotency_conflict`; a stale `expected_version` returns `stale_version`; a failed call leaves data, version and notifications unchanged and Core appends a denial audit row. Reads never change business data: the run a change applies to, leave hours, window states, the set in force and flags are computed from stored records and `virtual_now`, and `leave.preview` writes nothing. Reset is Core's: it restores the loaded seed and the time loaded with it (`reset_scope: app_instance`) and touches no other App; messages already delivered to Mail stay there. Evaluator records come from three places: (a) App state in the snapshot: activity rows with sequence, virtual time, actor `agent` or `event`, action, object ID and the `request_id` or `event_id` behind them, one for every committed Agent write, one for every applied event and one for each effect of that event (a change applied, a statement written, leave hours earned, a notification written); each setting change with the moment it was made and the run that used it; each pay statement with the settings it used; each inquiry, leave request and election set with its history; notifications with their creation time; (b) Core audit rows with virtual time and the projected `id`, `start` and `end`: one for every allowed call that is not a replay, one for every denied call, and one for every `env.advance_time` with the clock before and after; (c) full arguments and results in the supplied Agent execution trace. They join on `request_id`, `event_id` and version. Counting rules: count committed writes and event effects from the activity rows, one row each. Core returns the stored receipt for a repeated `request_id` or `event_id` before it appends an audit row, so a replay appears only in the trace, as a call whose result carries `duplicate: true`: count it as a retry of the original, never as a new action. A rejected attempt writes no activity row: count rejected attempts from the denial audit rows and the trace, one for each attempt, repeats included. Count reads from the allowed audit rows and the trace. Time-driven changes (a change locked, leave taken or lapsed, a window closed, an election set final or defaulted) run no App code and write no row: read them from the stored due times and the clock, and from the audit row of the `env.advance_time` call or the event that moved it. Take the snapshot before a reset, because reset clears the audit.
- **Events and notifications (required):** Seven events through `env.apply_event`, in Core's envelope. Payleaf has no clock event: Infra moves time with an event or with `env.advance_time`. An event is handled at its own time T, which is `ctx.virtual_now` inside the handler in runtime 1.6.0. Core rejects an event dated before the App's current time (`invalid_event`), and it validates the data after every event with the same rules as the seed; Payleaf also rejects a duplicate ID, an unknown calendar entry (except in a `calendar.changed` that adds one with its pay period, pay date and cut-off), an unknown statement, deposit, inquiry, leave request, leave type or plan, a pay run for an entry that is already `paid` or whose cut-off has not passed, a pay run with no earnings line or with taxes above its earnings, a calendar change to a paid entry, one that moves a cut-off that has already passed, one that puts a cut-off before T, or one that puts the cut-off after the pay date, a deposit update that does not follow `sent`, `returned`, `reissued`, an answer to an inquiry that is not open, a decision on a leave request that is not pending, a leave correction that would take a balance below zero, and a window that closes before it opens, that does not close before its plan year starts, or whose plan year already has a window (`invalid_event`, state unchanged).

- **Shared data and dependencies (required):** Stable IDs for calendar entries, pay statements and their lines, deposits, setting changes, inquiries, leave types, leave entries, leave requests, holidays, plans and their options, enrollment windows, election sets and notifications. The account's `account_id` and `owner_person_id` are the shared values of the run's `binding.json`, so the person has one ID in Payleaf and Mail, and notifications address the recipient by `person_ref`. The manager is named by `person_id`; a task that has the same person in Contacts or Messages gives them the same ID in its seeds, and Payleaf stores only a display name and a job title, not a copy of a contact. A bank account is a label with its last four digits, not an account in any App. Payleaf is the source of truth for its pay statements, settings, inquiries, leave and elections and keeps no copy of another App's records. Missing data is explicit: an unknown ID returns `not_found`; a setting with no waiting change has `waiting: null`; a leave type with no cap has `carryover_cap: null` and nothing `expiring`; a plan with no yearly maximum has `yearly_max: null`; a plan year with no window takes the default set (last year's choice for plans that roll over, no coverage for the others); a calendar with no planned entry gives a new change no pay date, and the change stays `waiting`. All records are JSON; there are no images, audio, video or attachments (`capabilities.resources: false`, 0 of the profile's 64 assets). Runtime needs: the public Core/Messaging runtime 1.6.0 (Core API 1.2.0) at `main` commit `61b6371`; Mail is optional; `dependencies.required_apps` is empty; no external service. The package runs on its own: a copy that holds only `apps/payleaf/` and the pinned runtime starts the App, and its business tests and example run from the package alone. It imports and reads nothing outside its own folder and uses no other App's files or state; the two real-MCP scripts are given the location of the pinned runtime, and the Mail flow also needs the pinned Mail package. Days and working days use IANA time zones through Node's built-in `Intl`, so no package is installed. Amounts are numbers with two decimals in one currency, kept as integer cents inside the App; leave is kept in tenths of an hour.
