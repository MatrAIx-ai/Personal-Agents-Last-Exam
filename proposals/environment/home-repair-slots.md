## 2. What you plan to build

**✍️ Your answer (required):** A browser app for one non-emergency service: cabinet-hinge adjustment. The MVP supports four end-to-end workflows: (1) browse a few available slots and their fixed, all-inclusive synthetic estimates within a supplied budget; (2) select a slot, review a temporary reservation, and confirm or discard it; (3) reschedule a confirmed booking; (4) cancel a reservation or booking and see the resulting state. Use four small views: slot list, review/confirm, booking details, and change/cancel. No real payment or provider contact occurs.

One deterministic world change creates the challenge: a competing synthetic customer takes the slot selected for a temporary reservation before confirmation. A task can test whether the agent preserves the person’s date window and all-inclusive budget when its initial choice disappears, and whether it reports that no suitable alternative remains rather than booking outside those limits. A failed confirmation creates no booking; a failed reschedule preserves the original booking. No path contacts a provider, makes payments, or shares access information.

### Integration details

- **Operations and access (required):** Target the pinned [public runtime and Web Host](https://github.com/MatrAIx-ai/Personal-Agents-Last-Exam/tree/61b637164e4abddf81536bb48935cdb688a69ff1/runtime), runtime 1.6.0 / Core API 1.2.0. Package boundary: `apps/home-repair-slots/` and the shared runtime only (Node built-ins; no external service or other App). Declare proposed Agent MCP tools in `tools.json`: `home_repair_slots.list_slots`, `home_repair_slots.get_reservation`, `home_repair_slots.get_booking` (read); `home_repair_slots.select_slot`, `home_repair_slots.confirm_reservation`, `home_repair_slots.discard_reservation`, `home_repair_slots.reschedule_booking`, `home_repair_slots.cancel_booking` (write). Selection creates the temporary reservation; cancellation of an unconfirmed selection uses discard. The four App-owned `gui/` views (slot list, review/confirm, booking details, change/cancel) use those same Agent tools through the public Web Host. Separate Infra MCP handles `env.load_seed`, `env.reset`, `env.apply_event`, virtual time control and `env.snapshot`; none is available to Agent.
- **State and lifecycle (required):** One synthetic customer per run. Persist scenario constraints, slot availability, at most one open temporary reservation, bookings and business history in the local App. A temporary reservation is a preview (no hold, no separate expiry timer); selecting another slot replaces the open preview. Slots with start at or before `ctx.virtual_now` are omitted from bookable results and rejected by select, confirm and reschedule. Only Infra advances that clock. Cancelling a future booking releases its slot; successful reschedule atomically releases the old slot and claims the new one. Past slots never become bookable. A failed reschedule retains the old booking and availability. Repeating cancel with a fresh ID returns `already_cancelled` without a new business change. Booking details remain readable after cancellation.

  Every Agent write includes `request_id` and observed `expected_version` (epoch/revision). Core returns the committed status and version; App results include the affected reservation or booking ID for read-back. (1) Replaying the exact successful confirm with its original arguments and request ID returns the saved receipt with `duplicate: true`, no second booking. Reusing a successful request ID with changed arguments is an `idempotency_conflict`. (2) Confirming with a new request ID and the version from before the competing event returns Core `stale_version`. (3) After reading the current state, a fresh confirm of that invalidated reservation returns App `slot_unavailable`; no booking is created. (4) A fresh confirm of an already confirmed reservation with the current version returns App `already_confirmed`; it creates no booking. Reset restores seeded state and virtual clock and clears Core receipts; the runner owns event scheduling, not App state.
- **Events and notifications (required):** One Infra-only event example for `env.apply_event` (with the current `expected_version`): `{"event_id":"slot-taken-001","at":"2027-01-12T09:15:00+08:00","operation":"home_repair_slots.slot_taken","payload":{"target":"open_reservation"}}`. At that boundary the handler resolves the sole open reservation, marks its still-future available slot taken by the synthetic competitor, and marks the preview invalidated. It rejects an absent open reservation or an already booked, past or unavailable slot without changing business state; an event never edits an existing confirmed booking. The accepted event advances the Core revision and the list marks or omits the now-unavailable slot. Stage this with two Agent sessions on the same run and no reset: select in session 1, pause, apply the event through Infra at the scenario boundary, then start confirmation in session 2. No automatic action-triggered scheduler is assumed. No Mail, Messages, Calendar, or provider notification.
- **Shared data and dependencies (required):** Synthetic service, provider, slot, reservation, and booking IDs link local records. Budget and requested date range come from the seed. Estimates are integer minor units in one seed currency; slots have a start and end with explicit UTC offsets and a scenario time zone. No images, attachments, addresses, access codes, real records, or required cross-App connection. Tasks can optionally use Calendar separately, without adding an integration to this App.
