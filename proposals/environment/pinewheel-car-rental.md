## 2. What you plan to build

**✍️ Your answer (required):** Build a resettable browser App and MCP business interface for one fictional North American rental-car company. The initial version will support three complete workflows:

1. **Search, quote, and reserve:** search pickup/return locations and times, compare available vehicle classes and rate plans, inspect an itemized quote and material restrictions, select optional equipment/protection and an additional driver, and create a reservation. Quotes will expose taxes, one-way or young-driver fees, deposits/authorization holds, mileage and fuel terms, cancellation rules, and qualification requirements before commit. Expected failures include no inventory, closed locations, invalid time ranges, ineligible drivers, expired quotes, and unsupported payment-method/class combinations.
2. **Manage or cancel before pickup:** retrieve a reservation, request changes to location, time, vehicle class, rate plan, extras, protection, or drivers, receive a replacement quote, and explicitly accept or reject the repriced itinerary. Cancellation will compute the disclosed fee/refund or no-show outcome according to the seeded rate policy. Modification and cancellation will support idempotent retry, stale-version rejection, and confirmation records.
3. **Manage an active rental and close it:** after a task-scheduled pickup event, inspect the agreement and request an extension or return-location change, receiving an approval, denial, or repriced result based on availability and policy. A task-scheduled return event will record time, location, mileage, fuel, and assessed items, then produce an itemized final receipt. Failures include late or disallowed extensions, an unavailable return location, duplicate requests, and attempts to modify a closed rental.

The environment is useful for personal-agent evaluation because a correct action depends on changing trip dates, location hours and inventory, driver eligibility, prior quoted terms, explicit user authority, and the distinction between a reservation, an active agreement, and a closed rental. It enables tasks where the cheapest initial quote is not the best valid choice or where a flight change requires a safe reprice rather than a silent edit.

The GUI will expose the same business state and actions as MCP through product-oriented pages for search/results, quote details, checkout, upcoming rentals, active rental management, and receipts. It will not be a generic state inspector.

## 3. Potential app connections

- **Internal personal apps (required):**
  - **Mail 1.3.0, optional in v1:** Pinewheel will publish reservation confirmation, accepted modification, cancellation/refund, pickup reminder, extension decision, and final-receipt messages through Mail's implemented `channel.email` receive contract in [`examples/apps/mail/contribution/contribution.json`](../../examples/apps/mail/contribution/contribution.json). Each connected workflow will verify the actual destination Mail record and Messaging receipt. Pinewheel remains independently runnable when Mail is not enabled; the business operation still returns an in-App confirmation. A failed or unavailable Mail delivery is reported separately and does not roll back the rental commit; v1 does not claim an atomic outbox or automatic queued retry.
  - **Calendar 1.3.0, optional Agent-orchestrated connection:** an authorized Agent may separately call Calendar's public business tools to create or update pickup/return events after a confirmed Pinewheel change. Pinewheel will not claim to send Calendar messages because Calendar currently has no Messaging receiver. Calendar is not a Pinewheel package dependency, and Calendar synchronization is excluded from v1 acceptance evidence unless a reviewer asks to add it through a separately approved interface.
- **Other apps and websites (required):** None required for v1. Future tasks may coordinate Pinewheel with airline, hotel, maps, roadside-assistance, toll, or payment-card environments, but those connections are deferred. Task/Infra events can represent a changed arrival time, location closure, inventory substitution, pickup, or return without requiring a live third-party service.

### Integration details

- **Operations and access (required):** Agent-facing MCP and GUI operations will cover location search, availability search, quote creation/read, reservation list/read/create/requote/modify/cancel, agreement read/extension/return-change requests, and receipt read. Exact names and schemas will be declared in `tools.json`; representative names are `rental.locations.search`, `rental.availability.search`, `rental.quote.create`, `rental.reservation.create`, `rental.reservation.requote`, `rental.reservation.modify`, `rental.reservation.cancel`, `rental.agreement.get`, `rental.agreement.extend`, `rental.agreement.change_return`, and `rental.receipt.get`. Infra-only `env.load_seed`, `env.apply_event`, `env.advance_time`, `env.snapshot`, and `env.reset` will load histories, inject world changes, advance deadlines, inspect outcomes, and restore a clean run. The Agent interface will not expose setup/reset/event injection.
- **State and lifecycle (required):** Each App instance represents one customer's account and is isolated by Core's `run_id` and `app_id`. Synthetic seed data will contain locations, operating hours, vehicle-class inventory, rate/policy tables, the renter profile, redacted payment-method metadata, and optional reservation/agreement history. A quote is immutable and expires at a declared virtual time; a reservation records the accepted quote and revision history; pickup converts it to an agreement; return closes the agreement and creates an immutable receipt. Writes use idempotency keys and expected state versions. Duplicate successful retries return the prior result, stale concurrent changes fail without partial state changes, and every commit returns object status plus Core epoch/revision. Reset replaces all business state, audit/receipts, and task-loaded history with the fixture baseline; snapshots expose deterministic review evidence but do not imply an Agent restore capability.
- **Events and notifications (required):** The App will accept task/Infra events for `rental.inventory_adjusted`, `rental.location_hours_changed`, `rental.reservation_no_show`, `rental.pickup_completed`, and `rental.return_recorded`. Event payloads will use stable location, reservation/agreement, vehicle-class, and event IDs plus an effective virtual timestamp. Events are idempotent and reject invalid lifecycle transitions; quote expiry is evaluated against Core's virtual time rather than injected as an event. Pinewheel will optionally publish compatible `channel.email` CloudEvents for the Mail messages listed above. For example, an accepted modification notification will identify the Pinewheel reservation as `source_object`, include a concise old/new itinerary and price summary in the Mail-owned payload, and retain the Messaging receipt; it will not expose a raw payment token, license number, or full App state. Sender commit, receiver commit, and delivery acknowledgement remain distinct outcomes. Task scenarios, not the App, decide when external events occur.
- **Shared data and dependencies (required):** Shared references include `person_id`, `rental_account_id`, `location_id`, `vehicle_class_id`, `quote_id`, `reservation_id`, `agreement_id`, `receipt_id`, and optional Calendar event IDs supplied by a task. Payment methods are synthetic redacted records (brand, last four digits, expiry month/year, and eligibility flags), never credentials. The initial App uses no required media attachments; generated vehicle/location images are ordinary PNG/JPEG UI assets with catalog provenance and graceful missing-image behavior. The package will run on its own with the repository's pinned public Core/runtime and Node.js 18+ using only built-ins. Mail 1.3.0 is an optional run-assembly dependency for notification evidence, not a hard dependency for core rental workflows; Calendar is an optional separately called App rather than a Pinewheel state dependency.
