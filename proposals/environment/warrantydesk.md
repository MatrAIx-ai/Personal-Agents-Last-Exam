## 2. What you plan to build

**Your answer (required):** A private, account-bound replacement coordination workspace combining serial-linked manufacturer/courier case records with a separate local continuity journal. The journal records user/IT-performed checks so the personal agent can coordinate a safe return; it is not a claim that a manufacturer can read workplace or banking authentication state.

Workflows: Inspect eligible remedy -> accept advance replacement -> observe actual delivery -> request user/IT verification by exact serial -> inspect performed results -> arrange courier return -> distinguish collection, manufacturer receipt, release request, actual posting and case close.

Entities: case and exact serial lineage, accepted remedy, old/new delivery state, typed external verification request, performed checks with chronological order and source, scheduled/actual pickup, manufacturer receipt, hold stages and closure.

Business rules: Delivery does not imply migrated authentication. A request acknowledgement never performs a check or erasure. Trusted Task actors perform user/IT work and post typed outcomes whose schema has no credential or code fields; fixtures contain no secrets. Provider facts and user/IT facts retain separate source roles and provenance, with no automatic transmission of the journal to a manufacturer. Only receipt of the serial required by the active return obligation can request hold release. Courier collection, manufacturer receipt and actual release posting remain separate. Personal continuity/retention policy belongs to the user/Task; the App does not automatically prevent unsafe early erasure on their behalf.

Reusable value: Laptop returns, security-token replacements and serial-matched trade-ins can reuse the request/physical-return/financial-posting separation. Actors and event timing remain Task-owned; the App's deadline and exception boundary is explicit below.

Related work: [#7 Refund-only Returns](https://github.com/MatrAIx-ai/Personal-Agents-Last-Exam/pull/7) covers a refund-request MVP; [#33 Personal Document Records](https://github.com/MatrAIx-ai/Personal-Agents-Last-Exam/pull/33) covers document/receipt management. WarrantyDesk instead owns an advance replacement's serial obligation, performed-check journal, collection, manufacturer receipt and hold-release stages. Neither is a required v1 dependency, and neither's data/balance is copied. Original purchase evidence may be seeded as text; future document/Mail integration requires its public contract and receiver-side proof. Approval is non-exclusive. Companion [Task #153](https://github.com/MatrAIx-ai/Personal-Agents-Last-Exam/pull/153) depends on validated delivery, not vice versa.

### V1 transitions and included modification paths

This fixes blocking review items 2 and 4. The interface, deadline and provenance choices also make the intended behavior for items 1 and 3 explicit.

| Object | States and producer | Preconditions / main errors |
| :--- | :--- | :--- |
| Case / remedy | Seed `open`; Agent acceptance makes `active`. Provider dispatch/delivery changes the replacement's separate fulfilment state. Agent withdrawal before original-device collection makes `withdrawal_pending`. Valid active-obligation receipt makes `return_received`; explicit close makes `closed` for normal fulfilment or `withdrawn` for a completed withdrawal. | One eligible advance-replacement offer per case. Accept only once. Withdraw only before original return handoff and any still-active pickup's cancellation cutoff, not after collection/receipt. A locked pickup returns `pickup_locked`. Closing is terminal. Errors: `ineligible`, `invalid_state`, `return_already_started`, `settlement_pending`. |
| Replacement fulfilment | `not_ordered -> ordered -> dispatched -> delivered`; only the provider events record dispatch/delivery. A pre-dispatch withdrawal changes ordered to `cancelled_before_dispatch`. | Every fact binds the case and seeded replacement serial. Delivery normally requires recorded dispatch, including after a withdrawal request. Neither order acceptance nor a pickup means delivery. `wrong_serial`, `missing_dispatch`, `order_cancelled`. |
| Hold | `none -> authorized` on accepted quoted remedy. Valid return receipt, or confirmed pre-dispatch order cancellation, requests `release_pending`. Only provider `hold.released` changes it to `released`. | One synthetic fixed-currency authorization per case, amount in integer minor units. No capture, extra charge, interest or refund-of-capture transition is claimed in v1. A release request is not a financial posting. `missing_receipt`, `wrong_obligation`, `settlement_pending`. |
| Pickup | Agent schedules `scheduled`; Agent can cancel or atomically reschedule before the displayed cutoff. Reschedule leaves the old generation `cancelled` and creates a new scheduled generation. Infra collection makes it `collected`. | At most one effectively active scheduled pickup per case/active return obligation; reads show stored and effective status. Slot, target serial and cancellation cutoff are visible. New-slot capacity/window is checked before committing a reschedule, so failure retains the old booking. No modification after collection. `slot_unavailable`, `cancellation_closed`, `pickup_inactive`, `wrong_serial`. |
| Verification request | Agent creates `pending`; trusted source reply makes it `performed` or `refused`; Agent may cancel pending requests. Completed facts are immutable. | Selector binds case, exact device serial, check kind and request attempt. At most one pending request per such subject/kind. `request_exists`, `request_not_pending`, `wrong_source`, `stale_generation`. Icons or acknowledgements never create successful independent checks. |
| Return obligation / receipt | Normal acceptance requires OLD-17 in the examples. After shipped-replacement withdrawal, the obligation instead requires returning NEW-42; the original old/new identities are never overwritten. Collection and manufacturer receipt are separate immutable facts. | A manufacturer receipt must match the active obligation's mode, serial, collected pickup generation and source. A different serial, absent collection or a cancelled pickup rejects the event and leaves the case/hold unchanged. |

**Quotes and consent boundary.** `remedy.preview` is read-only and shows the offer, fixed hold amount, active serial obligation, included terms and withdrawal effect. Accept/withdraw must provide its matching digest and a fresh Core version; changed terms return `quote_changed`. Accept creates the local provider order and authorization atomically; it does not debit a real bank. A business confirmation by an Agent is not proof of human consent. User approval and the $300 cap in the companion Task remain Task/user authority, not native platform confirmation.

**Pickup modification is included.** `pickup.cancel` before its strict cutoff preserves a cancelled historical record. `pickup.reschedule` validates a new future slot and atomically replaces the old scheduled generation; if the new slot fails, the old pickup remains scheduled. Neither operation erases earlier verification, delivery or financial facts, charges a fee or fabricates collection. At/after the cutoff they fail unchanged. After an actual collection, the pickup and active return obligation are locked.

**Withdrawal is included before original-device return.** A still-active original-device pickup must remain cancellable; otherwise withdrawal returns `pickup_locked` unchanged rather than bypassing the carrier cutoff.
- If the replacement is still recorded `ordered` and not dispatched, successful withdrawal cancels that order, cancels pending original-return pickups/requests, records `cancelled_before_dispatch` and requests hold release. Case closure waits for the actual provider release posting; no fake return receipt is made.
- If the replacement was dispatched or delivered, withdrawal switches the active return obligation to the replacement serial. Any pending original-return pickup/verification requests are cancelled with history retained. The hold remains authorized. Await delivery if necessary, then arrange collection and actual manufacturer receipt of the replacement before requesting release. The original device remains the user's; no unrelated original-device receipt can settle this branch.
- A withdrawal at/after original-device collection returns `return_already_started`; v1 does not pretend that a parcel in transit has been recalled. Different-SKU remedy changes, post-collection reversals, disputed charges and carrier interception are excluded. Only one advance-replacement offer is modelled; this does not promise a full retailer remedy menu.

For a normal case, `case.close` requires recorded replacement delivery, actual collection and matching manufacturer receipt of the original serial, plus posted hold release. For a delivered-replacement withdrawal it requires those facts for the replacement serial. The sole no-parcel exception is the explicitly recorded pre-dispatch cancellation plus posted release. Pending pickup, delivery, return or release requests alone cannot close any branch.

**Who can see verification.** This App is the user's coordination workspace, not a manufacturer database claiming access to banking or employer IT. A source-tagged local continuity journal records only whether a requested check actually ran, device serial, result and whether another device/factor was used. Allowed kinds include independent banking/work login, work enrollment and device erasure. Erasure is recorded only after a trusted user action, never performed by creating a request. Manufacturer/courier records occupy a separate provider section; v1 has no operation that sends the journal to them. Optional real correspondence through public Mail/Chat would be a later, separately verified integration. The App does not infer personal retention permission or block all unsafe actions; Task traces/judging must assess those boundaries.

### Event matching, examples and deadline effects

**Deterministic business selectors.** Case IDs, original/replacement serials and provider slot IDs come from the seed/eligible offer. Returned request/pickup IDs need not be predicted:
- Verification selector: `{case_id, device_serial, kind, request_attempt}`.
- Pickup/receipt selector: `{case_id, return_mode, device_serial, pickup_attempt}`, where `return_mode` is `original_return` or `withdrawal_return`.
- Dispatch/delivery and financial events bind `case_id`, replacement serial or return mode as applicable. Financial release must match the currently accepted physical receipt, or the explicit pre-dispatch cancellation reason.

Each new request or pickup gets the next attempt for that bound subject; cancellation/rescheduling never reuses a generation. The event must identify exactly that generation and valid source/state, not the latest pending object with a similar name. A stale response after cancel/recreate, wrong serial, cancelled pickup or zero matches is rejected unchanged. Multiple matches are `ambiguous_target` and fail closed. Core handles exact duplicate event replay and conflicting reuse; rejected events retain no accepted physical/financial effect or clock change.

Selectors are scoped to the bound account/run and the Core epoch captured with the target snapshot. The Infra adapter sends that snapshot's outer `expected_version`; after reset/seed replacement it discards prepared targets rather than attaching a fresh version to an old event. This uses Core's existing version boundary, not an invented App context epoch field. A Task can write first-attempt selectors in advance. Branching actor steps can inspect the real public Infra `env.snapshot`, resolve case/serial/kind/slot intent to exactly one pending target and use its returned selector. The App's delivered example/driver must demonstrate that process using the public management interface. If no applicable request/pickup exists, the conditional actor step emits no completion event and records the absence in its own trace. It must not choose a different generation to make an old scripted reply succeed. Invalid direct injections remain negative tests. Actor behavior does not require a pre-existing private Task runner.

Planned JSON event examples below show a normal return. They are not standalone valid without their stated Agent-created order/request/pickup prerequisites. All source IDs and permissions are seeded.
```jsonl
{"event_id":"wd-note-1","at":"2027-02-22T09:00:00-06:00","operation":"record.add","payload":{"id":"provider-note-1","source_actor_id":"manufacturer-1","body":"Two courier pickup slots are available."}}
{"event_id":"wd-dispatch-1","at":"2027-02-23T17:00:00-06:00","operation":"replacement.dispatched","payload":{"case_id":"case-1","replacement_serial":"NEW-42","source_actor_id":"manufacturer-1"}}
{"event_id":"wd-delivery-1","at":"2027-02-23T18:00:00-06:00","operation":"replacement.delivered","payload":{"case_id":"case-1","replacement_serial":"NEW-42","source_actor_id":"courier-1"}}
{"event_id":"wd-work-1","at":"2027-02-24T15:05:00-06:00","operation":"verification.reply","payload":{"selector":{"case_id":"case-1","device_serial":"NEW-42","kind":"independent_work_login","request_attempt":1},"source_actor_id":"user-1","status":"performed","result":{"success":true,"used_old_device":false}}}
{"event_id":"wd-collect-1","at":"2027-02-26T15:30:00-06:00","operation":"pickup.collected","payload":{"selector":{"case_id":"case-1","return_mode":"original_return","device_serial":"OLD-17","pickup_attempt":1},"source_actor_id":"courier-1"}}
{"event_id":"wd-receive-1","at":"2027-03-01T09:00:00-06:00","operation":"return.received","payload":{"selector":{"case_id":"case-1","return_mode":"original_return","device_serial":"OLD-17","pickup_attempt":1},"source_actor_id":"manufacturer-1"}}
{"event_id":"wd-release-1","at":"2027-03-01T15:00:00-06:00","operation":"hold.released","payload":{"case_id":"case-1","return_mode":"original_return","device_serial":"OLD-17","source_actor_id":"manufacturer-1"}}
```
Effects: append context; record actual dispatch and delivery separately; append the performed check only; record exact-serial collection; record actual manufacturer receipt and request release; finally record posted release. A successful work test does not imply bank readiness, actual shift login or erasure. A cancelled pickup reply or wrong serial cannot advance the case or hold.

For shipped-replacement withdrawal, collection/receipt/release use `return_mode:"withdrawal_return"` and the replacement serial. For pre-dispatch withdrawal, `hold.released` instead carries `reason:"cancelled_before_dispatch"`; it is valid only when that cancellation was already committed. Those branch controls are required in addition to the normal example.

**Deadlines do not self-execute.** Each seed offer specifies normal `return_due_at`, withdrawal-return due date, pickup windows and strict cancel/reschedule cutoffs with UTC offsets. All reads/writes use `ctx.virtual_now`, never a second App clock. At/after a return deadline, reads expose `overdue:true` if the active serial has not been received; they do not rewrite the case or fabricate a charge/release. A scheduled pickup whose window has passed is exposed as effectively missed, and cannot be collected by a late event pretending the window was still open. It no longer counts as a live pickup; a subsequent schedule may create a new attempt without rewriting the missed record. A withdrawal likewise need not cancel an already missed pickup. Collection of the replacement in a withdrawal branch requires its actual delivery first. Late receipt of the correct actually collected serial may be recorded with immutable `returned_late` evidence; financial status remains pending until a real provider release event.

**V1 explicitly excludes automatic overdue capture/charges and refunds after capture.** The fixed synthetic authorization/release model is narrower than live manufacturer/bank policy. Time passing may mark the displayed obligation overdue; it never converts the hold into a posted charge or silently releases it. Supporting a capture/fee/dispute lifecycle would require a later scope revision, states, provider events and tests. This exclusion does not permit normal closure without actual receipt/release evidence.

Infra advances the clock using `env.advance_time`; that operation alone invokes no business handler or event. Infra must process dated events before advancing beyond them and choose tie ordering explicitly. Reply, dispatch, collection, receipt and financial posting are accepted only through their declared events. Reads show effective deadline flags before any such event; no global scheduler, timer thread or native consent service is assumed.
