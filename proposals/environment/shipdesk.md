## 2. What you plan to build

**✍️ Your answer (required):** A resettable sender-facing browser App and MCP business interface for domestic parcel mailing. An agent prepares a shipment, compares services, buys and prints the right label, arranges pickup, and reconciles unused-postage refunds. Buying or printing a label never means the carrier has received the package. Scheduling or cancelling pickup never buys or refunds postage by itself.

| Workflow | First-version behavior and visible result | Modification, cancellation and failure paths |
| --- | --- | --- |
| W1 — Prepare and compare | Create/edit/delete shipment drafts. Select a saved or fixture-validated origin/destination, package type, weight, dimensions and ship date. Compare three services with exact price, latest handover, estimated delivery window and pickup eligibility. | Missing apartment information, unsupported addresses and oversized/overweight parcels produce field-specific errors. Address normalization is shown for explicit acceptance; the App never guesses a recipient or deletes an apartment field. Changing a draft invalidates its quote. |
| W2 — Buy and print postage | Preview a chosen service with exact addresses, package facts, ship date, total and refund terms. Confirm or abandon. A successful local simulated purchase creates one immutable label, charge, tracking ID and PDF asset. View, print or download it. | A quote is not a purchase. Expired/stale quotes or a seeded declined payment method create no label or charge. After purchase, address/service/ship-date changes require a new draft and purchase; the old label is preserved and may qualify for W5. |
| W3 — Manage shipping history | Find purchased labels by date, recipient, tracking ID and status; inspect original terms, PDF and charges; reprint or start a new draft with Ship Again. Inspect carrier acceptance and later progress. | Reprinting returns the same bytes and never purchases postage again. Ship Again creates an editable draft, not a shipment. A label-created record is distinct from accepted, in-transit and delivered scans. Foreign account IDs/PDFs are inaccessible. |
| W4 — Arrange pickup | Select owned eligible labels and an eligible origin/date, preview the declared package count and pickup instructions, then confirm. Amend or cancel before the published cutoff. Read the carrier's visit/missed result. | Cancelling pickup leaves labels and their charges intact. Labels with different origins/dates cannot silently be combined. A missed visit leaves unaccepted labels available for another eligible pickup or handover. Only explicit scans establish acceptance. |
| W5 — Refund unused postage | Inspect eligibility; preview and submit one refund request for an unused label; inspect or cancel a pending request; reconcile a later approval/denial and full credit. | An already accepted label, expired request window or existing pending/final refund rejects a new request. Requested does not mean refunded. An acceptance scan arriving during refund review prevents approval. Replaying approval adds no second credit. |

**First-version scale.** One fictional carrier, three domestic services, six postal zones, eight synthetic saved addresses, three package types, five principal views and six small fixtures: ordinary mailing; incomplete address; label bought but not handed over; missed pickup; refund/acceptance race; and read-only access. One sender account per run. A separate evaluation dataset contains six sender histories across the required 2025–2026 window; a Task chooses the account and cutoff.

**Business rules and product boundaries.**

- Rates come from a versioned local tariff using service, zones, package type, weight band and any declared dimensional-weight rule. Publish thresholds, units, rounding and all fixed fees at M1. Prices are USD integer cents. Three synthetic services have different disclosed prices and delivery estimates; an estimate is not a guarantee that a gift arrives by a personally important date.
- Drafts are mutable; purchased label terms and source PDF are immutable. Preview shows the full postal address, recipient, sender, package declaration, total, ship-by time, print deadline and refund window. One confirmed quote can create at most one label even when callers supply different request IDs. A successful transport retry returns the same purchase receipt.
- Purchases use a local simulator's seeded valid/declined payment-method state. A successful confirmation posts one simulated charge synchronously; a decline leaves the business state unchanged. There are no real card numbers, external bank accounts or hidden live transactions.
- Printing/download remains available through the label's disclosed print deadline. A later immutable history/receipt remains readable. PDF reprint reuses the original bytes/hash; changes require another label. Every generated PDF is visibly marked `SIMULATION — NOT VALID FOR POSTAGE`, with fictional tracking marks. It is a real local PDF asset, not a placeholder URL or genuine carrier postage.
- Pickup is free in this synthetic v1. It can include at most five owned, unaccepted labels with the same origin and ship date. Each sender can have at most one active pickup per origin address and pickup date, and each label can belong to at most one active pickup. A second booking for the same pair fails with `pickup_already_booked`. Changes/cancellation stop at the published cutoff, before the scheduled visit. Removing a label from pickup or cancelling the visit never refunds it. Starting a refund request detaches an unused label from a still-editable pickup; if the pickup is already locked, refuse and explain the prerequisite rather than partially modify it.
- An unused label is eligible for a refund request strictly before purchase time plus 30 days and only without an acceptance scan. Pending requests block new pickup association. Cancellation restores eligibility if the label is otherwise usable. Refund approval requires the label still be unaccepted and creates a full credit of the original charge. Refund denial preserves the charge and reason. If acceptance arrives during review, the scan atomically records custody and sets `ineligible_reason=carrier_accepted` on the pending request. GUI and MCP show the pending status, reason and acceptance time. A subsequent approval fails with `label_already_accepted` and produces no receipt, credit or state change. A subsequent denial closes the pending request as `denied`, retains the acceptance reason and original charge, and issues a denial receipt with zero credit.
- Use only `ctx.virtual_now`; reads calculate quote/print/cutoff/refund eligibility without mutating business data. Events, not elapsed time, establish carrier visits, acceptance, delivery and refund decisions. Writes/events validate against the effective clock and atomically commit their own effects. Neither a missed date nor a successful print automatically advances package custody. Task/Infra owns event timing and tie ordering.

**Personal-agent value.** A user might ask an agent to mail a birthday present before a trip, send an item to a relative with a new apartment, or recover postage bought twice after a printer problem. Their departure, budget, recipient address and printer availability affect the right action. The same App supports these tasks without knowing their preferred service, deadline priority or private rubric. It exposes receipts, original terms and actual carrier outcomes so success is checkable from state.

### Integration details

- **Operations and access (required):** Proposed `apps/shipdesk/` package. Agent operations cover saved shipping addresses; draft create/read/update/delete; local quotes; label/history/receipt reads; PDF retrieval; pickup and refund preview/confirm/cancel. Use lowercase `shipdesk.<name>` tools, exact schemas frozen at M1, and `request_id` plus `expected_version` on every write. Owner/read-only policies come from trusted account/person binding and seed identity, not tool arguments. GUI pages/controllers use `pale.web` version 1 through the shared Web Host, a registry that includes ShipDesk and the shared stylesheet. Browser and MCP share authoritative state. Management seed/history/reset/snapshot/events/time remain on Infra's separate connection, inaccessible to Agent callers.
- **State and lifecycle (required):** Separate public tariff/address-validation catalog from account-bound saved addresses, drafts, quotes, labels/assets, pickups, refunds and ledger records. Keep top-level `account_id`; isolate App instances/accounts/runs. Core supplies atomic commits, version checks and idempotent receipts. A changed payload under an accepted request ID conflicts; failed handlers leave business records unchanged. Reset restores the loaded baseline, asset references and seeded virtual time, clearing Core run receipts/audit. Export evidence before reset; do not promise arbitrary snapshot restore or a cross-App rollback.
- **Events and notifications (required):** Declare the following four operations consistently in App/contribution declarations, with a whole-event schema accepting their variants. Task scenarios supply order/timing; handlers return coded errors for foreign IDs, invalid transitions and conflicts. In-App notices reference their label/pickup/refund and effective time. No cross-App messaging in v1.

  **How prewritten events find a target.** Infra passes the event unchanged. ShipDesk resolves its target inside the loaded sender account when the event runs. Each scan, pickup result or refund decision supplies exactly one target form: the selector shown below, or a fixture-known `label_id`, `pickup_id` or `refund_request_id` for the corresponding operation. An unknown or inaccessible target returns `target_not_found`. A failed event leaves business state and receipts unchanged.

  For scans and refund decisions, match the immutable origin address ID, destination address ID and ship date on purchased labels. With two or more matches, require `select` (`earliest` or `latest`) or return `ambiguous_target`. Rank by purchase time, breaking ties by immutable per-account purchase sequence. Choose the label before checking custody or refund state so an ineligible selection cannot redirect an event to a different purchase. For events carrying a `provider_reference`, check for a previously applied reference within the account and operation before resolving the target again. Replaying the same business payload under a new event ID has one effect. A changed payload for that reference returns `provider_reference_conflict`.

  ```json
  {"event_id":"scan-001","at":"2026-11-28T10:00:00Z","operation":"shipdesk.carrier_scan","payload":{"origin_address_id":"addr-home","destination_address_id":"addr-family","ship_date":"2026-11-28","select":"earliest","status":"accepted","facility_id":"depot-01","provider_reference":"scan-ref-001"}}
  ```

  Acceptance requires a paid, unrefunded label awaiting handover. A new acceptance reference for an already accepted label fails with `label_already_accepted`. A refunded label or out-of-order progress scan returns `invalid_transition`. Later `in_transit` and `delivered` scans use the same label matching rule.

  ```json
  {"event_id":"pickup-001","at":"2026-11-28T09:00:00Z","operation":"shipdesk.pickup_result","payload":{"origin_address_id":"addr-home","pickup_date":"2026-11-28","outcome":"completed","provider_reference":"visit-ref-001"}}
  ```

  Match the unique active booking for the origin and pickup date. No booking for the pair returns `target_not_found`. If only cancelled or finished bookings exist, return `pickup_not_active`. Multiple active matches return `ambiguous_target`. For either `completed` or `missed`, record the visit and release its associations. A missed visit records the supplied reason. A completed visit can be followed by separate `carrier_scan` events for collected labels. The visit alone leaves custody and charges unchanged.

  ```json
  {"event_id":"refund-001","at":"2026-11-29T10:00:00Z","operation":"shipdesk.refund_result","payload":{"origin_address_id":"addr-home","destination_address_id":"addr-family","ship_date":"2026-11-28","select":"latest","outcome":"approved","provider_reference":"refund-ref-001"}}
  ```

  On the selected label, resolve its sole pending refund request, including a new request submitted after a cancellation. No request returns `target_not_found`. If only cancelled or final requests exist, return `refund_not_pending`. Multiple pending requests return `ambiguous_target`. A direct fixture ID targets that exact request and must pass the same pending-state check. Approval on an unused label credits its original charge once. For a pending request with recorded acceptance, apply the W5 race rules above. A denial records the carrier's reason and closes the request without a credit.

  ```json
  {"event_id":"tariff-001","at":"2026-12-01T00:00:00Z","operation":"shipdesk.tariff_update","payload":{"expected_revision":1,"new_revision":2,"rate_table_id":"tariff-2026-12"}}
  ```

  Select an already declared synthetic tariff revision and invalidate affected unconfirmed quotes. Purchased labels and charges retain their original price. Unknown rate tables and revision conflicts fail without mutation.
