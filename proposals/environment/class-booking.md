## 2. What you plan to build

**✍️ Your answer (required):** A resettable fitness app where a user checks their membership plan and trial rules, searches studio classes whose price depends on the plan and on prior visits, books, cancels, reschedules and waitlists classes without overlapping existing reservations, and registers for multi-week recreation programs whose sign-up windows open at a scheduled time with resident priority, a waitlist and a checkout that needs explicit payment approval. Class times, registration openings, waitlist promotions and studio cancellations run on the simulated clock.

Initial workflows, each complete end to end including modification, cancellation, confirmation and realistic errors:

1. **Plan and account.** Plan page with plan type, credits, free-trial status and end date, trial rules (for example "first visit at each studio included" and premium classes excluded), renewal date and a masked payment method. Account attributes that change eligibility (residency, self-reported skill level). Plan change or cancellation with confirmation and a proration preview.
2. **Class search and booking.** Browse by type, studio, neighborhood, date and time window. Each class shows capacity, rating and review count, and its price under the user's plan: "included in trial", a credit cost, or "not available on your plan". Booking is a preview (cost under the plan, conflicts with existing reservations, cancellation window) followed by a confirmation. Errors: full class (offers the waitlist), overlap with an existing reservation, class not included, insufficient credits, outside the booking horizon.
3. **Reservations.** Upcoming and past reservations; cancel inside the window or late-cancel with a fee preview; reschedule to another instance; check in; rate after class. Studio-initiated cancellations arrive as events with a notification and a credit return.
4. **Program registration.** Catalog of multi-week programs (for example adult tennis by level) with sessions, rosters, fees and registration windows that open at a scheduled time and depend on account attributes (resident or non-resident). Waitlist for the current session; cart and checkout that requires explicit payment confirmation; roster full leads to the waitlist; promotion events; confirmations and refunds on cancellation before a session starts.
5. **Studios and instructors.** Pages with location, ratings, amenities and schedules; schedule changes arrive as events.

Value for personal-agent tasks: fitness scheduling is where "free", "soon", "balanced" and "doesn't overlap" are personal constraints rather than single filters, and where the right booking depends on reservations the user already made, on plan rules that are easy to misread, and on windows that open at a specific moment. The author's reviewed PersonalAgentEval cases supply downstream tasks on this environment: filling a free-trial week with classes that are actually free (submitted alongside this proposal as a linked Task PR), registering for a city tennis class the moment sign-ups open while honoring a waitlist request made days earlier, and planning a week around coaching advice the user has already accepted.

## 3. Potential app connections

- **Internal personal apps (required):** Calendar: reservations and program sessions are created, moved and cancelled, and other commitments on the Calendar can be read for conflicts. Mail: confirmations, cancellations, waitlist promotions, registration-opening reminders and receipts. Contacts: None.
- **Other apps and websites (required):** A payments app for checkout and a maps app for distance are future links; the initial scope keeps distance as a field on each studio and models payment approval inside checkout.

### Integration details

- **Operations and access (required):** Agent-facing MCP operations: `classes.search|get`, `studios.get`, `plan.get|change|cancel`, `reservations.list|preview|confirm|cancel|reschedule|checkin|rate`, `waitlist.join|leave`, `programs.search|get`, `registrations.list|cancel`, `cart.add|remove|checkout.preview|checkout.confirm`, `program_waitlist.join|leave`, `account.get|update`, `payment_methods.list`. Writes with money or capacity effects (`reservations.confirm`, `checkout.confirm`, `plan.change`, `plan.cancel`) are approval-gated. A GUI renderer presents the plan, search results, class detail, reservations, program catalog, program detail, cart and checkout, and account pages for computer-use agents. Platform-facing operations: `env.reset`, `env.load_seed`, `env.snapshot`, `env.inject_event`.
- **State and lifecycle (required):** App state (studios, class templates, program catalog, fee and plan rules) is separated from account state (plan, credits, reservations, registrations, waitlist positions, payment method) and run state (clock, pending previews, event log). Seed validation checks capacities, time ranges and plan rules; reset restores the seed and clears previews; a preview expires after a configured simulated interval; confirm is idempotent by preview ID; a capacity change between preview and confirm returns a conflict and offers the waitlist.
- **Events and notifications (required):** Accepted events: `classes.cancelled_by_studio`, `classes.schedule_changed`, `classes.capacity_changed`, `waitlist.promoted`, `registration.window_opened` (clock-driven), `registration.roster_full`, `plan.renewed`, `plan.trial_ending`, `account.session_expired` (the app returns a signed-out state until `account.session_restored`, which only the user can trigger). Published notifications: text-email notifications to Mail for confirmations, cancellations, promotions, reminders and receipts, and calendar updates for reservations and program sessions, following the shared Mail and Calendar apps' formats. Task scenarios decide when events occur.
- **Shared data and dependencies (required):** Stable IDs for the person, account, studio, class instance, program session, reservation and registration; receipts by ID; studio images are generated for the project and addressed by asset ID. Depends on the shared Mail and Calendar apps and the platform clock; no external service at run time.
