Proposed PR title: `[Environment Proposal] [Fitness & wellbeing] Cadence class booking (ClassPass-inspired)`

- **Authors / GitHub handles (required):** Sunny Yuan ([@ZichenYuan](https://github.com/ZichenYuan)).
- **Reference app or website / URL (required):** Cadence, an independently branded synthetic studio class marketplace with credit plans and free trials; interaction patterns reference ClassPass (https://classpass.com/) and its public help pages only. No third-party code, assets or data are used.

## 2. What you plan to build

**✍️ Your answer (required):** A resettable studio class marketplace where a user checks their membership plan and trial rules, searches classes whose price depends on the plan and on prior visits, books, cancels, reschedules and waitlists classes without overlapping existing reservations, and reads studio pages with ratings and schedules. Class times, waitlist offers, plan renewals and studio cancellations run on the platform's virtual clock.

Initial workflows, each complete end to end including modification, cancellation, confirmation and realistic errors:

1. **Plan and account.** Plan page with plan type, credits, free-trial status and end date, trial rules (for example "first visit at each studio included" and premium classes excluded), renewal date and a masked payment method. Plan change or cancellation as a proration preview followed by a confirmation. Errors: a change already scheduled for the next renewal (`change_pending`), a payment method the fixture marks as declined (`payment_declined`), and a trial that can only be cancelled at its end.
2. **Class search and booking.** Browse by type, studio, neighborhood, date and time window. Each class shows capacity, rating and review count, and its price under the user's plan: "included in trial", a credit cost, or "not available on your plan". Booking is a preview (cost under the plan, conflicts with existing reservations, cancellation window) followed by a confirmation. Errors: full class (offers the waitlist), overlap with an existing reservation, class not included, insufficient credits, outside the booking horizon, expired or stale preview.
3. **Reservations.** Upcoming and past reservations with each reservation's notice history; cancel inside the window, or late-cancel after a fee preview; reschedule to another instance; check in; rate after class. Studio-initiated cancellations and schedule changes arrive as events, return credits where credits were spent, and publish a notice.
4. **Studios and instructors (read-only).** Pages with location, ratings, amenities and schedules; schedule and capacity changes arrive as events.

Value for personal-agent tasks: fitness scheduling is where "free", "soon", "balanced" and "doesn't overlap" are personal constraints rather than single filters, and where the right booking depends on reservations the user already made, on plan rules that are easy to misread, and on waitlists and cancellations that move after the plan is made. The author's reviewed PersonalAgentEval cases supply downstream tasks on this environment: filling a free-trial week with classes that are actually free (the linked Task PR #18), joining a waitlist for a full class and acting on the offer within the plan's rules, and planning a week around coaching advice the user has already accepted. Task #117, by another author, also plans to build on Cadence.

## 3. Potential app connections

- **Internal personal apps (required):** Mail 1.3.0, optional, used by workflows 2 and 3: Cadence publishes text notices (confirmations, cancellations, waitlist offers, trial-ending reminders, receipts) on `channel.email`, wire `urn:pale:email-message:2`, payload `urn:pale:email-payload:1`, received by Mail's `mail.receive_notification`; no files, so the attachments channel is not used. Calendar 1.3.0, optional, used by workflows 2 and 3 on the agent's side only: Calendar has no messaging receiver and Cadence cannot read other Apps, so the agent copies a reservation into Calendar with `calendar.create`, `calendar.update` and `calendar.cancel` and checks other commitments with `calendar.freebusy` or `calendar.list` when the task grants Calendar; Cadence is the source of truth for its reservations and checks overlaps only among them. Contacts, Files: None.
- **Other apps and websites (required):** A payments app and a maps app are future links; the initial scope keeps distance as a field on each studio and models payment approval inside plan changes and late-cancel fees.

### Integration details

- **Operations and access (required):** Agent-facing MCP operations, each declared read or write in `tools.json`. Reads: `classes.search`, `classes.get`, `studios.get`, `plan.get`, `reservations.list`, `reservations.get`, `waitlist.list`, `account.get`, `payment_methods.list`. Writes: `reservations.preview` (stores a preview with cost, conflicts, cancellation window and an expiry), `reservations.confirm`, `reservations.cancel_preview`, `reservations.cancel`, `reservations.reschedule`, `reservations.checkin`, `reservations.rate`, `waitlist.join`, `waitlist.leave`, `waitlist.accept`, `waitlist.decline`, `plan.preview`, `plan.change`, `plan.cancel`. Gated writes (`reservations.confirm`, `reservations.cancel` with a late fee, `waitlist.accept` when credits are charged, `plan.change`, `plan.cancel`) require a current preview or offer ID; whether the Agent may call each is decided by the task policy's allow-list and per-tool `ids` and `fields` constraints, which Core enforces. A fixture flag `require_user_confirmation` (default off) additionally makes a gated write return `approval_required` until the task applies a `user.confirmed` event through Infra carrying the preview ID, so the package runs with no user harness; a platform-level approval step, if one is added, belongs to Infra and this flag is the fallback. Agent-facing pages (plan, search, class, reservations, studio, account) are App-owned `gui/index.html` and `gui/src/app.js`, declared through the optional `pale.web` extension in `contribution/gui.json` and served by the public business Web Host over the Agent MCP connection; GUI actions call the same business tools under the same policy, and the model-side computer-use adapter is a platform component. Platform-facing operations, never listed on Agent connections: `env.load_seed`, `env.apply_event`, `env.reset`, `env.snapshot`, and the host-provided `env.advance_time`.
- **State and lifecycle (required):** App state (studios, class templates, fee and plan rules) is separated from account state (plan, credits, reservations with notice history, waitlist entries, payment method) and run state (pending previews and offers, event log). The clock is Core's `ctx.virtual_now`; windows, horizons and expiries are evaluated when an operation runs, and the App keeps no clock of its own. `validateSeed` rejects a class instance without capacity, time range or price rule, a reservation on an unknown class, and overlapping instances in one studio room; a class with no ratings shows "no ratings yet". Every write carries Core's `request_id` and the caller's `expected_version`: a repeated `request_id` returns the stored receipt with no second effect, and a stale `expected_version` is rejected before the handler runs, so the Agent re-reads and retries. In addition, a confirm whose preview has expired, or whose class changed since the preview, returns `preview_stale` with the current price and, if the class is now full, a waitlist offer. Reset restores this App instance's seed and clears previews, offers, receipts and the event log; business data is byte-identical after a reset round-trip, while Core's epoch and audit are Core's own; notices already delivered to Mail stay in Mail.
- **Events and notifications (required):** Accepted events, applied by Infra with `env.apply_event`, with the handler reading the event's `at` as the current time; effects and one example each are in the table below. Published notifications: send-only on `channel.email` to Mail 1.3.0 as described in the example notice below; `messaging.receives` is empty. Cadence commits its own change first and constructs the notice afterwards; Messaging delivers it as a separate commit. A rejected delivery leaves no Mail record and leaves Cadence's committed change unchanged, recorded as `notice_status: rejected` with the receipt in the reservation's notice history; an unknown acknowledgement halts the run for reconciliation as the runtime specifies; Cadence does not retry on its own because the runtime has no outbox, and nothing is rolled back. Task scenarios decide when events occur.
- **Shared data and dependencies (required):** Stable IDs for the person (the run binding's `person_id`), account, studio, class instance, reservation, waitlist entry, preview, offer and receipt. Studio images are PNG, one per studio, at most 25 assets and under 1 MiB decoded per bundle, addressed by asset ID; a studio without an image shows a placeholder. The package runs on its own with only the shared runtime (Core and Messaging) and its own fixtures: `app.json.dependencies` is empty, and Mail 1.3.0 and Calendar 1.3.0 are optional run-assembly connections, not package dependencies. The linked Task #18 expects the studio-cancellation notice in Mail, so its run assembly enables Mail and grants `channel.email` from Cadence to the user's Mail account. No external service at run time.

#### Accepted events

| Event | Effect on business state | Example (`{event_id, at, operation, payload}`) |
| :--- | :--- | :--- |
| `classes.cancelled_by_studio` | The class instance becomes `cancelled`; every reservation on it becomes `cancelled_by_studio` with any credits spent returned; waitlist entries on it become `expired`; one notice per affected account. | `{"event_id":"evt-1001","at":"2026-12-08T11:05:00-05:00","operation":"classes.cancelled_by_studio","payload":{"class_instance_id":"ci-7731","reason":"instructor_unavailable"}}` |
| `classes.schedule_changed` | The instance takes the new start time or instructor; booked reservations move with it and are marked `time_changed`, a later cancel carries no fee, and an overlap with the account's other reservations is flagged `conflict` in `reservations.list`; previews on the instance become stale; one notice per affected account. | `{"event_id":"evt-1002","at":"2026-12-07T09:00:00-05:00","operation":"classes.schedule_changed","payload":{"class_instance_id":"ci-7731","new_start":"2026-12-10T18:00:00-05:00","new_instructor_id":null}}` |
| `classes.capacity_changed` | Sets the instance capacity and makes its previews stale; a capacity below current bookings is rejected with `capacity_below_bookings` and changes nothing; raising capacity does not promote anyone by itself. | `{"event_id":"evt-1003","at":"2026-12-07T10:00:00-05:00","operation":"classes.capacity_changed","payload":{"class_instance_id":"ci-7731","capacity":14}}` |
| `waitlist.promoted` | The named entry moves from `waiting` to `offered` with the payload's expiry; `waitlist.accept` before expiry books the class and charges under the plan (or records "included"), `waitlist.decline` ends the offer, and an unanswered offer becomes `expired` when a later operation or event finds the time passed; one notice. Waitlist states: `waiting`, `offered`, `booked`, `declined`, `expired`, `left`. | `{"event_id":"evt-1004","at":"2026-12-09T08:00:00-05:00","operation":"waitlist.promoted","payload":{"waitlist_entry_id":"wl-311","offer_expires_at":"2026-12-09T20:00:00-05:00"}}` |
| `plan.renewed` | Credits reset to the plan's allotment, the renewal date advances one period, a receipt record is created, and a trial that renews becomes the paid plan named in the payload; one receipt notice. | `{"event_id":"evt-1005","at":"2026-12-13T00:05:00-05:00","operation":"plan.renewed","payload":{"account_id":"acct-amara","plan_id":"plan-8-credits","renewal_date":"2027-01-13"}}` |
| `plan.trial_ending` | Marks the trial-ending reminder as sent; no credit or plan change; one reminder notice stating the end date and what renews. | `{"event_id":"evt-1006","at":"2026-12-11T09:00:00-05:00","operation":"plan.trial_ending","payload":{"account_id":"acct-amara","trial_end":"2026-12-13"}}` |
| `account.session_expired` | Every Agent operation returns `signed_out` until the restore event; no other state changes, and previews keep expiring on the clock. | `{"event_id":"evt-1007","at":"2026-12-06T18:55:00-05:00","operation":"account.session_expired","payload":{"account_id":"acct-amara"}}` |
| `account.session_restored` | Clears the signed-out state. Both session events are App state scheduled by the task; Core has no sign-in concept and App authors implement no authentication. | `{"event_id":"evt-1008","at":"2026-12-06T19:06:00-05:00","operation":"account.session_restored","payload":{"account_id":"acct-amara"}}` |

#### Example notice (studio cancellation)

A full CloudEvents 1.0 envelope as Messaging routes it to Mail's `mail.receive_notification`; the `recipient` is a logical person reference that Infra binds to the user's Mail account.

```json
{
  "specversion": "1.0",
  "id": "cadence-notice-rsv-2041-cancelled",
  "source": "urn:pale:app:cadence:account:acct-amara",
  "type": "org.pale.mail.notification.v1",
  "datacontenttype": "application/json",
  "dataschema": "urn:pale:email-payload:1",
  "time": "2026-12-08T11:06:00-05:00",
  "subject": "rsv-2041",
  "data": {
    "channel": "channel.email",
    "recipient": { "kind": "person_ref", "id": "person-amara" },
    "source_object": { "app_id": "cadence", "account_id": "acct-amara", "object_type": "reservation", "object_id": "rsv-2041" },
    "content": {
      "title": "Cancelled by the studio: Strength 60 at Granite Barbell, Thu Dec 10, 5:30 PM",
      "body": { "format": "text/plain", "text": "Granite Barbell cancelled Strength 60 on Thursday, December 10 at 5:30 PM. Your reservation rsv-2041 is cancelled and nothing was charged; the class was included in your trial. Open Cadence to book a replacement." },
      "asset_ids": [],
      "deep_link": { "app_id": "cadence", "route_id": "reservations", "object_id": "rsv-2041" }
    },
    "extensions": []
  }
}
```
