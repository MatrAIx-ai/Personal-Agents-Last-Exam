**Proposed PR title** — [Environment Proposal] [Media & entertainment] Tidepool Audio podcasts and music

## 1. App and domains

- **Authors / GitHub handles (required):** @byshail

Spotify is the reference for the music library, collaborative playlists, the family plan and explicit-content filters. Apple Podcasts and Pocket Casts are the references for podcast follows, episode progress, the Up Next queue, automatic downloads and played-episode cleanup. ## 2. What you plan to build

**✍️ Your answer (required):** Tidepool Audio lets a personal agent manage a family's listening. Each member has their own podcast follows, episode progress, Up Next queue, music library and playlists. Listening happens on phones, earbuds, a car and a shared kitchen speaker, and each session is recorded under the account that was signed in on that device. Each session identifies the signed-in account, device, playback position, speed and start reason. A shared speaker can record several people’s listening under the same account. An optional speaker hint is unverified. The agent can then line up the right episodes, keep shared playlists suitable for a child, free storage before a trip and change the plan within the plan manager's authority.

### Three example requests

The seeded family has a plan manager, Priya, and three members: her partner Sam, Noor (teen) and Kai (child, explicit filter on). A kitchen smart speaker is signed into Priya's account. All people, shows, tracks and prices are fictional.

### Workflows

| Workflow | Entities and transitions | Confirm, modify, cancel and error paths |
| --- | --- | --- |
| W1 Catalog | Artist, album, track (with an `explicit` flag and an optional `clean_version_id`), show and episode (duration, chapters, notes, published time). Availability is `available` or `removed`. | Read-only. An unknown ID returns `not_found`. A removed item stays readable in history but cannot be queued, saved or downloaded (`unavailable`). |
| W2 Listening activity and progress | A listening session records the signed-in member, device, item, start and end positions, speed, and start reason (`user`, `autoplay`, `queue` or `voice`). Episode progress per member is `unplayed` → `in_progress` → `played`. | The agent can set a position or mark an episode played or unplayed for one member. Each change is recorded as `set_by: agent` with the value it replaced, and adds no session. A position beyond the duration returns `invalid_position`. A stale `expected_version` is rejected. |
| W3 Follows, Up Next and downloads | Follows have per-show settings: auto-download of the newest *n* episodes and auto-delete of played episodes after *d* days. Up Next is a versioned, ordered list per member. A download goes `queued` → `downloaded` → `removed` or `needs_check`. | Up Next is replaced as a whole list with `expected_version`. An accepted manual or automatic download reserves the item’s bytes immediately and stores a virtual completion time one simulated minute after acceptance. Reads show it as downloaded once that time arrives. Removing a queued item cancels it and releases the reservation. A download that exceeds the device's storage cap returns `storage_full` and changes nothing. A device that has not checked in for 30 days turns its downloads to `needs_check` on the virtual clock. Unfollowing a show keeps its downloads unless the agent removes them. |
| W4 Library and playlists | Saved tracks and albums. A playlist has an owner, a name, collaborators, visibility (`private`, `shared` or `collaborative`) and a versioned track list. Each track entry records the member who added it. | The owner and collaborators can add, remove and reorder tracks. Only the owner can change visibility or collaborators. A track that is explicit with the filter on is kept in the playlist but skipped for that member. Removing a collaborator keeps their earlier additions. |
| W5 Family plan and controls | The plan is `individual`, `duo` (2) or `family` (6). Members are `invited` → `active` → `removed`. A per-member explicit filter. The billing period has an optional scheduled change. | Only the plan manager can invite or remove members, change filters or change plans. A person can have at most one open invitation, and inviting them again returns `already_invited`. An open invitation counts toward the plan's member limit, so accepting it can never exceed the limit. An upgrade applies at once. A downgrade is scheduled for period end and is refused if the family has more members than the new plan allows (`too_many_members`). While a downgrade is pending, invitations count against the smaller plan's limit. A scheduled change can be revoked before period end. A failed charge sets `payment_due` for a 7-day grace period, after which downloads turn to `needs_check`. |

## 3. Potential app connections

- **Internal personal apps (required):** None in the first version. All five workflows complete inside Tidepool Audio. The task supplies commute times and trip dates in the user context. Tidepool sends no messages and receives none.
- **Other apps and websites (required):** None at runtime. Every show, episode, track and price is a synthetic record in the app.

### Integration details

- **Operations and access (required):** MCP only in the first version, with 33 agent operations. There are 16 read operations: `catalog.search`, `catalog.get_item`, `shows.get_episodes`, `family.get`, `members.list`, `devices.list`, `history.list`, `progress.get`, `follows.list`, `upnext.get`, `downloads.list`, `library.list`, `playlists.list`, `playlists.get`, `notifications.list` and `plan.preview_change`, which quotes a change without applying it. There are 17 write operations: `progress.set`, `follows.add`, `follows.remove`, `follows.update_settings`, `upnext.set`, `downloads.add`, `downloads.remove`, `library.save`, `library.unsave`, `playlists.create`, `playlists.update_tracks`, `playlists.update_settings`, `members.invite`, `members.remove`, `filters.update`, `plan.confirm_change` and `plan.revoke_change`. Every write names the member it affects. Each member can manage their own progress, follows, queue, downloads, library and playlists. Playlist owners manage sharing, and collaborators can edit tracks. Plan and filter changes require the manager role. Family membership alone gives no access to another member’s private listening history or library. The bound account comes from Infra, never from an argument, so a task can narrow tools, members and fields with `policies.json`. App errors are `not_found`, `unavailable`, `forbidden`, `invalid_position`, `storage_full`, `too_many_members`, `already_member`, `already_invited`, `no_pending_change` and `payment_due`. Core adds `invalid_arguments`, `permission_denied`, `stale_version` and `idempotency_conflict`. Infra alone uses `env.load_seed`, `env.apply_event`, `env.reset`, `env.snapshot`, `env.event_status`, `env.validate_bundle` and the runtime's `env.advance_time`. They are not on the agent connection, and Core returns `permission_denied` if the agent calls one. There is no reviewer console or GUI.
- **State and lifecycle (required):** The catalog, plan prices and limits are App state loaded from the run fixture. The family, members, devices, sessions, progress, follows, queues, downloads, library, playlists and billing period are account state bound to one account instance. A run loads both, plus the virtual clock. The seed schema accepts any family and history, including an account with payment due or a scheduled downgrade. Seed validation rejects duplicate IDs, dangling references, sessions longer than their item, more members than the plan allows, downloads beyond a device's cap and timestamps without a UTC offset (`invalid_seed`). Each write returns a receipt with the object ID and new version. Repeating a committed `request_id` returns the stored receipt marked `duplicate`. The same ID with different input returns `idempotency_conflict`, and a stale `expected_version` returns `stale_version`. A failed call leaves data and version unchanged, and reads never change business data. Destructive writes report what they removed: `downloads.remove` returns the bytes freed, and `members.remove` returns the downloads and playlist access that end. `family.get` shows the same counts beforehand. Time-based states are stored as due times and derived from `ctx.virtual_now` wherever they are read or checked, so Tidepool needs no timers or clock event. These states are auto-delete windows, the 30-day offline check, the payment grace period and scheduled plan changes. Infra moves the clock with an event or with `env.advance_time`. Reset (`reset_scope: app_instance`) restores the loaded catalog, account and clock without touching other Apps. Evaluator records come from three joined sources: App activity rows, Core audit rows and the supplied agent trace, joined on `request_id`, `event_id` and version. Each activity row records the sequence number, virtual time, actor (`agent` or `event`), action, object, member and the replaced value. There is one row per committed write or applied event, and none for a replay, a rejected call or a time-driven change. Infra takes the snapshot before reset.
- **Events and notifications (required):** Infra applies seven scenario events, and the runner controls their timing. `listening.record` appends a session and updates that member's progress or play count. An episode counts as played when the end position reaches its end-of-content marker. `episode.publish` adds an episode and queues auto-downloads on that member's devices that have auto-download on, or records `storage_full`. `catalog.update` removes an item or changes its explicit flag. `playlist.edit` applies a collaborator's addition, removal or reorder. `device.checkin` refreshes the device’s offline eligibility for 30 days. A billing hold that has outlasted its grace period still applies until payment succeeds. `billing.payment_result` records a paid or declined charge. `family.invite_response` moves an invited member to `active` or clears a declined invitation. An unknown member, device or item fails the whole event, and replaying the `event_id` of a committed event changes nothing.

  **How events find records the agent creates.** IDs of records the agent creates during the run, such as playlists and invitations, are not predictable, and no event needs them. Events find seeded records by ID and run-created records by a key the task author knows in advance. `playlist.edit` names its playlist either by `playlist_id` (seeded playlists only) or by `playlist_ref: {owner_member_id, name}`. The name match ignores case and surrounding spaces. `family.invite_response` names its invitation by `invitee_person_id`, the person's ID from `binding.json`, and matches that person's one open invitation in the family. The lookup happens when the event is applied. If nothing matches, the event fails with `target_not_found`. If more than one of the owner's playlists has that name, it fails with `ambiguous_target`. A `playlist.edit` whose `author_member_id` is not the owner or a collaborator at that moment fails with `not_collaborator`. A failed event changes nothing. `env.apply_event` returns `applied: false` with the failure code as its status, and Core's audit records a `deny` row with that code as `reason`, so a task can treat "the agent never created the playlist" as an observable outcome. A failed event stores no receipt, so `env.event_status` returns no receipt for it. Once the agent creates the playlist, the task can retry with the same `event_id` and the current `expected_version` and an `at` timestamp at or after the current virtual time. Only a committed event is replayed without a second effect. A successful `playlist.edit` applies its operations to the current track list in order, adds one version and records the author on each added track. The agent's own tools never take these keys: they use IDs returned by its reads and writes.

  Tidepool writes in-app notices, read with `notifications.list`, when an event publishes a followed episode, edits a collaborative playlist or declines a payment. A period-end plan change is visible in the effective plan returned by `family.get`. It writes none for the agent's own writes and none for time passing alone. It sends no cross-app notifications: `publishes` and `receives` are empty. In the scenario, Sam was cooking. The example event tells the agent that the kitchen speaker played the episode under Priya’s account. The device record alone cannot establish who was in the room.
- **Shared data and dependencies (required):** Node.js 18+ and the public Core runtime, reference revision `a4bce02`. The family's `account_id` and each member's `person_id` come from the run's `binding.json`. A task that also uses Contacts or Messages gives the same people the same IDs, and Tidepool keeps no copy of contact details. Fixtures ship as UTF-8 JSON. The first version has no audio files, artwork or other media (`capabilities.resources: false`, 0 of the reference profile's 64 assets). Durations, chapters, sizes and show notes are text and numbers. The package runs on its own with only Core: `dependencies.required_apps` is empty, and it reads nothing outside its own folder. Task authors keep grading judgments in the evaluator.
