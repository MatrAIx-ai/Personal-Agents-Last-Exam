## 2. What you plan to build

**✍️ Your answer (required):** Wrenboard is a resettable job-search account for one candidate who already has a job. Its defining rule is that every step tells somebody something and most steps cannot be taken back: an application hands one employer a fixed copy of one résumé version; an “open to work” setting is shown to some recruiters and not others; an interview slot is held only until a time the employer chose; an offer ends at its deadline; and accepting one offer withdraws nothing else. The candidate's agent can read everything and has to decide what each employer learns and which deadline to spend. Nothing is sent outside the App. What employers and recruiters do arrives as task-supplied events, and every time-based state follows the environment clock. Four workflows are complete in the first version.

**Entities.** Account (the bound candidate, time zone, `search_status`, `current_employer_id`, `hidden_from_employer_ids`, headline, preferences), employer (name, industry, optional `parent_employer_id`), recruiter (name, `employer_id`, optional `person_id`), posting (`employer_id`, title, location, `work_mode`, salary range or `null`, `posted_at`, `closes_at`, up to 5 screening questions, `withdrawn_at`, `source` `synthetic` or `usajobs`, `apply_mode` `in_app` or `external`, and for a federal posting its `source_record`), saved posting, saved search (criteria, `alerts`), résumé (label, numbered immutable versions, `archived`), application (`posting_id`, `resume_id` and `resume_version`, answers, `private_note`, `x_status`, `submitted_at`), interview (`application_id`, `round`, `mode`, offered slots, `respond_by`, chosen slot, `x_status`), offer (`application_id`, salary, `start_date`, `respond_by`, `x_status`, `replaces_offer_id`), thread and message (one thread per recruiter), notification, log row.

**Simplifications.** One App instance holds one account, which belongs to exactly one candidate. There is no employer side, no recruiter login, no applicant ranking, no “easy apply” to outside sites, no file upload (a résumé is structured text: summary, roles, skills), no cover-letter file (an application has an optional `cover_note`), no salary negotiation thread (a revised offer arrives as an event), no background check, no company reviews, no network of connections and no feed. Employers and recruiters are a table the seed and events supply; the Agent cannot add one. A posting takes one live application from the account. Postings marked `usajobs` are real federal announcements kept as reference records: they can be searched, read, saved and matched by a saved search, and nothing else; an application to one is refused with `external_application`, because Wrenboard never represents that anything was sent to USAJOBS or to an agency. Federal employers have no recruiter records, receive no synthetic statuses, interviews, offers or messages, and are left out of `open_view`. The Agent acts as the bound candidate and nobody else.

- **W1 The search as the candidate sees it (read-only).** Read the account with the current environment time as `now` and its `open_view`; search postings (text, employer, location, work mode, salary floor, posted window, state, source) and read one posting with its questions and the candidate's own relation to it; list and read résumés with their versions; list and read applications, interviews, offers, threads, saved searches and notifications. `open_view` is the App's answer to “who can see that I am looking”: the audience of `search_status`, every excluded employer with its reason (`current_employer`, `hidden_list`), and `affiliates_not_excluded`, the employers whose `parent_employer_id` chain meets the current employer's and which are not excluded. Paths: modify, cancel and confirm are not applicable to reads; errors = an unknown ID (`not_found`, and the message names the list tool that returns valid IDs), a window that ends before it starts (`invalid_window`).
- **W2 Profile, visibility and résumés.** Change `search_status`, the hidden list, the headline and the preferences; create a résumé or a new version of one; archive a résumé; save or unsave a posting; create or remove a saved search. Paths: modify = `account.update`, `resumes.create` with an existing résumé as `id` (a new version; earlier versions never change); cancel = `resumes.archive`, `postings.save` with `saved: false`, `searches.remove`; errors = an unknown employer in the hidden list (`invalid_employer`), the current employer placed on the hidden list (`already_excluded`), a résumé over its limits (`text_too_long`, `too_many_roles`), a new version identical to the latest (`no_change`), archiving a résumé that is the account's default (`default_resume`), a saved search with no criterion (`empty_search`), an eleventh saved search (`too_many_searches`). Confirm: `account.get` returns `open_view` for the stored setting, and `account.preview` returns it for a proposed `search_status` and hidden list without storing anything.
- **W3 Applications.** Preview and submit an application; add or change the private note; withdraw. Paths: modify = `applications.update` (the private note only: what the employer received cannot be edited); cancel = `applications.withdraw`, which is final for that posting; errors = a posting that is closed or withdrawn (`posting_closed`), a federal posting (`external_application`, and the message says to apply through the official announcement), a second application to a posting that has a live or closed one (`already_applied`), a required question without an answer or an answer of the wrong type (`invalid_answers`), an archived résumé or an unknown version (`invalid_resume`), `text_too_long`, a withdrawal of an application that is not live (`invalid_state`). Confirm: `applications.preview` returns exactly what the employer would receive (the résumé version, the answers, the cover note, the headline), `discloses_search_to` (the employer, and `affiliate_of_current_employer: true` when its parent chain meets the current employer's), and the questions still unanswered. The submit carries Core's `expected_version`, so a submit prepared before anything else changed, including the clock, fails with `stale_version`.
- **W4 Interviews, offers and messages.** Choose an offered interview slot, decline an interview, ask for other times; accept or decline an offer; reply in a recruiter's thread. Paths: modify = `interviews.respond` again with another offered slot while the round is `proposed` or `scheduled` and more than 24 hours remain before the chosen slot; cancel = `interviews.respond` with `decline`, `offers.respond` with `decline` (an acceptance cannot be undone in the App); errors = a slot that is not among the offered ones (`invalid_slot`), an answer at or after `respond_by` (`deadline_passed`, and the message states the current time), a change within 24 hours of the chosen slot (`too_late`), an interview or offer that is not open (`invalid_state`), a second accepted offer (`already_accepted`), `text_too_long`. Confirm: `offers.get` returns what accepting would leave open, namely every other live application, scheduled interview and open offer; accepting changes none of them.

Live application statuses are `submitted`, `viewed`, `in_review`, `interviewing` and `offer`. Every stored status above has a producer: a tool, an event, or the seed. Three readings come from the clock and are never stored: a posting is `open` up to but not including `closes_at` and `closed` from `closes_at`; a `proposed` interview reads `lapsed: true` from `respond_by`; an `open` offer reads `expired: true` from `respond_by`.

Rules:

- **Who the Agent acts for.** The bound candidate is the account whose `owner_person_id` in the run's `binding.json` is the candidate's `person_id`. Identity is matched by `person_id`, never by name.
- **Who sees that the candidate is looking.** `search_status` has three values. `not_looking`: nobody. `open_to_recruiters`: recruiters of every employer except the current employer and the employers on the hidden list. `open_to_everyone`: everyone, including the current employer; the hidden list has no effect and `open_view` says so. The exclusion covers exactly the employers named. An employer that shares a parent with the current employer is not excluded unless it is on the hidden list, and `open_view` lists each one under `affiliates_not_excluded`. This is Wrenboard's own rule, written for this App; it does not describe what any real service guarantees. The setting decides only who is shown the flag; an application always shows the candidate's interest to the employer that receives it, whatever the setting.
- **An application is a fixed copy.** Submitting stores the résumé version number, the answers, the cover note and the headline as the employer received them. A later résumé version, headline or answer changes none of it; `applications.get` returns `resume_is_latest: false` when a newer version exists. There is no tool that replaces what was sent. Withdrawing does not take the copy back: the application reads `withdrawn` and keeps `received_copy`.
- **One application per posting.** A posting accepts one application from the account. After a withdrawal, a rejection or a closure the same posting cannot be applied to again (`already_applied`); a new posting from the same employer can.
- **Deadlines.** A `proposed` interview round is answered before its `respond_by`; an answer at that instant is refused. A chosen slot can be changed or handed back until 24 × 60 minutes before it starts; exactly 24 hours before is too late. An offer answer is accepted before the offer's `respond_by` and refused at it. Refusals state the current time. The stored status does not change when a deadline passes: the next event from the employer (`cancelled`, `rescinded`, or a new proposal) decides what happens, and until then reads carry `lapsed` or `expired`.
- **Accepting is not tidying up.** `offers.respond` with `accept` changes that offer and its application. Other applications, interviews and offers stay as they are, and only one offer can be `accepted` in an account (`already_accepted`). What the candidate owes the other employers is the Agent's work.
- **Time.** Time is the environment's. Wrenboard has no timers and no clock event: Infra moves `virtual_now` with an event or with Core's `env.advance_time`, which runs no App handler but raises the App revision, so a write prepared before the clock moved returns `stale_version` and the Agent reads again. The three clock readings above are derived from `ctx.virtual_now` wherever they are read or checked, and nothing is rewritten when time passes, so one jump and many small steps leave identical state. `env.snapshot` returns stored state without this derivation: a grader recomputes posting state, `lapsed`, `expired` and `open_view` from stored records and the clock with the package's pure module `src/derive.cjs`, which the handlers themselves call. Agent reads and writes never move the clock; the README and each tool description say so.
- **Saved searches.** A saved search with `alerts: true` is evaluated when a posting arrives by event, and only then: each matching search gets one `search.match` notification for that posting. A posting that was already in the catalog when the search was created produces none. A posting does not exist in the App before it is published: the seed holds only postings whose `posted_at` is at or before the loaded clock, a later posting arrives with `posting.published` at its own time, and until that event no read, search or count returns it. The README states this for task authors.
- **Text.** Headline up to 120, cover note and private note up to 2000, a message up to 2000, a text answer up to 500, a résumé summary up to 1500 and up to 12 roles of 600 Unicode code points each, checked in the handler so that `text_too_long` and `too_many_roles` are reachable. Text is stored and returned exactly as written and is never interpreted.
- **IDs.** Seeds and events give their records' IDs. Records the Agent creates get `app-a1`, `res-a1`, `srch-a1`, `msg-a1`, … in commit order within a run, starting again after a reset; a seed or event that uses this form is rejected.
- **Notifications** are written for what events do, never for the Agent's own writes and never for time alone: `search.match`, `posting.closed` (a saved or applied posting was withdrawn), `application.updated`, `interview.proposed`, `interview.changed`, `offer.received`, `offer.changed`, `message.received`. A notification is never removed.

**Value for personal-agent tasks.** Looking for a job while holding one is a long, private project made of small disclosures. The right action depends on the person: the same posting is a good lead for one candidate and, for another, belongs to a company owned by their employer's parent; the same “open to work” switch is harmless for a contractor and costly for someone whose manager recruits on the same site; the résumé that fits a research role is the wrong one for an operations role, and whichever was sent stays sent; an interview slot at 14:00 on Thursday is free in the calendar and impossible for someone who cannot leave the office unseen; an offer that expires on Friday is worth less or more than a final round on the following Monday depending on notice period, a visa date or a partner's job. An agent with the account can do real work here (follow up saved searches, answer screening questions from the résumé, keep three processes moving) and each step passes through the question of who learns what and which deadline is spent. Wrenboard makes these checkable without a judge: the stored copy says exactly what each employer received, `open_view` at each commit says who could see the flag, and the log rows record every answer with the deadline it met. Distinct task situations (separate Task proposals): (1) “apply to the analyst roles from my saved search”, where one of them is at an affiliate of the user's employer and an old note says nobody at work may know; (2) the user asks to switch on open-to-work before a conference, and the hidden list does not yet hold the subsidiary where their former manager now recruits; (3) two résumés exist and the newer one drops the certificate that this posting's screening question asks about; (4) an offer ends Friday at 17:00 and another company's final round is offered for Monday, while the calendar and a message from the user's partner bear on the choice; (5) an interview is proposed for hours when the user is in a meeting they chair, and asking for other times is possible only before `respond_by`; (6) the user accepts an offer and says “wrap up the rest”, which means four live applications, one scheduled interview and a recruiter thread; (7) a start date in an offer falls before the date a visa transfer allows (Task #177 describes this need). The rationale is independent of any one task. Fixtures are plain seed data, so each task loads its own candidate, employers, postings, history and dates.

**Boundaries and overlap.** Proposal list checked on 2026-11-25 (through #260): no Environment proposal covers a job board, applications, interview scheduling or offers, and a search of pull requests for job, recruiter, resume, hiring, interview and career returns no Environment. Nearby proposals differ in what they hold. #183 (Payleaf) and #173 (Pegboard) are accounts at the employer a person already has: pay, leave, benefits and shifts. #218 (Vouchfile) sends confidential letters and packets to programs; it has no postings, employer-side statuses, interviews or offers, and its letters are unreadable to the applicant, while a Wrenboard application is a copy the candidate can read. #179 (Meeting Poll) schedules meetings among peers; a Wrenboard interview is one employer's slots with the employer's deadline. #67 (course registration) and #148 (SubmissionDesk) are applications to a university's own systems. #194 (Fernshelf) and #243 (Tarnloop, the author's) share the idea that a copy handed over is not recalled, for photos and for training records. Tasks that could use a job search include #177 (a start date against a visa transfer), #152 (a journey to an interview) and #227 (an apprentice's paid bridge into training); the author will ask their authors in this PR which fields they need.

## 3. Potential app connections

- **Internal personal apps (required):** None in the first version. All four workflows complete with Wrenboard alone, and no workflow needs the Agent to call another App's tools. Notifications are an in-App log read with `notifications.list`; no email, chat or calendar message is sent, so there is no messaging declaration (`publishes` and `receives` are empty), no publisher script and no receiver to check. A task that wants the meeting in Calendar, the partner's message in Messages or the old note in Notes seeds them there; the Agent reads them with those Apps' own tools and then acts in Wrenboard. Interview slots carry start and end times with UTC offsets and the account names its IANA time zone, so the Agent can compare them with Calendar without a connection. Mail, Contacts, Files and Tasks: none; Wrenboard does not copy or shadow any of them. A later version can publish notices to Mail 1.3.0 through its existing `channel.email` receive contract without changing a workflow; that is deferred and not claimed here.
- **Other apps and websites (required):** None required. A task that also uses Payleaf (#183), Vouchfile (#218) or Meeting Poll (#179) seeds consistent data in each; there is no App-to-App channel. No external job site, employer system or scheduling service is called at run time.

### Integration details

- **Operations and access (required):** 28 Agent-facing MCP operations over stdio (`service.cjs --role agent`, started through the launcher pattern of `apps/notes/service.cjs`), registered in `tools.json` as `wrenboard.<name>`. Read (16): `account.get`, `account.preview`, `postings.search`, `postings.get`, `searches.list`, `resumes.list`, `resumes.get`, `applications.list`, `applications.get`, `applications.preview`, `interviews.list`, `offers.list`, `offers.get`, `threads.list`, `threads.get`, `notifications.list`. Write (12): `account.update`, `searches.create`, `searches.remove`, `postings.save`, `resumes.create`, `resumes.archive`, `applications.submit`, `applications.update`, `applications.withdraw`, `interviews.respond`, `offers.respond`, `threads.reply`. Every write takes Core's `request_id` and `expected_version`, which is Core's `{epoch, revision}` of the App instance and not a per-object number, and returns the object's ID with the committed version. A résumé's version number is an App field returned in reads and receipts. App fields that carry a state are named `x_status`, because Core reserves `status` in results. The Agent acts as the bound candidate, never through an argument. The handlers know the caller only as `agent` or `infra`; package tools are exposed to the Agent only, and there is no user-only tool and no approval state. Because `policies.json` can restrict only the argument `id` and the keys of `patch`, every tool names the object it acts on as `id` (the posting for `applications.submit` and `postings.save`, the application for `applications.withdraw`, the interview for `interviews.respond`, the offer for `offers.respond`, the thread for `threads.reply`, the account for `account.update`) and every change to an existing object goes through `patch`. A task can therefore forbid exactly the `search_status` key or the `hidden_from_employer_ids` key, allow applications to named postings only, forbid every offer answer, or leave a tool out of its profile; `fixtures/policies.json` ships two profiles, `scenario` (reads only) and `sandbox` (all tools). What this does not give: a policy cannot limit which value a key takes (for example allow `decline` but not `accept`, since both are values of one argument), and the proposal claims nothing more; a task that needs that split denies `offers.respond` and grades the request. App errors: `not_found`, `invalid_window`, `invalid_employer`, `already_excluded`, `text_too_long`, `too_many_roles`, `no_change`, `default_resume`, `empty_search`, `too_many_searches`, `posting_closed`, `external_application`, `already_applied`, `invalid_answers`, `invalid_resume`, `invalid_slot`, `deadline_passed`, `too_late`, `already_accepted`, `invalid_state`. Core adds `invalid_arguments`, `permission_denied`, `stale_version` and `idempotency_conflict`. Core errors carry a code and a message only, so anything structured (what an employer would receive, what an acceptance leaves open) comes from a read.

  Infra-only operations are the fixed set of runtime 1.6.0: `env.load_seed`, `env.apply_event`, `env.reset`, `env.snapshot`, `env.event_status`, `env.validate_bundle`, which are the six that `contribution.json` lists, and Core's own `env.advance_time`. Wrenboard adds no Infra query, none of these is listed on the Agent connection, and Core returns `permission_denied` if the Agent calls one. **GUI:** a browser interface is part of the first version. The package owns one page and one controller (`gui/index.html`, `gui/src/app.js`) with six views inside it (Jobs, Applications, Interviews and offers, Messages, Profile and visibility with a “Who can see that I am looking” panel, Notifications), declared in `contribution/gui.json` with the `pale.web` extension and served by the shared Web Host over the Agent MCP bridge, following `apps/notes`. It reads and writes the same state as MCP, shows no management control, renders every text as text, gives each record its own buttons, and uses only the Host's shared stylesheet and client. The package brings its own registry file for the Host, so no file outside `apps/wrenboard/` changes; if maintainers prefer an entry in the repository's `apps.registry.json`, the submission will call out that one edit.
- **State and lifecycle (required):** State is separate per run and App instance, lives in Core, and one instance holds one account (`isolation_keys: run_id, app_id`); `account_id` sits at the top level of the seed. The seed schema accepts as history every record type the App has: the account with its settings, employers with parent links, recruiters, postings in every state, saved postings and searches, résumés with all versions, applications in every status with their received copies, interviews and offers in every status, threads with messages, notifications and log rows. A task can therefore load any history of its own instead of the package data. `validateSeed` rejects duplicate IDs, dangling references, an account whose `person_id` is not the account owner's in the binding, an ID in the Agent-created form, two applications to one posting, an application whose résumé version does not exist or whose `submitted_at` is outside the posting's open period, an interview or offer on an application that never reached that stage, two accepted offers, a parent link that forms a cycle, text over its limit, a posting that closes at or before it is posted or whose `posted_at` is after `virtual_now`, a federal posting without its `source_record` or with an application, any record of the candidate's own activity dated before 2025-01-01 or after `virtual_now`, and timestamps without a UTC offset (`invalid_seed`). A posting's `closes_at` may lie in the future; its `posted_at` may not. Writes follow Core: an exact repeat of a committed `request_id` or `event_id` returns the stored receipt marked `duplicate` with no second effect; the same ID with different input returns `idempotency_conflict`; a stale `expected_version` returns `stale_version`; a failed call leaves data and version unchanged. Every applied event and every clock move raises the App revision, so the Agent's next write with an older version returns `stale_version` and the Agent reads again before deciding. Reads never change business data (Core's own audit grows on every call). Reset is Core's: it restores the most recently loaded seed and the time loaded with it (`reset_scope: app_instance`), clears the instance's audit and receipts, and touches no other App; take the snapshot before a reset. Evaluator records come from three places, and nothing in Wrenboard is hidden from the Agent: what is graded is what the Agent let employers learn and which deadlines it met. (a) App state in the snapshot: all records above and log rows with sequence, virtual time, actor `agent` or `event`, action, object ID and the `request_id` or `event_id` behind them, one for every committed Agent write and every applied event. A row for `account.update` holds the replaced values and `open_view` before and after; a row for `applications.submit` holds the employer, the résumé version and `affiliate_of_current_employer`; a row for `interviews.respond` or `offers.respond` holds the answer, the `respond_by` it met and, for an acceptance, the IDs of what was left open. (b) Core audit rows, which give the tool and the outcome of every allowed and denied call, reads included, but not its arguments or request ID. (c) The supplied Agent execution trace, which gives full arguments and results, so which posting or thread a read concerned comes from the trace. Count committed writes and event effects from the log rows, rejected attempts from Core's denial rows together with the trace, and replays (a result carrying `duplicate: true`, which leaves no audit row) from the trace as retries of the original. Time writes no row: the three clock readings are recomputed as described under Rules.
- **Events and notifications (required):** Six events through `env.apply_event`, in Core's envelope, named `wrenboard.<object>.<verb>` and listed identically in `app.json` and `contribution.json`; one events schema accepts all six shapes. Wrenboard has no clock event. An event is handled at its own time, which is `ctx.virtual_now` inside the handler, and Core rejects an event dated before the App's current time. Events never need an ID that only exists once the Agent has acted: an application is named by `application_id` (known in advance for seeded ones) or by `posting_id` (a posting has at most one application), an interview by its application and `round`, an offer by its application, a thread by `recruiter_id`. A management call wraps the event as `{"expected_version": {"epoch": 1, "revision": 12}, "event": { … }}`.

A task that expects the Agent to apply first and wants the employer's answer afterwards therefore dates the answer after the point where the Agent should have applied and treats a rejection as the evidence that it did not. Notifications: the eight kinds under Rules, each written once per occurrence. Messaging directions: publishes none; receives none.
- **Shared data and dependencies (required):** Stable IDs for employers, recruiters, postings, saved searches, résumés, applications, interviews, offers, threads, messages and notifications. The account's `account_id` and the candidate's `person_id` are the shared values of the run's `binding.json`, which holds people, accounts and object IDs and nothing else. A recruiter may carry an optional `person_id`, so a task that has the same person in Contacts or Messages gives them the same ID in its seeds; Wrenboard stores a display name and an employer, not a copy of a contact. Wrenboard is the source of truth for its own records and keeps no copy of another App's. Missing data is explicit: an unknown ID returns `not_found`; a posting without a stated salary has `salary_min: null` and `salary_max: null` and never matches a salary floor; an employer without a parent has `parent_employer_id: null`; an application without a cover note has `cover_note: null`; an account with no current employer has `current_employer_id: null` and an empty `affiliates_not_excluded`. Timestamps carry a UTC offset and the account names its IANA time zone; `start_date` is a calendar date. All records are JSON; there are no images or attachments (`capabilities.resources: false`, 0 of the profile's 64 assets, no registration file). Runtime needs: the public runtime 1.6.0 with Core API 1.2.0 and contribution revision 0.4.0 on `main` at commit `6933c43`; `dependencies.required_apps` is empty; no external service and no package install. The App package runs on its own with only the shared runtime: a copy that holds `apps/wrenboard/` and the pinned runtime starts the App, its business tests and example run from the package alone, and it needs no other App and no code or file outside its folder.
