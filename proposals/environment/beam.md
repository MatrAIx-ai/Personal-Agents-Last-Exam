## 2. What you plan to build

**✍️ Your answer (required):** Beam is a PC game platform, modeled on Steam, where a user discovers, buys, plays and manages their games. The first version covers the core loop of the platform: finding, wishlisting and buying games, giving games to other people, keeping a library with playtime, paying through a wallet or saved cards, and refunding purchases under the platform's rules. It is designed to grow into a fuller platform (see scope boundary). Initial workflows:

1. **Store and purchase.** Browse and search a catalog, view game pages (price, current discount and its end time, genre, content rating, description, platform requirements), add to cart, and check out with the wallet or a saved card. Content ratings use a four-step ladder: `everyone`, `everyone_10`, `teen`, `mature`. The account page stores the user's PC specifications, which can be compared with each game's platform requirements. Failure states: insufficient wallet balance, declined card, game already owned, price changed before confirmation.
2. **Wishlist.** Add, remove and reorder wishlist items; see which wishlisted games are currently discounted and when each discount ends. Discount windows are stored with each game and evaluated against the virtual clock.
3. **Gifting.** Buy a game as a gift for another Beam user (identified by username or email), with an optional message. Gifts move through `sent → redeemed / declined`; a declined gift is refunded to the purchaser. Failure states: recipient already owns the game, unknown recipient.
4. **Library and playtime.** Owned games with acquisition source (purchased or received as a gift), date and recorded playtime.
5. **Wallet and payment methods.** Wallet balance and transaction history, add funds, add/remove/set default cards (masked). A simulated payment processor can approve or decline charges and indicates whether a card accepts refunds.
6. **Refunds.** Request a refund from order history: choose the game, a reason, and the destination (wallet or original payment method). Requests move through `submitted → approved / denied`. Requests within the rules are approved when submitted, and approved funds arrive after a settlement delay set in the seed (default seven simulated days). Requests outside the refund window or over the playtime limit are recorded and denied by default. Failure states: already refunded, original payment method that cannot receive refunds, redeemed gift whose refund is requested by the purchaser rather than the recipient.

**Refund rules for games.** Beam follows Steam's published refund policy for games (https://store.steampowered.com/steam_refunds, last updated April 23, 2024).

| Rule | Behavior in Beam |
| :--- | :--- |
| Eligibility | Refundable for any reason if requested within 14 days of purchase and played for under 2 hours. |
| Destination | Original payment method or wallet; if the original method cannot accept refunds, the full amount goes to the wallet. |
| Gifts | Unredeemed gifts follow the 14-day / 2-hour rule. Redeemed gifts can be refunded under the same conditions only if the recipient initiates it; funds return to the original purchaser. |
| Outside the rules | Users can still submit a request. It is denied by default; a seed can instead leave such requests `submitted` for a later `beam.refund.decided` event. |

Steam's rules for DLC, pre-purchases, bundles, wallet-fund refunds and other purchase types are deferred along with those product types.

**Why this is useful for personal-agent tasks.** Everyday platform actions involve money, time-bounded rules and the user's own history, so the right action depends on personal context: which of two recent purchases "the game I bought last week" means, whether a game is for the user or a gift for someone else, whether a standing payment or refund preference still applies, whether a purchase fits what the user already owns and can run, or whether a request should be explained and declined instead of submitted. The environment exposes the state needed to make those cases discoverable and checkable.

**Time and world events.** Refund windows, discount end times and refund settlement depend on the current time, and PALE tasks span multiple sessions of simulated world time. Beam reads the runtime's virtual clock (`ctx.virtual_now`). Infra sets it when it loads a seed and advances it with `env.advance_time` or an applied event; the agent cannot change it. Time-dependent values (current price, refund eligibility, whether refunded funds have arrived) are computed from stored timestamps and the current virtual time, so advancing the clock needs no Beam handler. Infra can also apply scheduled world events the agent does not cause: added playtime, a gift recipient redeeming, declining or requesting a refund for a gift, card status changes, decisions on refund requests left for review, and the start of a discount on a wishlisted game. Reset restores Beam's data and clock to the loaded seed.

## 3. Potential app connections

### Integration details

- **Operations and access (required):** Entry point: MCP over stdio (`service.cjs --role agent`), with tools registered in `tools.json` as `beam.<name>`; no GUI in the first version. Read (13): `catalog.search`, `game.get`, `account.get`, `cart.get`, `wishlist.get`, `library.list`, `orders.list`, `orders.get`, `gifts.list`, `wallet.get` (balance, ledger and masked cards), `refunds.list`, `drafts.get`, `notices.list`. Write (18): `cart.add`, `cart.remove`, `wishlist.add`, `wishlist.remove`, `wishlist.reorder`, `cards.add`, `cards.set_default`; `checkout.prepare` / `checkout.confirm`, `gift.prepare` / `gift.confirm`, `topup.prepare` / `topup.confirm`, `refund.prepare` / `refund.confirm`, `card_removal.prepare` / `card_removal.confirm`; `draft.cancel`. Each money-moving action has its own confirm tool, so a task policy can allow preparing a checkout but not confirming it, or allow purchases but not refunds; Core's `policies.json` allow-list returns `permission_denied` for anything else. When a call targets one object (game, order, gift, card or draft), the object is the argument `id`, so policy `ids` constraints can limit which objects a call may touch. App errors: `not_found`, `already_owned`, `insufficient_funds`, `card_declined`, `price_changed`, `unknown_recipient`, `recipient_owns_game`, `already_refunded`, `refund_destination_unavailable`, `recipient_must_request`, `draft_closed`, `invalid_amount`. Core adds `invalid_arguments`, `permission_denied`, `stale_version` and `idempotency_conflict`. Infra-only operations: `env.load_seed`, `env.apply_event`, `env.reset`, `env.snapshot`, `env.event_status`, `env.validate_bundle` and the host-provided `env.advance_time`; they are not listed or callable on the Agent connection.
- **State and lifecycle (required):** State is separate per run and App instance (`isolation_keys: run_id, app_id`); one instance holds one user's Beam account. The seed carries the catalog (games, prices, discount windows, content ratings, requirements), refund settings, the user's account (PC specifications, library with playtime, wishlist, cart, orders, gifts, wallet ledger, cards, refunds, notices) and the other Beam users who can send or receive gifts. The default fixtures supply a catalog and seed profiles; a task can load its own catalog and history through `env.load_seed` with the same schema. `validateSeed` rejects duplicate IDs, dangling references, timestamps without a UTC offset, a wallet balance that differs from its ledger, and library entries without a matching order or gift. Writes follow Core: each takes `request_id` and `expected_version` and returns `status: committed` with the new `{epoch, revision}`; an exact repeat returns the stored receipt with `duplicate: true`; the same ID with different input returns `idempotency_conflict`; a stale version returns `stale_version`; a rejected call returns its error code as `status` with `applied: false` and changes nothing. Checkout, gifts, wallet top-ups, refund requests and card removal use a prepare → confirm flow: prepare validates and stores a draft with a summary (items, price, payment source, total, refund destination and whether the request is within the rules) and moves no money; confirm re-validates at the current virtual time and commits the order, gift, top-up, refund request or card removal, or returns an error such as `price_changed` or `card_declined`; cancel closes the draft. A confirmed or cancelled draft cannot be confirmed again (`draft_closed`), so a retry never charges or refunds twice. Reads never change data. Core's per-App lock serializes writes. Reset is Core's: it restores the loaded seed and its time (`reset_scope: app_instance`) and does not touch Mail; notices already delivered stay in Mail until Mail is reset.
- **Events and notifications (required):** Accepted events, applied by Infra through `env.apply_event`; task scenarios define when they occur:

  | Operation | Example input | Effect |
  | :--- | :--- | :--- |
  | `beam.playtime.recorded` | `{"event_id":"ev-pt-40","at":"2027-03-01T22:30:00-05:00","operation":"beam.playtime.recorded","payload":{"game_id":"gm_017","minutes":95,"played_at":"2027-03-01T21:00:00-05:00"}}` | Adds playtime to the library entry, which can end refund eligibility |
  | `beam.gift.redeemed` | `{"event_id":"ev-gr-102","at":"2027-03-02T20:15:00-05:00","operation":"beam.gift.redeemed","payload":{"gift_id":"g_102"}}` | `sent` gift becomes `redeemed`; notice |
  | `beam.gift.declined` | `{"event_id":"ev-gd-102","at":"2027-03-02T20:15:00-05:00","operation":"beam.gift.declined","payload":{"gift_id":"g_102"}}` | `sent` gift becomes `declined`; refund `r_311` returns the price to the purchaser's original payment source; notice citing `g_102` and `r_311` |
  | `beam.gift.refund_requested` | `{"event_id":"ev-gq-102","at":"2027-03-04T10:00:00-05:00","operation":"beam.gift.refund_requested","payload":{"gift_id":"g_102","played_minutes":30,"reason":"not_interested"}}` | Recipient requests a refund of a redeemed gift; the refund rules decide it; approved funds return to the purchaser; notice |
  | `beam.card.status_changed` | `{"event_id":"ev-cs-2","at":"2027-03-05T09:00:00-05:00","operation":"beam.card.status_changed","payload":{"card_id":"card_2","status":"no_refunds"}}` | Card becomes `active`, `declining` (new charges fail with `card_declined`) or `no_refunds` (refunds to it are unavailable) |
  | `beam.refund.decided` | `{"event_id":"ev-rd-311","at":"2027-03-06T12:00:00-05:00","operation":"beam.refund.decided","payload":{"refund_id":"r_312","decision":"approved"}}` | Decides a request left `submitted`; notice |
  | `beam.discount.started` | `{"event_id":"ev-ds-17","at":"2027-03-07T10:00:00-05:00","operation":"beam.discount.started","payload":{"game_id":"gm_017"}}` | Writes a discount alert if the game is on the user's wishlist; the price itself comes from the seeded discount window |

  An unknown ID or an event that does not fit the current state (for example redeeming a declined gift) returns `invalid_event` and changes nothing. Notices: Beam writes each notice once to its notice log together with its full wire message: order and top-up receipts; gift sent, redeemed and declined; refund submitted, approved and denied; wishlist discount alerts. Messaging directions: publishes `channel.email` only; receives none. A sender script in the package, run by Infra with the trusted publisher connection, reads undelivered notices through `env.snapshot` and calls `router.publish`, using the notice ID as the CloudEvents `id` and the `request_id`; a retry returns Messaging's duplicate receipt, so Mail holds one record. The script does not write back into Beam, and no cross-App transaction is assumed: a rejected delivery creates no Mail record and leaves the Beam record unchanged; an unknown acknowledgement halts for reconciliation. Mail shows each notice as a message from `beam@pale.example` with the notice title as its subject; the Beam order, gift or refund ID appears in the title and body, so the message can be matched to the Beam record. Example wire message for the `beam.gift.declined` event above, validated against Mail's `urn:pale:email-message:2` schema with `runtime/contracts/schema-validator.cjs` at `main` commit `61b6371` (three broken variants fail): `{"specversion":"1.0","id":"ntc-0042","source":"urn:pale:app:beam:account:beam-ava","type":"org.pale.mail.notification.v1","time":"2027-03-02T20:15:00-05:00","datacontenttype":"application/json","dataschema":"urn:pale:email-payload:1","subject":"g_102","data":{"channel":"channel.email","recipient":{"kind":"person_ref","id":"person-ava"},"source_object":{"app_id":"beam","account_id":"beam-ava","object_type":"gift","object_id":"g_102"},"content":{"title":"Gift g_102 declined: $19.99 refunded to your wallet (refund r_311)","body":{"format":"text/plain","text":"Your gift of Lanternfall to mira_k (gift g_102) was declined on March 2. Refund r_311 returned $19.99 to your Beam wallet. New wallet balance: $27.49."},"asset_ids":[]},"extensions":[]}}`
- **Shared data and dependencies (required):** People and accounts: the user's Beam account, whose `account_id` and owner person ID come from the run's `binding.json`; other Beam users (gift recipients and senders) are seed records with username and email, not separate App accounts. Notices address the user as a `person_ref`, which Infra binds to the user's Mail account. Object references: game, order, gift, refund, card, draft and notice IDs; cards appear as brand and last four digits; amounts are integer cents in USD; content ratings use `everyone`, `everyone_10`, `teen` and `mature`. Media and attachments: none (`capabilities.resources: false`). Runtime: the public Core / Messaging runtime 1.6.0 (Core API 1.2.0) and Node.js 18+ built-ins; no external service. The package runs on its own: business tests run from `apps/beam` alone, `app:verify` needs only the shared runtime, and `dependencies.required_apps` is empty. The Beam → Mail check takes the Mail 1.3.0 package path as an argument.

## Appendix: example tasks this environment would support

1. **Which game?** The user asks to "refund the game I bought last week." Two games were bought that week; one has already been played for three hours. The agent must identify the intended, still-eligible game and confirm instead of guessing when the evidence is not decisive.
2. **A standing preference meets a rule.** Several sessions earlier the user said refunds should always go back to their card. This purchase was made with a card that cannot receive refunds. The agent should tell the user the money can only go to the wallet rather than silently submitting it.
3. **A purchase that fits the person.** The user asks the agent to buy a co-op game a friend recommended, paying from the wallet only. The agent must check that the user does not already own it, that the wallet covers it, and that the user's PC meets its requirements, and ask before topping up the wallet.
4. **Whose refund is it?** The user bought a game as a gift for their brother, who redeemed it and played for 30 minutes. The user now asks the agent to refund it. The agent should recognize that only the recipient can start this refund and explain that, rather than looking for a workaround.
