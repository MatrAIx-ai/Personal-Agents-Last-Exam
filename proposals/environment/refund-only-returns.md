# Environment Track proposal

**Proposed PR title:** `[Environment Proposal] [Shopping & groceries] Refund-only Returns (minimal MVP)`

Proposal only, prepared 2026-11-16. This deliberately narrows the earlier parcel-returns concept to a one-item, refund-only request workflow. No implementation, evaluation success, delivery date, expenditure, or maintenance commitment is claimed.

## 2. What you plan to build

**✍️ Your answer (required):** A browser app for one fictional merchant and one item per order. Four workflows: (1) locate a synthetic order and read its item, fixed refund amount, eligibility, and deadline; (2) prepare a refund-only request and review or discard it; (3) confirm one eligible request; (4) cancel it before dispatch. Use four views: order lookup, order detail, request review, and request status. A cancellation can be followed by a new request if the order remains eligible. There are no exchanges, store credit, fees, real refunds, or transfers. Confirmation only records a synthetic request; it never means money was returned.

The single initial world change is a visible return deadline passing between review and confirmation. The server checks the same clock displayed by the app. The agent must recognize the expiry rather than claim success or repeatedly submit. A confirmed eligible request persists if its deadline passes later; the deadline is for initiating the request, not cancelling it. Cancellation is permitted until the synthetic status is marked dispatched. A dispatched fixture tests the cutoff, but no carrier simulation or second dynamic event is required in the MVP. Invalid order IDs, ineligible/expired items, duplicate submissions, and cancellation after dispatch have explicit errors or idempotent outcomes. All policy facts needed for a safe action are visible.

## 3. Potential app connections

- **Internal personal apps (required):** None in the MVP. The order ID and user intent are local scenario inputs. Receipt-email and Calendar integrations are deferred.
- **Other apps and websites (required):** None in the MVP. A local order/request store supplies all state. No live merchant, carrier, payment processor, or support-agent connection is needed.

### Integration details

- **Operations and access (required):** Proposed access is the four browser views and a same-state action/observation surface for order lookup, eligibility/deadline inspection, request review/discard, confirmation, and cancellation before dispatch. Platform-only setup loads a synthetic scenario, resets it, and advances its controlled clock through the already-scoped deadline event. It exposes no carrier, payment, or actual-refund operation. Exact MCP/API methods and official setup/reset/clock hooks are TBD after release and design agreement, without expanding the declared MVP.
- **State and lifecycle (required):** Separate the merchant/policy definition from each run's synthetic account context, one-item orders, requests, clock, and event cursor. Reset restores all of them; any proposed snapshot covers the same local state. Confirmation is verified as a recorded request, never as money returned. Duplicate submissions return the existing outcome rather than a second active request. Confirmation rechecks current eligibility and deadline, while cancellation rechecks dispatch status; failed or concurrent attempts must not overwrite a valid request. A confirmed request survives later deadline expiry as already specified. Exact snapshot/idempotency representations remain TBD.
- **Events and notifications (required):** The task scenario schedules the single deadline-crossing event. Illustrative input facts are order_id=order-2 and simulated_time later than that order's return_deadline; output is expired eligibility and a failed new confirmation with no request created. Existing confirmed requests are preserved. Dispatched remains a static fixture for cancellation-cutoff tests, not another dynamic event or shipping simulation. Local UI/action results are the only notifications; no email or carrier messages. Official clock/event envelopes and hooks are TBD.
- **Shared data and dependencies (required):** Synthetic merchant, account, order, item, policy-version, and request IDs link the local stores. Each order has one item, a fixed informational amount, an explicit deadline, and a request status; exact fixture serialization will be agreed in design review. No receipts, labels, attachments, real identities, or payment details are collected. UI and the proposed adapter share the same local state; there is no external runtime service, live merchant/carrier connection, or dependency on another environment proposal.
